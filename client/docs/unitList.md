# Client 세대 목록 설계

작성일: 2026-10-10. 이 문서는 세대 관리 아래 세대 목록 화면의 구조와 사용자 조작 기준을 정의합니다. API 요청·응답·오류는 [세대 관리 API](../../docs/unitManagementApi.md), 저장 정책은 [도메인 규칙](../../docs/domainRules.md#3-관리대상--동--세대)과 [ERD](../../docs/erd.md#53-units)를 참조합니다.

**적용 상태:** 세대 목록과 추가·상세·수정·개별 삭제를 구현했습니다. 사용자 요청에 따라 768px 미만에서는 추가·상세·수정을 독립 페이지로 열고 공통 헤더에 `<` 뒤로가기를 표시합니다. 데스크톱에서는 기존 모달을 유지합니다. 편집 모드·선택 삭제는 제공하지 않으며 표시 개수는 목록 위 오른쪽에 둡니다.

## 1. 메뉴와 화면의 소속

메뉴 관계는 `세대 관리 → 세대 목록`입니다. 세대 관리는 업무 그룹 `household`, 세대 목록은 그 아래 화면 슬라이스 `unit-list`로 둡니다.

| 구분 | 기준 |
| --- | --- |
| 화면 슬라이스 | `src/screens/household/unit-list/` |
| 화면 공개 API | `src/screens/household/unit-list/index.ts` |
| 외부 Import | `@/screens/household/unit-list` |
| 진입 UI | `ui/unit-list-page/unitListPage.tsx` |
| 진입 UI 스타일 | `ui/unit-list-page/unitListPage.module.css` |
| 기존 URL | `/manage/[propertyId]/households` |

`household`에는 업무 그룹을 위한 통합 UI나 공개 API를 만들지 않습니다. 실제 화면이 필요한 코드와 공개 API를 소유합니다. 같은 그룹의 형제 화면도 서로 다른 슬라이스이며 직접 참조하지 않습니다.

## 2. 코드와 스타일의 책임

현재 구조는 다음과 같습니다. 실제 필요한 파일만 두며 빈 세그먼트나 미구현 메뉴를 만들지 않습니다.

```text
src/screens/household/unit-list/
├── index.ts
├── model/
│   └── unitList.ts
└── ui/
    └── unit-list-page/
        ├── unitListPage.tsx
        ├── unitListPage.module.css
        ├── _hooks/
        │   └── useUnitList.ts
        └── _components/
            ├── unit-list-header/
            ├── unit-list-summary/
            ├── unit-list-filters/
            ├── unit-list-table/
            └── unit-list-dialogs/
```

- 진입 UI는 화면 블록을 조합합니다. 조회·변경 상태와 이벤트 처리 전체를 진입 TSX에 넣지 않습니다.
- `features/unit-management/api/`는 목록과 독립 페이지가 공유하는 요청·응답 검증과 오류 안내를 소유합니다. 목록의 `model/`은 검색·정렬·페이지 계산, UI의 `_hooks/`는 조회·변경과 모달·페이지 진입 상태를 관리합니다.
- 상세 푸터는 `shared/ui/detail-actions`로 주민 상세와 공유합니다. 웹의 `닫기 → 수정 → 삭제` 순서·색상·오른쪽 정렬·구분선·여백과 모바일 페이지의 `목록으로 → 수정 → 삭제` 동일 너비 배치를 한곳에서 관리합니다.
- 독립 페이지는 `screens/household/unit-entry/`가 조합합니다. 세대 상세 표시는 `entities/property`의 `UnitDetail`, 입력·검증은 기존 `BuildingUnitFormModal`의 `presentation`으로 공유하며 페이지에서는 모달을 열거나 스크롤을 잠그지 않습니다.
- 내부 컴포넌트도 자기 폴더 안에 TSX와 CSS Modules를 함께 둡니다. 반응형 규칙도 그 컴포넌트의 CSS에서 관리합니다. 진입 UI의 CSS는 화면 전체 배치만 담당합니다.
- 목록 헤더(상위 메뉴명·제목·설명·오른쪽 버튼)는 `shared/ui/list-header`, 조회 건수·표시 개수는 `shared/ui/list-toolbar`, 필터·툴바·표·페이지네이션을 감싸는 배경·여백은 `shared/ui/list-card`로 주민 목록과 공유합니다. 각 화면은 내용과 행동·상태만 전달하고 공통 UI에는 도메인 조회나 저장을 넣지 않습니다.
- 표의 의미 구조·스크롤·빈 목록 표현은 `shared/ui/data-table`을 사용합니다. 동·호수·상태·주민 열과 세대 이벤트는 이 화면의 `unit-list-table`이 정의합니다. 공통 표에는 세대 정책이나 API 호출을 넣지 않습니다.
- 요약 카드의 표시·반응형 스타일은 `shared/ui/summary-card`의 `SummaryCard`를 사용합니다. `unit-list-summary`에는 전체 세대·사용중·공실의 집계와 카드 배치만 둡니다. 카드에는 제목·값·단위·아이콘·의미 색상을 전달합니다.
- 페이지 이동·표시 범위·반응형 배치는 `shared/ui/pagination`의 `Pagination`을 사용합니다. `세대` 단위와 `세대 목록 페이지` 접근성 이름은 화면이 전달하며 필터·페이지 크기·유효 페이지 계산은 기존 모델과 Hook에서 관리합니다. 표시 개수 선택은 기존 목록 위 오른쪽 위치를 유지합니다.
- 추가·수정·동 관리·자동 입력·삭제 확인은 기존 `entities/property`의 모달과 검증을 재사용합니다. 초기 등록과 저장된 목록의 상태·저장 방식은 각 호출자가 관리합니다. 상세와 공유 모달의 열기·닫기·초기 포커스·복귀·중첩 스크롤 잠금은 `shared/ui/client-modal`의 `ClientModal`을 사용합니다. 도메인 입력과 저장 정책은 모달 호출자가 소유합니다.

전체 UI의 동일 폴더 배치와 공개 API 규칙은 [Client AGENTS.md](../AGENTS.md#5-component-rules)를 따릅니다. `property-registration`의 진입 UI도 예외가 아닙니다.

## 3. 상세·수정·삭제의 역할

2026-10-10 사용자 요청에 따라 `행 클릭 → 상세 → 수정` 흐름을 유지하며 모바일에서는 동 관리·세대 자동 입력도 독립 페이지로 열고 데스크톱에서는 모달을 사용합니다. 한 세대 삭제는 상세에서 확인 창을 거쳐 처리합니다. 아래 모달 설명은 데스크톱 기준입니다.

| 위치·조작 | 역할 | 표현 |
| --- | --- | --- |
| 목록 위 오른쪽 드롭다운 | 페이지당 표시 개수 선택 | 기존 편집 버튼 위치, 10 / 20 / 50개 |
| 목록의 행·호수 버튼 | 해당 세대 상세 모달 열기 | 행 호버·포인터, 호수 버튼의 키보드 포커스 |
| 상세 모달의 `닫기` | 상세를 닫고 목록으로 복귀 | 회색 테두리·글씨 버튼 |
| 상세 모달의 `수정` | 해당 세대의 기존 수정 모달로 전환 | 연필 없는 초록색 테두리·글씨 버튼 |
| 상세 모달의 `삭제` | 해당 세대의 확인 창 열기 | 하단 오른쪽에 닫기·수정·삭제를 같은 간격으로 배치, 빨간색 테두리·글씨 버튼 |
| 삭제 확인 창의 `삭제` | 확인한 한 세대만 삭제 요청 | 빨간색 |
| 동 관리 목록의 연필 아이콘 | 동 이름 수정 폼 열기 | 초록색 연필 아이콘 버튼, 접근성 이름은 `동 이름 수정` |
| 동 관리 모달의 `삭제` | 동과 연결 세대의 범위를 확인한 뒤 삭제 | 기존 빨간색 쓰레기통 |

세대 행에는 관리 열·수정·삭제 버튼을 두지 않습니다. 수정 모달에도 별도 세대 삭제 진입점을 추가하지 않습니다. 동 관리의 삭제는 동 단위 작업이므로 상세의 한 세대 삭제와 구분합니다. 초기 등록의 초안 선택 삭제는 이 변경에 포함하지 않습니다.

상세는 기존 세대 목록 API의 동·호수·별칭·층·상태·주민 정보를 표시하며 추가 조회 API를 만들지 않습니다. 독립 페이지의 직접 접근·새로고침도 같은 API로 현재 대상을 확인합니다. 대표·등록 주민 수·가입 현황은 같은 응답의 주민 요약을 사용하고 조회 권한이 없으면 `—`로 둡니다. 클릭 동작이 있는 행에는 호버와 포인터를 표시합니다. 호수의 실제 버튼은 Enter·Space로 상세를 엽니다. 데스크톱 모달은 닫기·Escape 후 포커스를 복구하며 모바일 페이지는 헤더 뒤로가기·목록 버튼으로 돌아갑니다. 비활성 세대는 기존 기준처럼 수정 버튼을 비활성화합니다.

삭제 확인 창은 대상 동·호수와 개수를 표시하며 최초 포커스는 취소에 둡니다. 취소·Escape는 상세와 목록을 유지합니다. 요청 중에는 중복 제출과 취소·Escape를 막습니다. 실패하면 오류와 상세를 유지하고, 성공하면 서버 목록을 다시 조회한 뒤 데스크톱은 상세와 확인 창을 닫고 목록 제목으로 포커스를 돌리며 모바일은 목록 페이지로 이동합니다. 동 삭제는 기존 모달처럼 동 이름과 연결 세대 수를 확인하며 취소 시 해당 동을 유지합니다.

### 모바일 페이지와 헤더

| 주소 | 화면 | 헤더 뒤로가기 |
| --- | --- | --- |
| `/manage/[propertyId]/households/buildings` | 동 관리 | 세대 목록 |
| `/manage/[propertyId]/households/automatic` | 세대 자동 입력 | 세대 목록 |
| `/manage/[propertyId]/households/new` | 세대 추가 | 세대 목록 |
| `/manage/[propertyId]/households/[unitId]` | 세대 상세 | 세대 목록 |
| `/manage/[propertyId]/households/[unitId]/edit` | 세대 수정 | 해당 세대 상세 |

- 모바일 헤더 왼쪽에 기존 공통 chevron 아이콘을 회전한 `<`와 페이지 제목을 표시합니다. 768px 이상은 기존 로고 헤더를 사용합니다.
- 주소를 직접 열어도 같은 관리대상의 목록·상세로 돌아갑니다. 입력 취소·이탈·새로고침에는 초안을 보관하지 않습니다.
- 목록에서 선택한 동은 신규 페이지의 기본값으로 전달하고 서버에서 조회한 현재 동인지 확인합니다.
- 삭제 확인은 공통 확인 모달을 유지합니다. 동 관리·자동 입력은 `BuildingManager` / `AutomaticUnitEditor`의 `presentation="page"`를 사용해 `<section>`과 `<h1>`으로 표시하며 일반 모달·닫기 X·모달 스크롤 잠금을 사용하지 않습니다. 웹·초기 등록의 모달은 유지합니다. 동 관리 저장·삭제 후에는 페이지를 유지하고 서버 목록과 성공 토스트를 갱신합니다. 자동 입력은 생성 미리보기·중복 제외·원자적 일괄 저장을 재사용하고 실패 시 입력을 유지하며 성공하면 세대 목록으로 돌아갑니다. 세대 추가·수정 성공 또는 삭제 완료 후 목록을 재조회하고 성공 Toast를 표시합니다. 성공 이동 쿼리는 표시 후 URL에서 제거합니다.
- 존재하지 않거나 삭제된 세대, 수정할 수 없는 세대와 동이 필요한데 동이 없는 신규 입력은 안내와 목록 복귀를 제공합니다.

## 4. 목록 표시와 조회

- 상단에는 전체 세대·사용중·공실 카드 세 개를 둡니다. 카드 집계는 검색 결과가 아닌 관리대상 전체의 조회된 세대 기준입니다.
- 표에는 동·호수·상태·대표 주민·가입 현황을 표시합니다. 등록 주민 열은 제거하고 가입 현황은 대표 주민 바로 뒤에 둡니다. 동 없음 대상에서는 동 열·필터·입력을 숨깁니다. 별칭은 호수 아래에 표시하고 별칭·층의 별도 열은 두지 않습니다.
- 검색·동·상태 필터와 페이지 이동을 제공합니다. 필터의 X는 표시하지 않고 실제 전체 동·전체 상태 선택지와 초기화 버튼을 사용합니다. 페이지 크기 드롭다운은 목록 위 오른쪽에 두고 문구는 줄바꿈되지 않게 합니다. 이전·다음과 페이지 번호는 표 아래 중앙에 둡니다.
- 대표 주민 이름과 가입 현황의 `1/3 명`(가입 완료/등록 주민 수)만 기존 세대 조회 API의 `residentSummaries`로 표시합니다. 등록 주민이 없는 세대는 `0/0 명`을 표시합니다. 목록과 세대 상세의 가입 현황에는 같은 표기 함수를 사용하며 가입 완료 설명이나 승인 대기·미가입 보조 문구를 붙이지 않습니다. 관리소장 전용 주민 조회 권한을 유지하며 요약이 `null`인 부담당자에게는 `—`를 표시합니다. 가입 현황은 세대 자체의 승인 상태가 아니라 해당 세대 주민별 상태의 집계입니다. 판정과 응답은 [API 계약](../../docs/unitManagementApi.md#목록-조회)을 따릅니다.
- 주민 등록·수정·삭제·엑셀 완료 뒤 세대 목록 캐시도 무효화해 현재 이름·대표·소속·가입 인원을 다시 조회합니다. 별도 대표 변경과 주민 검색은 이 연동에 추가하지 않습니다.
- 추가·수정·삭제 성공은 본문에 남는 글씨 대신 화면 하단 중앙의 진한 초록색 배경·흰 글씨 공통 `Toast`로 4초간 표시합니다. X 버튼과 호버·포커스에 의한 타이머 정지는 사용하지 않습니다. 나타날 때 200ms, 4초 후 사라질 때 180ms의 이동·페이드 애니메이션을 적용하고 퇴장 후 제거합니다. 동작 줄이기 설정에서는 애니메이션을 생략합니다. 같은 성공 문구가 반복되어도 새 알림으로 처리합니다. 동 관리 모달이 열려 있어도 그 위에 표시하며 모달을 닫아도 남은 시간 동안 유지합니다. 실패·입력 오류는 해당 모달이나 페이지 안에 유지합니다.
- 조회 중·조회 실패·정상 빈 목록·검색 결과 없음을 구분합니다. 추가·수정·삭제 성공 후 서버 목록과 카드 집계를 갱신하며 저장 실패는 모달·페이지의 입력을 유지합니다.
- 조회 키는 계정·관리대상별로 분리하고 목록에서 이탈하면 세대 조회 캐시를 제거합니다. 요청 규격과 인증 처리는 공통 API 계약을 따릅니다.

## 5. 범위와 기존 등록 흐름

이 문서는 저장된 세대 목록 화면의 설계입니다. 초기 등록의 초안 삭제·단계 이동·최소 세대 조건을 저장된 목록의 정책으로 복사하지 않습니다. 초기 등록은 [등록 설계](propertyRegistration.md)를 따릅니다. 공유 모달의 재사용이 두 화면의 모든 버튼 배치까지 같아야 한다는 의미는 아닙니다.

변경 이력·과거 이름의 보존·상태 전이·주민 이동·청구 연계 삭제 제한은 후속 정책이며 이번 폴더 정리로 확정하지 않습니다. 이력·청구 연계를 위한 새 업무 테이블이나 API는 추가하지 않으며, 목록의 편집 제거로 기존 일괄 삭제 API를 제거하지 않습니다.

## 6. 구조와 동작 검증

- 목록 라우팅은 `@/screens/household/unit-list`, 독립 페이지는 `@/screens/household/unit-entry`의 공개 API를 사용합니다. 그룹 통합 Import, 화면 내부 파일 우회와 같은 그룹의 형제 화면 참조는 ESLint가 거부합니다.
- 화면·기능·Widget의 진입 UI와 내부 컴포넌트가 `ui/` 또는 `_components/` 바로 아래에 TSX를 나열하면 ESLint가 거부합니다. TSX의 CSS Modules는 같은 컴포넌트 폴더에 있는지 함께 확인합니다.
- `tests/architecture.spec.ts`에서 그룹·단독 화면 공개 API, 형제 화면 참조 금지, 상위 레이어 참조 금지와 UI 폴더 배치를 검증합니다.
- `tests/managementLayout.spec.ts`에서 행 상세·키보드 진입·수정 전환·모바일 배치와 관리·등록 주민 열과 편집 제거, 가입 현황과 상단 표시 개수 드롭다운, 토스트 자동 닫기, 상세 삭제의 취소·실패·중복 제출·목록 갱신과 동 삭제를 검증합니다.
- 320 / 767px에서 모바일 헤더 뒤로가기·독립 주소·새로고침·저장 실패와 재시도·수정·삭제·대상 없음과 페이지 폭을 확인하며 1440px에서는 기존 모달 동작을 검증합니다.
- 폴더 이동의 검증은 ESLint·TypeScript·빌드와 기존 화면 통합 테스트를 포함합니다. 실행 결과와 실행하지 못한 검증을 구분해 보고합니다.
