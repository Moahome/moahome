# Client 서비스 진입 설계

작성일: 2026-10-05. 관리대상별 진입 분기와 관련 화면은 후속 구현으로 남기고, 이 문서에는 연결 방향과 코드 배치 설계안을 기록합니다. 아래의 새 URL, 폴더와 파일은 아직 구현되지 않았습니다.

업무 기준은 [도메인 규칙의 로그인 이후 진입 기준](../../docs/domainRules.md#로그인-이후-진입-기준)을 참조합니다. 사용자 / 주민 / 관리대상 참여 관계는 [ERD](../../docs/erd.md), 세션 복원과 인증 처리의 현재 구현은 [보안 설계](../../docs/securityDesign.md#9-후속-구현과-검증)를 따릅니다. 관리대상 수와 역할별 업무 규칙은 이 문서에 중복 정의하지 않습니다.

## 1. 현재 구현과 후속 연결

현재 랜딩의 로그인 사용자용 `시작하기`, 로그인된 상태의 `/login` 접근과 `/login/callback`의 로그인 완료는 모두 `/start`로 이동합니다. 본인 정보 응답에는 관리대상 소속, 승인 대기 요청과 최근 사용한 관리대상 정보가 없어 사용자별 목적지를 결정하지 않습니다.

`/start`의 만들기 / 초대코드 참여 화면은 첫 방문 여부가 아니라 도메인 규칙의 진입 조건을 기준으로 사용하는 화면입니다. 현재 `/start`에 도착했다는 사실만으로 사용자의 관리대상이 없다고 판단하지 않습니다.

후속 구현에서는 세 진입점을 공통 `/entry`로 연결합니다. `/entry`가 세션과 필요한 소속 정보를 확인하고 도메인 규칙에 따라 최종 화면으로 이동하도록 구성합니다. 랜딩, 로그인 화면과 콜백에 관리대상 수 / 역할 조건을 각각 작성하지 않습니다.

```text
랜딩의 시작하기 / 로그인페이지의 정상 세션 확인 / 로그인 완료
    ↓
/entry: 세션과 관리대상 소속 정보 확인
    ↓
도메인 규칙에 따른 목적지 결정
    ↓
시작 / 승인 대기 / 관리대상 선택 / 관리자 대시보드 / 주민 홈
```

## 2. URL과 화면 배치 설계안

아래 경로는 후속 구현의 설계안입니다. 아직 없는 화면으로 현재 진입 링크를 변경하지 않으며, 실제 구현 시 화면 구성과 함께 경로를 확인합니다.

| 화면 | URL 설계안 | Client 화면 슬라이스 |
| --- | --- | --- |
| 공통 진입 처리 | `/entry` | `screens/service-entry/` |
| 만들기 / 초대코드 참여 | `/start` — 기존 경로 | `screens/start/` — 기존 슬라이스 |
| 승인 대기 | `/membership/pending` | `screens/membership-pending/` |
| 관리대상 선택 | `/properties` | `screens/property-select/` |
| 관리자 대시보드 | `/properties/[propertyId]/admin` | `screens/admin-dashboard/` |
| 주민 홈 | `/properties/[propertyId]/resident` | `screens/resident-home/` |

주민 홈은 관리대상 참여 권한과 해당 관리대상의 현재 세대 소속을 사용합니다. 로그인 계정, 주민과 세대를 같은 식별자로 취급하지 않습니다. URL의 `propertyId`나 브라우저에 남은 최근 사용 기록만으로 업무 API 접근권한을 부여하지 않습니다.

기존 관리대상에 참여한 사용자의 추가 관리대상 등록 / 초대코드 참여도 제공할 수 있어야 합니다. 공통 진입 분기를 연결할 때 기존 `/start?registration=...` 등록 흐름을 일괄 자동 이동으로 차단하지 않습니다. 추가 진입 버튼의 위치는 해당 업무 화면 구현 시 정합니다.

## 3. 처리 책임과 폴더 설계안

| 위치 | 책임 |
| --- | --- |
| `app/(main)/entry/page.tsx` | 공개 API를 통해 공통 진입 화면 연결 |
| `screens/service-entry/ui/serviceEntryPage.tsx` | 세션 / 소속 조회 조합, 확인 중 / 오류 표시와 최종 라우터 이동 |
| `features/enter-service/model/resolveEntry.ts` | 필요한 조회 결과를 받아 도메인 규칙에 따른 목적지 결정 |
| `entities/property/api/` | 접근 가능한 관리대상 조회와 API 응답 타입 |
| `entities/session/` | 기존 세션 복원 / 본인 정보 조회 재사용 |
| `app/(main)/properties/[propertyId]/admin/page.tsx` | 관리자 대시보드 화면 연결 |
| `app/(main)/properties/[propertyId]/resident/page.tsx` | 주민 홈 화면 연결 |

승인 대기 조회와 최근 사용 정보의 API / 모델은 실제 계약과 공유 범위가 결정된 뒤 책임에 맞는 슬라이스에 배치합니다. 현재 단계에서 빈 폴더, API 응답 타입이나 저장소를 미리 만들지 않습니다.

각 슬라이스는 외부에서 사용하는 진입점만 `index.ts`로 공개합니다. 화면 간 직접 Import를 만들지 않으며, 공통 목적지 결정은 기능 슬라이스에서 관리합니다. `resolveEntry.ts`는 화면 컴포넌트를 참조하지 않고 목적지 결과를 반환하며 라우터 호출은 화면에서 처리합니다.

## 4. 조회와 이동 시 처리 방향

- 세션과 목적지 결정에 필요한 조회가 끝날 때까지 확인 상태를 표시합니다. 로딩이나 일시 장애를 관리대상 0개로 처리하지 않습니다.
- 최근 사용 정보는 현재 접근 가능한 관리대상과 함께 확인합니다. 접근권한이 없어진 대상을 과거 기록만으로 열지 않으며, 유효한 최근 대상이 없는 경우의 진입은 도메인 규칙을 따릅니다.
- 역할 분기는 현재 선택한 관리대상의 참여 역할을 사용합니다. 계정의 플랫폼 역할을 관리대상 역할로 대신 사용하지 않습니다.
- 인증 실패와 일시 조회 장애를 구분합니다. 기존 세션 복원을 재사용하고 진행 중인 토큰 교체를 화면 이동이나 재시도로 취소하지 않습니다.
- 공통 진입 완료는 이력을 교체하는 이동으로 처리해 뒤로 가기가 중간 처리 화면을 반복하지 않게 합니다. 관리대상 선택과 진입 이후 전환은 해당 화면의 사용자 흐름에 맞춰 처리합니다.
- 업무 화면 직접 접근에도 현재 관리대상 접근권한을 확인합니다. Client의 목적지 결정은 Server의 인증 / 권한 검증을 대신하지 않습니다.

## 5. 후속 구현 순서와 미정 항목

1. 관리자 대시보드, 주민 홈, 관리대상 선택과 승인 대기 화면의 실제 범위를 정하고 이동 가능한 목적지를 준비합니다.
2. 접근 가능한 관리대상 / 역할, 필요한 주민 소속, 승인 대기와 최근 사용 정보의 조회 계약을 정합니다. 공통 요청 / 응답 / 오류 계약은 루트 `docs/`에서 관리하고 이 문서에서 참조합니다.
3. 최근 사용 정보의 저장 위치, 사용자별 분리, 갱신 시점과 로그아웃 / 권한 해제 시 처리를 결정합니다. 현재 단계에서는 임의의 DB 컬럼이나 브라우저 영속 저장을 추가하지 않습니다.
4. 공통 `/entry`와 목적지 결정을 구현하고 랜딩 / 로그인 / 콜백을 연결합니다. 추가 등록 흐름과 업무 화면 직접 접근도 함께 확인합니다.
5. 도메인 규칙의 진입 조건, 권한이 해제된 최근 대상, 조회 중 / 장애 / 재시도, 새로고침과 뒤로 가기를 테스트합니다.

여러 승인 대기 요청의 표시 방식 등 도메인 문서의 미정 정책은 관련 화면 구현 전에 확인합니다. 이 문서는 해당 정책이나 아직 없는 API 계약을 확정하지 않습니다.
