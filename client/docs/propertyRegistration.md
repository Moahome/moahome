# Client 관리대상 등록 설계

이 문서는 관리대상 등록 화면, 단계 이동, 브라우저 초안과 최종 제출의 Client 처리 방식을 정의합니다. 요청 필드 / 응답 / 오류 코드는 [공통 등록 API](../../docs/propertyRegistrationApi.md), 업무 정책은 [도메인 규칙](../../docs/domainRules.md)을 참조합니다.

작성일: 2026-10-05. 기본 정보 화면, 주소 검색, 검증 API 호출과 기본 입력 초안을 구현했습니다. 동·세대 이후 설정, 전체 등록 제출과 결과 조회의 Client 처리는 후속 구현 범위입니다. 아래 설계 중 해당 범위는 아직 구현되지 않았습니다.

## 1. 화면과 입력 책임

등록 흐름은 기본 정보 → 동·세대 → 관리계좌 → 관리비 항목 → 등록 정보 확인 순서로 구성합니다. PC에서는 기본 정보 폼을 모달, 모바일에서는 페이지로 사용하며 입력 폼과 검증을 공유합니다. 마지막 확인 화면은 저장 전 요약입니다. API의 저장 성공을 확인한 뒤에 완료를 표시합니다.

- 범용 입력은 `shared/ui/form-controls`의 Input / Dropdown / Radio, 클릭 버튼은 `shared/ui/button`의 Button을 공개 API로 가져옵니다. 화면에는 배치와 업무 처리만 남기고 공통 표현은 각 컴포넌트가 관리합니다. 사용법은 [Client README](../README.md#공통-입력-컴포넌트)를 따릅니다.
- 글자 수 계산, 입력값 정리, 단계별 검증과 추가 / 수정 / 삭제 상태는 등록 화면 / 기능 책임으로 관리합니다. 업무 정책을 범용 입력 컴포넌트 안에 넣지 않습니다.
- 이름, 동 / 세대 참조, 기본 계좌 수와 금액 등 입력 기준은 공통 API 계약을 참조합니다. 검증 수치나 API JSON 예시를 이 문서에 중복 정의하지 않습니다.
- 동의 clientId는 초안에서 유지해 세대 참조와 연결합니다. 배열 순서는 최종 요청의 표시 순서로 사용합니다.
- 건물 유형의 고정 옵션은 빌라 / 아파트 / 공동주택 / 기타이며 선택한 표시 문자열을 API에 전달합니다. 건물 유형과 동 구분 옵션은 `entities/property/constants/propertyOptions.ts`에서 관리합니다. Server의 문자열 계약을 유지하고 새로운 유형 Enum이나 유형별 업무 제한을 추가하지 않습니다. 은행 선택 목록과 코드 대응은 해당 설정 화면 구현 시 정리합니다.

### 현재 기본 정보 화면

- `/start`의 `관리할 곳 만들기`에서 `/start?registration=basic`으로 이동합니다. `features/property-registration`의 같은 폼을 PC 모달과 모바일 전체 화면으로 표시합니다. 모바일 상단 뒤로가기, PC 닫기 / 취소, Escape와 브라우저 뒤로가기는 등록을 취소합니다.
- 이름, 주소와 동 구분을 모두 입력하고 선택 입력의 형식도 유효해야 `등록하고 계속` 버튼이 활성화됩니다. 공백뿐인 이름은 입력으로 인정하지 않으며, 동 구분은 미선택으로 시작하고 `동 없음`도 명시적으로 선택해야 합니다. 글자 수는 API와 같은 Unicode 코드 포인트 기준으로 표시합니다.
- 건물 유형의 안내 문구는 미선택 placeholder에만 표시하며 실제 선택지에는 넣지 않습니다. 공통 Dropdown의 입력 폭에 맞춘 목록, 선택 표시와 키보드 이동을 사용하고 선택 해제 버튼으로 미선택 상태로 돌아갑니다. Escape로 목록을 닫을 때는 등록 화면을 취소하지 않습니다.
- 주소는 [카카오 우편번호 서비스](https://postcode.map.kakao.com/guide)의 공식 스크립트를 검색할 때 불러와 다이얼로그 안에 삽입합니다. 선택한 도로명 / 지번 주소를 읽기 전용 입력에 반영한 뒤 상세주소로 포커스를 이동합니다. 로딩 실패에는 재시도 / 닫기를 제공하고 기존 입력을 유지합니다.
- 현재 검증 성공에는 정리한 입력과 기본 정보 확인 안내를 표시합니다. 동·세대 화면이 준비 중이며 아직 업무 데이터를 저장하지 않았음을 안내합니다. 최종 등록 API는 호출하지 않습니다.
- 기본 입력은 사용자 ID와 함께 현재 탭의 `sessionStorage`에 보관하고 새로고침에서만 복원합니다. 등록 취소 / Client 라우트 이탈 / 로그아웃으로 폼이 제거되면 폐기하며, 새 진입과 다른 사용자의 입력은 복원하지 않습니다. 탭 저장소가 차단된 환경에서는 현재 화면의 메모리 입력만 유지합니다. 최종 제출 정보나 계좌번호는 이 기본 정보 초안에 포함하지 않습니다.

## 2. 기본 정보 검증과 단계 이동

1. 첫 단계에서 입력의 필수 여부와 길이를 확인합니다. 같은 입력 규칙을 Server에서도 검증합니다.
2. `등록하고 계속`을 선택하면 기존 `authenticatedAPI()`로 검증 요청을 보내고, 응답 대기 중에는 같은 버튼의 중복 요청을 막습니다.
3. 성공하면 정리한 입력을 Client 초안에 반영합니다. 현재는 기본 정보 확인 안내까지 제공하며 동 / 세대 단계 이동은 해당 화면 구현 시 연결합니다. 입력 오류와 일시 장애에는 현재 단계와 입력을 유지하며 인증 / 계정 오류에는 공통 API 계약과 아래 오류 표시 기준을 적용합니다.
4. 이전으로 돌아가면 초안의 기본 정보를 표시합니다. 수정 후 다시 다음으로 이동할 때 기본 정보를 재검증합니다.

기본 정보 검증에는 업무 데이터 쓰기가 없으므로 요청 중 취소나 통신 단절로 부분 등록이 생기지 않습니다. 최종 제출을 시작한 이후에는 아래 결과 확인 절차를 적용합니다.

## 3. 초안과 제출 상태

초안은 현재 사용자 / 탭 / 등록 흐름 단위로 입력과 현재 단계를 관리합니다. 브라우저 임시 저장의 구체적인 구현과 탭 복구 동작은 확정 정책을 만족하는지 Client 구현에서 검증합니다.

| 상태 | Client 처리 |
| --- | --- |
| 입력 중 | 단계 이동과 새로고침에 입력 / 현재 단계 유지, 취소 / 이탈 / 탭 닫기 / 로그아웃 시 초안 폐기 |
| 기본 정보 검증 중 | 같은 검증 버튼의 중복 입력 차단, 실패 시 현재 입력 유지 |
| 최종 제출 중 | 제출 ID / 본문을 고정하고 중복 입력과 초안 수정을 막음 |
| 결과 확인 중 | 저장 결과를 모르는 상태로 표시, 기존 ID로 결과 조회 또는 동일 본문 재시도 |
| 저장 완료 | 성공 응답을 확인하고 초안을 폐기한 뒤 생성한 관리대상으로 이동 |

최종 제출 직전에 requestId를 생성하고 제출 당시 본문을 고정합니다. 통신 재시도와 Access Token 재발급 후 재시도에는 같은 ID / 본문을 사용합니다. 명확한 검증 실패로 저장되지 않은 입력을 수정하면 새 ID로 제출할 수 있지만, 이전 결과가 불명확한 상태에는 먼저 조회합니다.

현재 탭에서 최종 제출 중 새로고침하면 제출 ID와 제출 당시 본문도 복원합니다. 최종 저장은 Server가 기본 정보를 포함한 전체 입력을 재검증하므로 첫 단계의 검증 응답을 저장 권한이나 검증 생략의 근거로 사용하지 않습니다.

탭 닫기 / 로그아웃으로 입력 초안을 폐기하더라도 이미 시작된 요청의 커밋을 취소하지 않습니다. 제출 후 결과가 불명확하면 민감한 본문과 구분해 최소한의 결과 확인 정보인 사용자 ID / requestId를 관리하고 재로그인도 같은 사용자에서만 조회합니다. 다른 계정에 이전 입력이나 결과를 전달하지 않습니다.

결과 확인 정보의 브라우저 저장 구현과 탭 복구, 이후 관리대상 목록 연결은 Client 구현에서 검증합니다. 이미 성공한 등록을 자동 삭제하거나 권한 해제로 처리하지 않습니다.

## 4. 오류 표시와 재시도

| 오류 | Client 처리 |
| --- | --- |
| 기본 정보 검증의 INVALID_REQUEST | 현재 입력 유지, 입력 기준 / 형식 확인 안내 |
| 기본 정보 검증의 통신 실패 / 일시 장애 | 현재 입력 유지, 다음 단계 이동 없이 검증 재시도 |
| 최종 등록의 INVALID_REQUEST | 오류 필드의 단계로 이동하고 Input / Dropdown의 error와 연결 |
| ACCESS_TOKEN_EXPIRED | 기존 authenticatedAPI가 같은 요청을 재발급 후 1회 재시도 |
| SESSION_EXPIRED / 인증 필요 | 기존 로그인 흐름 적용, 미확인 제출은 같은 사용자 재로그인 후 기존 requestId로 조회 |
| ACCOUNT_UNAVAILABLE | 초안 폐기, 기존 계정 이용 불가 흐름 적용 |
| ACCESS_DENIED | 접근 거부 안내, 과거 ADMIN 스냅샷으로 현재 권한을 복구하지 않음 |
| REGISTRATION_REQUEST_CONFLICT | 같은 ID로 본문을 덮어쓰지 않고 기존 성공 결과 확인 |
| REGISTRATION_IN_PROGRESS / 결과 조회의 404 | 입력 잠금과 ID 유지, 같은 ID / 본문 재시도 가능 |
| 최종 제출의 NETWORK_ERROR / INVALID_RESPONSE / HTTP_ERROR / 500 / 503 | 저장 실패로 단정하지 않고 결과 조회, 조회 자체가 실패하면 새 ID 생성 보류 |

최종 제출의 공통 전송 함수 15초 타임아웃도 결과가 불명확한 통신 실패로 처리합니다. 인증 / 서버 오류에서 검증 성공으로 다음 단계에 이동하지 않습니다. 201 / 200 / GET 성공을 확인하면 property.id로 관리대상을 선택해 관리자 진입 화면으로 이동합니다. 구체적인 화면 URL과 관리대상 목록 연결은 라우팅 구현 시 정합니다.

현재 ApiError는 HTTP 상태와 최상위 오류 코드만 유지합니다. 필드별 안내를 연결하려면 공통 전송에서 API의 안전한 errors 필드 / reason 정보를 보존하도록 확장해야 합니다. 메시지는 API 코드 / reason을 기준으로 표시하고 민감한 응답 원문을 그대로 노출하지 않습니다.

## 5. 구현 시 검증

- 기본 정보의 정상 입력 / 선택 필드 / 공백 정리와 검증 실패 시 입력 유지, 검증 버튼의 중복 요청 차단.
- PC 모달과 모바일 페이지의 공통 폼 사용, 라벨 / 설명 / 오류 연결과 반응형 표시.
- 이전 / 다음 이동과 새로고침 복원, 취소 / 이탈 / 탭 닫기 / 로그아웃 이후 초안 폐기, 계정 변경 시 초안 격리.
- 동 추가 / 수정 후 clientId 연결 유지와 세대 참조, 배열 순서 유지, 공용계좌 기본 지정과 항목 금액 검증.
- 제출 중 입력 잠금, 같은 requestId / 본문의 재시도, 제출 중 새로고침 후 요청 복원.
- 입력 오류의 단계 이동 / 필드 안내, 응답 유실 시 조회와 동일 요청 재시도, 다른 사용자에게 결과 확인 정보가 전달되지 않음.
- 저장 전 확인 화면과 저장 성공 표시의 구분, 성공한 property.id로 진입하고 초안을 폐기함.

기본 정보 화면의 사용자 상호작용과 API 경계는 `tests/propertyRegistration.spec.ts`에서 검증합니다. 검증 명령과 작성 규칙은 [Client AGENTS.md](../AGENTS.md)를 따릅니다. 위 전체 흐름 목록은 후속 구현 시 실행할 기준이며 이미 통과한 테스트를 의미하지 않습니다.
