# Client 주민 목록

갱신일: 2026-10-10. 주민 목록 화면과 조회 API를 구현했습니다. 업무 기준은 [도메인 규칙](../../docs/domainRules.md#확정된-주민-목록-조회), 데이터 구조는 [주민 명부](../../docs/erd.md#54-residents)와 [세대 주민 관계](../../docs/erd.md#55-unit_residents), 요청·응답·오류는 [주민 관리 API](../../docs/residentManagementApi.md)를 따릅니다.

## 1. 사용자 요청과 구현 범위

- 관리소장용 주민 목록을 `/manage/[propertyId]/residents`에 연결합니다.
- 삭제되지 않은 주민 전체를 표시합니다. 주민의 활성·비활성 상태 필터는 제공하지 않고 가입 상태 필터는 별도로 제공합니다.
- 연락처는 끝 4자리만 표시합니다. 전체 번호의 상세 공개는 후속 범위입니다.
- 한 세대에 여러 주민이 있으면 주민마다 한 행을 표시합니다. 각 주민의 현재 소속 세대는 하나만 표시하며 과거 세대를 합산하지 않습니다.
- 등록·상세·수정·대표 변경·엑셀 등록과 세대 목록의 주민 연동은 아직 구현하지 않습니다.
- 후속 등록 화면은 사용자 요청에 따라 웹에서는 모달, 모바일에서는 별도 페이지로 제공합니다. 이번에는 등록 버튼이나 임시 등록 화면을 추가하지 않습니다.

## 2. 현재 화면

| 영역 | 구현 |
| --- | --- |
| 요약 카드 | 전체 주민·가입 완료·미가입·승인 대기. 필터와 페이지에 관계없이 조회한 전체 명부 기준 |
| 필터 | 이름·연락처 끝 4자리·동/호수 검색, 동·관계·가입 상태와 초기화 |
| 표 위 | 필터 결과 수와 10 / 20 / 50명씩 보기 |
| 표 | 주민명·연락처·소속 세대·관계·대표 주민·가입 상태 |
| 표 아래 | 세대 목록에서 분리한 공통 페이지네이션. 표시 범위와 페이지 이동 |

가입 상태는 서버의 `signupStatus`를 받아 카드·표·필터에서 동일하게 사용합니다. 판정 기준은 [API의 가입 상태 판정](../../docs/residentManagementApi.md#가입-상태-판정)을 따릅니다. 승인 대기는 사용자 결정에 따라 명부에서 확인된 주민만 집계합니다. 미확인 신청자는 주민으로 추가하지 않습니다.

전체 주민은 세 가지 가입 상태의 합이며, 검색·필터를 적용해도 카드 집계는 전체 명부를 유지합니다. PC에서는 네 카드를 한 줄에, 모바일에서는 두 열에 배치합니다. 가입 완료는 등록 화면과 공유하는 공통 체크 아이콘, 승인 대기는 공통 Warning 색상과 시계 아이콘으로 표시합니다.

관리자의 주민 명부 등록과 주민의 서비스 가입은 구분합니다. 명부 등록만으로 서비스 가입이 완료되지는 않습니다. 가입 완료·확인된 대기 신청에 해당하지 않는 주민은 미가입이며, 확인된 가입 신청이 승인 전이면 승인 대기입니다.

동 필터는 서버의 등록·저장 순서를 그대로 쓰지 않고 세대 목록과 같은 공통 정렬 함수로 동 이름순으로 표시합니다. 숫자를 인식하므로 `2동 → 10동 → 101동 → 102동 → 103동` 순서이며 문자 동 이름도 같은 한국어 비교 기준을 사용합니다.

전화번호 전체를 브라우저로 전달하지 않습니다. `phoneLast4`만 받아 `•••• 1234`로 표시하며 값이 없으면 `—`로 표시합니다. 검색도 서버가 제공한 끝 4자리 범위에서 동작합니다.

소속 세대는 동이 있으면 `103동 301호`, 동이 없으면 `301호`로 표시합니다. 현재 관계가 없거나 소속 세대가 삭제되었으면 `—`로 표시하며 주민 행 자체는 유지합니다. 같은 301호에 김민수와 박서연이 있으면 두 행의 소속 세대가 같고, 서버의 대표 여부가 참인 사람에게만 `대표` 배지를 표시합니다. 최초 지정과 변경 권한은 [확정된 세대 대표 지정과 변경](../../docs/domainRules.md#확정된-세대-대표-지정과-변경)을 따르며 이번 조회 화면이 대표를 지정하거나 변경하지는 않습니다.

동이 없는 관리대상에서는 동 필터를 숨깁니다. 표만 가로 스크롤되며 모바일에서도 페이지 전체가 화면 폭을 넘지 않도록 합니다. 조회 중·조회 실패·권한 거부·빈 명부·검색 결과 없음을 구분하고 실패 시 이전 명부를 표시하지 않습니다.

## 3. 구조와 상태

- 화면은 `screens/household/resident-list/`에 두고 라우트는 공개 `index.ts`로 연결합니다. 형제 `unit-list` 슬라이스를 직접 참조하지 않습니다.
- 관계 선택지는 `entities/resident/constants/residentOptions.ts`에 둡니다.
- 카드·페이지네이션·표·입력·선택·버튼은 기존 `shared/ui` 공개 API를 사용합니다. 공통 UI는 주민 조회나 정책을 소유하지 않습니다.
- API는 관리대상의 명부 전체를 한 번 조회합니다. 세대 목록과 동일하게 화면에서 검색·필터·페이지 분할을 수행하며 필터·표시 개수 변경 시 첫 페이지로 이동합니다.
- 조회 키에는 현재 사용자와 관리대상 ID를 포함합니다. 저장소에 명부를 보관하지 않으며 잘못된 관리대상·중복 주민·전체 번호가 들어간 `phoneLast4` 등 계약에 맞지 않는 응답은 실패로 처리합니다.
- 관리 공통 틀의 접근권한과 주민 조회권한은 구분합니다. 부담당자도 공통 틀에는 접근할 수 있지만 주민 API는 관리소장만 허용합니다.

## 4. 후속 작업

아래 입력·저장 흐름은 구현 전 검토할 제안이며 확정된 입력 정책이나 구현 상태로 취급하지 않습니다.

- 등록: 웹 모달·모바일 페이지에서 입력 폼과 검증을 공유하는 구성을 제안합니다. 이름·연락처·기존 세대·관계의 필수 여부와 중복 판정은 후속 등록 계약에서 정합니다. 대표 최초 지정은 서버의 확정 정책을 따릅니다.
- 상세·수정: 현재 주민 정보와 세대 관계를 확인하고 수정하는 흐름을 설계합니다. 전체 연락처 공개·변경 반영 범위는 별도 구현합니다.
- 세대 목록 연동: 대표 주민과 가입 상태 정보를 실제 조회에 연결합니다. 현재 세대 목록의 `—` 표시는 유지합니다.
- 엑셀 등록: 업로드·미리보기·행별 오류·저장 흐름과 중복·부분 성공 처리를 후속 계약에서 정합니다.

작업 순서는 공통 카드·페이지네이션 분리 → 주민 목록 → 등록·상세·수정 → 세대 목록의 주민 정보 연동 → 엑셀 등록입니다. 현재 두 번째 단계까지 구현했습니다.

## 5. 검증

`tests/managementLayout.spec.ts`에서 사람별 행과 같은 세대의 여러 주민, 대표 표시, 세 가지 가입 상태와 네 카드 집계, 마스킹, 검색·필터·페이지 이동·표시 개수, 동 없음, 조회 중·오류·재시도·권한 거부·빈 목록과 잘못된 연락처·가입 상태 응답을 검증합니다. 1440 / 375 / 320px에서 페이지 폭과 모바일 배치를 확인합니다. 실행 명령은 [Client 검사 규칙](../AGENTS.md#9-test--build)을 따릅니다.
