# Client 주민 목록 설계안

작성일: 2026-10-10. 주민 목록의 후속 구현을 위한 설계안입니다. 업무 정책은 [도메인 규칙](../../docs/domainRules.md#4-사용자--주민--참여--권한), 데이터 구조는 [ERD의 주민 명부](../../docs/erd.md#54-residents)와 [세대 주민 관계](../../docs/erd.md#55-unit_residents)를 기준으로 확인합니다. 이 문서는 Client의 표시와 조작을 다루며 API 계약이나 서버 저장 절차를 확정하지 않습니다.

## 1. 사용자 요청과 현재 범위

- 사용자는 주민 목록 구현에 앞서 설계를 문서로 남기고 세대 목록의 카드·페이지네이션을 공통으로 분리하도록 요청했습니다.
- 같은 세대에 여러 주민이 소속되는 경우를 지원합니다. 대표자는 그 세대에 소속된 사람이며, 세대별 주민 수와 대표 여부를 구분해 표시합니다.
- 이번에 구현한 부분은 `shared/ui/summary-card`와 `shared/ui/pagination` 분리 및 기존 세대 목록 적용입니다.
- 주민 목록·등록·상세·수정·엑셀 등록 화면, 주민 테이블·Migration·API와 세대 목록의 실제 주민 연동은 아직 구현하지 않습니다. 주민 메뉴의 준비 중 상태를 유지합니다.
- 아래 화면 구성과 흐름은 제안입니다. 시안이나 제안의 버튼·상태·입력 항목을 확정된 사용자 요구로 취급하지 않습니다.

## 2. 여러 주민과 대표자 표시

현재 세대 소속 기준은 도메인 규칙을 따릅니다. 한 세대에 두 사람이 소속되면 주민 목록은 사람마다 한 행을 표시하고, 두 행의 소속 세대는 동일하게 표시합니다.

최초 지정과 변경 권한은 [확정된 세대 대표 지정과 변경](../../docs/domainRules.md#확정된-세대-대표-지정과-변경)을 따릅니다. 아래는 김민수가 해당 호수에 먼저 등록되고 박서연이 나중에 등록된 경우의 표시 예시입니다.

| 주민명 | 소속 세대 | 관계 | 대표 여부 |
| --- | --- | --- | --- |
| 김민수 | 103동 301호 | 임차인 | 대표 |
| 박서연 | 103동 301호 | 가족 | — |

- 주민 목록의 행과 표시 건수는 주민 기준입니다. 이 예시는 주민 두 명, 세대 한 개입니다.
- 대표 여부는 ERD의 `unit_residents.is_household_rep`에 대응하는 표시입니다. 로그인 계정의 관리자 권한이나 빌라·동 대표 이력과 혼동하지 않습니다.
- 세대 목록은 301호 한 행에 대표 주민을 표시하고, 후속 세대 상세에서 해당 세대의 여러 주민을 확인하는 흐름을 제안합니다. 실제 연동 전에는 현재의 `—` 표시를 유지합니다.
- 시안의 `103동 301호 외 1세대`처럼 한 주민의 현재 소속을 여러 세대로 표시하지 않습니다. 과거 소속 이력의 표시 방식은 후속 설계입니다.
- 최초 등록 시 대표 여부는 자동 지정 결과로 표시하고 일반 입력으로 선택받지 않습니다. 대표 변경 조작은 확정된 권한에 따라 관리소장에게만 제공합니다. 실제 변경 UI는 주민 기능 구현 시 설계합니다.
- 대표자의 퇴거 등 예외 처리는 위 도메인 규칙의 미정 항목을 따릅니다. 소유자 여부나 서비스 가입 완료를 이유로 대표를 자동 변경하지 않습니다.

## 3. 화면 구성 제안

현재 메뉴는 `세대 관리 → 주민 목록`입니다. 후속 화면 슬라이스는 `screens/household/resident-list/`, URL은 `/manage/[propertyId]/residents`를 제안합니다. 형제 세대 목록 슬라이스는 직접 참조하지 않고 공통 공개 API를 사용합니다.

| 영역 | 구성 제안 |
| --- | --- |
| 상단 | 제목·설명과 주민 등록 버튼. 엑셀 등록은 해당 기능 구현 시 연결 |
| 요약 | 전체 주민·가입 완료·미가입 카드. 집계 대상과 상태 판정은 후속 계약에서 확정 |
| 필터 | 이름·연락처·동/호수 검색, 동·관계·가입 상태 선택과 초기화 |
| 표 위 | 검색 결과 수와 10 / 20 / 50개씩 보기 |
| 표 | 주민명·연락처·소속 세대·관계·대표 여부·가입 상태 |
| 표 아래 | 표시 범위와 이전·다음·페이지 번호 |

- 카드 집계는 현재 페이지의 행 수와 구분합니다. 전체 관리대상 집계를 제안하며 필터 적용 범위는 구현 전에 확정합니다.
- 페이지네이션은 세대 목록의 배치와 동작을 기준으로 재사용하되 단위는 주민에 맞게 전달합니다. 필터·표시 개수 변경 시 첫 페이지로 이동합니다.
- 동이 없는 관리대상에서는 동 필터를 숨기고 소속 세대는 호수로 표시합니다.
- 가입 요청은 주민 명부와 별도 데이터입니다. 명부에 없는 신청자도 있으므로 승인 대기 요청 건수를 주민 수와 합산하지 않습니다. 대기 요청 건수와 가입 요청 화면 링크를 별도로 표시하는 방식을 제안하며, 주민별 승인 대기 배지는 연결 기준을 확정한 뒤 제공합니다.
- 행 클릭·주민명 버튼 → 상세 → 수정 흐름을 제안합니다. 체크박스·관리 열·더보기 메뉴는 실제 작업 항목과 필요성이 정해졌을 때 추가합니다.
- 조회 중·조회 실패·빈 명부·검색 결과 없음을 구분합니다. 연락처 공개·마스킹 범위와 전화번호 검색 방식은 저장 방식 및 조회 권한과 함께 결정합니다.

## 4. 등록·상세·수정과 엑셀 등록 제안

- 단건 등록은 공통 `ClientModal` 안에서 이름·연락처·기존 세대 선택·관계를 입력하고 대표 여부는 자동 지정 결과로 표시하는 방식입니다. 필수 입력과 허용값은 정책 확정 후 적용합니다. 동이 있으면 동을 먼저 고르고 해당 동의 세대를 선택합니다.
- 관리자 명부 등록으로 로그인 계정을 자동 연결하거나 주민 접근권한을 부여하지 않습니다. 계정 연결과 승인은 도메인 규칙의 가입 승인 흐름을 따릅니다.
- 저장 성공 후 서버 목록과 카드 집계를 갱신하고 공통 `Toast`를 표시합니다. 저장 실패에는 입력과 오류를 모달에 유지합니다.
- 상세에는 주민 정보·현재 세대·관계·대표 여부·가입 정보를 표시하고 수정으로 연결하는 방식을 제안합니다. 연락처 수정의 반영 범위와 세대 이동은 별도 정책 확인이 필요합니다.
- 삭제·퇴거는 상세 버튼을 먼저 만들지 않고 이력·권한 처리 정책을 확정한 뒤 설계합니다.
- 엑셀은 업로드 → 미리보기·행별 오류 확인 → 저장 흐름을 제안합니다. 단건 등록의 검증을 재사용하되 중복 판정, 전체 성공 / 부분 성공, 재업로드 처리는 후속 API 계약에서 정합니다.

## 5. 공통 컴포넌트와 후속 순서

- `SummaryCard`는 제목·값·단위·아이콘·의미 색상만 받습니다. 집계·상태 판정과 카드 개수·배치는 각 화면의 책임입니다.
- `Pagination`은 총 개수·현재 페이지·페이지 수·페이지 크기·단위·접근성 이름·이동 콜백을 받습니다. 데이터 조회·필터·페이지 보정은 사용하는 화면에서 관리합니다.
- 표는 `shared/ui/data-table`, 입력·선택은 `shared/ui/form-controls`, 버튼·모달·성공 알림은 기존 공통 UI를 사용합니다.
- 기존 동·세대 조회를 주민 화면에서도 사용할 때는 재사용 책임을 확인해 하위 레이어로 분리합니다. 세대 화면 내부 API를 직접 가져오지 않습니다.

권장 순서는 공통 카드·페이지네이션 분리 → 주민 목록 → 등록·상세·수정 → 세대 목록의 주민 정보 연동 → 엑셀 등록입니다. 이번 작업은 첫 단계만 구현합니다. 후속 구현 전에는 등록·수정 권한, 입력 필수 여부, 관계 선택지, 대표 지정의 미정 예외 처리, 가입 상태·카드 집계와 중복 주민 확인 기준을 확정해야 합니다.
