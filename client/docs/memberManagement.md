# 주민 역할과 관리자 관리 화면

기준일: 2026-10-24. 아래 기존 화면 설명은 현재 구현이며 신규 주민 초대 화면은 마지막 절의 미구현 설계로 구분합니다. 공통 정책은 [도메인 규칙](../../docs/domainRules.md#주민-참여-흐름), 요청·오류는 [참여자 관리 API](../../docs/memberManagementApi.md)를 참조합니다.

## 주민 목록·상세

목록의 열 제목과 상세·수정 폼의 라벨은 모두 `역할`로 통일합니다. 목록에 역할을 추가하고 주민 구분·세대 대표·가입 상태와 구분합니다. 미가입을 주민 권한으로 표시하지 않습니다. 현재 연결 계정의 역할을 서버에서 조회합니다.

주민 상세는 기존 PC 중앙 모달·모바일 독립 상세를 유지합니다. 기존 상세의 필드 행에 `역할`을 표시하고, 기존 주민 수정 폼에서 같은 공통 Dropdown으로 주민·부담당자를 선택합니다. 가입 전 주민은 역할 선택을 비활성화하며 주민 상세에 초대코드·가입 승인 안내·별도 권한 관리 영역을 넣지 않습니다. 주민 정보와 역할은 하나의 수정 요청·트랜잭션으로 저장합니다.

현재 가입 신청·명부 연결·승인·거절은 기존 사이드바 `가입 요청` 메뉴에서 처리합니다. 목록 행을 누르면 PC에서는 기존 크기의 중앙 모달, 모바일에서는 헤더 뒤로가기가 있는 독립 상세를 표시합니다. 신청 계정·세대·마스킹 연락처·신청일을 확인하고 명부의 주민을 선택해 승인합니다. 참여 링크는 이 메뉴에서 복사하며 현재 주민 화면 `/join/[propertyId]`는 코드 없이 동·호수와 필수 연락처만 입력받습니다. 신규 전체 공유·개인 지정 초대는 아직 연결하지 않았습니다.

## 설정과 초대 입력

사용자 후속 지시에 따라 `/manage/[propertyId]/settings`의 `등록 및 참여` 항목에는 같은 이름의 진입 버튼을 둡니다. 헤더 행동 영역·참여자 표·참여자 선택·외부 부담당자 초대·초대 신청·관리소장 인계 UI를 넣지 않습니다. 버튼은 `/properties/add`로 연결하며 [서비스 진입 설계](serviceEntry.md#관리할-곳-추가참여-진입-2026-10-17)를 따릅니다. 2026-10-18에 추가한 별도 관리계좌 카드의 정정 버튼은 [계좌 변경 설계](managementLayout.md#설정의-계좌-변경-2026-10-18)를 따릅니다.

외부 부담당자용 코드 입력은 기존 `/invitations`를 재사용합니다. 코드 원문을 URL·저장소에 넣지 않으며 신청 성공 뒤 입력을 지웁니다. 역할 변경·인계·코드 발급·승인의 서버 API는 유지하지만 별도 관리자 관리 화면은 현재 제공하지 않습니다. 주민 역할 수정은 주민 수정 폼을 사용합니다.

## 목록 표현

가입 요청은 주민 목록과 같은 공통 ListCard 안에 DataTable을 넣습니다. 흰 카드·테두리·보조색 표 헤더로 페이지 배경과 구분하고 상태는 배지로 표시합니다. 빈 목록도 아이콘·제목·참여 링크 안내를 카드 안에 표시합니다.

## 가입 요청 모바일 주요 버튼 (2026-10-17)

모바일(767px 이하)에서는 `주민 참여 링크 복사`를 제목·설명 아래 한 줄 전체 너비의 버튼으로 표시한다. 최소 높이 56px·글자 크기 16px로 제공하고 글자는 가운데 정렬한다. PC의 기존 헤더 오른쪽 배치는 유지한다.

## 주민 초대 개편 화면 설계

상태: 미구현. 공통 입력·권한·승인 기준은 [도메인 규칙](../../docs/domainRules.md#주민-참여-흐름)을 참조합니다. 기존 화면에서 초대 기능이 없다는 설명은 아래 신규 기능의 금지 정책이 아닙니다.

### 전체 공유 초대

관리소장이 공통 링크와 코드를 관리하고 공유합니다. 가입 요청 화면의 링크 복사 동선을 재사용하되 코드 발급·변경·폐기를 어디에 배치할지는 구현 전에 정합니다. 부관리자는 기존 가입 요청 승인·거절을 수행하며 코드 발급 권한을 임의로 확대하지 않습니다.

주민은 공통 링크에서 코드 검증 후 이름·선택 전화번호·동 및 호수를 입력합니다. PC는 가입 정보 모달을 사용하고 모바일의 독립 페이지·전체 화면 모달 중 구성은 미정입니다. 기존 로그인 세션이 있으면 다시 로그인하지 않으며 코드·입력 상태를 유지하며 로그인으로 연결하는 방법을 설계합니다. 제출은 로그인 계정을 사용하고 결과는 승인 대기로 표시합니다.

관리자 검토 화면은 신청 이름과 계정 닉네임을 구분하고 전화번호 미입력을 오류나 가짜 마스킹 번호로 표시하지 않습니다. 이름·세대 입력만으로 명부 주민을 자동 선택하거나 승인하지 않습니다.

### 개인 지정 초대

주민 목록에 `미연결 주민` 필터와 개인 링크 발급·복사·재발급·철회 동선을 추가합니다. 발급 가능 여부는 서버의 현재 계정 미연결·미삭제·유효 세대 기준을 사용하며 `미가입` 카드나 `NOT_JOINED` 값과 동일시하지 않습니다. 구체적인 행·상세 내 버튼 배치는 주민 목록 구현 설계에서 정합니다.

수락 화면은 세션을 확인하고 대상 명부 정보를 표시한 뒤 참여 의사를 받습니다. 정상 정보 확인 후 참여하는 기본 흐름은 재입력·관리자 재승인 없이 자동 승인합니다. 전체 연락처를 표시할 필요성·마스킹 범위와 수락 전 정보 노출 범위는 API 설계에서 정합니다.

추가 논의 중인 화면 분기는 `[정보가 맞아요 · 참여하기]`와 `[정보 수정 요청]`입니다. 전자는 기존 명부로 가입을 완료하고 후자는 이름·전화번호 정정 내용을 제출한 뒤 관리자 확인을 기다리는 설계안입니다. 정정 요청은 가입 완료로 표시하지 않고 주민 권한을 먼저 부여하지 않습니다. 다른 사람의 초대나 동·호수 불일치는 담당자 확인으로 연결합니다. 이 분기는 [도메인 설계안](../../docs/domainRules.md#개인-초대-정보-확인과-정정의-설계안)이며 확정·구현 전입니다.

서버의 연결·권한·초대 사용 저장이 성공한 뒤에만 완료로 표시합니다. 만료·철회·이미 사용됨·다른 계정 연결·세대 변경은 완료와 구분하고 재로그인으로 기존 계정을 임의 교체하지 않습니다. 주민 홈은 아직 없으므로 실제 목적지는 홈 연결 시점과 함께 정합니다.

외부 부담당자용 `/invitations` 코드 입력을 주민 공유 코드 입력이나 개인 링크 수락 화면으로 그대로 재사용하지 않습니다. 비회원 공지·문의 진입도 이 가입 흐름과 별도로 유지합니다.
