# 공용 통장 거래 분류 화면 설계

작성일: 2026-10-16. 상태: **화면 설계안, 미구현**. 업무 요구와 예시는 [공통 설계](../../docs/bankingManagement.md), 확정 정책은 [도메인 규칙](../../docs/domainRules.md#공용-통장의-동별-거래-분류), 데이터 관계는 [ERD](../../docs/erd.md#94-공용-통장-거래-분류-확장-설계안)를 따릅니다.

통장 거래에서 입금·출금을 선택해 분류하고 확정 결과를 동별로 조회합니다. 아래 메뉴·열·버튼·진입 경로는 구현을 위한 제안이며 모두 사용자 확정 요구로 취급하지 않습니다.

## 1. 메뉴와 진입 경로

| 화면 | 경로 설계 | 역할 |
| --- | --- | --- |
| 거래 내역 | `/manage/[propertyId]/banking/transactions` | 원본 입출금 조회·분류 진입 |
| 엑셀 업로드 | `/manage/[propertyId]/banking/upload` | 파일 검증·미리보기·원본 가져오기 |
| 모바일 거래 상세 | `/manage/[propertyId]/banking/transactions/[transactionId]` | 직접 접근·새로고침 가능한 상세와 분류 |
| 동별 수입·지출 | `/manage/[propertyId]/banking/buildings` | 전체·동별 수납·배분 지출·기간 수지 조회 |

기존 `통장 거래 → 거래 내역·엑셀 업로드` 목적지는 유지하고 동별 현황을 추가하는 안입니다. 기존 입금 확인·월별 수납 메뉴도 같은 수납 기록을 사용합니다. 실제 메뉴 활성화는 화면 구현 시 수행합니다. 계좌 추가·업로드 이력·내부이체 메뉴를 이번 화면의 선행 조건으로 만들지 않습니다.

## 2. 거래 내역

본문 맨 위 ListHeader에 제목·설명과 엑셀 업로드 행동을 배치합니다. 아래에 기간·입출금 구분·분류 상태·검색·표시 개수를 둡니다. 기간은 은행 거래일 기준이며 월별 고지서 조회와 구분합니다. 공용 계좌 하나를 사용하는 화면에 동별 통장 선택을 만들지 않습니다.

표의 제안 열은 거래일시·상대방 및 적요·입금액·출금액·거래 후 잔액·분류 상태입니다. 분류 상태는 미분류·수납 연결·지출 연결·보류 같은 표시값으로 구성하되 실제 저장 Enum은 확정하지 않습니다. 기존 원장과 신규 지출 연결에서 표시값을 구성합니다.

- 행 클릭과 키보드 Enter·Space로 상세를 엽니다. 중복 상세 버튼 열을 두지 않습니다.
- 최근 은행 확인 잔액에는 원본 거래 시점을 표시하며 자료가 없으면 확인 필요로 표시합니다.
- 목록 상단의 입금·출금 합계는 기간·거래 범위를 명시하고 페이지 이동으로 바뀌지 않게 합니다. 검색·상태 필터가 요약 집계에 미치는 범위는 API 설계에서 정합니다.
- 전체 원본 내역에는 분류 전 거래도 표시합니다. 동 필터는 동 귀속이 확인된 결과만 표시하며 한 출금의 전체 금액을 각 동의 부담액으로 오인하게 만들지 않습니다.
- 미분류·기타 귀속을 별도로 확인할 수 있게 하고 미분류를 특정 동의 거래로 자동 지정하지 않습니다.

## 3. 상세와 분류

PC는 중앙 ClientModal, 767px 이하는 독립 상세 페이지를 사용합니다. 모바일 헤더의 `<`는 같은 관리대상의 거래 목록으로 돌아가며 본문·푸터에 목록 버튼을 추가하지 않습니다. 직접 접근·로딩·오류·대상 없음에서도 헤더 뒤로가기를 유지합니다.

상세 상단에는 변경할 수 없는 은행 원본을 표시하고 아래에 업무 분류 입력을 배치합니다. 원본 일시·금액·상대방·적요·잔액과 관리자가 지정한 분류·메모를 구분합니다. 일반 폼에서 원본 내용을 수정하지 않습니다.

### 입금

동·호수와 누적 부과·수납·미납·선입금을 확인합니다. 이름·동호수 일치 자동 확정과 세대 선택 범위는 [기존 입금 화면](paymentManagement.md)과 [입금 API](../../docs/paymentApi.md)를 재사용합니다. 새로운 세대 선택 범위를 임의로 넓히지 않습니다.

확정 전에 입금 전액·고지서 반영 합계·남는 선입금을 구분해 표시합니다. 기존 수동 수납 연결 후보가 있으면 동일 수납을 다시 만드는 대신 기존 연결 절차를 제공합니다. 이미 연결된 거래는 실제 수납과 배분을 조회합니다. 수납 취소도 기존 권한·사유·전체 취소 계약을 따릅니다.

동일 수납을 두 메뉴에서 처리할 수 있으므로 저장 성공 후 거래 상세·목록·입금 원장·월별 수납·동별 현황의 관련 조회를 갱신하는 설계입니다. 화면끼리 별도 금액을 저장하지 않습니다.

### 지출

비용 과목·부담 동·배분 방식·동별 금액을 입력하는 안입니다. 선택 동 균등 배분은 결과를 검토하게 하고 직접 입력은 합계 차이를 표시합니다. 기본 부담 동을 로그인 사용자나 출금 계좌로 추측하지 않습니다.

한 출금을 여러 비용 과목으로 나눌 때는 항목별 금액과 각 항목의 동별 배분을 표시합니다. 항목 합계와 출금액, 각 항목의 배분 합계가 모두 맞아야 합니다. 균등 배분의 나머지 정책을 확정하기 전에는 나머지를 임의의 동에 숨겨 반영하지 않습니다.

저장 실패에는 입력을 유지하고 저장 중 중복 제출·닫기·Escape를 막습니다. 취소·재분류 화면은 해당 정책을 결정한 뒤 추가하며 확정 지출을 일반 편집으로 덮어쓰지 않습니다.

### 기타 거래와 보류

이자·환급 등 관리비 수납이 아닌 거래를 특정 세대 고지서에 억지로 배분하지 않습니다. 기타 분류와 귀속 정책을 정하기 전에는 확인 필요 상태를 유지합니다. 지출 보류의 저장 상태·사유·해제는 신규 지출 계약에서 정의하며 기존 Payment 보류를 출금에 재사용하지 않습니다.

## 4. 동별 수입 지출 조회

조회 기간과 `전체 동 / 특정 동`을 선택합니다. 동 선택지는 실제 저장된 동을 사용하고 개수를 고정하지 않습니다. 요약은 기간의 확정 수납·배분 지출·기간 수지이며 공통 설계의 [지표 기준](../../docs/bankingManagement.md#5-조회-금액과-잔액의-구분)을 따릅니다.

전체 화면에는 동별 행을 표시하고 특정 동에서는 세대별 수납과 비용 과목별 지출을 확인하는 구성을 제안합니다. 지출 상세에는 공용 통장의 원래 출금액·해당 동 부담액·다른 부담 동을 구분해 표시합니다. 동별 지출 행을 클릭하면 같은 원본 거래와 확정 지출로 연결됩니다.

기초금액·기타 거래 귀속이 정해지기 전에는 기간 수지를 동별 보유 잔액이나 회계 손익으로 표시하지 않습니다. 원본 미연결 수동 수납과 미분류 거래 때문에 은행 입출금과 차이가 날 수 있음을 해당 집계 가까이에서 확인할 수 있게 합니다.

## 5. 공통 UI와 코드 책임

ListHeader·ListCard·DataTable·FilterTabs·Pagination·CalendarPicker·FileDropzone·Button·ClientModal·Toast를 기존 공개 API로 재사용합니다. 엑셀 행동·상태 색상·모달과 모바일 복귀는 [Client 규칙](../AGENTS.md)을 따릅니다.

화면을 만들 때 `screens/banking/<화면 슬라이스>`로 업무 그룹을 구성하고 형제 화면을 직접 참조하지 않습니다. 수납 기능과 도메인 모델을 재사용하되 화면에서 다른 Widget 내부 파일을 가져오지 않습니다. 현재 입금 Widget에 묶인 공유 책임은 구현 시 실제 재사용 범위를 보고 적절한 하위 레이어로 옮깁니다. 아직 화면 폴더나 빈 슬라이스를 생성하지 않습니다.

조회 키는 계정·관리대상·기간·거래 범위를 포함합니다. 원본 개인정보와 분류 초안을 URL·브라우저 영속 저장소에 보관하지 않습니다. 조회 실패·권한 거부·정상 빈 목록·필터 결과 없음을 구분하고 오류를 예시 거래로 대체하지 않습니다.

## 6. 구현 시 검증 기준

- 입금 분류 확정 후 같은 고지서 수납과 동별 수납이 함께 갱신되고 재확정으로 증가하지 않음.
- 공동지출의 원본 출금 1건과 각 동 부담액을 구분하며 전체 합계를 이중 계산하지 않음.
- 미분류·기타 거래·수동 수납과 기간 기준의 차이를 표시하고 동별 수지를 은행 잔액으로 표시하지 않음.
- 저장 실패 입력 유지, 동시 변경 충돌, 취소 후 재조회와 다른 메뉴의 캐시 갱신.
- PC 중앙 모달·모바일 독립 경로·헤더 복귀·새로고침·직접 접근·320px 표시.
- 다른 관리대상 응답 차단·현재 권한 확인·원본 개인정보의 저장소 미보관.

검증 명령은 [Client AGENTS.md](../AGENTS.md#9-test--build)를 따릅니다. 위 항목은 후속 구현의 검증 기준이며 현재 테스트 통과를 의미하지 않습니다.
