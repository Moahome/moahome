# Client 관리 레이아웃 설계

작성일: 2026-10-09. **상태: 사용자 합의에 따른 구현 예정 설계.** 이 문서의 레이아웃, 사이드바와 대시보드 경로는 아직 구현하지 않았습니다.

이번 범위는 사이드바·드롭다운·메뉴 링크를 분리한 공통 관리 레이아웃과 `임시 페이지`만 표시하는 대시보드입니다. 각 업무 메뉴는 자기 경로와 페이지를 가지며 같은 레이아웃을 공유합니다. 기본 진입은 [서비스 진입 설계](serviceEntry.md), 관리 권한은 [공통 관리 영역 접근 API](../../docs/managementAccessApi.md), 업무 정책은 [도메인 규칙](../../docs/domainRules.md)을 따릅니다.

## 1. 공통 레이아웃과 경로

관리 영역의 공통 범위는 `/manage/[propertyId]/...`입니다. `propertyId`는 실제 관리대상 UUID입니다. 로그인 후 기본 도착지는 `/manage/[propertyId]/dashboard`로 정하며, 대시보드는 사이드바의 여러 메뉴 중 하나입니다. 세대 목록·주민 목록과 다른 업무 페이지는 대시보드와 나란히 관리 영역 아래에 배치합니다.

### 라우팅 파일과 화면의 관계

| 구성 | 책임 |
| --- | --- |
| `app/(main)/manage/[propertyId]/layout.tsx` | 관리 영역 전체의 공통 레이아웃 연결 |
| 메뉴별 `app/.../page.tsx` | 해당 URL을 화면 슬라이스의 공개 API에 연결 |
| 메뉴별 `screens/<화면>/ui/...Page.tsx` | 해당 메뉴의 실제 본문 구성 |

`app`의 `page.tsx`와 `screens`의 화면 컴포넌트는 한 페이지의 라우팅 연결과 본문을 나눈 것입니다. 각 업무 화면은 자기 화면 슬라이스를 사용하며 사이드바가 화면 컴포넌트를 직접 가져와 교체하지 않습니다.

아래는 대시보드와 후속 메뉴 페이지의 관계를 보여 주는 구조 예시입니다. 이번 구현 대상은 공통 `layout.tsx`와 임시 대시보드이며, 후속 업무 페이지 파일은 해당 메뉴를 구현할 때 추가합니다.

```text
src/app/(main)/manage/[propertyId]/
├── layout.tsx                 ← 모든 관리 메뉴의 공통 틀
├── dashboard/
│   └── page.tsx               ← 대시보드 메뉴
├── households/
│   └── page.tsx               ← 세대 목록 메뉴, 후속
├── residents/
│   └── page.tsx               ← 주민 목록 메뉴, 후속
└── billing/
    └── monthly/
        └── page.tsx           ← 월별 부과 내역 메뉴, 후속

src/screens/management-dashboard/
├── index.ts
└── ui/
    └── managementDashboardPage.tsx
```

후속 메뉴도 각자의 `screens` 공개 API를 연결합니다. 위 예시는 설계이며 현재 생성된 파일 목록이 아닙니다.

- `layout.tsx`는 `widgets/management-layout`의 공개 API로 공통 틀을 연결합니다.
- `ManagementLayout`은 인증·현재 관리 권한 확인, 사이드바, 모바일 메뉴 버튼과 본문 영역을 조합합니다. 메뉴 목록·드롭다운·링크의 JSX와 스타일은 각각의 컴포넌트가 담당합니다.
- 하위 `page.tsx`는 해당 `screens`의 공개 API로 본문을 연결합니다. 관리대상 안에서 페이지를 바꾸면 공통 틀은 유지하고 `children`으로 들어오는 본문만 바꿉니다.
- 본문의 `main` 영역은 공통 레이아웃에서 한 번 제공합니다. 대시보드 화면 안에 별도의 `main`을 중첩하지 않습니다.
- 루트 레이아웃이나 기존 `/start` 화면에 관리자 사이드바를 붙이지 않습니다. 관리자 레이아웃은 관리 경로 하위에만 적용합니다.

라우팅 파일은 Server Component를 기본으로 유지하고 클릭, 펼침 상태, 현재 경로와 브라우저 인증 처리가 필요한 Widget 내부에 Client 경계를 둡니다. 현재 Access Token은 브라우저 메모리에 있으므로 Next.js 라우팅 파일에서 임의로 인증정보를 추정해 업무 API를 호출하지 않습니다.

## 2. 컴포넌트 분리와 메뉴 링크

### 컴포넌트 구조

```text
src/widgets/management-layout/
├── index.ts
└── ui/
    ├── managementLayout.tsx
    ├── managementLayout.module.css
    ├── _components/
    │   └── management-sidebar/
    │       ├── managementSidebar.tsx
    │       ├── managementSidebar.module.css
    │       ├── sidebar-dropdown/
    │       │   ├── sidebarDropdown.tsx
    │       │   └── sidebarDropdown.module.css
    │       └── sidebar-link/
    │           ├── sidebarLink.tsx
    │           └── sidebarLink.module.css
    └── _constants/
        └── managementNavigation.ts
```

| 구성 | 책임 |
| --- | --- |
| `ManagementLayout` | 권한 확인, PC / 모바일 배치와 `children` 본문 조합 |
| `ManagementSidebar` | 서비스 로고·메뉴 목록·로그아웃 조합, 그룹과 단일 링크 배치 |
| `SidebarDropdown` | 상위 그룹의 펼침 버튼, 열림 상태·화살표·하위 목록과 접근성 처리 |
| `SidebarLink` | 메뉴 목적지의 Next.js `Link`, 현재 페이지 강조와 준비 중 표시 |
| `managementNavigation` | 메뉴 ID·이름·아이콘·그룹 자식·목적지 경로·이동 가능 상태 |

각 UI 컴포넌트는 자신의 폴더와 CSS Module을 가집니다. 사이드바 전용 드롭다운과 링크는 `management-sidebar` 내부에 두고 별도 파일로 구현합니다. `ManagementSidebar`는 이 컴포넌트를 조합하며 펼침 동작과 각 링크의 표현을 한 파일에 작성하지 않습니다.

Widget 외부에는 `ManagementLayout`의 공개 API를 제공합니다. 페이지는 공통 레이아웃이 적용된 경로 아래에 본문을 연결하므로 사이드바를 페이지마다 가져오지 않습니다. Widget이 상위 레이어의 `screens`를 참조하지 않으며 링크는 URL로 페이지를 연결합니다.

### 메뉴별 목적지

제공된 시안의 메뉴를 다음처럼 구성합니다. 표의 목적지는 `/manage/[propertyId]` 뒤에 붙이는 경로 설계안입니다. 모든 이동 항목에 자신의 목적지를 정의하고 현재 관리대상 UUID를 넣어 실제 링크를 만듭니다.

| 상위 그룹 | 이동 항목 | 목적지 |
| --- | --- | --- |
| 없음 | 대시보드 | `/dashboard` |

| 세대 관리 | 초대 관리 | `/invitations` |
| 관리비 부과 | 월별 부과 내역 | `/billing/monthly` |
| 관리비 부과 | 관리비 부과하기 | `/billing/create` |
| 관리비 부과 | 부과 항목 관리 | `/billing/items` |
| 입금 관리 | 입금 확인·매칭 | `/payments/matching` |

세대 관리·관리비 부과 등 상위 그룹은 `SidebarDropdown`의 버튼으로 여닫고 각 하위 항목은 `SidebarLink`로 연결합니다. 대시보드·공지사항·설정처럼 하위 항목이 없는 메뉴는 단일 링크로 배치합니다. 상위 그룹을 펼치는 동작과 하위 페이지로 이동하는 동작을 구분합니다.

### 링크 연결과 구현 상태

`managementNavigation`은 메뉴 설정 데이터만 관리합니다. 그룹에는 자식 목록을, 이동 항목에는 목적지와 이동 가능 상태를 정의합니다. 컴포넌트는 이 데이터를 순회해 구성하고 메뉴마다 조건문과 이동 핸들러를 반복하지 않습니다.

이동 가능한 항목은 `SidebarLink` 안에서 실제 `href`를 가진 Next.js `Link`로 렌더링합니다. 예를 들어 세대 목록의 완성된 주소는 `/manage/{실제 관리대상 UUID}/households`입니다. 링크를 누르면 해당 URL의 `page.tsx`가 연결한 본문으로 이동하며 공통 레이아웃은 유지됩니다. 링크의 새 탭 열기와 브라우저 기본 동작도 유지합니다.

이번 연결에서는 대시보드만 이동 가능한 상태로 둡니다. 나머지 항목도 위 표의 목적지 설계를 유지하되 실제 업무 페이지를 구현하기 전에는 준비 중으로 표시합니다. 준비 중 항목을 누르면 없는 주소나 `#`로 이동시키지 않습니다. 해당 업무를 구현할 때 메뉴별 `page.tsx`와 화면 슬라이스를 연결하고 링크를 활성화합니다. 사이드바 작업을 위해 업무 화면의 내용이나 빈 페이지를 일괄 생성하지 않습니다.

## 3. 펼침과 현재 페이지 표시

- `SidebarDropdown`의 상위 메뉴 버튼은 클릭 / Enter / Space로 하위 목록을 펼치거나 접습니다. 여러 그룹을 각각 여닫을 수 있게 합니다.
- 초기에는 현재 경로에 해당하는 그룹을 펼칩니다. 현재 구현 대상인 대시보드는 단일 링크이므로 다른 그룹은 접힌 상태에서 시작합니다.
- 페이지가 바뀌면 `SidebarDropdown`은 해당 페이지의 그룹을 펼치고 `SidebarLink`는 현재 링크를 강조합니다. 경로 비교는 실제 메뉴 경로와 구간을 사용해 다른 메뉴 이름의 일부가 우연히 일치하는 것으로 선택하지 않습니다.
- `SidebarLink`는 선택한 링크에 `aria-current="page"`를, `SidebarDropdown`은 펼침 버튼에 `aria-expanded`와 `aria-controls`를 제공합니다. 닫힌 하위 항목은 포커스 / 접근성 탐색에서 제외합니다.
- 각 그룹의 열림 상태는 해당 `SidebarDropdown`에서 관리하며 공통 레이아웃이 유지되는 동안 보존합니다. 메뉴 펼침을 기억하기 위한 별도 브라우저 영속 기록은 만들지 않습니다.
- 아이콘, 선택 표시, 배경·글씨·테두리는 기존 브랜드와 전역 색상 토큰을 사용합니다. 펼침 애니메이션은 짧게 적용하고 `prefers-reduced-motion`에서는 생략합니다.

기존 `shared/ui/form-controls`의 Dropdown은 값을 선택하는 입력입니다. 메뉴 탐색의 펼침 처리는 별도 `SidebarDropdown`으로 분리합니다. 기존 Button, BrandMark와 LogoutButton은 공개 API로 재사용하며 사이드바의 조합 코드에 입력 Dropdown의 업무를 추가하지 않습니다.

## 4. PC와 모바일

PC에서는 왼쪽 사이드바와 오른쪽 본문을 나란히 배치합니다. 메뉴가 높이를 넘으면 사이드바 내부에서 스크롤할 수 있게 하고 긴 이름이 본문을 밀어내지 않도록 합니다.

모바일에서는 사이드바를 메뉴 버튼으로 여는 서랍 형태로 표시합니다. 닫기 버튼, Escape와 바깥 영역으로 닫을 수 있게 하고, 열려 있는 동안 배경 스크롤과 포커스를 제한합니다. 닫으면 메뉴 버튼으로 포커스를 돌리며 실제 페이지를 선택한 경우에는 이동 후 메뉴를 닫습니다. PC 전환이나 레이아웃 이탈 시에도 스크롤 잠금을 정리합니다.

공통 틀에는 서비스 로고와 로그아웃 동작을 제공해 관리 화면에서도 기존 인증 흐름을 사용할 수 있게 합니다. 시안의 별도 상단 알림·프로필 구성과 관리대상 전환 UI의 배치는 후속 범위입니다. 여러 관리대상을 지원할 수 있도록 선택 대상은 URL과 현재 권한 응답으로 구분합니다.

## 5. 현재 권한 확인과 화면 상태

관리대상 직접 접근은 세션 확인 뒤 공통 API의 해당 관리대상 권한 조회를 거칩니다. 목록에 포함됐던 사실이나 등록 성공 응답만으로 본문을 표시하지 않습니다.

| 상태 | 레이아웃 처리 |
| --- | --- |
| 세션 / 현재 관리 권한 확인 중 | 이전 관리대상 이름·본문을 숨기고 확인 상태 표시 |
| 권한 확인 성공 | 확인한 대상의 사이드바와 하위 본문 표시 |
| 인증 거부 / 계정 이용 불가 | 기존 인증 흐름에 따라 로그인으로 이동 |
| 현재 관리 권한 없음 | 이전 본문을 숨기고 접근 거부 및 서비스 재진입 동작 제공 |
| 네트워크 / 내부 조회 장애 | 이전 본문을 숨기고 해당 조회 재시도 제공 |
| 관리대상 ID 형식 오류 | API를 호출하지 않고 잘못된 접근 상태와 서비스 재진입 동작 제공 |

재진입 동작은 `/entry`에서 목록을 새로 확인하게 합니다. 거부된 ID를 최근 기록에서 제거할 때는 현재 사용자와 제거 대상 ID가 같은지 확인해 늦은 응답이 다른 선택을 지우지 않도록 합니다. 실패를 빈 목록으로 처리해 `/start`로 자동 이동하지 않습니다.

관리대상 ID 변경, 새 진입, 새로고침과 브라우저 기록 복원에서는 현재 권한을 다시 확인합니다. 이전 대상의 쿼리 결과를 새 대상의 화면에 잠시 표시하지 않습니다. 기존 등록 완료 화면에서 적용한 `pagehide` 숨김과 `pageshow.persisted` 재검증 원칙을 관리 레이아웃에도 적용해 로그아웃 전 화면을 그대로 복원하지 않습니다.

동일 관리대상 안에서 공통 레이아웃이 유지되는 동안에도 후속 업무 API는 Server에서 각 요청의 현재 권한을 검증해야 합니다. 레이아웃의 확인 결과를 업무 API의 권한 증명으로 사용하지 않습니다.

## 6. 임시 대시보드의 범위

대시보드 본문은 `임시 페이지`라는 문구만 표시합니다. 인사말, 청구·수납·미수·지출 카드, 처리할 일, 일정, 최근 입금과 공지 본문을 채우지 않습니다. 시안의 금액·건물명·사용자명·건수를 실제 데이터처럼 넣지 않습니다.

아직 없는 주민 화면, 승인 요청 처리, 회계·정산 화면, 관리대상 설정과 통계 API를 이번 작업의 선행 조건으로 만들지 않습니다.

## 7. 구현 시 검증

- 관리 경로에서 공통 사이드바가 표시되고 `/start`와 공개 화면에는 표시되지 않음.
- 대시보드 본문은 `임시 페이지`만 표시하고 가상 업무 데이터가 없음.
- 각 메뉴 그룹의 클릭·키보드 펼침 / 접힘, 준비 중 항목의 이동 차단과 현재 링크 표시.
- 메뉴 설정·사이드바 조합·드롭다운 동작·링크 표시가 각각의 파일과 스타일로 분리됨.
- 모든 이동 항목에 자신의 목적지 경로가 정의되고 활성 항목이 현재 관리대상 UUID를 포함한 실제 `Link`로 연결됨.
- 후속 하위 페이지 연결 시 메뉴별 URL과 화면 슬라이스로 이동하고 동일 레이아웃에서 본문만 교체되며 해당 그룹이 펼쳐짐.
- PC 메뉴 스크롤, 긴 이름, 320px / 390px 모바일의 가로 넘침과 열기·닫기·포커스·스크롤 복원.
- 직접 URL 접근, 주민 역할 / 다른 사용자 / 권한 종료의 거부, 조회 중과 장애 시 이전 본문 숨김.
- 관리대상 변경과 로그아웃 후 뒤로가기 / bfcache 복원에서 계정·대상 정보가 섞이지 않음.

구현할 때 [Client AGENTS.md](../AGENTS.md)의 정적 검사·빌드·통합 테스트를 수행합니다. 위 항목은 계획이며 이번 문서 작성에서 통과한 테스트로 보고하지 않습니다.
