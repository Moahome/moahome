# 주민 관리 API

작성일: 2026-10-10. 현재 구현 범위는 주민 목록·등록·상세·연락처 공개·수정·삭제·엑셀 업로드·목록 엑셀 다운로드입니다. 업무 기준은 [도메인 규칙](domainRules.md#확정된-주민-목록-조회), 스키마는 [ERD](erd.md#54-residents), 화면은 [Client 주민 목록](../client/docs/residentList.md)을 따릅니다. 삭제·세대 이동 시 대표 승계를 지원하며 별도의 임의 대표 변경 API는 아직 제공하지 않으며 명부 재등록은 기존 등록 API에서 처리합니다.

## 목록 조회

`GET /api/properties/{propertyId}/residents`

- `Authorization: Bearer <accessToken>`이 필요합니다.
- 정상 계정과 현재 활성 관리대상·참여를 확인한 뒤 해당 관리대상의 관리소장(`ADMIN`)에게만 허용합니다. 부담당자·주민·다른 관리대상 관리자·플랫폼 관리자라는 이유만으로는 접근할 수 없습니다.
- `propertyId`는 UUID입니다. 조회 조건과 서버 페이지네이션 파라미터는 없습니다. 삭제되지 않은 주민 전체를 이름·ID 순서로 반환하고 Client에서 필터와 페이지를 처리합니다.
- 주민의 저장 상태로 행을 제외하지 않습니다. 현재 세대 관계(`ACTIVE`, 미삭제)만 결합하고 과거 관계로 주민 행을 중복하지 않습니다.
- 성공과 Controller 오류 응답에 `Cache-Control: no-store`를 적용합니다.

### 응답

HTTP `200`. 명부가 비었으면 `residents: []`입니다.

```json
{
  "propertyId": "11111111-1111-4111-8111-111111111111",
  "hasBuildings": true,
  "buildings": [
    { "id": "22222222-2222-4222-8222-222222222222", "name": "103동" }
  ],
  "residents": [
    {
      "id": "33333333-3333-4333-8333-333333333333",
      "name": "김민수",
      "phoneLast4": "1234",
      "unitId": "44444444-4444-4444-8444-444444444444",
      "buildingId": "22222222-2222-4222-8222-222222222222",
      "unitNumber": "301",
      "relationType": "TENANT",
      "representative": true,
      "signupStatus": "NOT_JOINED"
    }
  ]
}
```

| 필드 | 의미 |
| --- | --- |
| `hasBuildings` | 관리대상의 동 구분 사용 여부 |
| `buildings` | 동 필터와 이름 표시용 동 목록: 미삭제·활성 동, 표시 순서·이름 순 |
| `residents[].id`, `name` | 주민 명부 ID와 이름 |
| `phoneLast4` | 숫자 4자리 또는 `null`. 전체 번호·암호문·HMAC은 조회하거나 반환하지 않음 |
| `unitId`, `buildingId`, `unitNumber` | 현재 미삭제 세대. 동 없음은 `buildingId: null` |
| `relationType` | `OWNER / TENANT / FAMILY / OTHER` 또는 현재 소속 없음의 `null`. `OWNER` 표시명은 소유주 |
| `representative` | 현재 세대 관계의 대표 여부 |
| `signupStatus` | `APPROVED`(가입 완료), `NOT_JOINED`(미가입), `PENDING`(승인 대기) |

현재 관계가 없거나 세대가 삭제되었으면 세대 ID·동 ID·호수·관계는 모두 `null`, 대표 여부는 `false`이며 주민 행은 반환합니다. 가입 상태는 계정 ID의 존재 여부와 구분해 다음 기준으로 계산합니다. 계정 ID와 신청 연락처는 반환하지 않습니다.

### 가입 상태 판정

사용자 요청에 따라 승인 대기는 **명부의 누구인지 확인된 주민만** 표시·집계합니다. 명부에 없거나 확인되지 않은 신청을 주민 행으로 추가하거나 같은 세대의 주민에게 임의로 연결하지 않습니다.

아래는 조회 구현의 판정 기준입니다. 신청·승인·자동 매칭 절차를 구현했다는 뜻은 아닙니다.

1. `APPROVED`: 주민에 연결된 계정의 현재 세대 `APPROVED` 요청이 미삭제로 존재하고, 같은 관리대상의 참여가 `ACTIVE`이며 종료·삭제되지 않았을 때입니다.
2. `PENDING`: 위 가입 완료에 해당하지 않고, 주민 ID가 확인 연결된(`MATCHED` / `MANUAL`) 현재 세대의 미삭제 `PENDING` 요청이 존재할 때입니다. `POSSIBLE` 후보·미확인 신청·다른 세대 요청은 제외합니다.
3. `NOT_JOINED`: 위 두 조건에 해당하지 않는 주민입니다. 계정만 연결된 기록, 거절·취소·삭제된 신청과 과거 세대 승인만으로 가입 완료·승인 대기를 표시하지 않습니다.

주민당 한 상태를 반환하고 여러 신청은 `EXISTS`로 확인하므로 주민 행과 카드 집계가 중복되지 않습니다. 전체 주민 수는 가입 완료·미가입·승인 대기 주민 수의 합입니다. 전체 가입 요청 건수와는 구분합니다.

### 오류

기존 공통 오류 형태 `{ "code": "...", "message": "..." }`를 사용하고 전화번호·SQL·명부 원문을 오류에 넣지 않습니다.

| HTTP | 코드 | 조건 |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | 잘못된 관리대상 UUID |
| 401 | 공통 인증 오류 코드 | 인증정보 없음·만료·무효 |
| 403 | `ACCESS_DENIED` | 현재 관리소장 권한 없음, 대상 접근 불가 |
| 403 | `ACCOUNT_UNAVAILABLE` | 정상 사용 가능한 계정 아님 |
| 503 | `RESIDENT_SERVICE_UNAVAILABLE` | 저장소 조회 실패 |
| 500 | `INTERNAL_SERVER_ERROR` | 그 외 예상하지 못한 오류 |

인증 필터의 오류는 [관리 영역 접근 API](managementAccessApi.md)의 공통 인증 처리를 따릅니다.

## 주민 등록

`POST /api/properties/{propertyId}/residents`

현재 관리소장(`ADMIN`)만 허용하며 Bearer 인증과 현재 계정·관리대상·참여 검증은 목록과 같습니다. 동·세대는 기존 `GET /api/properties/{propertyId}/units`로 조회하고 선택합니다. 새로운 동이나 세대를 자동 생성하지 않습니다.

```json
{
  "requestId": "66666666-6666-4666-8666-666666666666",
  "name": "김민수",
  "phone": "010-1234-5678",
  "unitId": "44444444-4444-4444-8444-444444444444",
  "relationType": "TENANT"
}
```

| 필드 | 입력 계약 |
| --- | --- |
| `requestId` | 필수 UUID. 한 등록 폼에서 생성하고 같은 등록의 재시도에 같은 값·내용을 사용합니다. 생성된 주민 ID로 사용합니다. |
| `name` | 필수. 앞뒤 공백 제거 후 Unicode 코드 포인트 기준 1~50자 |
| `phone` | 선택. 생략·`null`·공백은 연락처 없음. 입력 시 최대 64자, 숫자·공백·괄호·하이픈과 선행 `+`만 허용 |
| `unitId` | 필수 UUID. 같은 관리대상의 미삭제·비활성 아님 세대. 동 있음이면 같은 대상의 활성 동에 속해야 합니다. |
| `relationType` | 선택. `OWNER / TENANT / FAMILY / OTHER`. 생략·`null`·공백은 `OTHER`로 정규화 |

국내 번호는 구분 기호를 제거한 `0[1-9]`로 시작하는 9~11자리를 `+82` 형식으로 변환합니다. 국제번호는 `+`와 국가번호를 포함한 4~15자리 숫자 형식으로 정규화합니다. 이는 입력 형식 검증이며 번호 소유나 실제 수신 가능 여부를 인증하지 않습니다. 공통 `PhoneSecurity`로 AES-GCM 암호문·HMAC·끝 네 자리를 함께 저장하며 키 준비는 [개발 환경 가이드](developmentGuide.md#server-환경변수)를 따릅니다.

이름과 정규화된 연락처가 모두 같은 미삭제 명부가 있으면 `409`이며 연락처가 없는 주민은 이름만으로 중복 처리하지 않습니다. 정확히 일치하는 삭제 명부가 하나이면 기존 주민 ID를 유지하고 삭제 표시를 해제해 재등록합니다. 과거 관계는 유지하고 새 현재 관계를 저장하며 종료된 로그인 권한·가입 승인은 복구하지 않습니다. 같은 세대의 삭제 전 대표는 현재 대표가 없을 때만 복원합니다. 일치하는 삭제 명부가 여러 개이면 임의 병합하지 않고 `409 RESIDENT_RESTORE_REQUIRED`로 안내합니다.

주민과 현재 세대 관계를 같은 트랜잭션으로 저장합니다. 최초 등록 여부는 해당 세대의 전체 관계 이력 기준이며 첫 저장이 성공한 주민을 대표로 지정합니다. 이후 추가는 대표를 변경하지 않습니다. 빈 대표의 자동 승계·공실 상태 변경·계정 연결·신청 승인·권한 부여는 수행하지 않습니다. 응답 유실 후 같은 요청 ID·내용을 재시도하면 새 주민 없이 기존 결과를 반환하며 다른 내용으로 재사용하면 충돌입니다.

HTTP `201`, `Cache-Control: no-store`:

```json
{
  "id": "66666666-6666-4666-8666-666666666666",
  "propertyId": "11111111-1111-4111-8111-111111111111",
  "unitId": "44444444-4444-4444-8444-444444444444",
  "representative": true
}
```

신규 등록의 `id`는 요청 ID와 같고 재등록의 `id`는 기존 주민 ID이므로 요청 ID와 다를 수 있습니다. 전체 전화번호·암호문·HMAC·계정 ID는 반환하지 않습니다. 성공 후 Client는 주민 목록을 재조회해 카드와 표를 갱신합니다.

| HTTP | 코드 | 조건 |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | UUID·필수 입력·이름·연락처·관계 형식 오류 |
| 400 | `INVALID_UNIT` | 다른 대상·삭제·비활성 세대 또는 사용할 수 없는 동 |
| 409 | `DUPLICATE_RESIDENT` | 이름·연락처가 모두 같은 미삭제 명부 존재 |
| 409 | `RESIDENT_RESTORE_REQUIRED` | 등록 시 같은 이름·연락처의 삭제 명부가 여러 개여서 수동 확인 필요. 수정에서 다른 삭제 명부와 충돌 |
| 409 | `REGISTRATION_CONFLICT` | 기존 요청 ID를 다른 정보로 사용하거나 기존 관계 변경·삭제 |
| 503 | `PHONE_SECURITY_UNAVAILABLE` | 연락처 저장용 외부 키 미설정·사용 불가. 평문 저장 없이 전체 실패 |

인증·권한·저장소·예상하지 못한 오류는 목록의 공통 오류 계약과 같습니다. 오류 메시지에 입력 원문·SQL을 포함하지 않습니다.

## 주민 상세·연락처 공개·수정·삭제

모두 목록과 동일한 Bearer 인증·현재 관리소장 권한을 확인하며 관리대상·주민 ID는 UUID입니다. 다른 관리대상의 주민과 삭제된 명부는 `404 RESIDENT_NOT_FOUND`입니다. 성공·Controller 오류·삭제의 빈 응답에도 `Cache-Control: no-store`를 적용합니다.

### 기본 상세

`GET /api/properties/{propertyId}/residents/{residentId}` → HTTP `200`.

목록 행의 필드에 `propertyId`, `buildingName`, `createdAt`, `updatedAt`, `hasLinkedRequests`, `representativeCandidates`를 추가합니다. 후보는 저장된 현재 관계가 대표인 주민의 같은 세대 미삭제 구성원 중 본인을 제외한 `{ id, name }` 배열입니다. 세대가 삭제되어 표시 동·호수가 `null`이어도 현재 관계가 남아 있으면 승계 후보를 반환해 직접 선택할 수 있게 합니다. 세대가 없으면 해당 필드는 목록처럼 `null`입니다. 기본 응답은 `phoneLast4`만 포함하며 전체 번호·암호문·HMAC·계정 ID를 포함하지 않습니다.

### 전체 번호 공개

`POST /api/properties/{propertyId}/residents/{residentId}/phone-reveal` → HTTP `200`, `{ "phone": "+821012345678" }` 또는 연락처 없음의 `{ "phone": null }`.

상세의 공개 버튼에서만 호출합니다. 원문은 브라우저 컴포넌트의 일시 상태로 표시하며 기본 상세 캐시·저장소·URL에 보관하지 않습니다. 복호화 실패나 키 사용 불가에는 원문 없는 `503 PHONE_SECURITY_UNAVAILABLE`을 반환합니다.

### 수정

`PUT /api/properties/{propertyId}/residents/{residentId}` → HTTP `200`, 갱신된 기본 상세 응답.

```json
{
  "name": "예시 주민",
  "unitId": "44444444-4444-4444-8444-444444444444",
  "relationType": "TENANT",
  "phoneAction": "KEEP",
  "phone": null,
  "replacementResidentId": null,
  "expectedUpdatedAt": "2026-10-10T06:00:00Z"
}
```

이름·세대·주민 구분의 검증과 중복 기준은 개별 등록과 같으며 본인은 중복 검사에서 제외합니다. `expectedUpdatedAt`은 직전 상세의 수정 시각이며 다른 수정이나 대표 승계로 바뀌면 `409 RESIDENT_CHANGED`로 거부합니다.

| `phoneAction` | 처리 |
| --- | --- |
| `KEEP` | 기존 보호 연락처 유지. `phone`은 `null` 또는 생략. 복호화 없이 수정 가능 |
| `REPLACE` | 유효한 새 `phone` 필수. 명부와 같은 주민으로 확인 연결된 미삭제 가입 신청의 암호문·HMAC·끝 네 자리를 함께 변경 |
| `REMOVE` | 연락처 3개 컬럼을 함께 비움. 연결된 신청이 있으면 신청 연락처 필수 제약 때문에 `409 CONTACT_REQUIRED_FOR_REQUEST` |

연결된 신청은 같은 관리대상에서 `matched_resident_id`와 `MATCHED / MANUAL`로 확인된 요청, 또는 연결 계정의 `APPROVED` 요청입니다. `POSSIBLE`·미확인 신청을 연락처 일치만으로 수정하지 않습니다. 상태·신청 세대·계정 연결을 새로 변경하지 않습니다.

대표가 다른 동·호수로 이동할 때 남은 주민이 있으면 `replacementResidentId`로 같은 세대의 후보 한 명을 직접 선택해야 합니다. 비대표·남은 주민 없음은 `null`입니다. 이동은 과거 관계를 종료하고 새 현재 관계를 만들며 기존 이력을 덮어쓰지 않습니다. 도착 세대의 기존 대표는 유지하고 전체 관계 이력이 없는 최초 세대이면 이동한 주민이 대표가 됩니다.

### 삭제

`DELETE /api/properties/{propertyId}/residents/{residentId}`:

```json
{
  "expectedUpdatedAt": "2026-10-10T06:00:00Z",
  "replacementResidentId": "55555555-5555-4555-8555-555555555555"
}
```

대표 승계와 수정 시각 검증은 수정과 같습니다. HTTP `204`, 본문 없음. 명부와 현재 관계를 소프트 삭제하고 해당 관리대상의 연결된 `RESIDENT` 접근권한을 종료합니다. 명부 삭제로 실제 퇴거 상태·퇴거일을 생성하지 않습니다. 다른 관리대상과 `ADMIN / MANAGER` 참여는 유지합니다. 확인 연결된 대기 신청은 `CANCELED`로 처리하며 승인 이력은 보존합니다. 이미 삭제된 같은 대상의 명부에 대한 재시도는 `204`입니다. 삭제·승계·권한 종료·대기 취소는 하나의 트랜잭션입니다.

추가 오류는 아래와 같으며 등록의 중복·세대·입력·공통 권한 오류도 적용합니다.

| HTTP | 코드 | 조건 |
| --- | --- | --- |
| 404 | `RESIDENT_NOT_FOUND` | 대상 주민 없음·다른 관리대상·삭제됨 |
| 409 | `RESIDENT_CHANGED` | 조회 후 주민 정보나 대표 여부가 변경됨 |
| 409 | `REPRESENTATIVE_REQUIRED` | 남은 주민이 있는 대표의 이동·삭제에서 새 대표 미선택 |
| 400 | `INVALID_REPRESENTATIVE` | 본인·다른 세대·삭제 주민 또는 승계가 필요 없는 상황의 선택 |
| 409 | `CONTACT_REQUIRED_FOR_REQUEST` | 연결된 신청이 있는 주민의 연락처 삭제 |
| 503 | `PHONE_SECURITY_UNAVAILABLE` | 새 연락처 저장 또는 기존 번호 공개의 보안 설정·복호화 실패 |

동·세대 삭제에 따른 현재 주민 전체 삭제·권한 종료·대기 취소는 [세대 관리 API](unitManagementApi.md#세대동-삭제)를 따릅니다. 같은 세대의 주민 전체를 제거하므로 대표 승계는 하지 않으며 과거에만 소속되었던 주민과 다른 세대·관리대상의 명부는 유지합니다.

## 주민 목록 엑셀 다운로드

`POST /api/properties/{propertyId}/residents/export`

- Bearer 인증과 해당 관리대상의 현재 `ADMIN` 권한을 검증합니다. 일반 목록 조회는 전체 번호를 반환하지 않습니다.
- 요청은 `{ "residentIds": ["33333333-3333-4333-8333-333333333333"] }`입니다. Client가 현재 검색·필터 결과 전체의 ID를 동·호수 순서로 전달하며 현재 페이지로 제한하지 않습니다.
- `residentIds`는 비어 있지 않은 UUID 배열이며 중복·`null`을 허용하지 않습니다. 전체 ID가 해당 관리대상의 미삭제 주민인지 검증하며 다른 관리대상·삭제·누락 ID가 하나라도 있으면 부분 파일 대신 `404 RESIDENT_NOT_FOUND`를 반환합니다.
- 응답은 HTTP `200`, `{ "residents": [{ "name": "예시 주민", "phone": "+821012345678", "unitLabel": "102동 301호" }] }`입니다. 요청 ID 순서를 유지하고 주민명·전체 연락처·동호수만 반환합니다. 주민 구분·대표 여부·가입 상태·내부 ID·암호문·HMAC은 포함하지 않습니다. 연락처 없음은 `null`, 현재 세대 없음은 `unitLabel: "—"`입니다.
- 성공·Controller 오류에 `Cache-Control: no-store`를 적용합니다. 권한은 `401 / 403`, 잘못된 요청은 `400 INVALID_REQUEST`, 복호화·키 오류는 원문 없는 `503 PHONE_SECURITY_UNAVAILABLE`입니다.
- Client는 응답의 일부 행에서 주민명·연락처·동호수를 미리보기로 표시하며 연락처는 `**** 5678`처럼 끝 네 자리만 표시합니다. 동일한 전체 응답으로 주민명·전체 연락처·동호수 세 열의 XLSX를 생성합니다. 국내 휴대폰은 파일에 하이픈을 넣어 저장하며 번호 없는 셀은 비웁니다. 원문 응답은 현재 화면의 일시 상태에서만 사용하고 조회 캐시·URL·브라우저 저장소에 보관하지 않습니다.

## 엑셀 검증과 일괄 등록

두 API 모두 목록과 같은 Bearer 인증·현재 관리소장 권한을 검증하고 응답에 `Cache-Control: no-store`를 적용합니다. 업로드 양식은 Client 정적 파일이며 업로드 결과는 브라우저에서 마스킹한 CSV로 생성합니다. 전체 번호를 담는 주민 목록 다운로드는 [별도 내보내기 API](#주민-목록-엑셀-다운로드)를 사용합니다.

### 파일 검증

`POST /api/properties/{propertyId}/resident-imports`

`multipart/form-data`의 `file` 필드로 `.xlsx` 하나를 보냅니다. 파일은 최대 5MB이며 첫 시트의 첫 행은 정확히 `동 / 호수 / 이름 / 주민 구분 / 연락처`입니다. 기존 파일 호환을 위해 네 번째 헤더 `관계`도 허용합니다. 2~1,001행에 최대 1,000명의 데이터를 입력합니다. 빈 행은 집계하지 않으며 수식·오류·논리값 셀은 해당 행의 오류로 표시하고 실행하지 않습니다. 압축 해제 총량·항목 수도 제한합니다.

- 이름·기존 세대는 필수, 연락처·주민 구분은 선택이며 빈 주민 구분은 `OTHER`로 저장합니다. 정규화는 개별 등록과 같습니다. 호수와 연락처는 텍스트 셀로 입력해 앞자리 0을 유지합니다.
- 동 이름은 기존 동 정규화 기준으로 연결하며 `102`와 `102동`을 같은 동으로 찾습니다. 호수 끝의 `호`는 제거합니다. 동 없는 관리대상은 동 칸을 비워야 합니다. 활성 동·미삭제·비활성 아님 세대만 연결하며 자동 생성하지 않습니다.
- 관계는 `소유주 / 임차인 / 가족 / 기타`를 권장합니다. 기존 자료의 `소유자 / 주인 / 세입자` 및 `OWNER / TENANT / FAMILY / OTHER`도 변환합니다.
- 동일 관리대상의 미삭제 명부와 이름·정규화 연락처가 모두 같으면 중복입니다. 파일 안에서도 같은 두 값의 앞선 정상 행이 있으면 뒤 행을 중복으로 표시합니다. 연락처가 없으면 이름만으로 중복 판정하지 않습니다. 삭제 명부 하나와 정확히 일치하면 `READY`와 `재등록 가능 · 기존 주민 기록 재사용` 안내를 반환하며 선택 후 저장할 때 재사용합니다. 여러 삭제 명부와 일치하면 오류로 안내합니다.
- 검증만으로 주민·세대 관계를 저장하지 않습니다. 검증 결과는 작성자·관리대상에 묶여 24시간 유효합니다. 원본 파일은 보관하지 않고 임시 데이터의 연락처는 암호화합니다.

HTTP `200`:

```json
{
  "importId": "77777777-7777-4777-8777-777777777777",
  "expiresAt": "2026-10-11T06:00:00Z",
  "rows": [
    {
      "rowNumber": 2,
      "building": "102동",
      "unitNumber": "301",
      "name": "예시 주민",
      "relationType": "FAMILY",
      "phoneLast4": "1234",
      "status": "READY",
      "reason": "등록 가능",
      "representative": false
    }
  ]
}
```

`rowNumber`는 헤더를 포함한 원본 엑셀 행 번호이며 선택·저장 순서에 사용합니다. 화면과 다운로드의 표시 열에서는 제외합니다. `relationType`은 등록 API와 같으며 잘못된 관계는 `null`입니다. 연락처는 유효한 입력의 끝 네 자리 또는 `null`만 반환하며 원문·암호문·HMAC·내부 재시도 ID는 반환하지 않습니다. 검증 단계의 `representative`는 `false`이며 실제 저장 결과에서 확정합니다.

### 선택한 행 등록

`POST /api/properties/{propertyId}/resident-imports/{importId}/commit`

```json
{ "rowNumbers": [2, 4, 5] }
```

중복 없는 1~1,000개의 행 번호가 필요하며 같은 작성자가 같은 관리대상에 업로드한 유효한 검증의 `READY` 행만 선택할 수 있습니다. 행 번호의 요청 배열 순서와 관계없이 엑셀의 원래 순서로 저장합니다. 각 행의 저장 직전에 권한·세대·중복을 다시 검증합니다. 주민과 세대 관계는 행마다 함께 저장하며 오류·중복은 제외하고 나머지를 계속 등록합니다. 최초 대표 지정은 [도메인 정책](domainRules.md#확정된-주민-엑셀-일괄-등록)을 따릅니다.

HTTP `200`의 구조는 검증 응답과 같으며 전체 행을 원본 순서로 반환합니다.

| `status` | 의미 | 단계 |
| --- | --- | --- |
| `READY` | 등록 가능한 정상 행 | 검증 |
| `DUPLICATE` | 기존 명부 또는 파일 내 중복으로 제외 | 검증·완료 |
| `ERROR` | 입력·세대·명부 복구 필요 등의 오류로 제외 | 검증·완료 |
| `SUCCESS` | 주민과 현재 세대 관계 저장 성공 | 완료 |
| `NOT_SELECTED` | 정상 행이지만 선택하지 않아 저장하지 않음 | 완료 |

저장소 장애·통신 실패에는 이미 성공한 행이 있을 수 있습니다. 같은 `importId`·선택을 그대로 재시도하면 행별 고정 주민 ID로 이전 결과를 복구하고 나머지를 처리합니다. 연락처 없는 주민도 같은 검증의 재시도에서 새로 생성하지 않습니다. 브라우저 이탈·새로고침 후 결과 복원 API는 제공하지 않으므로 저장 결과가 불확실하면 주민 목록을 먼저 확인합니다.

| HTTP | 코드 | 조건 |
| --- | --- | --- |
| 400 | `INVALID_EXCEL_FILE` | 형식·확장자·크기·압축 구조 오류 |
| 400 | `INVALID_EXCEL_HEADER` | 첫 시트 헤더가 양식과 다름 |
| 400 | `EMPTY_EXCEL_FILE` | 입력된 주민 행 없음 |
| 400 | `EXCEL_ROW_LIMIT` | 1,001행보다 아래에 데이터/행이 있음 |
| 400 | `INVALID_REQUEST` | 잘못된 UUID·빈 선택·중복 번호·정상 행 외 선택 |
| 404 | `IMPORT_EXPIRED` | 검증 없음·만료·다른 작성자/관리대상 |
| 503 | `PHONE_SECURITY_UNAVAILABLE` | 연락처 보안 설정 사용 불가. 평문 저장 없이 재시도 안내 |

인증·권한·저장소·예상하지 못한 오류는 목록의 공통 오류를 따릅니다. 행 오류의 `reason`은 고정 안내이며 입력 원문·예외 메시지·SQL을 넣지 않습니다.

## 저장 구조와 검증 범위

`V20261010041826__create_resident_directory.sql`로 `residents`와 `unit_residents`를 생성합니다. 같은 관리대상의 주민·세대만 관계를 맺도록 복합 FK를 두고, 미삭제 현재 관계를 주민당 하나로 제한하는 부분 UNIQUE 인덱스를 적용합니다. 같은 세대에 여러 주민은 허용합니다.

`V20261010043914__create_membership_request_read_model.sql`로 가입 상태 조회에 필요한 `membership_requests` 저장 구조를 추가합니다. 신청의 세대·확인 주민이 같은 관리대상인지 복합 FK로 보장하고 같은 계정·세대의 중복 대기를 제한합니다. 초대 연결 컬럼과 FK는 초대 기능 구현 시 추가합니다.

`V20261010055020__create_resident_import_batches.sql`로 작성자·관리대상·암호화된 검증 행과 만료시각을 저장하는 임시 테이블을 추가했습니다. 만료한 배치는 매시간 삭제합니다.

개별·엑셀 등록과 최초 대표 자동 지정, 상세·번호 공개·수정·삭제와 삭제/이동 시 명시적 대표 승계를 구현했습니다. 주민 재등록은 기존 등록·엑셀 저장 API에서 지원하며 별도 대표 변경·계정 연결·가입 요청 생성·가입 승인 API는 아직 제공하지 않습니다. 조회는 저장된 신청·승인 기록을 읽습니다. PostgreSQL 통합 테스트에서 빈 DB 전체 Migration과 이전 스키마의 후속 Migration, 실제 조회·등록·무결성 제약과 동시 대표 지정·중복·롤백·동일 요청 재시도를 검증합니다.
