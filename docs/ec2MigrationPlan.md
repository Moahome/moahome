# Lightsail에서 EC2로 이관하는 계획

기준일: 2026-10-30. 초기 서버를 구축할 때 준비해 둘 항목과 향후 애플리케이션 서버 교체 절차를 정리합니다.

상태: 사전 계획. 사용자는 나중에 EC2로 이관할 때 참고할 별도 문서를 요청했습니다. 아래 단일 EC2 전환 방식은 기존의 짧은 점검 허용 방향을 구체화한 설계안이며, EC2 생성·이관 자동화·운영 전환을 구현하거나 검증한 상태는 아닙니다. 대상 사양·점검 시간·Redis 이전 방식은 이관 시점에 정합니다.

초기 구성은 [운영 배포 계획](deploymentPlan.md), 호스트 준비·인증서·배포 명령은 [Server 배포 가이드](../server/docs/deploymentGuide.md)를 따릅니다. 인증·키 정책은 [보안 설계](securityDesign.md), 저장 구조는 [도메인 규칙](domainRules.md)·[ERD](erd.md)를 기준으로 하며 이 문서에서 변경하지 않습니다.

## 1. 이관을 검토할 시점과 범위

사용자 수만으로 EC2 전환 시점을 정하지 않습니다. CPU 사용률·버스트 잔량, 메모리·디스크, DB 연결, 응답시간·오류율을 관측해 앱 서버와 DB 중 실제 병목을 구분합니다. 메모리 부족이면 Lightsail 8GB 확장도 비교하고, 지속 CPU 성능이나 네트워크 구성·여러 서버 운영이 필요하면 EC2를 검토합니다.

첫 이관안은 같은 서울 리전에서 애플리케이션 서버 한 대를 교체하는 방식입니다. 앱 버전·DB 스키마·암호화 키 교체를 함께 진행하지 않고 검증된 버전을 유지합니다. EC2 4GB로 옮기는 것만으로 성능 개선을 보장하지 않습니다.

| 대상 | 이관 방향 |
| --- | --- |
| Spring Boot·Nginx | 검증한 이미지와 Compose 설정으로 EC2에서 재배포 |
| RDS PostgreSQL | 기존 인스턴스·데이터 유지, 새 EC2의 사설 접근 설정 추가 |
| Redis | 새 호스트의 별도 볼륨으로 상태 이전하거나, 사전에 정한 초기화·복구 절차 적용 |
| API 도메인 | `api.villamoa.kr`을 유지하고 DNS의 대상 IP 변경 |
| 프론트 Vercel | 기존 프론트 유지. API URL·인증 계약이 같으면 서버 IP 변경만으로 재빌드하지 않음 |
| 파일·비밀값·인증서 | 저장 위치별로 별도 이전·복구 확인 |
| GitHub Actions·GHCR | 기존 검증·이미지 게시 흐름 재사용, 새 서버의 이미지 읽기 권한 확인 |

여러 앱 서버·ALB·자동 확장·관리형 Redis 전환은 후속 설계입니다. 여러 앱 서버가 각자 로컬 Redis를 사용하면 인증·초대 상태가 공유되지 않으므로 단일 서버 교체 절차를 그대로 확장하지 않습니다. 분산 작업·동시성 검증도 별도로 필요합니다.

## 2. 처음 구축할 때 준비할 항목

| 항목 | 지금 준비할 내용 | 현재 상태와 확인할 한계 |
| --- | --- | --- |
| DB 분리 | 업무 DB는 비공개 RDS에 두고 앱 서버와 분리 | 초기 구축안에 포함. 실제 AWS 연결은 별도 검증 |
| 배포 재현 | 커밋 SHA·이미지 digest, Compose·설정 템플릿과 복구할 버전 기록 | Dockerfile·운영 Compose·배포 스크립트 작성됨. 원격 CI·GHCR 게시 확인 필요 |
| 서버 주소 | 앱에서 서버 IP 대신 API 도메인 사용 | 공개 URL 환경변수와 카카오 콜백 설정을 실제 도메인으로 연결해야 함 |
| 암호화·검색 키 | 서버 밖 보호된 위치에 복구 가능한 사본, 키 ID·버전과 접근 권한 관리 | 환경변수 연결·키링 규칙이 있음. 운영 보관처·복구 시험은 구축 때 준비 |
| Redis 데이터 | 영속화·백업 위치, 복원 검증과 유실 시 복구 절차 기록 | Compose의 `redis_data`는 호스트 로컬 볼륨. 서버 밖 백업이나 자동 이전이 구현된 것은 아님 |
| 영구 파일 | 영구 보관할 파일이 생기면 비공개 S3 등 서버 수명과 독립된 저장소 검토 | 현재 업로드 원본·보고서를 영구 보관하는 정책을 추가하지 않음 |
| 인증서·호스트 설정 | Certbot 상태·갱신 설정·Nginx 설정과 복구 경로 기록 | 인증서 발급·갱신 스크립트와 타이머가 있음. 실제 공인 인증서 검증은 별도 |
| 운영 기록 | 환경별 이미지·네트워크·백업·전환 시각·검증 결과를 보호된 위치에 기록 | 비밀값·개인정보 원문을 Git이나 일반 실행 로그에 남기지 않음 |

서버 안의 Docker 볼륨과 `.env.prod`만 남겨 두는 방식은 서버 외부 백업이 아닙니다. 운영 키 보관처는 접근 통제된 암호화 보관소나 Secrets Manager·Parameter Store 등의 후보에서 정하되, 선택한 저장소에서 현재 앱의 환경변수·파일 설정으로 안전하게 주입하는 절차도 준비합니다. 해당 서비스와 앱이 이미 연동됐다고 가정하지 않습니다.

키 목록·길이·키링 연결은 [개발 가이드의 Server 환경변수](developmentGuide.md#server-환경변수)를 따릅니다. 복호화 키뿐 아니라 계좌·연락처 검색용 HMAC 키와 등록 요청 지문 키도 유지해야 검색·중복 검사·기존 요청 비교를 이어갈 수 있습니다. 서버 교체를 이유로 키를 새로 생성하지 않으며, 기존 데이터에 필요한 이전 키 ID·버전도 보존합니다.

## 3. EC2 대상과 네트워크 준비

처음에는 기존 RDS와 같은 리전·VPC에 EC2 한 대를 두는 구성을 우선 검토합니다. 기본 후보는 공인 IP를 가진 EC2와 Nginx이며, ALB·NAT Gateway가 반드시 필요한 구성으로 정하지 않습니다. 사설 서브넷이나 ALB를 선택하면 이미지 다운로드·업데이트 경로와 추가 비용을 함께 설계합니다.

- 인스턴스 유형은 메모리 외에 CPU의 지속 성능·버스트 방식·아키텍처로 비교합니다. 기존 x86 이미지에는 `t3`·`t3a` 같은 x86 대상이 단순하며, `t4g` 같은 ARM 대상으로 바꾸면 API와 Redis·Nginx를 포함한 모든 이미지의 해당 아키텍처 지원·빌드·검증이 필요합니다. 같은 태그가 다른 아키텍처에서도 실행된다고 가정하지 않습니다. [Docker 다중 플랫폼 안내](https://docs.docker.com/build/building/multi-platform/)
- 메모리를 늘릴 때는 기존 Compose의 `mem_limit`, JVM 힙과 Redis `maxmemory`도 검토합니다. 현재 4GB용 제한값이 새 서버의 메모리를 자동으로 활용하는 것은 아니며, OS·Nginx·Redis 영속화 작업의 여유를 포함해 조정·검증합니다.
- 초기 Lightsail과 RDS의 연결은 해당 리전 기본 VPC 피어링을 사용합니다. EC2 전환에서는 RDS가 있는 VPC·서브넷·라우팅을 다시 확인하고 RDS 보안 그룹에 새 EC2 보안 그룹의 PostgreSQL 5432 접근을 추가합니다. 기존 Lightsail 허용 규칙은 복구 기간 종료 후 제거합니다. [Lightsail 피어링](https://docs.aws.amazon.com/lightsail/latest/userguide/lightsail-how-to-set-up-vpc-peering-with-aws-resources.html), [RDS 보안 그룹](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Overview.RDSSecurityGroups.html)
- RDS의 Public access를 켜서 연결 문제를 우회하지 않습니다. 기존 RDS 엔드포인트·앱 계정·CA 검증을 유지하고 새 호스트에서 `sslmode=verify-full` 연결을 확인합니다.
- 웹 공개 포트는 80·443, SSH는 운영자 접근 경로로 제한합니다. Spring Boot 8080·Redis 6379를 인터넷에 공개하지 않습니다.
- EC2용 고정 공인 IPv4와 DNS 전환을 준비합니다. Lightsail의 고정 IP·DNS 설정이 EC2로 자동 이전된다고 가정하지 않습니다. A·AAAA 레코드와 실제 TTL을 함께 기록합니다. [Lightsail 내보내기 범위](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-faq-export-to-ec2.html)

기존 서버 스냅샷을 EC2로 내보내는 방법도 있지만, 이 계획의 기본안은 새 호스트에 같은 Docker 배포를 재현하는 것입니다. 스냅샷 내보내기만으로 RDS·Redis 최신 상태·운영 키·DNS 전환까지 완료되는 것은 아닙니다.

## 4. Redis·파일·키의 이전 방식 결정

### Redis

현재 Redis의 역할과 유실 처리는 [기존 운영안](deploymentPlan.md#5-redis-운영안)과 [Server 초대 설계](../server/docs/memberManagement.md#redis-이전-상세-설계와-진행-상태-2026-10-25)를 따릅니다. 이관 전에 다음 두 방식 중 적용할 방식을 정하고 시험합니다.

| 방식 | 전제와 확인할 내용 |
| --- | --- |
| 최신 상태를 보존해 이전 | 기존 앱과 모든 쓰기 주체를 멈춘 뒤 Redis를 정상 종료하고, 버전·설정에 맞는 전체 영속화 자료를 새 볼륨으로 옮겨 복원 시험. TTL·세션 교체·로그아웃·초대 소비 상태와 DB의 대응 관계 확인 |
| 새 Redis로 시작 | 기존 세션 재로그인·미사용 초대코드 명시적 재발급·진행 중 OAuth 재시작이 필요함을 운영 절차에 반영. 접수·완료된 요청 등 DB의 기존 결과는 유지하며 Redis 소실을 이유로 새 요청을 중복 제출하지 않음 |

Redis 8의 AOF는 단일 파일이라고 가정하지 않습니다. manifest·base·incremental 파일 등 버전에 맞는 영속화 자료를 일관되게 확보하며, 쓰기나 rewrite 중인 볼륨을 단순 복사하지 않습니다. 만료시각을 처음부터 다시 부여하거나 오래된 백업으로 소비·철회된 인증값을 되살리지 않습니다. 실제 백업·복원 명령은 격리 시험에서 확인한 뒤 실행 기록에 남깁니다. [Redis 영속화 안내](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

같은 RDS를 바라보는 구·신 앱에 서로 다른 Redis 상태를 붙여 동시에 운영하지 않습니다. DNS 변경만으로 기존 앱의 API 요청·세션 갱신·백그라운드 쓰기가 모두 멈추지는 않습니다.

### 파일·키·인증서

- 영구 파일이 있다면 실제 목록·저장 위치·크기·무결성을 확인합니다. 서버 로컬에 있는 파일은 최종 쓰기를 멈춘 뒤 이전하고 새 경로·권한을 검증합니다. S3를 사용 중이면 객체를 다시 복사하기보다 새 서버의 접근 권한과 앱 연결을 확인합니다.
- `.env.prod`·외부 키링·GHCR 읽기 자격 증명은 보호된 경로로 주입합니다. 원문을 이 문서나 전환 기록에 복사하지 않으며, 실제 배포에 쓰는 키 ID·버전을 확인합니다. 키 유실은 RDS 백업만으로 복구할 수 없습니다.
- 같은 API 도메인을 유지하는 기본안에서는 기존 인증서와 Certbot 상태를 안전하게 이전하고 갱신 경로·소유권을 확인합니다. `live`의 링크만 복사하지 않고 `/etc/letsencrypt`의 관련 상태 전체를 보호해 다룹니다. DNS 전환 전 HTTP 인증 요청은 기존 서버로 갈 수 있으므로 새 서버에서 재발급만 실행하면 된다고 가정하지 않습니다.
- 기존·신규 호스트의 인증서 갱신 작업이 겹치지 않게 전환 시점을 정하고, 새 호스트의 webroot·hook·타이머는 [Server 인증서 가이드](../server/docs/deploymentGuide.md#5-nginx-최초-인증서와-자동-갱신)에 따라 확인합니다.

## 5. 전환 전 검증

운영 RDS·Redis를 수정하지 않는 격리 환경에서 새 호스트의 배포 재현·복원·실패 복구를 먼저 시험합니다. 기존 버전 이미지, 키링 주입, Redis TTL, 업로드·출력과 기존 연락처·계좌의 복호화·검색을 확인합니다. 검증 로그에는 개인정보 원문을 남기지 않습니다.

신규 EC2에 운영 API를 미리 실행해 준비 상태만 확인하는 방식은 사용하지 않습니다. 현재 앱은 서버 시작과 매시간 자동 부과 누락분을 확인하며, 시작 시 Flyway도 실행할 수 있습니다. 실제 운영 RDS에 연결하는 API 시작은 아래 절차에서 기존 API와 백그라운드 작업을 정지한 뒤 수행합니다. 별도 무쓰기 검증 모드가 구현됐다고 가정하지 않습니다.

전환 전에 다음 항목을 운영 기록에 채웁니다.

- 대상 EC2·디스크·IP·보안 그룹, RDS 연결과 DNS의 현재 값·TTL
- 동일하게 유지할 API 이미지 SHA·digest·플랫폼과 Redis·Nginx 이미지 버전
- 이전할 볼륨·파일·키 ID·인증서와 검증한 복원 방법
- 선택한 Redis 처리 방식, 사용자 안내, 허용 점검 시간과 복구 판단 기준
- 점검 응답 적용·해제 방법과 구·신 서버를 각각 정지·재기동하는 방법
- 백업 위치·복원 확인 시각, 전환·복구 담당자와 보호된 실행 기록 위치

현재 저장소에는 DNS 전환·점검 모드·Redis 서버 간 이전을 자동 처리하는 스크립트가 없습니다. 실제 전환 전 점검용 503 응답과 해제 절차를 준비·시험합니다. 기존 배포 스크립트가 서버 간 이관까지 수행한다고 판단하지 않습니다.

## 6. 운영 전환 순서

1. 점검 시간을 안내하고 DNS TTL을 사전에 조정합니다. 기존 TTL의 캐시가 줄어들 시간을 확보하며, 낮은 TTL이 모든 클라이언트의 즉시 전환을 보장한다고 가정하지 않습니다.
2. 기존 호스트의 공개 업무 경로는 점검 응답으로 전환하고, 신규 호스트는 운영자 전용 접근으로 제한합니다. 기존 진행 요청의 종료를 확인한 뒤 Lightsail API와 모든 백그라운드 쓰기 주체를 정지합니다. 재기동되지 않도록 확인하고 인증서 갱신 작업의 실행 주체도 정리합니다.
3. 쓰기가 멈춘 시점의 RDS 복구 지점과 Redis·필요 파일·설정 사본을 확보합니다. Redis를 선택한 방식대로 준비하고, 새 호스트의 키·인증서·파일 권한을 확인합니다. RDS 자체는 교체하지 않습니다.
4. EC2에 기존과 같은 API 이미지를 배포합니다. 기존 API가 멈춘 상태에서만 운영 RDS에 연결하고, 실제 적용 이미지·DB 스키마·Redis 연결과 내부 readiness를 확인합니다. 이미지 배포 명령은 [기존 배포 가이드](../server/docs/deploymentGuide.md#6-api-배포와-복구)를 따릅니다. 배포 스크립트는 Nginx도 시작·reload하므로, 실행 후에도 새 호스트의 보안 그룹 등 운영자 전용 접근 제한이 유지되는지 확인합니다.
5. API 도메인을 새 EC2 IP로 직접 해석하도록 제한된 검증 경로를 사용해 HTTPS·인증서·로그인·재발급·권한·복호화·주요 업무를 확인합니다. readiness의 `200 {"status":"UP"}`만으로 업무 검증을 대체하지 않습니다. 검증 과정에서 생기는 DB·Redis 쓰기도 기록합니다.
6. DNS의 A·필요한 AAAA 레코드를 새 대상에 맞추고 외부 검증을 통과한 EC2의 웹 공개 접근을 열고 점검 상태를 해제합니다. 구 서버는 점검 응답과 API 정지를 유지해 이전 IP를 사용하는 클라이언트의 쓰기를 막습니다.
7. 오류율·응답시간·인증 실패·DB 연결·Redis 메모리와 주요 합계를 관측합니다. 구·신 서버에 쓰기가 분산되지 않았는지 확인합니다.
8. 실제 전파·업무 검증과 복구 기간이 끝나면 새 호스트의 인증서 갱신·백업·배포 경로를 확인하고 기존 Lightsail 접근 규칙·자격 증명·리소스를 정리합니다. 기존 서버의 재기동 방지와 보호 자료 보관·폐기를 확인한 뒤 종료합니다.

새 IP의 HTTPS 직접 검증에는 예를 들어 다음 방식을 사용할 수 있습니다. API 도메인은 구매한 도메인을 사용하는 [접속 구성](deploymentPlan.md#2-접속-구조와-네트워크)을 따르며, `203.0.113.10`은 설명용이므로 실제 EC2 공인 IP로 교체합니다. 점검 중에는 운영자에게 허용한 검증 경로에서만 확인합니다.

```bash
curl --fail --silent --show-error \
  --resolve api.villamoa.kr:443:203.0.113.10 \
  https://api.villamoa.kr/actuator/health/readiness
```

API 도메인이 같으면 기존 Client API URL·쿠키·CORS·카카오 콜백을 유지하는 것이 기본안입니다. 도메인 자체를 바꾸는 경우는 프론트 재빌드·허용 Origin·쿠키·OAuth 등록까지 영향을 확인하는 별도 변경으로 다룹니다.

## 7. 실패 시 복구

기존 서버와 복구 자료는 전환 완료 판단 전까지 보관하되, 기존 API는 정지 상태로 유지합니다. DNS만 되돌리는 것을 복구 완료로 보지 않습니다.

| 실패 시점 | 복구할 때 확인할 내용 |
| --- | --- |
| 신규 운영 API 시작 전 | 기존 RDS와 기존 Redis가 최종 정지 시점의 상태인지 확인한 뒤 신규 쪽 실행을 막고 기존 API·업무 경로 복구 |
| 신규 API 시작 후 | 공개 점검 상태를 유지하고 신규 API·백그라운드 쓰기를 정지. 시작 작업·검증·사용자 요청이 이미 RDS·Redis를 변경했을 수 있으므로 최신 상태 확인 |
| 신규 서버에서 쓰기가 발생한 뒤 구 서버로 복귀 | 동일 RDS 유지·구 이미지 호환성을 확인하고 최신 Redis 상태의 역이전 또는 사전에 정한 초기화·재로그인·초대 재발급 절차 적용. 구 Redis의 과거 세션·초대 상태를 그대로 재사용하지 않음 |
| 키·영구 파일·Redis 상태의 정합성을 확인할 수 없음 | 점검 상태에서 복구 자료와 현 상태를 대조. 확인되지 않은 상태로 업무를 재개하지 않음 |

복귀 대상 한 곳에서만 쓰기가 가능한 것을 확인한 뒤 DNS·점검 응답을 전환합니다. 전파 중 다른 IP를 사용하는 클라이언트에는 점검 응답을 유지합니다. 앱 서버 교체 실패를 이유로 RDS를 과거 시점으로 즉시 복원하지 않으며, DB 복원이 필요하면 이후 거래 유실을 포함한 [공통 복구 기준](deploymentPlan.md#7-백업복구와-관측)을 따릅니다.

## 8. 완료 기준과 비용

- 기존 RDS의 자료·주요 합계가 유지되고 연락처·계좌 복호화와 검색이 정상이다.
- 로그인·재발급·로그아웃과 현재 관리자·주민 권한 확인이 정상이며 Redis 이전·초기화 결과가 안내와 일치한다.
- 세대·주민·초대·부과·수납·통장·정산·현재 파일 출력의 주요 흐름을 확인했다.
- 새 IP의 HTTPS·인증서 갱신·readiness·백업·로그 회전과 배포·복구 절차를 확인했다.
- 이전 IP에는 업무 쓰기가 도달하지 않고, 구 서버를 다시 켜도 운영 쓰기가 재개되지 않도록 정리했다.
- 검증한 시각·이미지·DNS·복구 결과와 아직 확인하지 못한 항목을 기록했다.

이관 비용은 실행 시점의 서울 공식 견적으로 다시 계산합니다. EC2 컴퓨팅·EBS·공인 IPv4·트래픽·스냅샷과 관측 비용 외에, 준비·복구 기간 동안의 Lightsail과 EC2 중복 비용을 포함합니다. 같은 RDS를 유지하더라도 백업·검증용 복원 인스턴스·AZ 간 전송, 선택 시 ALB·NAT·관리형 Redis·키 보관 서비스 비용은 별도로 확인합니다. 초기 비용 추정치를 미래 EC2 청구 상한으로 사용하지 않습니다.
