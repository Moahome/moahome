# 초기 설정의 주민 명부 등록과 전화번호 동의 확인 검토안

작성일: 2026-11-06. 상태: **구현 전 기획·검토안**.

사용자가 요청한 화면 추가와 아직 고민 중인 전화번호 동의 방안을 정리합니다. 아래의 제안·미정 항목은 확정 정책이나 구현 완료를 의미하지 않습니다. 이번 작업은 문서 작성이며 화면·API·DB·엑셀 파일은 변경하지 않았습니다.

## 1. 요청한 작업과 검토 중인 사항

| 구분 | 내용 |
| --- | --- |
| 사용자 요청 | 관리대상 초기 설정에서 동 설정 다음에 주민 목록 등록 페이지 추가 |
| 사용자 요청 | 주민을 직접 입력하거나 엑셀로 업로드하는 두 가지 방식 제공 |
| 사용자 요청 | 업로드 화면에서 현재 주민 업로드 화면처럼 엑셀 양식 다운로드 제공 |
| 사용자 구상 | 페이지 상단의 라디오 버튼으로 직접 입력 / 엑셀 업로드 전환 |
| 사용자 검토 중 | 엑셀에 전화번호 동의 확인 열을 추가하고 `O`인 경우에만 전화번호 저장 |
| 이 문서의 제안 | 전화번호 없이도 명부 등록 허용, 동의 확인 기록 구분, 기존 등록 경로의 적용 범위 정리 |

## 2. 현재 구현과 변경 시 주의할 점

- 현재 초기 설정은 **기본 정보 → 동·세대 및 담당자 → 관리계좌 및 잔고 → 관리비 설정 → 최종 확인**의 다섯 단계입니다. 마지막 제출에서 전체 정보를 한 번에 저장합니다.
- 현재 주민 개별 등록과 엑셀 업로드는 저장된 관리대상·세대를 대상으로 합니다. 이름·소속 세대는 필수이고 연락처·주민 구분은 선택입니다.
- 배포 중인 양식은 동 있음 `동 / 호수 / 이름 / 연락처 / 주민 구분`, 동 없음 `호수 / 이름 / 연락처 / 주민 구분`입니다. 서버는 일부 과거 양식도 지원합니다.
- 기존 업로드는 검증 결과를 임시 DB에 보관하고 선택한 정상 행을 행별로 저장합니다. 연락처는 임시 데이터에서도 암호화하고 원본 파일은 저장하지 않습니다.
- 기존 초기 설정은 새로고침 복원을 위해 초안과 제출 본문을 브라우저 `sessionStorage`에 보관합니다. 별도 주민 업로드 화면은 파일·화면 상태를 메모리에만 두고 새로고침 시 폐기합니다.
- 확인한 주민 ERD·등록 코드에는 전화번호 동의 확인을 위한 별도 필드가 없습니다. 현재 암호화 저장과 이번 동의 확인 제안은 서로 다른 처리입니다.

따라서 주민 업로드 페이지를 그대로 연결할 수는 없습니다. 초기 설정에서는 아직 관리대상·세대 ID와 관리자 참여가 없으며, 기존 업로드의 행별 저장도 초기 설정의 전체 저장·실패 시 전체 롤백 기준과 다릅니다.

## 3. 화면 구성 제안

### 단계와 입력 방식

변경할 흐름은 다음과 같습니다. 페이지 제목은 `주민 명부 등록`을 제안합니다.

```text
기본 정보 → 동·세대 및 담당자 → 주민 명부 등록 → 관리계좌 및 잔고 → 관리비 설정 → 최종 확인
```

상단에 같은 그룹의 라디오 버튼 `직접 입력` / `엑셀 업로드`를 배치하고 아래 입력 영역을 바꿉니다. 최초 선택은 직접 입력을 제안합니다. 업로드한 뒤 빠진 주민을 직접 추가할 수 있도록 **입력 방식은 둘이지만 최종 주민 초안 목록은 하나**로 관리하는 방안을 권장합니다. 라디오 전환만으로 이미 추가한 주민을 지우지 않습니다.

주민 등록을 초기 설정의 필수 완료 조건으로 추가하지 않고 `나중에 등록`을 제공하는 방안을 제안합니다. 전화번호 동의가 아직 없거나 명부가 준비되지 않아도 관리대상 설정을 진행할 수 있게 합니다. 실제 건너뛰기 허용 여부와 버튼 문구는 구현 전에 확정합니다.

### 직접 입력

- 앞 단계에서 만든 동·세대 초안 중 소속 세대를 선택하고 이름·선택 연락처·주민 구분을 입력합니다. 동 없는 관리대상에서는 호수만 선택합니다.
- 연락처 옆에 기본 미선택 체크박스 `주민에게 전화번호 수집·이용 동의를 받았음을 확인합니다`를 둡니다. 관리자가 대신 주민의 동의를 하는 표현은 사용하지 않습니다.
- 전화번호는 동의 확인 후 입력할 수 있도록 활성화하는 방안을 제안합니다. 확인을 해제할 때 이미 입력한 번호가 있다면 삭제를 안내하고 제거합니다.
- 추가한 주민은 목록에서 확인·수정·삭제할 수 있도록 합니다. 대표 주민·가입 상태·계정 연결을 새로운 입력 항목으로 추가하지 않습니다.

### 엑셀 업로드

- `양식 다운로드 → 파일 선택 → 검증 결과 확인 → 선택한 정상 행을 초안에 추가` 순서를 제안합니다. 이 단계에서는 주민을 DB에 등록하지 않습니다.
- 기존 동 있음 / 없음 양식을 바탕으로 하되 전화번호 동의 확인 열을 추가할 경우 양식과 서버 파서를 함께 변경합니다.
- 기존 파일 크기·행 수·수식 셀 제한과 연락처 정규화는 재사용을 검토합니다. 아직 저장하지 않은 세대 초안에 대한 연결 검증이 추가로 필요합니다.
- 검증 결과에는 등록 가능한 주민 수, 오류 수, 전화번호 제외 수를 구분해 표시합니다. 동의 없는 전화번호를 제외하는 것과 주민 행 전체를 제외하는 것을 구분합니다.
- 목록에 추가한 뒤 새 파일을 올릴 때는 기존 목록에 추가하는지 교체하는지 명시합니다. 기본은 추가를 제안하며 중복·동명이인 기준은 기존 정책을 따릅니다.

최종 확인에는 주민 수, 전화번호 포함 수, 전화번호 제외 수와 수정 진입점을 추가하는 방안을 제안합니다. 최종 저장에서 선택한 주민까지 함께 저장하고, 완료 뒤 실제 주민 목록에서 확인할 수 있어야 합니다.

## 4. 전화번호 동의 열 제안

### 열 이름과 값

열은 하나만 추가하되 이름을 **`전화번호 수집·이용 동의 확인`**으로 명확하게 적는 것을 권장합니다. 단순 `개인정보 동의`는 이름·세대·전화번호 중 어떤 정보와 어떤 목적을 뜻하는지 모호합니다.

| 양식 | 제안하는 열 순서 |
| --- | --- |
| 동 있음 | 동 / 호수 / 이름 / 연락처 / 전화번호 수집·이용 동의 확인 / 주민 구분 |
| 동 없음 | 호수 / 이름 / 연락처 / 전화번호 수집·이용 동의 확인 / 주민 구분 |

엑셀 드롭다운은 `O / X`를 제공하고 기본값은 비워 둡니다. `O`를 미리 채운 예시는 제공하지 않는 방안을 제안합니다. 작성 안내는 별도 안내 시트에 두어 첫 시트의 데이터 헤더를 유지합니다.

### 저장 판단 제안

다음 표는 검토안이며 기존 API 동작이 아닙니다. 이름·세대 등 다른 입력이 정상인 경우를 전제로 합니다.

| 동의 확인 | 연락처 | 제안 처리 |
| --- | --- | --- |
| `O` | 정상 번호 | 주민과 전화번호 저장 |
| `O` | 빈칸 | 전화번호 없이 주민 저장. 실제 번호가 없으므로 번호에 대한 동의 기록을 임의 생성하지 않음 |
| `X` 또는 빈칸 | 빈칸 | 전화번호 없이 주민 저장 |
| `X` 또는 빈칸 | 번호 있음 | 전화번호를 제외하고 주민만 등록 가능. `동의 미확인으로 전화번호 제외` 경고 표시 |
| `O` | 잘못된 번호 | 행 오류로 표시하고 번호 수정 후 선택 가능 |
| 그 외 값 | 어떤 값이든 | 동의 확인 값 오류로 표시하고 수정 안내 |

앞뒤 공백 제거 후 영문 `O`만 동의 확인으로 인정하는 단순한 규칙을 제안합니다. 숫자 `0`, 한글 `ㅇ`, 동그라미 기호 등은 자동으로 동의로 추정하지 않습니다. 소문자 `o` 등을 허용할지는 파서 구현 전에 결정합니다.

기존 양식에는 동의 확인 열이 없습니다. **권장안은 새 양식을 안내하고 다시 업로드하도록 하는 것**입니다. 과거 양식을 계속 받을 경우에도 번호가 있다는 이유로 동의가 확인된 것으로 처리하면 안 됩니다. 과거 양식 지원 종료 범위는 기존 운영 중 업로드까지 포함해 결정해야 합니다.

### 제외하는 시점

`O`가 아닌 전화번호는 최종 주민 저장 직전에만 빼는 것으로 끝내지 않습니다. 파싱 후 검증용 임시 데이터 생성 전에 제외하고, 암호문·HMAC·끝 네 자리·로그·오류 메시지·결과 파일에도 남기지 않는 방안을 제안합니다. 중복 판단도 제외된 번호를 몰래 이용하지 않고, 번호 없는 주민에 대한 기존 정책을 적용합니다.

다만 원본 엑셀을 서버에 전송하면 서버는 원본 번호를 일시적으로 읽게 됩니다. 이 방식의 의미는 `동의 미확인 번호를 보관하지 않음`이며 `서버가 수집하지 않음`을 보장하지 않습니다. 서버로 보내는 것부터 제한하려면 브라우저에서 읽어 해당 번호를 제거한 정제 데이터만 보내는 설계가 추가로 필요합니다. 양식 안내에도 동의받지 않은 번호는 작성하지 않도록 명시합니다.

## 5. O 표시를 보완할 아이디어

### 관리자의 확인과 주민의 실제 동의를 구분

`O`는 관리자가 기존에 동의를 받았다고 표시한 값입니다. 이것만으로 주민이 언제 어떤 안내를 받고 동의했는지까지 입증했다고 간주하지 않는 것이 좋습니다.

동의에 근거해 수집·이용할 경우 목적, 항목, 보유·이용 기간, 거부권과 거부 시 불이익을 알려야 합니다. 이는 [개인정보 보호법 제15조 제2항](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1020398563)의 고지 사항입니다. 아래 기록 제안은 이 요구를 고려한 제품 설계 의견이며, 그 자체로 적법성을 보장하는 기준은 아닙니다.

최소 기능은 엑셀 열 하나로 유지하면서 서버에는 다음 정보를 구분해 기록하는 방안을 제안합니다. 구체적인 테이블·컬럼은 아직 결정하지 않습니다.

| 기록 후보 | 의미와 주의점 |
| --- | --- |
| 확인한 관리자와 서버 기록 시각 | 누가 모아홈에 동의 확인을 기록했는지. 실제 주민 동의일로 대체하지 않음 |
| 입력 경로 | 직접 입력 / 엑셀 업로드 구분 |
| 실제 동의일·동의 방식·증빙 참조 | 관리자가 보관한 동의 기록과 연결할 필요가 있을 때 검토. 수집 범위·필수 여부는 미정 |
| 동의받은 안내 내용 또는 버전 | 실제 사용한 안내와 연결 가능한 경우에 기록. 새 표준 안내 버전을 과거 동의에 임의 적용하지 않음 |

서명 이미지·동의서 파일 업로드는 개인정보를 더 보관하게 되므로 첫 구현의 필수 기능으로 넣지 않는 것을 제안합니다. 실제 증빙 보관 주체·방식은 정해야 합니다. 번호 변경이나 동의 철회 시에는 이전 확인을 새 번호에 자동 승계하지 않도록 별도 정책이 필요합니다.

### 동의가 준비되지 않은 주민도 등록

권장하는 운영 흐름은 **이름·세대 중심으로 명부 등록 → 전화번호 동의 확인 후 번호 추가**입니다. 향후 주민이 가입할 때 본인이 직접 번호와 동의를 입력하는 방법도 검토할 수 있습니다. 이는 이번 주민 명부 화면 추가의 필수 구현 범위에는 넣지 않습니다.

전화번호 열만 보완해도 이름·세대 역시 개인정보라는 점은 남습니다. 관리 주체와 모아홈의 역할, 기존 명부를 서비스에 올리는 근거, 전화번호의 구체적 이용 목적과 보유 기간은 별도로 확인해야 합니다. 동의 외의 처리 근거 적용 여부도 검토 대상이며, 이 문서에서는 전화번호를 동의 확인 후 저장하는 제품 방안을 제안합니다.

## 7. 해야 할 일과 순서

1. **화면·개인정보 정책 확정**: 위 결정 목록 중 첫 구현에 필요한 범위를 정합니다. 전화번호 동의 안내와 실제 동의 기록 보관 방식을 먼저 준비합니다.
2. **기준 문서 갱신**: 확정한 업무 정책은 도메인 규칙, 필요한 저장 구조는 ERD, 초기 등록 요청과 업로드 변경은 각 기존 API 계약에 반영합니다. 화면·브라우저 처리는 Client 문서, 저장·트랜잭션은 Server 문서에서 상세화합니다.
3. **초기 등록 저장 설계**: 주민과 세대 초안의 안정적인 연결, 거주 관리소장 중복, 대표 순서, 최종 원자적 저장과 동일 요청 재시도에 주민 목록을 포함합니다. 기존 운영 업로드의 부분 성공을 초기 등록에 그대로 적용하지 않습니다.
4. **공통 처리 재사용 정리**: 기존 주민 입력 검증·연락처 보호·엑셀 파서를 확인합니다. 초기 설정과 운영 화면이 함께 사용할 부분만 적절한 공통 책임으로 옮기며, 초기 설정 기능이 기존 업로드 화면 슬라이스를 직접 참조하지 않게 합니다.
5. **엑셀 양식·검증 변경**: 동 있음 / 없음 양식과 안내·드롭다운을 수정하고 파서·미리보기·오류·과거 양식 처리 및 임시 데이터에서의 번호 제외를 함께 적용합니다.
6. **주민 등록 단계 구현**: 진행 표시를 여섯 단계로 맞추고 직접 입력·업로드·공통 초안·이전/다음 이동·최종 확인을 연결합니다. 이전 단계에서 세대 삭제·변경 시 주민 연결을 재검증하고 다른 세대로 자동 연결하지 않습니다.
7. **기존 연락처 경로 반영**: 확정된 적용 범위에 맞춰 개별 등록·업로드·번호 수정 등에서도 같은 동의 판단이 적용되게 합니다.
8. **검증**: Client·Server 각 규칙에 따른 검사와 빌드를 수행하고 다음 업무 시나리오를 확인합니다.

검증할 주요 시나리오는 다음과 같습니다.

- 동 있음 / 없음, 여러 주민이 같은 세대에 속하는 경우, 아직 등록할 주민이 없는 경우
- 직접 입력 뒤 업로드 및 업로드 뒤 직접 입력, 중복·동명이인·선택 제외와 대표 순서
- `O / X / 빈칸 / 잘못된 값`과 정상·빈·잘못된 전화번호의 조합, 과거 양식
- 동의 미확인 번호가 임시 저장·암호문·HMAC·끝 네 자리·로그·결과 파일에 남지 않는지
- 이전 단계의 동·세대 수정·삭제, 거주 관리소장과의 중복, 새로고침·이탈·계정 변경 시 확정된 초안 처리
- 최종 저장 실패 시 전체 롤백, 응답 유실 뒤 같은 요청 재시도 시 주민까지 중복 없이 복구
