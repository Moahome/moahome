# 관리대상 생성 권한과 시스템 관리 개발 계획

기준일: 2026-11-03. 상태: **개발 예정 / 생성 권한 제한과 시스템 관리 화면 미구현**.

공개 배포 후 승인받지 않은 사용자가 새 관리대상을 만들어 사용하는 것을 제한합니다. 로그인과 초대코드 참여는 유지하고, 시스템 관리자가 허용한 계정만 `관리할 곳 만들기`를 이용하게 합니다. 이 문서는 개발 계획이며, 작성만으로 현재 코드나 운영 서버의 권한이 바뀌지는 않습니다.

## 1. 사용자와 정한 개발 방향

| 항목 | 개발 방향 |
| --- | --- |
| 방문·로그인 | 기존처럼 허용 |
| 초대코드 참여 | 기존 초대 검증·참여 신청·가입 승인 흐름 유지 |
| 관리대상 생성 | 시스템 관리자가 생성 권한을 허용한 계정만 가능 |
| 승인 유지 | 계정별 지속 허용. 회수 전까지 생성 가능하며 일회성·횟수·만료 제한을 추가하지 않음 |
| 생성 권한 회수 | 이후 새 관리대상 생성 금지. 기존 관리대상의 참여·자료·이용 권한은 유지 |
| 작성 중 회수 | 이미 등록 화면을 작성 중이어도 최종 저장 전에 회수되면 신규 생성 금지 |
| 승인 협의 | 아는 이용자와 시스템 밖에서 서면으로 협의. 서비스 안에 연락·승인 신청·알림 기능을 만들지 않음 |
| 최초 시스템 관리자 | 운영자가 DB 쿼리로 직접 지정 |
| 이후 시스템 관리자 지정 | 시스템 관리의 회원 관리에서 회원을 시스템 관리자로 승격하고 관리자 목록에서 확인 |
| 프로젝트 위치 | 별도 루트 `admin/` 프로젝트 없이 기존 `client/` 안에 구현. 접속 주소는 `/admin` |

생성 권한 부여와 시스템 관리자 승격은 서로 다른 기능입니다. 관리대상을 만들도록 허용했다고 시스템 관리자 권한을 주지 않습니다.

## 2. 현재 구현과 달라지는 점

현재는 정상 로그인 계정이면 관리대상 등록을 진행할 수 있고, 등록 성공 시 해당 관리대상의 관리소장으로 지정됩니다. 앞으로는 **등록하기 전에 생성 허용 여부를 확인**하고 저장할 때도 다시 검사합니다. 생성 성공 후 관리소장으로 지정하는 기존 처리는 유지합니다.

| 현재 구현 | 개발할 변경 |
| --- | --- |
| `users.system_role`에 `USER / ADMIN` 저장 | 시스템 관리자 판별에 기존 값 사용 |
| `GET /api/users/me`에서 `systemRole` 제공 | 현재 계정의 관리대상 생성 가능 여부도 조회하도록 확장 |
| 정상 로그인만으로 등록 가능 | 별도 생성 권한 검사 추가 |
| 시스템 관리자 운영 화면·역할 변경 API 없음 | 회원 관리·관리자 목록·생성 권한 관리·관리자 승격 기능 추가 |

기존 기준은 [도메인 규칙](../domain/domainRules.md#플랫폼-권한과-관리대상-권한), [사용자 ERD](../domain/erd.md#41-users), [관리대상 등록 API](../api/propertyRegistrationApi.md)입니다. 해당 문서의 자유 등록 설명은 현재 구현을 나타냅니다. 구현 단계에서 새 정책에 맞춰 관련 설명과 계약을 함께 갱신하며 실제 운영 배포 여부는 별도로 확인합니다.

## 3. 권한 구분과 구현 제안

| 권한 | 의미 | 저장·조회 방향 |
| --- | --- | --- |
| 시스템 관리자 | 서비스 회원의 생성 권한과 시스템 관리자 지정을 관리 | 기존 `users.system_role = ADMIN` 사용 |
| 관리대상 생성 허용 | 새 관리대상을 만들 수 있음 | 시스템 관리자 역할과 별도로 계정별 허용 여부 저장 |
| 관리대상별 역할 | 특정 관리대상의 관리소장·부담당자·주민 | 기존 `property_members.role` 사용 |

시스템 관리자 승격은 기존 계정의 `system_role`을 변경하는 방식으로 설계합니다. 관리자 목록은 해당 역할의 계정을 조회하며, 목록 표시만을 위한 별도 관리자 테이블은 만들지 않습니다. 시스템 관리자라는 이유로 모든 관리대상의 주민·통장·수납 자료에 접근하게 하지는 않습니다.

다음 세부 사항은 사용자 확정 정책과 구분하는 **구현 제안**입니다.

- 시스템 관리자는 별도 생성 승인 없이 관리대상을 생성할 수 있게 합니다.
- 기존 가입자와 신규 가입자의 별도 생성 허용 여부는 기본 미허용으로 두고 필요한 회원만 허용합니다. 기존 계정이나 관리소장이라는 이유로 자동 허용하지 않으며 기존 관리대상 이용은 유지합니다.
- 새 관리대상 등록 과정의 통장 파일 업로드·미리보기에도 같은 생성 권한을 적용합니다. 기존 관리대상의 통장 업로드는 기존 업무 권한을 따릅니다.

위 제안은 구현 전에 확인하고 도메인 규칙에 반영합니다. 실제 컬럼명·응답 필드명은 ERD와 API 계약에서 정합니다.

## 4. 이용 화면과 흐름

### 생성 권한이 없는 회원

`관리 시작하기`를 누르면 등록 화면에 진입시키지 않고 아래 안내를 표시합니다. 서비스 안에 별도 신청 버튼이나 문의 양식은 추가하지 않습니다.

> 관리대상 생성 권한이 필요합니다.
> 시스템 관리자에게 권한 승인을 받아주세요.

초대코드 입력은 기존 흐름으로 계속 이용할 수 있습니다.

### 생성 권한이 있는 회원

```text
관리 시작하기 → 기존 초기 설정 작성 → 최종 저장에서 현재 권한 확인
→ 전체 등록 성공 → 해당 관리대상의 관리소장으로 진입
```

작성 중 권한이 회수됐다면 저장 시 신규 생성을 거부하고 안내합니다. 회수 전에 이미 등록이 성공했다면 기존 관리대상으로 취급합니다. 응답을 받지 못했을 때는 기존 결과 조회·중복 방지 절차로 성공 여부를 확인하며 새 관리대상을 중복 생성하지 않습니다.

### 시스템 관리 화면

기존 `client/`의 `/admin`에서 제공합니다. 프로필 메뉴에 시스템 관리자에게만 `시스템 관리`를 표시하는 것을 진입점으로 제안합니다. 관리대상이 없는 계정도 접근할 수 있도록 특정 관리대상의 설정 메뉴와 분리합니다.

| 화면 | 개발할 기능 |
| --- | --- |
| 회원 관리 | 회원 검색·목록, 계정 식별자·표시명·계정 상태·시스템 역할·생성 허용 여부 확인, 생성 권한 부여·회수, 시스템 관리자 승격 |
| 관리자 목록 | 현재 시스템 관리자로 지정된 계정 확인 |

관리자 목록은 별도로 가입시키는 명단이 아니라 회원 중 시스템 관리자 역할을 가진 사람들의 목록입니다. 닉네임은 중복될 수 있으므로 계정 식별자도 확인해 정확한 회원을 선택합니다. 승인 협의는 서면으로 진행하며 서비스에 연락처 수집이나 연락 기능을 추가하지 않습니다.

시스템 관리자 역할 해제 기능은 승격과 별도의 구현 제안입니다. 추가한다면 본인·마지막 관리자 해제와 운영 복구 방식을 먼저 정하며, 확정된 사용자 요구로 취급하지 않습니다.

## 5. 최초 시스템 관리자 지정

1. 최초 관리자가 될 사람이 기존 로그인 절차로 계정을 만듭니다.
2. 운영자가 대상 계정을 확인하고 DB 쿼리로 해당 계정의 `users.system_role`을 `ADMIN`으로 변경합니다.
3. 서버가 현재 역할을 조회해 시스템 관리 접근을 허용하는지 확인합니다.
4. 이후 추가 시스템 관리자는 `/admin`의 회원 관리에서 승격하고 관리자 목록에서 지정 결과를 확인합니다.

실제 운영 계정 ID·접속 정보·비밀값을 문서나 코드에 넣지 않습니다. 이번 문서 작업에서 운영 DB 쿼리를 실행하거나 실제 계정 역할을 변경하지 않습니다.

## 6. Client 개발 범위

- 기존 `client/`에 `/admin`을 연결합니다. 로그인·API 호출·공통 UI·색상 토큰을 재사용하고 화면 구조는 [Client 규칙](../../client/AGENTS.md)을 따릅니다.
- 회원 관리와 관리자 목록을 제공하고, 프로필 진입점은 PC·모바일 및 관리대상이 없는 시작 화면에서도 사용할 수 있게 설계합니다.
- `/admin` 직접 접근도 현재 로그인·시스템 관리자 역할을 확인합니다. 권한 확인 전에는 관리자용 회원 자료를 표시하지 않습니다.
- `/start`의 신규 등록 단계와 `/properties/add` 직접 접근에 생성 권한 확인을 적용합니다. 버튼에서만 검사하지 않습니다.
- 권한 확인 중·조회 실패·미허용을 구분합니다. 조회 실패를 생성 허용으로 간주하지 않고 재시도할 수 있게 합니다.
- 권한 변경 후 서버의 현재 결과로 화면을 갱신합니다. 로그아웃·계정 전환 시 이전 계정의 회원 목록과 권한 캐시를 정리합니다.
- 생성 권한 회수 시 신규 저장 금지 안내를 적용합니다. 초안 보존·폐기는 [기존 등록 설계](../../client/docs/propertyRegistration.md)를 기준으로 상세화하고, 회수 후 초안으로 등록 제한을 우회하지 못하게 합니다.

## 7. Server와 API 개발 범위

- 계정별 생성 허용 여부를 저장하고 조회·변경할 수 있게 합니다. 저장 구조·기본값·제약은 확정된 정책에 따라 ERD와 Migration에 반영합니다.
- 시스템 관리자 전용 회원 조회, 생성 권한 부여·회수, 시스템 관리자 승격과 관리자 목록 조회 API를 개발합니다.
- 시스템 관리 API는 요청마다 정상 계정과 현재 시스템 관리자 역할을 검사합니다. 일반 회원이 API를 직접 호출해 자신을 승격하거나 생성 권한을 바꿀 수 없게 합니다.
- 등록의 기본 정보 검증·최종 생성에서 공통 생성 권한 검사를 사용합니다. 등록 과정의 통장 업로드·미리보기도 적용 대상으로 검토하며 새 진입점이 누락되지 않게 합니다.
- 최종 저장 시 현재 권한을 확인하고 거부된 요청은 관리대상·세대·계좌·참여 권한 등 일부 자료도 저장하지 않습니다. 기존 등록의 전체 트랜잭션과 중복 방지를 유지합니다.
- 회수와 생성 요청이 동시에 실행될 때의 처리 순서는 Server 설계에서 구체화합니다. 회수가 먼저 확정된 뒤 신규 생성이 확정되는 일이 없도록 보장하며, 이미 생성이 확정된 대상에는 회수를 소급 적용하지 않습니다.
- 성공한 등록 결과의 조회·재시도는 신규 생성과 구분하고 기존 현재 접근권한 검사를 유지합니다. 회수 후 결과 확인이 막혀 성공한 등록을 중복 제출하게 만들지 않습니다.
- 권한 변경과 관리자 승격은 서버가 인증한 처리자 기준으로 수행합니다. 처리자·대상·변경 전후 값·시각을 추적하는 저장 방식은 Server 설계에서 정하는 것을 제안합니다.
- 미인증·권한 부족·저장 실패를 구분합니다. 권한 부족은 `403`으로 거부하고 실패를 승인 완료나 승격 완료로 표시하지 않습니다.

시스템 관리 API의 상세 요청·응답·오류는 공통 계약으로 작성합니다. 기존 등록 API 변경은 [관리대상 등록 API](../api/propertyRegistrationApi.md)에 모으고, 화면·초안은 Client 문서, 저장·동시성은 Server 문서에서 관리합니다.

## 8. 개발 순서

1. 3절의 구현 제안을 확인하고 [도메인 규칙](../domain/domainRules.md)에 승인 기준을 반영합니다. 생성 전 승인과 생성 후 관리소장 자동 지정이 혼동되지 않게 기존 설명을 맞춥니다.
2. [ERD](../domain/erd.md)와 공통 API 계약을 정리합니다. 기존 자유 등록 설명, 최초 관리자 지정과 회원 관리에 의한 승격 절차도 관련 문서에서 맞춥니다.
3. Server에 권한 저장·회원 관리·관리자 승격·목록·생성 제한을 구현하고 직접 API 호출과 등록 트랜잭션을 검증합니다.
4. Client에 `/admin`, 회원 관리·관리자 목록, 프로필 진입점과 등록 제한 안내를 구현합니다.
5. 최초 관리자 계정과 기존 이용자 중 생성 허용 대상을 준비하고 Migration·서버 검사·관리자 지정·화면 배포 순서를 맞춥니다. 기존 계정이나 관리대상 자료를 임의 삭제하지 않습니다.
6. 실제 배포 후 생성 차단·허용·회수, 관리자 승격과 목록 반영, 초대 참여와 기존 관리대상 이용을 확인합니다.

## 9. 구현 검증 기준

- 일반 회원이 관리자 API 직접 호출이나 `/admin` 직접 접근으로 회원 자료를 보거나 권한을 변경하지 못합니다.
- 생성 미허용 회원은 버튼·등록 URL·직접 API 호출로 새 관리대상을 생성하지 못하며 거부 후 부분 저장이 없습니다.
- 허용 회원은 기존 초기 설정을 완료하고 해당 관리대상의 관리소장이 됩니다. 생성 허용만으로 시스템 관리자가 되지 않습니다.
- 생성 허용은 한 번 생성한 뒤에도 유지됩니다. 회수하면 작성 중이었어도 신규 생성은 금지하고 기존 관리대상 이용은 유지합니다.
- 최초 DB 지정과 이후 회원 관리 승격이 현재 서버 권한에 반영되고 관리자 목록에 나타납니다.
- 권한 변경 실패·중복 실행, 작성 중 회수·동시 저장, 응답 유실·동일 요청 재시도와 결과 조회를 검증합니다.
- 초대코드 참여·기존 가입 승인·관리대상별 업무 권한에 회귀가 없고 시스템 관리자 역할로 다른 관리대상에 우회 접근하지 못합니다.
- PC·모바일, 권한 조회 실패, 로그아웃·계정 전환을 확인하고 PostgreSQL Migration과 필수 검사·테스트·빌드는 [Client 규칙](../../client/AGENTS.md)과 [Server 규칙](../../server/AGENTS.md)을 따릅니다.

문서 작성 단계에서는 링크·경로와 요구·제안·현재 구현 상태의 구분을 검증합니다. 기능 구현·빌드·운영 DB 적용은 아직 수행하지 않았습니다.
