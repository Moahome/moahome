# 건물별 공지와 주민 메시지 서비스 기획

기준일: 2026-11-13. 건물별 공지 공간, 모아홈 내부 알림톡·문자 발송과 채널톡 문의를 로그인 주민 서비스보다 먼저 추진합니다. 이번 작업은 공지사항 화면과 편집기를 먼저 기획하며 문자 발송은 후순위로 둡니다. 현재 기능은 미구현이며, 확정 정책은 [도메인 규칙](../domain/domainRules.md#건물-안내와-주민-메시지의-확정-방향)을 따릅니다. 아래 화면 구성과 연결 방식은 구현 설계안입니다.

## 공지사항 우선 기획

### 사용자 요청과 현재 상태

2026-11-13 사용자 요청은 기존 문서·구현 여부를 확인하고 공지사항 메인·상세·작성·수정 페이지와 글자 크기·이미지 삽입이 가능한 편집기를 검토하는 것입니다. 코드 구현보다 문서 기획을 먼저 진행하며 문자 발송은 후순위입니다. 임시저장·중요 표시·상단 고정 등 아래 추가 기능은 제안이며 확정 요구사항과 구분합니다.

| 확인 영역 | 현재 상태 |
| --- | --- |
| 공통 기획 | 이 문서에 비회원 공지·메시지 발송·담당자 문의 방향이 있음 |
| 관리자 메뉴 | `공지사항` 단일 메뉴가 있고 준비 중으로 표시됨 |
| 관리자 페이지 | `/manage/{propertyId}/notices`는 `ComingSoonPage` 안내 화면 |
| 주민 열람·편집기 | 실제 공지 목록·상세·작성·수정과 리치 텍스트 편집기 미구현. Client 의존성에도 편집기 패키지 없음 |
| API·저장 | 공지 업무 API·테이블·Migration 없음. [ERD](../domain/erd.md#02-현재-전화번호-정책)는 공지 저장 구조를 후속 설계로 명시 |
| 재사용 가능 요소 | 기존 관리 레이아웃과 `StateMessage`의 `empty-notice` 상태 그림·문구 |

첨부 아이디어의 공지 게시와 메시지 발송 분리는 유지합니다. 최초 범위를 전체·선택 발송과 발송 내역까지 넓히는 제안은 이번 우선순위에서 제외하고, 편집기와 실제 주민 열람을 먼저 연결하는 안으로 조정합니다. 첨부에서 언급한 `moahome_menu_design_v2.1` 원문은 현재 저장소에서 확인되지 않아 현재 메뉴 코드와 [관리 레이아웃 문서](../../client/docs/managementLayout.md#메뉴별-목적지)를 기준으로 합니다.

### 첫 개발 범위 제안

| 구분 | 제안 범위 |
| --- | --- |
| 관리자 공지 관리 | 목록·검색·상세·작성·수정·삭제 |
| 작성 편의 | 리치 텍스트 편집기, 본문 이미지, 미리보기, 수동 임시저장, 미저장 변경 이탈 확인 |
| 게시 설정 | 중요 표시와 상단 고정, 즉시 게시 |
| 주민 안내 | 로그인 없는 관리대상별 공지 목록·상세, 모바일 열람 |
| 후속 단계 | 문자·알림톡, 수신자 선택·발송 내역, 채널톡 연결 |
| 추가 검토 | 예약·게시 종료일, 파일 첨부, 수정 이력 화면, 읽음 확인, 댓글·반응 |

첫 개발은 관리대상 전체에 공개하는 공지부터 시작하는 안을 권합니다. 대상 지정 공지의 기존 제공 방향은 유지하되 지정 단위·열람 제한을 결정한 뒤 추가합니다. 특정 동이나 주민을 표시하거나 그들에게만 링크를 보냈다는 이유로 접근이 제한되지는 않습니다. 공개 공지에 개인정보나 개인 관리비를 넣지 않는 기존 기준을 따릅니다.

문자·알림톡 기능이 없는 단계에서는 발송 설정과 비활성 발송 버튼을 공지 작성 화면에 미리 배치하지 않습니다. 발송을 도입할 때도 공지 게시·수정과 발송 요청은 별도 동작으로 연결합니다.

### 페이지 구성 제안

사이드바는 기존 `공지사항` 단일 메뉴를 유지합니다. 여기서 메인 페이지는 관리자 공지 목록을 뜻하며 서비스 랜딩·대시보드와 구분합니다.

| 페이지 | 주소 후보 | 주요 구성 |
| --- | --- | --- |
| 관리자 목록 | `/manage/{propertyId}/notices` | 제목 검색, 전체·게시됨·임시저장 필터, 공지 작성 버튼, 목록·페이지 이동 |
| 관리자 상세 | `/manage/{propertyId}/notices/{noticeId}` | 제목·상태·중요 표시, 게시일·수정일, 본문, 목록·수정·삭제 |
| 작성 | `/manage/{propertyId}/notices/new` | 제목, 본문 편집기, 중요·고정 설정, 임시저장·미리보기·게시 |
| 수정 | `/manage/{propertyId}/notices/{noticeId}/edit` | 기존 내용 불러오기, 같은 편집 폼, 미리보기·변경 저장 |
| 주민 목록·상세 | 기존 `/p/{건물식별자}` 예시의 목록·상세 경로 | 건물명, 게시된 공지 목록과 읽기 전용 본문. 관리 버튼 없음 |

작성·수정은 같은 폼과 편집기 구성을 재사용하고, 주소와 최종 동작을 구분합니다. 미리보기는 별도 고정 페이지보다 현재 입력값을 보여주는 패널이나 대화상자로 시작하는 안을 제안합니다. 미리보기 자체는 저장·게시하지 않습니다. 실제 경로와 화면·상태 상세는 구현 결정 후 Client 문서에서 관리합니다.

목록은 관리 업무에 맞춰 데스크톱에서는 표, 모바일에서는 제목 중심의 목록으로 보여줍니다. 표의 항목 후보는 `상태 / 제목 / 게시일 / 수정일`이며 중요·고정 표시는 제목 가까이에 둡니다. 고정된 게시 공지를 먼저, 나머지는 최초 게시일 내림차순으로 정렬하고 일반 수정으로 게시일이 바뀌지 않는 안을 권합니다. 조회수는 첫 범위에서 제외하며 향후 도입하더라도 비회원 조회 횟수를 주민별 읽음 확인으로 취급하지 않습니다.

주민 상세는 관리자 미리보기와 같은 본문 표시 규칙을 사용합니다. 글이 없을 때와 검색 결과가 없을 때를 구분하고, 삭제되거나 존재하지 않는 공개 링크에서는 본문 대신 찾을 수 없다는 안내를 제공합니다. 임시저장 공지와 그 이미지도 공개 주소만으로 열리지 않게 설계합니다.

### 작성 화면과 편집기 제안

입력 순서는 `제목 → 본문 → 게시 설정`으로 단순하게 구성합니다. 데스크톱은 본문을 넓게 두고 게시 설정을 보조 영역에, 모바일은 같은 항목을 세로로 배치합니다. 작성 영역의 동작 예시는 다음과 같습니다.

```text
공지 작성

제목  [예: 공용 전기 설비 점검 안내]

[본문·소제목] [글자 크기] [굵게·기울임·밑줄]
[목록] [정렬] [링크] [이미지] [실행 취소·다시 실행]
┌──────────────────────────────────────┐
│ 11월 15일 오전 10시부터 점검합니다.    │
│                                      │
│ [본문에 삽입한 안내 이미지]            │
└──────────────────────────────────────┘

게시 설정  [ ] 중요 공지로 표시  [ ] 목록 상단에 고정

[취소] [임시저장] [미리보기] [게시]
```

| 편집 기능 | 첫 범위 제안 |
| --- | --- |
| 글자 크기 | 작게·기본·크게·아주 크게의 제한된 단계. 임의 수치 입력보다 모바일 가독성을 우선 |
| 문단 | 본문·소제목, 굵게·기울임·밑줄, 글머리·번호 목록, 왼쪽·가운데·오른쪽 정렬 |
| 링크 | 주소 삽입·수정·해제. 허용하는 주소 형식을 검증 |
| 이미지 | 파일 선택·붙여넣기로 본문에 삽입, 삭제, 대체 텍스트, 본문 폭 안에서 비율 유지 |
| 기본 조작 | 실행 취소·다시 실행, 서식 지우기, 키보드 조작, 한글 입력 조합 확인 |
| 후속 검토 | 표 편집, 이미지 자르기·자유 배치, 글꼴 변경, 동영상 삽입, HTML 직접 편집 |

색상 선택은 우선 제외하고 프로젝트 공통 토큰으로 본문과 도구 모음을 구성합니다. 중요도는 본문의 임의 색상보다 중요 표시로 전달합니다. 이미지가 있는 공지라도 점검 시간 등 핵심 안내를 텍스트로 함께 작성할 수 있게 안내합니다.

편집기 후보는 **Tiptap을 우선 검토**합니다. 필요한 도구만 구성하는 방식이 위 범위에 맞는다는 판단입니다. 공식 문서에서 [글자 크기 확장](https://tiptap.dev/docs/editor/extensions/functionality/fontsize)과 [이미지 표시 확장](https://tiptap.dev/docs/editor/extensions/nodes/image)을 확인할 수 있습니다. 다만 이미지 표시와 [붙여넣기·드롭 처리](https://tiptap.dev/docs/editor/extensions/functionality/filehandler)는 서버 업로드를 제공하지 않으므로 파일 저장·검증·공개 제어를 별도로 설계해야 합니다. 채택 전 현재 React·Next.js 환경의 호환성, 필요한 패키지의 이용 조건과 한글 입력을 확인합니다.

이미지 삽입은 일반 첨부파일 다운로드와 구분합니다. 이미지 업로드 중·실패·완료를 표시하고 완료되지 않은 이미지를 포함해 게시하지 않는 안을 제안합니다. 업로드 응답이 유실된 경우에도 저장된 파일을 확인할 수 있어야 합니다. 이미지는 임시 소유 정보를 두고 공지 저장 시 연결하는 방식을 검토하며, 다른 관리대상의 파일을 참조하지 못하게 검증합니다. 미사용 파일은 공지 저장·수정과의 경합을 피하는 정리 기준이 필요합니다. 허용 형식·파일 크기·개수·보관 기간은 구현 전에 정합니다.

### 게시 상태와 저장 동작 제안

처음에는 `임시저장 → 게시됨`으로 시작하고 예약·종료 상태는 추가하지 않는 안을 권합니다. 중요는 제목의 강조 표시이고 고정은 목록의 정렬 규칙이므로 각각 별도 옵션으로 둡니다.

- 임시저장은 서버에 수동 저장하는 안을 우선 검토합니다. 자동저장은 후속으로 두고 저장되지 않은 변경을 가진 화면을 나갈 때 확인합니다.
- 게시된 공지의 수정은 저장 전까지 주민 화면에 반영하지 않습니다. 수정 화면의 `변경 저장`으로 즉시 공개 내용을 바꾸는 안이며, 게시된 글의 수정 초안을 별도로 보관하는 기능은 후속 검토합니다.
- 삭제는 확인 후 공개 목록·상세에서 제외하는 소프트 삭제안을 권합니다. 복원 UI와 삭제 자료·이미지의 보존 기간은 별도 결정합니다.
- 제목·본문의 필수 여부와 길이 제한, 이미지로만 구성된 본문의 허용 여부는 확정하지 않았습니다. 초기안은 공백이 아닌 제목과 의미 있는 본문을 게시 조건으로 검토합니다.

생성·게시·수정·삭제는 중복 클릭과 응답 유실 후 재시도를 고려합니다. 생성 작업의 요청 식별자·결과 확인, 수정 버전 충돌·삭제 후 수정 차단을 API 계약에서 정한 뒤 구현합니다. 타임아웃을 저장 실패로 안내하거나 같은 글을 새 요청으로 반복 생성하지 않습니다. 두 관리자가 동시에 수정하면 나중 저장이 앞선 변경을 덮어쓰지 않도록 버전 검사를 권합니다.

본문 저장 형식은 구조화 JSON을 후보로 두고, 허용 문단·서식·링크·이미지 참조를 서버에서 검증하는 방식을 검토합니다. HTML을 사용한다면 허용 태그·속성에 따른 정제가 필요합니다. 공개 렌더링과 캐시·이미지 응답에서도 임시저장·삭제 상태와 관리대상 경계를 지키도록 설계합니다. 관리자 작성 권한은 기존 확정 정책을 적용하고, 수정·삭제 권한의 세부 범위는 아래 결정 항목에서 확인합니다.

### 구현 전에 결정할 사항

| 항목 | 권장안과 확인할 내용 |
| --- | --- |
| 첫 공개 범위 | 전체 공개 공지를 먼저 제공하고 대상 지정은 접근 정책 결정 후 추가할지 |
| 임시저장 | 서버 수동 저장을 포함할지. 같은 관리대상의 다른 관리자가 초안을 열람·수정할 수 있는지 |
| 수정·삭제 권한 | ADMIN·MANAGER가 다른 관리자가 작성한 공지도 변경할 수 있는지 |
| 게시 설정 | 중요 표시·상단 고정을 모두 제공할지, 고정 수 제한이 필요한지 |
| 편집기·이미지 | Tiptap 채택, 도구 범위, 이미지 형식·용량·개수·저장소·공개 및 삭제 방식 |
| 삭제·이력 | 소프트 삭제, 자료 보존 기간, 변경자·시각 외 이전 본문 보존 필요 여부 |

이 결정을 마친 뒤 도메인 규칙·ERD에 확정 범위를 반영하고, 공지 관련 요청·응답·오류·재시도는 하나의 `docs/api/` 계약에 모읍니다. 화면·초안·이미지 요청 정보의 수명은 `client/docs/`, 저장·동시 수정·파일 정리는 `server/docs/`에서 해당 계약을 참조하도록 상세화합니다. 이 단계에서는 API·테이블·Migration이나 화면 코드를 추가하지 않습니다.

## 목표와 서비스 구분

주민이 알림톡·문자의 버튼을 눌러 자기 건물의 공지를 확인하고 건물 담당자에게 문의할 수 있게 합니다. 공지 확인을 위해 모아홈 회원가입·카카오 로그인·초대코드 입력을 요구하지 않습니다.

이 기획에서 건물별 공간은 기존 관리대상인 `Property`에 연결합니다. 단지 내부의 동인 `Building`과 구분하며, 드림하이츠 링크에서는 드림하이츠에 해당하는 공지를 제공합니다.

| 영역 | 제공하는 경험 |
| --- | --- |
| 주민 안내 공간 | 건물 공지 목록·상세 확인, 메시지 문의 진입 |
| 기존 관리자 영역 | 공지 작성·공개, 명부 기반 수신 대상 선택, 알림톡·문자 발송, 차량 내역·차량 승인 |
| 채널톡 상담 | 건물 담당자 문의, 차량 조회, 차량 등록·수정 요청 |
| 후순위 로그인 주민 서비스 | 가입 승인 후 개인 관리비 등 권한이 필요한 정보 조회 |

관리자 영역과 비회원 안내 공간은 별도 접근 흐름을 사용합니다. 공지 링크 방문이나 채널톡 상담 시작으로 기존 주민 계정 연결·가입 승인·`property_members` 권한을 생성하지 않습니다.

[전체 공유·개인 지정 주민 초대](../domain/domainRules.md#주민-참여-흐름)는 카카오 로그인 계정에 권한을 연결하는 별도 기능입니다. 이 기획의 공지 발송용 수신자별 링크를 주민 초대의 일회용 수락 링크로 겸용하지 않습니다.

## 공지 확인 흐름

```text
드림하이츠 주민에게 공지 안내 발송
→ 공지 확인 버튼 선택
→ 드림하이츠의 해당 공지 상세 열람
→ 같은 관리대상의 공지 목록 또는 메시지 문의로 이동
```

건물 공지 목록과 개별 공지 상세에 각각 연결할 수 있게 설계합니다. `/p/{건물식별자}`는 주소 예시이며 실제 경로는 Client 구현 설계에서 정합니다. URL에 주민 이름·전화번호·차량번호를 넣는 방식으로 이용자를 식별하지 않습니다.

전체 공지와 대상 지정 공지를 구분합니다. 대상 지정 공지의 선택 단위 및 열람 제한은 [남은 결정](#구현-전에-정할-사항)을 따릅니다. 특정 주민에게만 발송했다는 이유로 해당 공지가 다른 방문자에게 비공개가 된 것으로 취급하지 않습니다. 공지의 열람 대상과 메시지 수신 대상은 각각 판단해야 합니다.

## 관리자 작성과 발송 흐름

```text
관리대상 선택
→ 전체 공지 또는 대상 지정 공지 작성
→ 미리보기·공개
→ 주민에게 알리기
→ 수신 대상·메시지·공지 링크 확인
→ 모아홈에서 발송 요청
→ 수신자별 결과 확인
```

수신 대상의 기본 선택은 현재 관리대상 명부 전체입니다. 관리자가 그 명부 안에서 수신 대상을 선택할 수 있게 합니다. 모아홈 가입 여부와 채널톡 상담 이력을 발송 대상의 전제 조건으로 두지 않습니다.

다음은 발송 화면과 처리의 설계안입니다.

| 처리 | 설계안 |
| --- | --- |
| 공지 공개와 발송 | 별도 동작으로 처리해 공지 수정만으로 다시 발송되지 않게 함 |
| 수신 대상 확인 | 선택 인원·실제 수신 번호 수·연락처 누락 인원을 구분 |
| 중복 번호 | 같은 발송에서 같은 번호로 중복 전송하지 않도록 처리 |
| 발송 결과 | 수신자별 요청·성공·실패를 구분하고 제공자가 반환하는 실패 사유 확인 |
| 재발송 | 결과가 확인된 실패 대상에 대해 선택적으로 처리하며 결과 미확인 건은 중복 발송 여부를 먼저 확인 |
| 발송 이력 | 누가 어느 관리대상에서 어떤 내용과 대상으로 요청했는지 추적 |

관리소장과 동대표의 발송 기능은 기존 주민 명부 전체 열람·연락처 원문 공개 권한과 별개입니다. 동대표의 명부 열람·수정 권한은 [관리자 업무 권한](../domain/domainRules.md#관리자-업무-권한-2026-10-24-최종-정정)을 따릅니다. 발송에 필요한 수신 대상 선택용 정보와 공통 API를 따로 설계하고, 발송 기능 때문에 기존 명부 열람 권한을 변경하지 않습니다.

문자·알림톡은 외부 발송 서비스를 통해 전달하되 주민 대상 선택과 발송 요청의 사용자 흐름은 모아홈 안에서 제공합니다. 초기 운영을 채널톡 관리자 화면의 수동 발송으로 대신하는 것은 현재 요구 범위에 맞지 않습니다.

## 건물 담당자 메시지 문의

```text
드림하이츠 안내 공간에서 문의 선택
→ 드림하이츠 문의 메뉴 진입
→ 상담 목적 선택
→ 드림하이츠 담당자에게 전달
```

채널톡 문의 메뉴는 다음과 같이 구성합니다.

```text
드림하이츠 문의

[차량 조회]
[차량 등록]
[차량 수정]
[관리자 문의]
```

등록과 수정은 각각 별도 버튼으로 구분합니다. 요청 내용을 메시지로 받아 건물 담당자가 관리자 영역의 차량 승인에서 확인하고 처리 결과를 안내합니다. 주민용 차량 목록·신청서·승인 대기 화면이나 자동 승인 절차를 이 범위에 추가하지 않습니다.

담당자에게 관리대상 정보가 함께 전달돼야 합니다. 채널톡을 건물별 채널로 나눌지, 하나의 채널에서 상담을 배정할지는 기술 설계에서 정합니다. 어느 구성이든 다른 건물 담당자에게 문의나 주민 정보가 잘못 전달되지 않게 해야 합니다.

## 관리자 차량 관리

주민의 채널톡 요청을 처리하는 관리자 메뉴를 다음과 같이 구성합니다. 주민용 차량 화면과 구분합니다. 현재 사이드바에 그룹·하위 항목을 표시하며 업무 페이지는 아직 준비 중입니다. 배치와 경로는 [Client 관리 레이아웃](../../client/docs/managementLayout.md#메뉴별-목적지)에서 관리합니다.

```text
차량 관리
├─ 차량 내역
└─ 차량 승인
```

| 메뉴 | 처리 범위 |
| --- | --- |
| 차량 내역 | 현재 관리대상에 등록된 차량번호와 연결 동·호수 등 차량 자료 확인 |
| 차량 승인 | 채널톡으로 접수된 차량 등록·수정 요청의 내용 확인과 승인 처리 |

```text
주민이 채널톡에서 차량 등록 또는 차량 수정 선택
→ 내용을 메시지로 제출
→ 건물 담당자가 차량 승인에서 요청 확인
→ 주민·세대·차량 자료를 검토하고 승인
→ 승인된 자료를 차량 내역과 조회용 자료에 반영
→ 상담창 또는 알림으로 처리 결과 안내
```

위 흐름은 연결 설계안입니다. 채널톡 요청을 승인 목록에 자동 접수할지 담당자가 접수할지, 승인·반려·추가 확인의 상태와 결과 안내 방식은 아직 정하지 않았습니다. 상담 메시지 수신만으로 차량 자료를 자동 등록·수정하지 않습니다.

## 명부 주민의 차량 조회

차량 조회는 명부에 있는 주민을 대상으로 합니다. 다음은 주민과 관리대상 연결을 확인한 뒤 제공할 응답 예시입니다.

```text
차량번호 전체를 입력해 주세요.
→ 123가4567

등록된 차량은 102동 201호입니다.
```

정확히 일치하는 차량을 찾지 못하거나 자료가 중복되면 동·호수를 추정하지 않고 담당자 확인으로 연결하는 방안을 제안합니다. 조회는 주민에게 연결된 관리대상 안에서 수행합니다.

자동 조회에는 차량번호↔세대 대조 자료와 조회 연동이 필요합니다. 관리자 차량 내역·승인 결과와 상담 조회가 같은 유효 차량 자료를 사용하도록 설계합니다. 저장 위치, 초기 입력·가져오기와 실제 반영 방법은 아직 정하지 않았습니다. 주민의 신규 등록·수정 요청 창구는 위 채널톡 버튼을 사용합니다.

명부 연락처로 안내를 발송하는 것과 상담자를 그 명부 주민으로 확인하는 것은 다른 단계입니다. 공용 건물 링크 방문, 채널톡 상담 시작 또는 직접 입력한 전화번호만으로 주민 확인이 끝난 것으로 처리하지 않습니다.

수신자별 접근 링크를 검증한 뒤 명부 정보와 채널톡 이용자를 연결하는 방식은 검토할 설계안입니다. 사용자가 채택한 정책이나 본인 인증이 완료된 방식으로 기록하지 않습니다. 링크 전달·만료·재접속·명부 변경 시 처리와, 차량 동·호수 안내에 필요한 주민 확인 수준을 정한 뒤 연결합니다. 별도 전화번호 인증을 필수로 도입한 것은 아닙니다.

## 구현 순서 제안과 완료 기준

1. **공지 공간과 관리자 작성**: 위 [우선 기획](#공지사항-우선-기획)의 목록·상세·작성·수정·편집기와 비회원 열람을 먼저 연결하는 안을 제안합니다. 전체 공개부터 시작할지 결정하고 대상 지정 공지는 접근 정책을 정한 뒤 연결합니다.
2. **모아홈 내부 전체 발송**: 공지 게시 이후의 후속 단계로 기본 명부 전체·선택 발송, 메시지 확인, 외부 발송·결과 확인을 연결합니다. 제공 API 확인과 발신·템플릿 준비는 이 단계에서 진행합니다.
3. **건물 담당자 문의와 차량 관리**: 명부 주민 연결과 담당자 분리를 설계하고 채널톡 문의·차량 등록·수정 버튼, 관리자 차량 내역·승인을 연결합니다. 요청 접수와 승인 반영 방식은 구현 전에 정합니다.
4. **차량 자동 조회**: 차량 자료와 주민 확인 방식을 정한 뒤 승인된 관리대상 차량번호를 조회해 상담창으로 안내합니다.

2026-11-13 요청에 따라 첫 개발 묶음은 공지 화면·편집기·주민 열람을 중심으로 제안하며, 실제 발송과 담당자 문의 연결은 후속 단계로 구분합니다. 차량 자동 조회의 완료를 첫 공지 발송의 선행 조건으로 두지 않습니다. 이 순서는 구현 제안이며 일정이나 구현 완료를 의미하지 않습니다.

요청·응답·오류 계약과 저장 구조는 정책 결정 후 해당 API 문서와 [ERD](../domain/erd.md)에 반영합니다. 현재 기획만으로 새 API·테이블·Migration을 만들지 않습니다.
