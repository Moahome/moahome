# 건물별 공지와 주민 메시지 서비스 기획

기준일: 2026-11-14. 관리자 공지 관리·편집기와 주민 비로그인 목록·상세·건물 링크 발급·회수 기능을 구현했습니다. 운영 배포와 구현은 구분합니다. 확정 정책은 [도메인 규칙](../domain/domainRules.md#건물-안내와-주민-메시지의-확정-방향), 실제 요청·응답은 [공지사항 API](../api/noticeApi.md)를 따릅니다. 메시지 발송·수신자 지정·상담 연결 등 아래 후속안은 구현 완료로 취급하지 않습니다.

## 공지사항 우선 기획

### 사용자 요청과 현재 상태

2026-11-13에는 관리자 공지 목록·상세·작성·수정과 편집기 기획을 요청했습니다. 이후 구현한 기능과 후속 범위를 다음과 같이 구분합니다.

| 영역 | 2026-11-14 현재 상태 |
| --- | --- |
| 관리자 공지 관리 | 관리대상별 목록·검색·상세·작성·수정·삭제 구현. 관리자 인증 필요 |
| 작성·파일 | Tiptap 편집기, 글자 크기·RGB 색상·문단 서식, 이미지·첨부파일 구현 |
| 초안 | 사용자·관리대상·공지별 브라우저 임시저장과 불러오기·삭제, 미저장 변경 이탈 확인 구현. 서버 초안·공유 초안과 구분 |
| 권한·조회수 | 작성자 수정·본인 열람 집계 제외, 관리소장의 모든 공지 삭제 구현. 정확한 동작은 API 계약 참조 |
| 서버 저장 | notices·notice_assets·notice_access_links와 S3 파일 저장. 관리자·주민 파일 접근 분리 |
| 주민 열람 | 같은 건물의 공개 목록·상세·파일, 링크 발급·회수와 읽기 세션 구현 |
| 발송·문의 | 명부 기반 알림톡·문자 발송과 채널톡 주민 연결 미구현 |

관리자 경로는 /manage/{propertyId}/notices, 그 아래 개별 공지 상세·new·개별 공지 edit입니다. 주민용 화면은 관리자 메뉴와 별도 진입점으로 구현합니다. 저장된 공지는 같은 건물의 유효한 주민 링크에서 모두 읽을 수 있으며, 관리자 API의 인증은 유지합니다.

### 초기 문서 요청과 후속 구현

2026-11-14 사용자 요청은 일반 주민이 로그인 없이 공지를 읽고, 나중에 채널톡·알림톡 등의 링크로 접속할 수 있는 페이지를 검토하는 것입니다. 임의 URL 접근을 제한하고 접속 시 열람용 토큰을 설정하는 방식과 수신자 제한의 가능성을 문의했으며, 우선 문서 작성을 요청했습니다.

이후 사용자 결정에 따라 아래 [주민 비로그인 열람과 전용 링크](#주민-비로그인-열람과-전용-링크)의 건물 공개 목록·상세와 회수 전 재사용 정책을 구현했습니다. 수신자별 링크·기기 제한·주민 읽음 집계는 후속 범위입니다. 기존의 전화번호 인증 없는 열람 기준을 유지합니다.

## 목표와 서비스 구분

주민이 알림톡·문자의 버튼을 눌러 자기 건물의 공지를 확인하고 건물 담당자에게 문의할 수 있게 합니다. 공지 확인을 위해 모아홈 회원가입·카카오 로그인·초대코드 입력을 요구하지 않습니다.

이 기획에서 건물별 공간은 기존 관리대상인 `Property`에 연결합니다. 단지 내부의 동인 `Building`과 구분하며, 드림하이츠 링크에서는 드림하이츠에 해당하는 공지를 제공합니다.

| 영역 | 제공하는 경험 |
| --- | --- |
| 주민 안내 공간 | 건물 공지 목록·상세 확인, 메시지 문의 진입 |
| 기존 관리자 영역 | 공지 작성·공개, 명부 기반 수신 대상 선택, 알림톡·문자 발송, 차량 내역·차량 승인 |
| 채널톡 상담 | 건물 담당자 문의, 차량 조회, 차량 등록·수정 요청 |
| 후순위 로그인 주민 서비스 | 가입 승인 후 개인 관리비 등 권한이 필요한 정보 조회 |

관리자 영역과 비회원 안내 공간은 별도 접근 흐름을 사용합니다. 공지 링크 방문이나 채널톡 상담 시작으로 기존 주민 계정 연결·가입 승인·`property_members` 권한을 생성하지 않습니다.

[전체 공유·개인 지정 주민 초대](../domain/domainRules.md#주민-참여-흐름)는 카카오 로그인 계정에 권한을 연결하는 별도 기능입니다. 이 기획의 공지 발송용 수신자별 링크를 주민 초대의 일회용 수락 링크로 겸용하지 않습니다.

## 주민 비로그인 열람과 전용 링크

### 사용자 결정과 첫 구현

2026-11-14 사용자 답변으로 **같은 건물의 주민 공개 공지 목록·상세 열람**, **관리자가 회수할 때까지 링크 재사용**을 선택했습니다. 건물은 `Property`이며 `Building` 동 구분과 다릅니다. 첫 구현은 건물별 활성 링크 하나입니다. 링크 전달받은 타인도 열람할 수 있으며 특정 주민 본인 확인을 보장하지 않습니다.

| 항목 | 현재 구현 |
| --- | --- |
| 주민 화면 | 별도 `/notices` 진입, 건물 목록·공지 상세. 관리자 메뉴와 분리 |
| 열람 범위 | 해당 건물의 모든 미삭제 공지와 현재 참조된 파일 |
| 공개 동작 | 기존·새 글 모두 공개. 관리자 전용 구분·별도 공개 버튼 없음 |
| 링크 관리 | 관리자 목록에서 발급·복사·회수. 두 관리자 역할 허용 |
| 재접속 | 회수 전 링크를 다시 사용할 수 있음. 세션 만료와 링크 유효 상태를 구분 |
| 접근 차단 | 일반 URL·잘못된 링크·다른 건물·삭제된 공지·회수된 링크는 자료를 반환하지 않음 |
| 조회수 | 기존 관리자 집계와 분리. 주민 읽음·고유 인원 통계 미구현 |
| 메시지 | 주소 복사만 제공. 알림톡·문자·채널톡 자동 발송은 후속 |

### 화면에서 사용할 것과 제거한 것

사용자 시안의 주민용 목록·상세 구조를 기존 공통 컴포넌트로 구성합니다. 2026-11-14 후속 사용자 정정에 따라 별도 공지 보기 화면을 제거하고 링크에서 목록으로 바로 연결합니다. 상단 모아홈·현재 공지 메뉴·건물명과 건물 배너를 표시합니다. 목록은 검색·총 건수·제목·작성일·페이지 이동을 제공하고 중요 공지를 상단 영역에 모읍니다. 2026-11-14 후속 사용자 정정에 따라 중요 공지는 상단 중요 공지 영역에서만 표시하고 전체 공지 목록에서는 해당 글 자체를 제외합니다. 일반 공지만 페이지당 10개씩 표시하며 중요 공지와 중복하지 않습니다. 상세에는 실제 공지 제목·중요 배지·작성일·서식 본문·이미지·첨부파일을 제공합니다.

- `ListHeader`, `ListCard`, `Input`, `Button`, `DataTable`, `ListToolbar`, `Pagination`, 공통 상태·오류 표시를 재사용합니다.
- 기존 본문 편집·열람과 첨부파일 UI는 `entities/notice`로 옮겨 관리자·주민 화면이 공유합니다. 파일 요청 함수만 각 인증 흐름에 맞게 주입합니다.
- 홈·단지안내·이용안내의 미구현 탭, 번호·구분·조회수 열, 분류 배지, breadcrumb와 ‘공지 상세’ 제목, 이전·다음 글은 두지 않습니다. 건물 배너와 중요 공지 영역은 후속 정정에 맞춰 반영합니다.
- PC 상세는 `목록` 버튼, 모바일은 헤더 뒤로가기만 둡니다. 일정 안내 상자는 작성한 본문 서식이며 별도 일정 필드를 추가하지 않습니다.

### 열람 흐름

~~~text
관리자가 공지 저장(기존·새 공지 모두 주민 열람 가능)
→ 관리자가 건물 링크 발급·복사
→ 주민에게 링크 전달(현재 자동 발송 연동 없음)
→ 주민이 링크를 열면 브라우저에서 자동으로 읽기 세션 교환
→ 서버가 링크를 검증하고 별도 읽기 세션 발급
→ 같은 건물의 공개 목록·상세·파일 열람
→ 링크 회수·공지 삭제 시 이후 요청 차단
~~~

GET·공유 미리보기로 링크를 소비하거나 조회수를 올리지 않습니다. 링크 토큰은 URL fragment에서 메모리로 옮긴 뒤 주소에서 제거하며 웹 저장소에 보관하지 않습니다. 읽기 세션은 관리자 로그인 쿠키와 분리합니다. 계정 가입·주민 승인·관리 권한을 만들지 않습니다. 수명·오류·재시도는 [API 계약](../api/noticeApi.md#주민-읽기-api), 화면 처리는 [Client 문서](../../client/docs/residentNotices.md), 저장·잠금은 [Server 문서](../../server/docs/residentNotices.md)를 따릅니다.

### 후속 결정과 미구현 범위

수신자별 링크·대상 지정 공지, 발송 서비스·템플릿, 주민별 읽음 확인, 유휴 만료·기기 고정, 엣지 요청 제한과 이상 접근 탐지·보존 기간은 후속 검토입니다. 첫 구현을 명부 수신자 본인 확인이나 대량 시도 방어의 적용 완료로 기록하지 않습니다. 2026-11-14 후속 사용자 요청으로 공지 상세에는 작성자의 표시 이름을 제공합니다. 그 밖의 개인정보·개인 관리비·주민 명부·차량 자료는 주민 공지 공간에 공개하지 않는 기존 기준을 유지합니다.


## 관리자 작성과 발송 흐름

```text
관리대상 선택
→ 전체 공지 또는 대상 지정 공지 작성
→ 미리보기·공개
→ 주민에게 알리기
→ 수신 대상·메시지·공지 링크 확인
→ 모아홈에서 발송 요청
→ 수신자별 결과 확인
```

수신 대상의 기본 선택은 현재 관리대상 명부 전체입니다. 관리자가 그 명부 안에서 수신 대상을 선택할 수 있게 합니다. 모아홈 가입 여부와 채널톡 상담 이력을 발송 대상의 전제 조건으로 두지 않습니다.

다음은 발송 화면과 처리의 설계안입니다.

| 처리 | 설계안 |
| --- | --- |
| 공지 공개와 발송 | 별도 동작으로 처리해 공지 수정만으로 다시 발송되지 않게 함 |
| 수신 대상 확인 | 선택 인원·실제 수신 번호 수·연락처 누락 인원을 구분 |
| 중복 번호 | 같은 발송에서 같은 번호로 중복 전송하지 않도록 처리 |
| 발송 결과 | 수신자별 요청·성공·실패를 구분하고 제공자가 반환하는 실패 사유 확인 |
| 재발송 | 결과가 확인된 실패 대상에 대해 선택적으로 처리하며 결과 미확인 건은 중복 발송 여부를 먼저 확인 |
| 발송 이력 | 누가 어느 관리대상에서 어떤 내용과 대상으로 요청했는지 추적 |

관리소장과 동대표의 발송 기능은 기존 주민 명부 전체 열람·연락처 원문 공개 권한과 별개입니다. 동대표의 명부 열람·수정 권한은 [관리자 업무 권한](../domain/domainRules.md#관리자-업무-권한-2026-10-24-최종-정정)을 따릅니다. 발송에 필요한 수신 대상 선택용 정보와 공통 API를 따로 설계하고, 발송 기능 때문에 기존 명부 열람 권한을 변경하지 않습니다.

문자·알림톡은 외부 발송 서비스를 통해 전달하되 주민 대상 선택과 발송 요청의 사용자 흐름은 모아홈 안에서 제공합니다. 초기 운영을 채널톡 관리자 화면의 수동 발송으로 대신하는 것은 현재 요구 범위에 맞지 않습니다.

## 건물 담당자 메시지 문의

```text
드림하이츠 안내 공간에서 문의 선택
→ 드림하이츠 문의 메뉴 진입
→ 상담 목적 선택
→ 드림하이츠 담당자에게 전달
```

채널톡 문의 메뉴는 다음과 같이 구성합니다.

```text
드림하이츠 문의

[차량 조회]
[차량 등록]
[차량 수정]
[관리자 문의]
```

등록과 수정은 각각 별도 버튼으로 구분합니다. 요청 내용을 메시지로 받아 건물 담당자가 관리자 영역의 차량 승인에서 확인하고 처리 결과를 안내합니다. 주민용 차량 목록·신청서·승인 대기 화면이나 자동 승인 절차를 이 범위에 추가하지 않습니다.

담당자에게 관리대상 정보가 함께 전달돼야 합니다. 채널톡을 건물별 채널로 나눌지, 하나의 채널에서 상담을 배정할지는 기술 설계에서 정합니다. 어느 구성이든 다른 건물 담당자에게 문의나 주민 정보가 잘못 전달되지 않게 해야 합니다.

## 관리자 차량 관리

주민의 채널톡 요청을 처리하는 관리자 메뉴를 다음과 같이 구성합니다. 주민용 차량 화면과 구분합니다. 현재 사이드바에 그룹·하위 항목을 표시하며 업무 페이지는 아직 준비 중입니다. 배치와 경로는 [Client 관리 레이아웃](../../client/docs/managementLayout.md#메뉴별-목적지)에서 관리합니다.

```text
차량 관리
├─ 차량 내역
└─ 차량 승인
```

| 메뉴 | 처리 범위 |
| --- | --- |
| 차량 내역 | 현재 관리대상에 등록된 차량번호와 연결 동·호수 등 차량 자료 확인 |
| 차량 승인 | 채널톡으로 접수된 차량 등록·수정 요청의 내용 확인과 승인 처리 |

```text
주민이 채널톡에서 차량 등록 또는 차량 수정 선택
→ 내용을 메시지로 제출
→ 건물 담당자가 차량 승인에서 요청 확인
→ 주민·세대·차량 자료를 검토하고 승인
→ 승인된 자료를 차량 내역과 조회용 자료에 반영
→ 상담창 또는 알림으로 처리 결과 안내
```

위 흐름은 연결 설계안입니다. 채널톡 요청을 승인 목록에 자동 접수할지 담당자가 접수할지, 승인·반려·추가 확인의 상태와 결과 안내 방식은 아직 정하지 않았습니다. 상담 메시지 수신만으로 차량 자료를 자동 등록·수정하지 않습니다.

## 명부 주민의 차량 조회

차량 조회는 명부에 있는 주민을 대상으로 합니다. 다음은 주민과 관리대상 연결을 확인한 뒤 제공할 응답 예시입니다.

```text
차량번호 전체를 입력해 주세요.
→ 123가4567

등록된 차량은 102동 201호입니다.
```

정확히 일치하는 차량을 찾지 못하거나 자료가 중복되면 동·호수를 추정하지 않고 담당자 확인으로 연결하는 방안을 제안합니다. 조회는 주민에게 연결된 관리대상 안에서 수행합니다.

자동 조회에는 차량번호↔세대 대조 자료와 조회 연동이 필요합니다. 관리자 차량 내역·승인 결과와 상담 조회가 같은 유효 차량 자료를 사용하도록 설계합니다. 저장 위치, 초기 입력·가져오기와 실제 반영 방법은 아직 정하지 않았습니다. 주민의 신규 등록·수정 요청 창구는 위 채널톡 버튼을 사용합니다.

명부 연락처로 안내를 발송하는 것과 상담자를 그 명부 주민으로 확인하는 것은 다른 단계입니다. 공용 건물 링크 방문, 채널톡 상담 시작 또는 직접 입력한 전화번호만으로 주민 확인이 끝난 것으로 처리하지 않습니다.

수신자별 접근 링크를 검증한 뒤 명부 정보와 채널톡 이용자를 연결하는 방식은 검토할 설계안입니다. 사용자가 채택한 정책이나 본인 인증이 완료된 방식으로 기록하지 않습니다. 링크 전달·만료·재접속·명부 변경 시 처리와, 차량 동·호수 안내에 필요한 주민 확인 수준을 정한 뒤 연결합니다. 별도 전화번호 인증을 필수로 도입한 것은 아닙니다.

| 연결 | 확인할 내용 |

| 알림톡 템플릿 | 건물명·공지 내용·상세 링크 구성의 검수, 변수·버튼의 허용 범위 |
| 문자 대체 | 알림톡 실패 시 자동 대체 여부와 중복 전송 방지 |
| 채널톡 이용자 연결 | 명부 주민과 상담자의 연결 방법, 건물별 담당자 접근 범위 |

채널톡은 웹 SDK에서 익명 이용자와 서비스가 식별정보를 연결한 이용자를 구분합니다. 식별정보를 전달할 때는 서버 검증과 member hash 등 해당 서비스의 보호 방식을 함께 설계합니다. [공식 웹 SDK 안내](https://developers.channel.io/en/articles/Quickstart-d27c51d1)

워크플로우의 입력폼은 외부 메신저에서 동작하지 않습니다. 웹 채널톡과 카카오 상담톡을 함께 지원한다면 메시지로 번호를 받는 공통 흐름을 검토합니다. 외부 API 호출은 ALF 태스크의 커스텀 함수 등 지원 방식과 이용 조건을 확인해야 하며, 질문지 추가만으로 모아홈 자료 조회가 연결되지는 않습니다. [워크플로우 안내](https://docs.channel.io/help/ko/articles/워크플로우-FAQ-0907d9ff), [커스텀 함수 안내](https://docs.channel.io/help/ko/articles/커스텀-함수-0d5fc628)

알림톡은 승인받은 정보성 템플릿으로 발송합니다. 템플릿 검토와 외부 서비스 설정은 화면 구현과 함께 진행할 준비 항목입니다. [알림톡 안내](https://docs.channel.io/help/ko/articles/9747de9a)

## 구현 순서 제안과 완료 기준

1. **주민 열람 접근 정책과 화면**: 건물 공개 목록·상세·링크 발급·회수·읽기 세션·파일 접근 검사를 구현했습니다. 운영 반영 여부는 배포 이력으로 확인합니다. 수신자 지정·읽음 집계는 후속 범위입니다.
2. **모아홈 내부 전체 발송**: 공지 게시 이후의 후속 단계로 기본 명부 전체·선택 발송, 메시지 확인, 외부 발송·결과 확인을 연결합니다. 제공 API 확인과 발신·템플릿 준비는 이 단계에서 진행합니다.
3. **건물 담당자 문의와 차량 관리**: 명부 주민 연결과 담당자 분리를 설계하고 채널톡 문의·차량 등록·수정 버튼, 관리자 차량 내역·승인을 연결합니다. 요청 접수와 승인 반영 방식은 구현 전에 정합니다.
4. **차량 자동 조회**: 차량 자료와 주민 확인 방식을 정한 뒤 승인된 관리대상 차량번호를 조회해 상담창으로 안내합니다.

2026-11-14 현재 주민 비로그인 열람의 첫 구현을 추가했으며, 실제 발송과 담당자 문의 연결은 후속 단계로 구분합니다. 차량 자동 조회의 완료를 첫 공지 발송의 선행 조건으로 두지 않습니다. 후속 단계의 순서는 제안이며 일정이나 미구현 기능의 완료를 의미하지 않습니다.

요청·응답·오류 계약과 저장 구조는 정책 결정 후 해당 API 문서와 [ERD](../domain/erd.md)에 반영합니다. 현재 기획만으로 새 API·테이블·Migration을 만들지 않습니다.
