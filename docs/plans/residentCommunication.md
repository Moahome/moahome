# 건물별 공지와 주민 메시지 서비스 기획

기준일: 2026-11-14. 관리자 공지 관리와 편집기는 구현했으며, 주민의 비로그인 공지 열람·전용 링크·메시지 발송·상담 연결은 후속 기획입니다. 확정 정책은 [도메인 규칙](../domain/domainRules.md#건물-안내와-주민-메시지의-확정-방향), 관리자 기능의 실제 구현 계약은 [공지사항 API](../api/noticeApi.md)를 따릅니다. 아래 주민 접근 방식은 설계안이며 문서 작성만으로 채택·구현·배포된 것으로 취급하지 않습니다.

## 공지사항 우선 기획

### 사용자 요청과 현재 상태

2026-11-13에는 관리자 공지 목록·상세·작성·수정과 편집기 기획을 요청했습니다. 이후 구현한 기능과 후속 범위를 다음과 같이 구분합니다.

| 영역 | 2026-11-14 현재 상태 |
| --- | --- |
| 관리자 공지 관리 | 관리대상별 목록·검색·상세·작성·수정·삭제 구현. 관리자 인증 필요 |
| 작성·파일 | Tiptap 편집기, 글자 크기·RGB 색상·문단 서식, 이미지·첨부파일 구현 |
| 초안 | 사용자·관리대상·공지별 브라우저 임시저장과 불러오기·삭제, 미저장 변경 이탈 확인 구현. 서버 초안·공유 초안과 구분 |
| 권한·조회수 | 작성자 수정·본인 열람 집계 제외, 관리소장의 모든 공지 삭제 구현. 정확한 동작은 API 계약 참조 |
| 서버 저장 | notices·notice_assets와 S3 파일 저장 구현. 파일도 현재 관리자 권한으로 보호 |
| 주민 열람 | 로그인 없는 주민용 화면·열람 링크·전용 세션 미구현 |
| 발송·문의 | 명부 기반 알림톡·문자 발송과 채널톡 주민 연결 미구현 |

관리자 경로는 /manage/{propertyId}/notices, 그 아래 개별 공지 상세·new·개별 공지 edit입니다. 주민용 화면은 관리자 메뉴와 별도 진입점으로 설계합니다. 관리자 글 저장을 비회원 공개로 간주하거나 기존 관리자 API의 인증을 해제하지 않습니다.

### 이번 문서 기획의 범위

2026-11-14 사용자 요청은 일반 주민이 로그인 없이 공지를 읽고, 나중에 채널톡·알림톡 등의 링크로 접속할 수 있는 페이지를 검토하는 것입니다. 임의 URL 접근을 제한하고 접속 시 열람용 토큰을 설정하는 방식과 수신자 제한의 가능성을 문의했으며, 우선 문서 작성을 요청했습니다.

이번에는 아래 [주민 비로그인 열람과 전용 링크](#주민-비로그인-열람과-전용-링크) 설계와 미정 정책을 정리합니다. 주민별 링크, 토큰 수명·재사용·기기 제한과 조회수 집계 방식은 아직 확정하지 않았습니다. 기존의 전화번호 인증 없는 열람 기준을 유지하며 문자 인증은 강화 대안으로만 기록합니다.

## 목표와 서비스 구분

주민이 알림톡·문자의 버튼을 눌러 자기 건물의 공지를 확인하고 건물 담당자에게 문의할 수 있게 합니다. 공지 확인을 위해 모아홈 회원가입·카카오 로그인·초대코드 입력을 요구하지 않습니다.

이 기획에서 건물별 공간은 기존 관리대상인 `Property`에 연결합니다. 단지 내부의 동인 `Building`과 구분하며, 드림하이츠 링크에서는 드림하이츠에 해당하는 공지를 제공합니다.

| 영역 | 제공하는 경험 |
| --- | --- |
| 주민 안내 공간 | 건물 공지 목록·상세 확인, 메시지 문의 진입 |
| 기존 관리자 영역 | 공지 작성·공개, 명부 기반 수신 대상 선택, 알림톡·문자 발송, 차량 내역·차량 승인 |
| 채널톡 상담 | 건물 담당자 문의, 차량 조회, 차량 등록·수정 요청 |
| 후순위 로그인 주민 서비스 | 가입 승인 후 개인 관리비 등 권한이 필요한 정보 조회 |

관리자 영역과 비회원 안내 공간은 별도 접근 흐름을 사용합니다. 공지 링크 방문이나 채널톡 상담 시작으로 기존 주민 계정 연결·가입 승인·`property_members` 권한을 생성하지 않습니다.

[전체 공유·개인 지정 주민 초대](../domain/domainRules.md#주민-참여-흐름)는 카카오 로그인 계정에 권한을 연결하는 별도 기능입니다. 이 기획의 공지 발송용 수신자별 링크를 주민 초대의 일회용 수락 링크로 겸용하지 않습니다.

## 주민 비로그인 열람과 전용 링크

### 주민 화면과 접근 범위

제안하는 첫 화면은 휴대폰에서 읽기 편한 공지 상세입니다. 건물명·제목·게시 시각·서식 있는 본문·허용된 이미지와 첨부파일을 제공하고 관리자 메뉴·작성·수정·삭제 기능은 제공하지 않습니다. 작성자 표시명 등 주민 응답의 정확한 필드는 구현 계약에서 정합니다.

공지 하나의 링크로 해당 공지만 허용하는 안을 우선 검토합니다. 같은 건물의 공지 목록 이동은 별도 범위 결정이 필요하며, 개별 공지 링크가 있다는 이유로 전체 목록이나 다른 주민 대상 공지를 열어주지 않습니다. 목록을 제공할 때도 서버가 현재 열람 범위에 포함되는 항목만 반환해야 합니다.

| 구분 | 제안과 보장 범위 |
| --- | --- |
| 링크 없이 일반 주소로 접속 | 화면 틀·일반 안내만 제공. 본문·첨부파일·제한된 공지 목록은 반환하지 않음 |
| 유효한 전용 링크로 접속 | 링크에 정한 관리대상·공지 범위의 읽기 권한만 발급 |
| 발송받은 주민 본인 확인 | 링크만으로는 보장할 수 없음. 전달받은 타인도 링크를 사용할 수 있음 |
| 기존 관리자·주민 계정 | 링크 방문으로 계정 가입·주민 승인·관리 권한을 생성하거나 기존 로그인 세션을 대체하지 않음 |

기존 /p/{건물식별자}는 주소 예시입니다. 실제 화면 경로와 링크 토큰 전달 위치는 아직 정하지 않았으며, 건물 ID·공지 ID나 주소를 숨기는 것만으로 접근을 허용하지 않습니다.

### 제안하는 열람 흐름

~~~text
관리자가 주민에게 공개할 공지와 열람 범위를 확인
→ 서버가 수신자별·공지별 전용 링크 발급
→ 메시지로 링크 전달
→ 주민이 열람 진입 화면에서 공지 보기 선택
→ 서버가 링크의 유효성·만료·차단·공지 공개 상태 검증
→ 통과한 브라우저에 공지 읽기 전용 세션 발급
→ 권한을 검사하며 본문·이미지·첨부파일 열람
~~~

수신자별 링크는 발급·회수할 대상을 구분하는 설계안이며 주민 본인 인증 수단은 아닙니다. 연락처 없는 주민, 한 번호를 공유하는 주민과 한 번에 여러 공지를 안내할 때의 링크 발급 단위는 별도 결정합니다. 링크 발급만 준비하는 단계와 실제 메시지 발송 연동은 나눌 수 있으며, 관리자의 수동 전달을 초기 운영으로 채택할지는 미정입니다.

### 링크 토큰과 열람 세션

링크 토큰은 입장 자격을 확인하는 값이고, 열람 세션은 검증을 통과한 브라우저의 이후 요청을 확인하는 값으로 분리하는 안을 제안합니다. 접속한 누구에게나 열람 세션을 발급하면 임의 URL 접근을 막을 수 없으므로 반드시 유효한 링크 또는 기존 유효 열람 세션을 먼저 확인합니다. 새로고침마다 새로운 권한을 만들지 않고 세션을 검증해 재사용하는 안입니다.

| 항목 | 구현 설계안 |
| --- | --- |
| 링크 토큰 | 암호학적으로 안전한 난수 사용. 주민 이름·전화번호·차량번호를 URL이나 토큰 내용에 넣지 않음 |
| 서버 저장 | 링크 원문 대신 해시와 관리대상·열람 범위·만료·회수 여부 등을 저장하는 안. 테이블·컬럼은 미확정 |
| 열람 세션 | 링크 검증 후 서버에서 별도 발급. 기존 계정 인증과 구분되는 Secure·HttpOnly 쿠키와 서버 검증 사용 |
| 매 요청 검사 | 관리대상·허용 공지·공개 및 삭제 상태·링크 회수·세션 만료를 서버에서 확인. 화면 버튼 숨김만으로 보호하지 않음 |
| 파일 | 본문과 같은 열람 범위를 적용. 자산 ID나 S3 주소만 알면 파일을 읽을 수 있게 만들지 않음 |
| 종료 | 링크 회수·공지 삭제·주민 공개 중단 시 이미 발급한 열람 세션의 본문·파일 접근도 차단하는 안 |

열람 전의 공지 공개 조건은 아직 정하지 않았습니다. 현재 관리자 저장 모델의 존재·삭제 여부만으로 주민 공개를 자동 허용하지 않고, 공개 여부와 링크 발급 조건을 먼저 결정해야 합니다.

쿠키를 지운 경우, 카카오 인앱 브라우저와 외부 브라우저 사이 이동, 다른 기기에서의 재접속은 새 브라우저로 취급될 수 있습니다. 첫 기기에 링크를 묶으면 정상 주민의 재열람이 막히거나 타인이 먼저 연 링크를 본인이 못 열 수 있으므로 기기 고정을 기본 보안 정책으로 확정하지 않습니다.

### 링크 전달과 주민 확인의 한계

| 방식 | 이용 경험과 한계 |
| --- | --- |
| 전용 링크만 사용 | 로그인·전화번호 인증 없이 열람 가능. 임의 주소 추측을 제한하고 링크를 만료·회수할 수 있으나 전달받은 타인을 구별할 수 없음 |
| 전용 링크와 문자 인증 | 수신 번호에 대한 추가 확인 가능. 기존의 전화번호 인증 없는 열람 정책 변경과 인증 비용·재인증 기준 결정 필요 |
| 첫 브라우저에 고정 | 이후 다른 브라우저의 사용을 제한할 수 있으나 최초 방문자가 지정 주민이라는 증거는 되지 않음 |

첫 단계는 개인정보 없는 일반 공지에 전용 링크를 쓰는 안을 검토합니다. 이는 제안이며 사용자가 수신자별 링크 방식을 확정했다는 뜻은 아닙니다. 관리비 개인 내역·명부·차량 자료는 기존 비회원 공개 금지 기준을 유지하고, 열람 세션을 차량 상담자의 주민 확인으로 재사용하지 않습니다.

### 미리보기·주소 노출·재시도

- 메시지의 링크 미리보기·보안 검사 요청과 실제 주민 열람을 구분합니다. 최초 GET만으로 일회용 링크를 소비하거나 조회수·주민 읽음으로 집계하지 않는 안을 제안합니다. 미리보기에는 제한된 제목·본문·파일을 노출하지 않습니다.
- 링크 진입 후 명시적인 열람 요청으로 검증·세션 발급을 수행하는 안입니다. 세션 발급 요청의 허용 Origin·CSRF 보호와 재시도 계약은 기존 로그인 쿠키와 구분해 정합니다.
- URL·접근 로그·오류 추적·분석 도구·외부 문의 이동에 링크 원문이 남지 않게 설계합니다. 토큰 검증 후 주소 정리, Referrer-Policy: no-referrer, 비공개 응답의 Cache-Control: no-store를 검토합니다. 검색 제외 표시나 주소 정리는 서버 접근 검사를 대신하지 않습니다.
- 토큰을 URL fragment로 전달하는 안도 후보이며, 브라우저 이력·스크립트 노출까지 방지하는 수단은 아닙니다. 실제 알림톡·채널톡·문자 서비스의 버튼과 인앱 브라우저에서 토큰이 보존되는지 확인한 뒤 전달 형식을 정합니다.
- 추측·대량 시도는 요청 제한으로 방어하고, 다른 공지나 관리대상 ID로 바꾼 요청은 거부합니다. 실패 화면은 특정 주민의 존재·전화번호·공개되지 않은 공지 내용을 드러내지 않습니다.
- 세션 발급의 응답 유실을 권한 발급 실패로 단정하지 않습니다. 재시도에서 기존 결과를 확인할 방법을 API 계약에 정합니다. 일회용 링크를 채택한다면 동시 소비와 발급 응답 유실의 복구 방법까지 결정한 뒤 구현합니다.
- 링크 재발급·회수 요청도 중복 클릭과 응답 유실을 고려합니다. 동일 요청 재시도로 링크를 계속 새로 만들거나 의도하지 않은 이전 링크 회수가 반복되지 않게 계약을 정합니다.
- 해시만으로 이미 발급한 링크 원문을 복원할 수는 없습니다. 발급 응답 유실·메시지 재전송에 필요한 원문의 보호·보관 수단 또는 안전한 재발급 방식을 정해야 하며, 해시 저장만으로 동일 링크 재전송까지 구현됐다고 가정하지 않습니다.

### 조회수와 읽음 확인

현재 관리자 조회수의 작성자 제외 규칙은 [공지사항 API](../api/noticeApi.md#저장과-재시도)를 유지합니다. 비회원 열람을 현재 관리자 상세 GET에 단순 연결하면 조회수 증가와 인증이 섞이므로 별도 권한·집계 계약이 필요합니다.

권장안은 열람 세션 안에서 공지당 한 번만 집계하고, 미리보기·파일 요청·세션 발급·동일 요청 재시도는 조회수에서 제외하는 것입니다. 세션·브라우저 기준 횟수와 실제 주민 수·읽음 확인을 구분합니다. 비로그인 상태에서는 작성자 본인 여부도 항상 확인할 수 없으므로 작성자 제외의 판정 방법과 주민 열람을 기존 조회수에 합산할지는 미정으로 둡니다. 수신자 링크가 열렸다는 기록을 해당 주민 본인의 읽음으로 표시하지 않습니다.

### 구현 전에 결정할 열람 정책

| 결정 항목 | 남은 질문 |
| --- | --- |
| 링크 방식 | 공통 링크와 수신자별 링크 중 어떤 방식을 채택할지, 동일 수신 번호의 발급 단위 |
| 열람 범위 | 개별 공지만 열지, 건물 전체·일부 공지 목록까지 허용할지 |
| 공개 기준 | 기존 공지의 주민 공개를 어떤 동작·상태로 허용하고 중단할지 |
| 유효기간 | 링크 만료, 세션의 유휴·절대 만료와 공지 공개 기간을 어떻게 구분할지 |
| 재접속 | 링크를 재사용할지 일회용으로 할지, 기기 변경·쿠키 삭제 시 복구 방법 |
| 재발급·회수 | 새 링크 발급 시 이전 링크·기존 세션을 언제 종료할지 |
| 명부 변경 | 퇴거·주민 삭제·전화번호 변경이 이미 발급한 링크에 미치는 영향 |
| 집계 | 익명 작성자 열람·같은 세션의 반복 열람·조회수 합산과 보존 기준 |
| 주민 확인 강화 | 링크 전달의 한계를 수용할지, 기존 기준을 바꿔 별도 확인을 추가할지 |

정책 결정 후 관련 요청·응답·오류·중복 처리 계약은 기존 공지사항 API 문서에 함께 추가합니다. 화면·토큰 수명은 Client 문서, 저장·트랜잭션·동시 소비 처리는 Server 문서에서 계약을 참조하도록 작성합니다. 현재 문서 기획만으로 새 API·테이블·Migration을 추가하지 않습니다.

검증은 링크 없는 요청·범위 위반·만료/회수와 파일 우회 접근, 세션 재시도·미리보기 집계 제외를 대표 흐름으로 확인하는 방향입니다. 기존 권한·재시도 검사와 합칠 수 있는 항목을 우선 재사용하고 동일 업무를 화면 폭만 바꿔 반복 추가하지 않습니다.

기술 검토 참고: [OWASP URL 토큰 보안](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), [OWASP 세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). 비밀번호 재설정 토큰의 일회용 정책을 공지 링크의 확정 정책으로 그대로 적용하지 않습니다.

## 관리자 작성과 발송 흐름

```text
관리대상 선택
→ 전체 공지 또는 대상 지정 공지 작성
→ 미리보기·공개
→ 주민에게 알리기
→ 수신 대상·메시지·공지 링크 확인
→ 모아홈에서 발송 요청
→ 수신자별 결과 확인
```

수신 대상의 기본 선택은 현재 관리대상 명부 전체입니다. 관리자가 그 명부 안에서 수신 대상을 선택할 수 있게 합니다. 모아홈 가입 여부와 채널톡 상담 이력을 발송 대상의 전제 조건으로 두지 않습니다.

다음은 발송 화면과 처리의 설계안입니다.

| 처리 | 설계안 |
| --- | --- |
| 공지 공개와 발송 | 별도 동작으로 처리해 공지 수정만으로 다시 발송되지 않게 함 |
| 수신 대상 확인 | 선택 인원·실제 수신 번호 수·연락처 누락 인원을 구분 |
| 중복 번호 | 같은 발송에서 같은 번호로 중복 전송하지 않도록 처리 |
| 발송 결과 | 수신자별 요청·성공·실패를 구분하고 제공자가 반환하는 실패 사유 확인 |
| 재발송 | 결과가 확인된 실패 대상에 대해 선택적으로 처리하며 결과 미확인 건은 중복 발송 여부를 먼저 확인 |
| 발송 이력 | 누가 어느 관리대상에서 어떤 내용과 대상으로 요청했는지 추적 |

관리소장과 동대표의 발송 기능은 기존 주민 명부 전체 열람·연락처 원문 공개 권한과 별개입니다. 동대표의 명부 열람·수정 권한은 [관리자 업무 권한](../domain/domainRules.md#관리자-업무-권한-2026-10-24-최종-정정)을 따릅니다. 발송에 필요한 수신 대상 선택용 정보와 공통 API를 따로 설계하고, 발송 기능 때문에 기존 명부 열람 권한을 변경하지 않습니다.

문자·알림톡은 외부 발송 서비스를 통해 전달하되 주민 대상 선택과 발송 요청의 사용자 흐름은 모아홈 안에서 제공합니다. 초기 운영을 채널톡 관리자 화면의 수동 발송으로 대신하는 것은 현재 요구 범위에 맞지 않습니다.

## 건물 담당자 메시지 문의

```text
드림하이츠 안내 공간에서 문의 선택
→ 드림하이츠 문의 메뉴 진입
→ 상담 목적 선택
→ 드림하이츠 담당자에게 전달
```

채널톡 문의 메뉴는 다음과 같이 구성합니다.

```text
드림하이츠 문의

[차량 조회]
[차량 등록]
[차량 수정]
[관리자 문의]
```

등록과 수정은 각각 별도 버튼으로 구분합니다. 요청 내용을 메시지로 받아 건물 담당자가 관리자 영역의 차량 승인에서 확인하고 처리 결과를 안내합니다. 주민용 차량 목록·신청서·승인 대기 화면이나 자동 승인 절차를 이 범위에 추가하지 않습니다.

담당자에게 관리대상 정보가 함께 전달돼야 합니다. 채널톡을 건물별 채널로 나눌지, 하나의 채널에서 상담을 배정할지는 기술 설계에서 정합니다. 어느 구성이든 다른 건물 담당자에게 문의나 주민 정보가 잘못 전달되지 않게 해야 합니다.

## 관리자 차량 관리

주민의 채널톡 요청을 처리하는 관리자 메뉴를 다음과 같이 구성합니다. 주민용 차량 화면과 구분합니다. 현재 사이드바에 그룹·하위 항목을 표시하며 업무 페이지는 아직 준비 중입니다. 배치와 경로는 [Client 관리 레이아웃](../../client/docs/managementLayout.md#메뉴별-목적지)에서 관리합니다.

```text
차량 관리
├─ 차량 내역
└─ 차량 승인
```

| 메뉴 | 처리 범위 |
| --- | --- |
| 차량 내역 | 현재 관리대상에 등록된 차량번호와 연결 동·호수 등 차량 자료 확인 |
| 차량 승인 | 채널톡으로 접수된 차량 등록·수정 요청의 내용 확인과 승인 처리 |

```text
주민이 채널톡에서 차량 등록 또는 차량 수정 선택
→ 내용을 메시지로 제출
→ 건물 담당자가 차량 승인에서 요청 확인
→ 주민·세대·차량 자료를 검토하고 승인
→ 승인된 자료를 차량 내역과 조회용 자료에 반영
→ 상담창 또는 알림으로 처리 결과 안내
```

위 흐름은 연결 설계안입니다. 채널톡 요청을 승인 목록에 자동 접수할지 담당자가 접수할지, 승인·반려·추가 확인의 상태와 결과 안내 방식은 아직 정하지 않았습니다. 상담 메시지 수신만으로 차량 자료를 자동 등록·수정하지 않습니다.

## 명부 주민의 차량 조회

차량 조회는 명부에 있는 주민을 대상으로 합니다. 다음은 주민과 관리대상 연결을 확인한 뒤 제공할 응답 예시입니다.

```text
차량번호 전체를 입력해 주세요.
→ 123가4567

등록된 차량은 102동 201호입니다.
```

정확히 일치하는 차량을 찾지 못하거나 자료가 중복되면 동·호수를 추정하지 않고 담당자 확인으로 연결하는 방안을 제안합니다. 조회는 주민에게 연결된 관리대상 안에서 수행합니다.

자동 조회에는 차량번호↔세대 대조 자료와 조회 연동이 필요합니다. 관리자 차량 내역·승인 결과와 상담 조회가 같은 유효 차량 자료를 사용하도록 설계합니다. 저장 위치, 초기 입력·가져오기와 실제 반영 방법은 아직 정하지 않았습니다. 주민의 신규 등록·수정 요청 창구는 위 채널톡 버튼을 사용합니다.

명부 연락처로 안내를 발송하는 것과 상담자를 그 명부 주민으로 확인하는 것은 다른 단계입니다. 공용 건물 링크 방문, 채널톡 상담 시작 또는 직접 입력한 전화번호만으로 주민 확인이 끝난 것으로 처리하지 않습니다.

수신자별 접근 링크를 검증한 뒤 명부 정보와 채널톡 이용자를 연결하는 방식은 검토할 설계안입니다. 사용자가 채택한 정책이나 본인 인증이 완료된 방식으로 기록하지 않습니다. 링크 전달·만료·재접속·명부 변경 시 처리와, 차량 동·호수 안내에 필요한 주민 확인 수준을 정한 뒤 연결합니다. 별도 전화번호 인증을 필수로 도입한 것은 아닙니다.

## 구현 순서 제안과 완료 기준

1. **주민 열람 접근 정책과 화면**: 관리자 공지 관리·편집기는 구현한 상태입니다. 위 [전용 링크 설계](#주민-비로그인-열람과-전용-링크)의 미정 정책을 결정한 뒤 주민용 상세·링크 발급·열람 세션·파일 접근 검사를 연결하는 안을 제안합니다. 건물 목록은 열람 범위 결정 후 연결합니다.
2. **모아홈 내부 전체 발송**: 공지 게시 이후의 후속 단계로 기본 명부 전체·선택 발송, 메시지 확인, 외부 발송·결과 확인을 연결합니다. 제공 API 확인과 발신·템플릿 준비는 이 단계에서 진행합니다.
3. **건물 담당자 문의와 차량 관리**: 명부 주민 연결과 담당자 분리를 설계하고 채널톡 문의·차량 등록·수정 버튼, 관리자 차량 내역·승인을 연결합니다. 요청 접수와 승인 반영 방식은 구현 전에 정합니다.
4. **차량 자동 조회**: 차량 자료와 주민 확인 방식을 정한 뒤 승인된 관리대상 차량번호를 조회해 상담창으로 안내합니다.

2026-11-14 현재 다음 개발 묶음은 주민 비로그인 열람으로 제안하며, 실제 발송과 담당자 문의 연결은 후속 단계로 구분합니다. 차량 자동 조회의 완료를 첫 공지 발송의 선행 조건으로 두지 않습니다. 이 순서는 구현 제안이며 일정이나 구현 완료를 의미하지 않습니다.

요청·응답·오류 계약과 저장 구조는 정책 결정 후 해당 API 문서와 [ERD](../domain/erd.md)에 반영합니다. 현재 기획만으로 새 API·테이블·Migration을 만들지 않습니다.
