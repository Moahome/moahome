# 회계·정산과 손익계산서 추가 기획

기준일: 2026-11-07. 상태: **개발 범위·기본 처리 기준 확정, 기본 과목·코드 확정 및 저장·비용 선택·손익 연결 구현, 정식 자동전표·원장은 미구현**.

사용자는 기존 관리비 부과·수납·지출을 연결한 손익계산서와 월별·연간 조회를 이번 개발 대상으로 정하고 제시한 권장안을 승인했습니다. 후속 요청으로 메뉴를 우선 구현했습니다. 기존 월별 정산은 이름·Client 경로만 이동했습니다. 손익계산서는 후속 요청으로 기간·동 조회·표·그래프·Excel/PDF/PNG에 실제 확정 청구·지출과 관리자 분류 저장을 연결했고, 계정별 원장은 2026-11-07 통장·미수·선수금·손익 원천별 조회·기간 누계·원본 상세·다운로드를 연결했고 계정과목 설정에는 과목 조회·추가·수정·중지·재개·미사용 삭제를 연결했습니다. 구현한 [손익 API](../api/incomeStatementApi.md)·분류 저장과 정식 자동전표·연간 회계·마감을 구분합니다.

계정과목의 범용 구성·관리 원칙과 발생 기준 손익·권한·이번 메뉴 및 개발 범위는 **사용자 확정**입니다. 기준 문서는 [회계 도메인 규칙](../domain/domainRules.md#9-회계)입니다. 2026-11-05 요청의 기본 과목·코드 범위를 반영하고 개별 번호를 확정하고 기본 계정 저장·기존 거래의 비용 분류·손익 연결을 구현했습니다. 정식 통장 분개·원장은 후속입니다. 추가 계정·기초 잔액 등 실제 확인 자료와 예외별 상세 처리는 여전히 보완해야 하며, [ERD](../domain/erd.md#11-회계)의 정식 전표 물리 스키마는 아직 확정하지 않았습니다.

## 1. 목적과 현재 상태

기존 업무를 반복 입력하지 않고 부과·수납·지출에서 회계 기록을 생성하여, 기간별 정산과 과목별 손익을 조회하는 것이 목표입니다. 합계에서 개별 거래와 원래 업무까지 추적할 수 있도록 합니다.

| 영역 | 현재 구현 | 확정된 후속 개발 범위 |
| --- | --- | --- |
| 관리비 부과 | 부과 항목·월별 청구·확정 이력 | 부과 항목과 수익 계정 연결, 회계 귀속 기준 |
| 수납 | 실제 입금·청구 충당·선입금·취소 | 미수금·선수금 등 회계 계정과 연결 |
| 지출 | 지출명·출금일·통장·동/외부 부담 배분 | 계정과목·귀속 월, 필요 시 과목별 분할 |
| 월별 정산 | 기존 업무 조회·점검·종합보고서 | 월별·연간·선택 기간의 부과·수납·지출 확인 |
| 회계 | 실제 손익·원천 원장 조회와 계정과목 설정·변경 이력; 정식 전표 미구현 | 계정과목 연결 → 최소 자동전표 → 손익계산서 |

손익 원천 연결의 실제 구현은 [Server 설계](../../server/docs/incomeStatement.md)에 기록합니다. 기존 회계 전체 범위의 구현 완료로 확대하지 않습니다.

현재 `fee_template_items`와 `charge_items`에는 `revenue_account_id`가 있지만 해당 필드를 사용하는 정식 자동전표 연결은 없습니다. 현재 손익 분류는 별도의 이력 테이블을 사용합니다. `expenses.category_encrypted`는 계정과목 ID가 아니라 지출명 문자열입니다. ERD의 계정과목·전표·과목별 지출 상세는 설계안이며, 컬럼이나 문서의 존재를 구현 완료로 해석하지 않습니다.

현재 계약은 [관리비 부과](../api/billingApi.md), [수납](../api/paymentApi.md), [통장·지출](../api/bankingManagement.md), [월별 정산](../api/monthlySettlementApi.md)을 참조합니다.

### 과거 검토 의견의 반영 기준

2026-11-04 사용자는 전달한 검토 의견이 과거 시스템을 기준으로 작성됐을 수 있으므로, 현행과 맞는 내용을 선별해 반영하도록 요청했습니다. 과거 구축계획서·ERD의 제목이나 버전을 현재 구현 상태의 근거로 사용하지 않습니다. 현재 도메인 규칙·API·실제 코드·Migration을 함께 확인하고 차이가 있으면 구현 전에 정리합니다.

검토 의견에서 다음 내용을 설계 기준으로 반영했습니다. 이어진 사용자 승인으로 수익·비용의 기본 인식 기준과 개발 범위도 확정했으며, 확인이 필요한 실제 자료와 예외 처리까지 임의 확정하지 않습니다.

- 기존 월별 정산의 실제 자금·부과·수납 조회와 손익계산서의 회계 집계를 구분합니다. 회계 기능 추가를 이유로 현재 정산을 손익계산서로 대체하지 않습니다.
- 실제 입금과 수익을 구분하고, 기존 잔액 인계·청구 충당·선입금 사용으로 수익이나 실제 입금을 중복 생성하지 않습니다. 내부 이체는 운영 수익·비용과 구분합니다. 세부 기준은 [수납·정산 정책](../domain/domainRules.md#월별-정산-집계-기준)을 따릅니다.
- 부과 항목·지출명과 회계 계정을 분리하며, 외부 계정코드의 앞자리만으로 자산·부채·수익·비용을 판단하지 않습니다.
- 원장·손익과 향후 추가할 일월계표·재무상태표는 같은 회계 기록과 확인된 기초 잔액에서 집계하는 방향입니다. 보고서마다 별도 금액을 입력해 일치시키지 않으며, 은행의 실제 확인 잔액은 장부와의 대조 자료로 구분합니다.
- 과목 연결보다 먼저 수익·비용의 인식 기준과 예외를 결정합니다. 회계상 처리 근거가 없는 거래를 임의로 일반 수익·비용에 포함하지 않습니다.

일월계표·재무상태표의 제품 화면과 첨부 코드 체계의 전면 도입은 이번 범위에 포함하지 않습니다. 지출당 한 과목만 허용하지 않고 필요한 거래의 과목별 분할을 지원합니다. 과거 의견을 그대로 따르지 않고 현재 확정 범위를 기준으로 설계합니다.

## 2. 확정 메뉴 구성

현재 `정산 / 마감`을 `회계·정산`으로 확장합니다. 별도의 중복 회계 그룹을 추가하지 않고 아래 네 하위 메뉴로 구성합니다.

```text
회계·정산
├─ 정산 현황
├─ 손익계산서
├─ 계정별 원장
└─ 계정과목 설정
```

| 메뉴 | 목적 |
| --- | --- |
| 정산 현황 | 기존 월별 정산을 바탕으로 부과·수납·미수·지출·통장 잔액을 기간별 확인 |
| 손익계산서 | 수익·비용과 영업손익·당기손익을 과목별 확인 |
| 계정별 원장 | 과목 합계에 포함된 개별 거래와 원천 업무 확인 |
| 계정과목 설정 | 사용할 과목과 부과·기타 입금·지출의 연결 관리 |

부과·수납·지출의 등록·확정은 기존 업무 화면과 연결하고 같은 거래를 다시 입력하지 않습니다. 미지급·선급·회계 정정에 필요한 입력은 실제 지급이나 기존 원천을 중복 생성하지 않도록 별도 상세 설계합니다. 전표는 원장·거래 상세에서 확인하고 이번에는 범용 전표 관리 메뉴를 만들지 않습니다.

현재 메뉴 구현은 아래와 같습니다. 정산 현황의 기존 월별 조회·집계·보고서 내용과 Server API는 유지하며, 실제 마감 확정·잠금·재오픈은 후속 범위입니다.

| 메뉴 | Client 경로 | 구현 상태 |
| --- | --- | --- |
| 정산 현황 | `/manage/[propertyId]/accounting/settlement` | 기존 월별 정산 이동. 연간·기간별 확대는 미구현 |
| 손익계산서 | `/manage/[propertyId]/accounting/income-statement` | 실제 청구·지출 조회·관리자 분류 저장·기간/동·표·그래프·다운로드. 정식 전표는 미구현 |
| 계정별 원장 | `/manage/[propertyId]/accounting/ledger` | 101·102·103·201·손익 원천별 조회·기간 누계·원본 상세·다운로드 구현. 202 등록 및 정식 전표 원장 미구현 |
| 계정과목 설정 | `/manage/[propertyId]/accounting/accounts` | 과목 조회·추가·수정·중지·재개·미사용 추가 과목 삭제 |

이전 `/closing/monthly`와 다운로드 하위 경로는 조회 조건을 보존해 새 경로로 이동합니다. 상세 화면·Client 소스 구성은 [정산 현황](../../client/docs/monthlySettlement.md)을 참조합니다.

## 3. 계정과목의 의미와 확정된 구성 방향

계정과목은 거래를 회계상 성격에 따라 모으는 분류입니다. 지출명 `10월 승강기 수리`를 비용 계정 `수선비`에 연결하면, 다른 이름으로 등록한 수리 지출도 같은 과목에서 집계할 수 있습니다.

사용자가 승인한 계정과목의 구성·추가·보호·이력·식별 원칙은 [도메인 기준](../domain/domainRules.md#계정과목의-범용-구성과-관리-원칙-2026-11-04-사용자-확정)을 따릅니다. 아래 후보 표는 기존 검토 내용이며, 후속 [사용자 요구](../domain/domainRules.md#계정-코드-체계와-통장-입출금-연결-2026-11-05-사용자-요구)의 확정 기본 과목·번호는 3.1절을 따릅니다. 화면 구성의 최종 기준은 Client 문서를 참조합니다.

| 구분 | 의미 | 기본 과목 후보 |
| --- | --- | --- |
| 자산 | 보유하거나 받을 금액 등 | 보통예금, 관리비 미수금, 외부 부담금 미수금 |
| 부채 | 지급·반환 등의 의무가 있는 금액 | 선수금, 미지급금 |
| 자본 | 자산에서 부채를 차감한 순액 | 기초 순자산 등에 필요한 계정, 명칭·처리 미정 |
| 수익 | 해당 기간에 인식하는 수익 | 관리비수익, 이자수익, 기타수익 |
| 비용 | 해당 기간에 인식하는 비용 | 관리용역비, 청소비, 수도광열비, 수선비, 보험료, 지급수수료, 정화조 청소비 |

위 후보 전체가 기본 과목으로 확정된 것은 아닙니다. 작성 시 확인한 첨부 PDF의 목록 전체나 특정 건물명·계정코드를 제품 기본값으로 복제하지 않습니다. 원본은 저장소에 포함되어 있지 않으며, 확인한 자료 구조는 [6절](#6-기존-자료-적용과-첨부-검토-기록)에 기록합니다. 새 코드 범위는 첨부 코드의 전면 도입이 아닌 이번 사용자 요구를 기준으로 합니다.

주민에게 청구하는 `청소비` 부과 항목과 업체에 지급하는 `청소비` 비용은 서로 다른 역할입니다. 일반 관리비 부과 항목은 기존 확정 기준대로 하나의 관리비 수익 계정에 연결하고 항목별 내역을 유지합니다. 이번 요청의 표시 이름은 `관리비수입`이며 예치·적립 등 별도 성격은 자동 통합하지 않습니다.

### 공통 기본 과목과 관리대상별 추가 과목

| 구성 | 예시 | 사용 방식 |
| --- | --- | --- |
| 모아홈 기본 과목 | 관리비수익, 이자수익, 청소비, 수선비 | 여러 관리대상에서 사용하는 범용 과목을 기본 제공 |
| 관리대상별 추가 과목 | 승강기 유지보수비, 소방 점검비 | 설정 권한이 있는 관리자가 해당 대상에 필요한 세부 과목 추가 |
| 거래에 별도로 연결할 정보 | 관리대상, 동, 세대, 통장 | 어느 대상의 거래인지 구분하고 해당 정보로 조회·집계 |

예를 들어 A건물과 B건물에 각각 발생한 관리비 부과를 아래처럼 연결합니다. 표시 금액은 설명용입니다.

| 관리대상 | 계정과목 표시 이름 | 금액 |
| --- | --- | ---: |
| A건물 | 관리비수익 | 1,000,000원 |
| B건물 | 관리비수익 | 800,000원 |

이 예시는 같은 범용 과목 이름을 사용하면서 관리대상별로 구분한다는 뜻입니다. 현재 구현은 기본 과목에서 생성한 관리대상별 독립 계정 행을 사용합니다.

### 설정 흐름 제안

초기에는 기본 과목을 제공하고, 관리자가 필요한 경우 계정과목 설정에서 이름·유형·보고서상 분류를 지정해 추가하는 흐름을 제안합니다. 추가한 과목은 해당 관리대상의 부과·입금·지출 중 과목 성격에 맞는 업무에서 선택하도록 합니다. 유형·분류와 다른 업무에 연결하지 않도록 검증합니다.

이미 사용한 과목을 더 이상 선택하지 않으려면 사용 중지로 처리하고 과거 거래·전표 조회는 유지하는 방향입니다. 사용 중지 시 기존 반복 부과 설정과 자동전표 연결의 영향도 확인하도록 상세 절차를 설계합니다. 필수 계정 보호와 기존 기록의 계정 ID 연결을 우선하며, 이름이나 코드를 바꿔 과거 거래를 다른 성격의 계정으로 재사용하지 않습니다.

회계 과목 설정은 ADMIN, MANAGER는 조회로 확정했습니다. 요청한 기본 과목·코드 범위 외의 추가 계정과 필수 계정 전체 목록, 개별 번호, 과목 변경·중지·삭제는 [2026-11-07 확정 표](../domain/domainRules.md#계정과목-설정의-변경사용-중지삭제-2026-11-07-사용자-확정)를 따릅니다. 과목 추가 기능이 확정된 수익·비용 인식 기준을 임의로 바꿀 수 있다는 뜻은 아닙니다.

### 3.2 코드로 계정과목을 인식하는 연결 설계안

코드 입력은 과목을 찾는 방법이며, 거래 성격을 판단하는 단계와 구분합니다. 다음 흐름을 기존 통장·수납·지출 업무에 연결하는 안입니다.

1. 은행 업로드 또는 수동 등록으로 기존 거래를 확인합니다. 통장·방향·일자·금액·수납/지출/내부 이체 연결을 재사용합니다.
2. 선택한 관리대상에서 코드를 검색해 `코드 · 과목명 · 유형`을 표시합니다. 예를 들어 `802` 입력은 해당 대상의 청소비 과목 ID를 찾습니다. 다른 대상·없는 코드·사용 중지 과목은 신규 연결에 사용할 수 없습니다.
3. 입금은 미수 회수·선수금·기타 입금·내부 이체 등 기존 원천 성격을 확인합니다. 출금은 이번 발생 비용의 지급인지, 이미 기록한 미지급금의 지급인지 구분합니다. 현재 확정 지출은 기존 지출 날짜의 월에 귀속하며 별도 날짜·귀속 월 입력을 받지 않습니다.
4. 과목 ID, 금액, 원천 ID, 통장 ID와 필요한 청구·세대·동·거래처 연결을 확인합니다. 한 거래의 과목별 분할 금액은 총액과 맞추고 각 분할의 부담 배분도 검증합니다.
5. 기존 업무 권한에 따라 거래를 확정하고 회계 처리 상태를 별도로 추적합니다. 전표는 계정 ID와 업무 역할 매핑으로 생성하며 특정 코드 문자열을 조건문에 고정하지 않습니다. 차변·대변 및 원천 금액을 대조하고 중복 생성·실패 재시도를 관리합니다.

입금·출금 방향은 자금 이동 구분입니다. 현재 원본의 `INCOME/EXPENSE`와 수납 용도의 `HOUSEHOLD/OTHER/SHARED`를 각각 회계의 수익/비용·계정 코드로 치환하지 않습니다. 회계 설정·과목 연결 정정 권한과 기존 통장 업무의 처리 권한도 구분합니다. 후속 사용자 요청에 따라 기본 과목명·통상 표기의 계정 매칭은 자동 적용하며 기존 명시적 분류가 우선합니다. 원본 금액·부담 배분과 기존 명시적 귀속 이력은 변경하지 않습니다.

코드는 관리대상 안에서 하나의 과목만 찾을 수 있도록 유일하게 관리하고 코드 범위와 별도 저장한 계정 유형의 일치를 검사하는 안입니다. 화면·파일에는 코드와 명칭을 함께 표시하고 내부 저장·전표 연결은 계정 ID를 유지합니다. 코드 변경은 미사용 추가 과목만 허용하며 사용한 코드를 다른 성격의 과목에 재사용하지 않습니다.

### 3.3 업무별 코드 연결 예시

아래는 기존 확정 정책을 3.1절 코드안으로 설명한 **후속 자동전표 예시**입니다. 현재 손익 조회가 이 전표를 생성한다는 뜻은 아닙니다. 양수 청구와 확인된 거래를 전제로 하며, 미정인 환불·음수 청구·취소 처리는 이 표로 확정하지 않습니다.

| 업무 예시 | 차변 | 대변 | 연결·검증 |
| --- | --- | --- | --- |
| 관리비 100,000원 부과 확정 | 102 미수금 100,000 | 401 관리비수입 100,000 | 부과월에 한 번 수익 인식 |
| 위 청구에 80,000원 입금·충당 | 101 통장 80,000 | 102 미수금 80,000 | 잔여 미수 20,000; 수익 추가 없음 |
| 잔여 미수 20,000원에 50,000원 입금·충당 | 101 통장 50,000 | 102 미수금 20,000 + 201 선수금 30,000 | 입금 전액과 청구 충당·선수 잔액 일치 |
| 위 선수금 30,000원을 다음 확정 청구에 충당 | 201 선수금 30,000 | 102 미수금 30,000 | 다음 청구의 부과 수익은 별도; 새 입금 없음 |
| 당월 청소비 50,000원 발생·즉시 지급 | 802 청소비 50,000 | 101 통장 50,000 | 기존 지출 날짜의 월로 귀속 |
| 당월 청소비 50,000원 발생·아직 미지급 | 802 청소비 50,000 | 202 미지급금 50,000 | 은행 원본·가상 출금 생성 없음 |
| 위 미지급금 다음 달 지급 | 202 미지급금 50,000 | 101 통장 50,000 | 원래 채무에 연결; 청소비 중복 없음 |
| 한 출금에 청소비 30,000원·수선비 20,000원 | 802 청소비 30,000 + 806 수선비 20,000 | 101 통장 50,000 | 과목별 합계·부담 배분 검증 |
| 전기료 182,660원 지급, 우리 몫 91,330원·외부 몫 91,330원 | 804 수도전기료 91,330 + 102 미수금 91,330 | 101 통장 182,660 | 확정 배분의 외부 몫은 자동으로 미수금에 연결; 비용에 합산하지 않음 |
| 위 외부 부담금 91,330원 회수 | 101 통장 91,330 | 102 미수금 91,330 | 기존 회수 입금 연결을 사용하며 관리비수입·기타수익을 만들지 않음 |
| 예금이자 등 기타 입금 218원 확정 | 101 통장 218 | 901 영업외수익 218 | 확정 입금액·기존 동 배분 사용; 미수금 회수액은 먼저 제외 |
| 같은 관리대상 A통장 → B통장 100,000원 | 101 통장(B) 100,000 | 101 통장(A) 100,000 | 서로 다른 통장 ID·내부 이체 원천 연결; 손익 없음 |

즉시 지급 예시와 미지급 후 지급 예시는 서로 다른 처리 경로이며 같은 비용에 모두 적용하지 않습니다. 기존 통장·미수·선입금 인계 금액도 신규 입금·수익으로 다시 만들지 않습니다. 외부 부담 회수는 확인된 채권을 줄이는 흐름을 유지하며, 선급 비용·추가 수익·미확인 거래는 위 목록의 아무 코드에 강제로 넣지 않습니다.

### 3.4 현재 구현과 남은 개발 범위

| 확인 대상 | 현재 구현 | 남은 범위 |
| --- | --- | --- |
| 계정 저장 | 기존 `accounting_accounts`에 code 추가, 자산·부채·손익 그룹과 범위·유일성 검사, 기존 ID·분류 이력 보존 | 과목 설정은 후속 구현한 [API](../api/accountingAccountsApi.md) 참조 |
| 기본 과목 | 현재 기본 19개를 대상별 생성, 기존 관리비수익 ID를 401 관리비수입으로 연결 | 추가 자산·부채·자본 등 실제 필요 과목 |
| 선택·API | 코드 오름차순 응답·비용 선택, 추가 비용 코드 지정 또는 814~899 빈 코드 배정 | 전체 계정 설정 화면·정식 원장 |
| 부과·지출 | 일반관리비의 401 기본 연결과 원본 항목 합산, 기존 지출 날짜 기준 비용 계정 자동·수동 매칭 | 과목 분할·미지급/선급 전표 |
| 외부 부담 | 102 미수금 발생·실제 회수·잔액 조회, 우리 몫만 비용에 반영 | 회수 포기·차액 등 미정 예외·정식 분개 |
| 전표·마감 | 미구현 | 차대변 검증·정정·실패 재처리·원장·마감 |

실제 저장과 계약은 [ERD](../domain/erd.md#11-회계)와 [손익 API](../api/incomeStatementApi.md)를 따릅니다. 원본 금액·청구·수납을 다시 만들지 않았으며 기본 계정 코드 제공을 자동전표 전체 구현 완료로 보고하지 않습니다.

후속 구현은 다음 결과로 확인합니다.

- 같은 코드로 다른 관리대상의 과목을 선택할 수 없으며 없는 코드·유형 불일치·사용 중지 과목은 신규 연결에서 거부합니다.
- 코드 검색으로 선택한 과목 ID가 거래 상세·전표·원장에 일관되게 연결됩니다. 통장 ID·계정 ID·청구 ID를 서로 대체하지 않습니다.
- 3.3절의 부과·부분 수납·초과 입금·선수 충당·미지급 후 지급·분할·내부 이체에서 원천 금액과 차변/대변이 일치하고 같은 입금·수익·비용이 두 번 반영되지 않습니다.
- 재요청·실패 재처리는 전표를 중복 생성하지 않고, 과목 정정은 이력과 원천 추적을 보존합니다. 기존 계정 ID·손익 분류 이력이 유실되지 않습니다.
- 코드 미연결·성격 미확인·회계 처리 실패는 건수·금액·원천을 표시합니다. 문서·코드만 부여한 상태를 전표·손익 반영 완료로 표시하지 않습니다.

### 3.5 지출 등록 시 코드 선택

2026-11-06 추가 사용자 지시에 따라 은행 출금의 이체 체크는 비용이 아닌 [통장간 거래 처리](../api/bankingManagement.md#한쪽-은행-원본에서-양쪽-이체-반영-2026-11-06)로 전환합니다. 2026-11-07 후속 지시로 수동 입금·지출에도 [수동 계좌 간 이체 등록](../api/bankingManagement.md#수동-계좌-간-이체-등록-2026-11-07)을 제공합니다.

반복 부과 설정에서 기본 수익 계정을 연결하고 확정 청구에는 당시 연결을 보존하는 안입니다. 임시·직접 입력 항목에도 연결 방법이 필요합니다. 계정 설정을 바꿨다는 이유로 과거 확정 청구와 전표가 자동 변경되지 않도록 합니다.

### 지출과 기타 입금

지출명·원본 날짜는 유지하고 현재 확정 지출의 기본 비용 월은 그 날짜에서 사용합니다. 별도의 날짜·변경 사유 입력을 추가하지 않습니다. 기본 과목명·통상 표기·입력한 코드로 비용 계정을 자동 매칭합니다. 전기료·전기요금은 804, 엘리베이터는 803, 정화조는 807, 문자수수료는 808입니다. 여러 과목에 매칭되면 확인 대상으로 남기고 기존 명시적 분류를 우선합니다. 기타 입금에도 회계 분류가 필요하며 현재 동별 귀속·외부 회수 연결과 함께 설계합니다.

한 번의 출금에 청소비와 수선비가 섞이면 과목별 금액 분할을 지원합니다. 과목별 금액 합계와 지출 총액을 맞추며 각 과목의 동·외부 부담 배분까지 연결합니다. 기존 총액 배분을 근거 없이 각 과목에 복제하지 않습니다. 상세 저장 설계는 [지출 ERD](../domain/erd.md#104-expense_lines)를 검토하되 기존 설계를 그대로 채택한 것으로 보지 않습니다.

외부 부담은 후속 확정 정책 D4에 따라 102 미수금으로 처리합니다. 정산 제외·회수 포기·차액의 상세 처리와 과거 미수 전환 근거는 별도로 보완합니다.

### 최소 자동전표

사용자는 원천 업무를 처리하고 시스템이 전표를 생성합니다. 원천 거래를 복사해 별도 업무로 관리하지 않고 연결 식별자와 처리 상태로 추적합니다. 최소 범위에도 다음 조건이 필요합니다.

- 동일 원천·동일 처리에 대한 중복 생성 방지와 실패 후 재시도.
- 업무 확정·청구 충당·회계 처리 완료 상태의 구분과 누락 확인.
- 취소·삭제·은행 원본 연결 등 기존 업무 변경 시 회계 반영·정정 이력 보존.
- 계정·금액·귀속 기간·원천 연결과 전표 차변/대변 합계 검증.
- 과목 연결 변경이 과거 보고서를 소급 변경하지 않도록 당시 연결 보존.

선입금은 확정 정책 D8을 적용하고, 환불·음수 청구·과거 월 충당은 단순 수납 예시로 처리하지 않습니다. 실제 거래 성격과 상세 정책을 보완하며 미처리를 숨기지 않습니다. 재처리는 ADMIN 권한입니다. 회계 실패와 원천 업무의 처리 순서·복구 방식은 후속 상세 설계로 정합니다.

## 5. 확정된 기간별 정산과 손익 조회 범위

월별·연간·직접 선택한 기간을 지원합니다. 후속 사용자 요청에 따라 손익계산서에는 별도 12개월 비교 탭을 두지 않고 시작·종료 월의 기간 선택과 월별 추이를 연결합니다. 화면을 기간마다 별도로 늘리지 않고 같은 집계 기준과 원장을 사용합니다. 회계연도 시작 월은 관리대상별로 설정하며 달력연도가 필요한 대상은 1월 시작으로 설정합니다. 실제 시작 월은 해당 대상의 설정값으로 확인합니다.

| 손익계산서 Excel | `Sheet1!A1:E22`. 과목과 당기·전기 비교 열, 각 기간의 세부 금액·소계 열. 매출액 → 매출원가 → 매출총이익 → 판매비와 관리비 → 영업손익 → 영업외수익·비용 → 세전손익 → 소득세등 → 당기손익 순서 | 수익·비용 과목과 소계·손익 행을 구분하고 중복 합산하지 않음. 원본은 손실을 양수 금액과 손실 행 이름으로 표시하므로 제품의 부호·행 이름 표시는 별도 결정 |
| 일월계표 Excel | `Sheet1!A1:G18`. 가운데 계정과목, 왼쪽 차변 `계 / 대체 / 현금`, 오른쪽 대변 `현금 / 대체 / 계`. 자산·매출·판매관리비의 그룹·상세 행과 금월소계·잔고·합계 표시 | 계정별 차변·대변 이동의 집계 예시. 그룹 행·상세 행·소계를 함께 더하지 않으며, 이 집계표 자체를 개별 부과·수납·지출 연결의 원천으로 사용하지 않음 |
| 재무상태표 Excel | `Sheet1!A1:E27`. 과목과 당기·전기 비교 열. 자산은 유동·비유동 및 세부 구분, 이어 부채·자본과 각 총계 표시. 당기·전기 순손실 설명도 포함 | 특정 기간의 수익·비용 흐름과 기준일의 자산·부채·자본 잔액을 구분. 첨부의 계정 배치가 회계 정책의 적정성을 보증하는 것은 아님 |

손익계산서에서 확인한 비용 행은 관리비·청소비·수도광열비·수선비·보험료·지급수수료·정화조이고, 영업외 항목에는 이자수익·잡손실이 있습니다. 이는 원본의 표시 이름이며 기본 과목 전체를 확정한 목록은 아닙니다. 건물명이 포함된 매출 과목은 제품의 범용 `관리비수익`과 관리대상 정보를 분리하는 예시로만 활용합니다.

확인한 손익 계산의 관계는 `매출총이익 = 매출액 - 매출원가`, `영업손익 = 매출총이익 - 판매비와 관리비`, `세전손익 = 영업손익 + 영업외수익 - 영업외비용`, `당기손익 = 세전손익 - 세금`입니다. 이는 첨부 수치를 대조한 계산 관계이며, 모아홈의 수익·비용 인식일이나 세금 계산 정책을 확정한 것은 아닙니다. 별도 계산 열 없이 입력된 집계값을 담은 보고서이므로 세부 전표와 원천 업무의 적정성까지 검증할 수는 없습니다.

참고 자료의 회계연도는 10월부터 다음 해 9월이고 손익계산서는 당기 1개월과 전기 12개월을 비교합니다. 제품은 관리대상별 회계연도 설정과 비교 기간 명시를 적용하며, 원본의 기간을 모든 대상의 고정값으로 사용하지 않습니다. 기존 은행 거래 업로드에 회계 보고서 업로드 기능이 추가된 것으로 해석하지 않습니다.

### 이 문서로 확인할 수 있는 범위

현재 문서는 첨부를 보지 않아도 계정과목 관리 원칙, 요청한 기본 과목·코드 범위와 배정안, 확정한 개발 범위·수익 및 비용 기준을 읽을 수 있습니다. 추가 계정·개별 자료의 성격·예외별 정정·저장 방식까지 모두 정해진 구현 명세는 아닙니다. 남은 상세 설계는 7절에 구분하며, 누락된 결정을 저장소 밖의 첨부 파일에 맡기지 않습니다.

원본의 정확한 서식이나 개별 금액을 다시 대조해야 하는 작업은 원본에 접근할 수 있는 환경에서 별도로 확인해야 합니다. 위 요약을 원본 파일의 사본이나 회계 적정성 검증 결과로 취급하지 않습니다.

| 단계 | 범위 | 다음 단계 전 확인 |

### 남은 상세 설계와 자료 확인

요청한 기본 과목·코드 범위를 바탕으로 3.1절 확정 코드를 기준으로 추가 계정·필수 계정 전체 목록과 보고서 분류, 일반 관리비 통합 이후의 세분화, 과목 변경·중지·삭제는 2026-11-07 확정 표를 적용합니다. 대상별 예치·적립 성격과 기초 잔액은 실제 자료를 확인합니다. 별도 시작 월 입력은 후속 정정으로 제거합니다. 음수 청구·환불·회수 포기·수납 후 정정은 아직 결정되지 않은 업무 처리를 승인된 것으로 기록하지 않고 별도 정리합니다.

현재 기본 과목은 관리대상별 `accounting_accounts`에 저장하고 관리대상+코드 유일 제약과 계정 ID 연결을 구현했습니다. 정식 전표의 저장·동기/비동기 처리·재시도 방식과 추가 계정의 변경 이력은 후속으로 상세 설계합니다. 기술 선택을 모두 사용자에게 개별 승인받아야 한다는 뜻은 아닙니다. 예외 정책과 원천 대조를 해결하기 전 전체 회계 구현을 완료한 것으로 표시하지 않습니다.

## 8. 후속 설계 문서의 책임

확정 정책은 [도메인 규칙](../domain/domainRules.md#9-회계), 저장 구조는 [ERD](../domain/erd.md#11-회계)에 반영합니다. 공유 API 계약은 구현 범위 확정 후 기능 단위로 모읍니다. 화면·상태·브라우저 동작은 `client/docs/`, 저장·트랜잭션·동시성·재처리는 `server/docs/`에서 관리합니다.

현재는 메뉴·기존 정산 경로 이동, 손익 원천 조회·시작 기준·계정 코드·분류 이력·외부 미수금 조회·표·그래프·다운로드를 구현했습니다. Client 브라우저의 모의 API 검증과 Server 서비스·격리 PostgreSQL Migration 검증을 구분합니다. 손익 API와 4개 저장 테이블 및 후속 코드 Migration을 사용하며 정식 전표·원장·분할·미지급/선급·마감 테스트를 구현했다고 보고하지 않습니다. 메뉴 연결·경로 호환·기존 정산·다운로드의 검증은 해당 Client 테스트에서 수행하며, 전체 회계 기능의 검증과 구분합니다.
