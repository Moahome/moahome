# 회계·정산과 손익계산서 추가 기획

기준일: 2026-11-04. 상태: **개발 범위·기본 처리 기준 사용자 확정, 상세 설계·예외 처리 보완 필요, 회계 기능 미구현**.

사용자는 기존 관리비 부과·수납·지출을 연결한 손익계산서와 월별·연간 조회를 이번 개발 대상으로 정하고 제시한 권장안을 승인했습니다. 메뉴는 기존 정산 / 마감을 회계·정산으로 확장합니다. 기존 설계 변경도 허용하며, 이번 문서는 확정 기준과 남은 상세 설계를 기록합니다. 코드·API·Migration 구현 완료와 구분합니다.

계정과목의 범용 구성·관리 원칙과 발생 기준 손익·권한·이번 메뉴 및 개발 범위는 **사용자 확정**입니다. 기준 문서는 [회계 도메인 규칙](../domain/domainRules.md#9-회계)입니다. 최종 계정 목록·기초 잔액 등 실제 확인 자료와 예외별 상세 처리는 여전히 보완해야 하며, [ERD](../domain/erd.md#11-회계)의 최종 물리 스키마는 아직 확정하지 않았습니다.

## 1. 목적과 현재 상태

기존 업무를 반복 입력하지 않고 부과·수납·지출에서 회계 기록을 생성하여, 기간별 정산과 과목별 손익을 조회하는 것이 목표입니다. 합계에서 개별 거래와 원래 업무까지 추적할 수 있도록 합니다.

| 영역 | 현재 구현 | 확정된 후속 개발 범위 |
| --- | --- | --- |
| 관리비 부과 | 부과 항목·월별 청구·확정 이력 | 부과 항목과 수익 계정 연결, 회계 귀속 기준 |
| 수납 | 실제 입금·청구 충당·선입금·취소 | 미수금·선수금 등 회계 계정과 연결 |
| 지출 | 지출명·출금일·통장·동/외부 부담 배분 | 계정과목·귀속 월, 필요 시 과목별 분할 |
| 월별 정산 | 기존 업무 조회·점검·종합보고서 | 월별·연간·선택 기간의 부과·수납·지출 확인 |
| 회계 | 수익 계정 연결용 필드 일부 존재, 실제 계정 관리·전표·손익 미구현 | 계정과목 연결 → 최소 자동전표 → 손익계산서 |

현재 `fee_template_items`와 `charge_items`에는 `revenue_account_id`가 있지만 실제 과목 설정·연결 기능은 없습니다. `expenses.category_encrypted`는 계정과목 ID가 아니라 지출명 문자열입니다. ERD의 계정과목·전표·과목별 지출 상세는 설계안이며, 컬럼이나 문서의 존재를 구현 완료로 해석하지 않습니다.

현재 계약은 [관리비 부과](../api/billingApi.md), [수납](../api/paymentApi.md), [통장·지출](../api/bankingManagement.md), [월별 정산](../api/monthlySettlementApi.md)을 참조합니다.

### 과거 검토 의견의 반영 기준

2026-11-04 사용자는 전달한 검토 의견이 과거 시스템을 기준으로 작성됐을 수 있으므로, 현행과 맞는 내용을 선별해 반영하도록 요청했습니다. 과거 구축계획서·ERD의 제목이나 버전을 현재 구현 상태의 근거로 사용하지 않습니다. 현재 도메인 규칙·API·실제 코드·Migration을 함께 확인하고 차이가 있으면 구현 전에 정리합니다.

검토 의견에서 다음 내용을 설계 기준으로 반영했습니다. 이어진 사용자 승인으로 수익·비용의 기본 인식 기준과 개발 범위도 확정했으며, 확인이 필요한 실제 자료와 예외 처리까지 임의 확정하지 않습니다.

- 기존 월별 정산의 실제 자금·부과·수납 조회와 손익계산서의 회계 집계를 구분합니다. 회계 기능 추가를 이유로 현재 정산을 손익계산서로 대체하지 않습니다.
- 실제 입금과 수익을 구분하고, 기존 잔액 인계·청구 충당·선입금 사용으로 수익이나 실제 입금을 중복 생성하지 않습니다. 내부 이체는 운영 수익·비용과 구분합니다. 세부 기준은 [수납·정산 정책](../domain/domainRules.md#월별-정산-집계-기준)을 따릅니다.
- 부과 항목·지출명과 회계 계정을 분리하며, 외부 계정코드의 앞자리만으로 자산·부채·수익·비용을 판단하지 않습니다.
- 원장·손익과 향후 추가할 일월계표·재무상태표는 같은 회계 기록과 확인된 기초 잔액에서 집계하는 방향입니다. 보고서마다 별도 금액을 입력해 일치시키지 않으며, 은행의 실제 확인 잔액은 장부와의 대조 자료로 구분합니다.
- 과목 연결보다 먼저 수익·비용의 인식 기준과 예외를 결정합니다. 회계상 처리 근거가 없는 거래를 임의로 일반 수익·비용에 포함하지 않습니다.

일월계표·재무상태표의 제품 화면과 첨부 코드 체계의 전면 도입은 이번 범위에 포함하지 않습니다. 지출당 한 과목만 허용하지 않고 필요한 거래의 과목별 분할을 지원합니다. 과거 의견을 그대로 따르지 않고 현재 확정 범위를 기준으로 설계합니다.

## 2. 확정 메뉴 구성

현재 `정산 / 마감`을 `회계·정산`으로 확장합니다. 별도의 중복 회계 그룹을 추가하지 않고 아래 네 하위 메뉴로 구성합니다.

```text
회계·정산
├─ 정산 현황
├─ 손익계산서
├─ 계정별 원장
└─ 계정과목 설정
```

| 메뉴 | 목적 |
| --- | --- |
| 정산 현황 | 기존 월별 정산을 바탕으로 부과·수납·미수·지출·통장 잔액을 기간별 확인 |
| 손익계산서 | 수익·비용과 영업손익·당기손익을 과목별 확인 |
| 계정별 원장 | 과목 합계에 포함된 개별 거래와 원천 업무 확인 |
| 계정과목 설정 | 사용할 과목과 부과·기타 입금·지출의 연결 관리 |

부과·수납·지출의 등록·확정은 기존 업무 화면과 연결하고 같은 거래를 다시 입력하지 않습니다. 미지급·선급·회계 정정에 필요한 입력은 실제 지급이나 기존 원천을 중복 생성하지 않도록 별도 상세 설계합니다. 전표는 원장·거래 상세에서 확인하고 이번에는 범용 전표 관리 메뉴를 만들지 않습니다.

실제 마감 확정·잠금·재오픈은 후속 범위입니다. 새 메뉴와 경로는 아직 구현하지 않았으며 현재 월별 정산의 조회·집계·보고서 동작은 유지합니다.

## 3. 계정과목의 의미와 확정된 구성 방향

계정과목은 거래를 회계상 성격에 따라 모으는 분류입니다. 지출명 `10월 승강기 수리`를 비용 계정 `수선비`에 연결하면, 다른 이름으로 등록한 수리 지출도 같은 과목에서 집계할 수 있습니다.

사용자가 승인한 계정과목의 구성·추가·보호·이력·식별 원칙은 [도메인 기준](../domain/domainRules.md#계정과목의-범용-구성과-관리-원칙-2026-11-04-사용자-확정)을 따릅니다. 이 절은 해당 방향을 업무 예시로 설명하며, 세부 목록과 화면 구성은 기획안입니다.

| 구분 | 의미 | 기본 과목 후보 |
| --- | --- | --- |
| 자산 | 보유하거나 받을 금액 등 | 보통예금, 관리비 미수금, 외부 부담금 미수금 |
| 부채 | 지급·반환 등의 의무가 있는 금액 | 선수금, 미지급금 |
| 자본 | 자산에서 부채를 차감한 순액 | 기초 순자산 등에 필요한 계정, 명칭·처리 미정 |
| 수익 | 해당 기간에 인식하는 수익 | 관리비수익, 이자수익, 기타수익 |
| 비용 | 해당 기간에 인식하는 비용 | 관리용역비, 청소비, 수도광열비, 수선비, 보험료, 지급수수료, 정화조 청소비 |

후보는 최종 계정 목록·회계 분류가 아닙니다. 작성 시 확인한 첨부 PDF의 목록 전체나 특정 건물명·계정코드를 제품 기본값으로 복제하지 않습니다. 원본은 저장소에 포함되어 있지 않으며, 확인한 자료 구조는 [6절](#6-기존-자료-적용과-첨부-검토-기록)에 기록합니다. 초기 기본 과목은 현재 업무에 필요한 범위로 추리는 안입니다.

주민에게 청구하는 `청소비` 부과 항목과 업체에 지급하는 `청소비` 비용은 서로 다른 역할입니다. 우선 부과 항목들을 하나의 `관리비수익` 계정에 연결하고 기존 항목별 내역을 유지하는 안과, 수익 계정을 세분화하는 안 중 선택합니다.

### 공통 기본 과목과 관리대상별 추가 과목

| 구성 | 예시 | 사용 방식 |
| --- | --- | --- |
| 모아홈 기본 과목 | 관리비수익, 이자수익, 청소비, 수선비 | 여러 관리대상에서 사용하는 범용 과목을 기본 제공 |
| 관리대상별 추가 과목 | 승강기 유지보수비, 소방 점검비 | 설정 권한이 있는 관리자가 해당 대상에 필요한 세부 과목 추가 |
| 거래에 별도로 연결할 정보 | 관리대상, 동, 세대, 통장 | 어느 대상의 거래인지 구분하고 해당 정보로 조회·집계 |

예를 들어 A건물과 B건물에 각각 발생한 관리비 부과를 아래처럼 연결합니다. 표시 금액은 설명용입니다.

| 관리대상 | 계정과목 표시 이름 | 금액 |
| --- | --- | ---: |
| A건물 | 관리비수익 | 1,000,000원 |
| B건물 | 관리비수익 | 800,000원 |

이 예시는 같은 범용 과목 이름을 사용하면서 관리대상별로 구분한다는 뜻입니다. 두 관리대상의 연결이 하나의 공통 계정 행을 공유할지, 기본 과목에서 생성한 각각의 계정 행을 사용할지는 물리 설계에서 결정합니다.

### 설정 흐름 제안

초기에는 기본 과목을 제공하고, 관리자가 필요한 경우 계정과목 설정에서 이름·유형·보고서상 분류를 지정해 추가하는 흐름을 제안합니다. 추가한 과목은 해당 관리대상의 부과·입금·지출 중 과목 성격에 맞는 업무에서 선택하도록 합니다. 유형·분류와 다른 업무에 연결하지 않도록 검증합니다.

이미 사용한 과목을 더 이상 선택하지 않으려면 사용 중지로 처리하고 과거 거래·전표 조회는 유지하는 방향입니다. 사용 중지 시 기존 반복 부과 설정과 자동전표 연결의 영향도 확인하도록 상세 절차를 설계합니다. 필수 계정 보호와 기존 기록의 계정 ID 연결을 우선하며, 이름이나 코드를 바꿔 과거 거래를 다른 성격의 계정으로 재사용하지 않습니다.

회계 과목 설정은 ADMIN, MANAGER는 조회로 확정했습니다. 최종 기본·필수 계정 목록과 코드, 명칭·코드 변경과 과거 표시, 미사용 과목 삭제 범위는 구현 전에 정합니다. 과목 추가 기능이 확정된 수익·비용 인식 기준을 임의로 바꿀 수 있다는 뜻은 아닙니다.

## 4. 확정 기준에 따른 기존 업무 연결

수익·비용·외부 부담·선수금의 기준은 [사용자 확정 정책](../domain/domainRules.md#회계정산-개발-범위와-처리-기준-2026-11-04-사용자-확정)을 따릅니다. 이 절은 구현 시 연결할 정보를 설명하며, 실제 저장·트랜잭션 구조는 후속 상세 설계에서 정합니다.

| 기존 업무 | 연결할 정보 | 자동 기록의 의미 |
| --- | --- | --- |
| 관리비 부과 확정 | 부과 항목 → 수익 계정, 청구·세대·동·귀속 기간 | 수익과 받을 돈 발생. 양수 청구 예시이며 음수 청구는 별도 정책 필요 |
| 관리비 수납 확정·충당 | 실제 입금 통장·일자·세대와 청구 충당 내역 | 통장 이동과 미수 회수·선수금 사용을 구분. 부과 수익을 중복 생성하지 않음 |
| 기타 입금 확정 | 입금 성격 → 계정, 동 귀속·외부 회수 연결 | 이자수익·기타수익·외부 부담금 회수 등을 구분 |
| 지출 확정 | 지출명과 별도의 계정, 귀속 월, 통장, 부담 배분 | 비용 또는 자산·채무 등 거래 성격에 맞는 기록 |
| 내부 통장 이체 | 보내는 통장·받는 통장과 원천 연결 | 수익·비용이 아닌 통장 간 이동 |

### 부과 항목

반복 부과 설정에서 기본 수익 계정을 연결하고 확정 청구에는 당시 연결을 보존하는 안입니다. 임시·직접 입력 항목에도 연결 방법이 필요합니다. 계정 설정을 바꿨다는 이유로 과거 확정 청구와 전표가 자동 변경되지 않도록 합니다.

### 지출과 기타 입금

지출명은 유지하고 계정과목과 비용 귀속 월을 출금일과 별도로 관리합니다. 이전 확정 내역을 이용한 과목 추천은 가능하지만 이름이 같다는 이유로 새 거래의 성격을 자동 확정하지 않습니다. 기타 입금에도 회계 분류가 필요하며 현재 동별 귀속·외부 회수 연결과 함께 설계합니다.

한 번의 출금에 청소비와 수선비가 섞이면 과목별 금액 분할을 지원합니다. 과목별 금액 합계와 지출 총액을 맞추며 각 과목의 동·외부 부담 배분까지 연결합니다. 기존 총액 배분을 근거 없이 각 과목에 복제하지 않습니다. 상세 저장 설계는 [지출 ERD](../domain/erd.md#104-expense_lines)를 검토하되 기존 설계를 그대로 채택한 것으로 보지 않습니다.

외부 부담은 확정 정책 D4에 따라 처리합니다. 다만 현재 지출 배분만으로 회수할 권리까지 확인된 것으로 해석하지 않습니다. 정산 제외·회수 포기·차액의 상세 처리와 과거 미수 전환 근거는 별도로 보완합니다.

### 최소 자동전표

사용자는 원천 업무를 처리하고 시스템이 전표를 생성합니다. 원천 거래를 복사해 별도 업무로 관리하지 않고 연결 식별자와 처리 상태로 추적합니다. 최소 범위에도 다음 조건이 필요합니다.

- 동일 원천·동일 처리에 대한 중복 생성 방지와 실패 후 재시도.
- 업무 확정·청구 충당·회계 처리 완료 상태의 구분과 누락 확인.
- 취소·삭제·은행 원본 연결 등 기존 업무 변경 시 회계 반영·정정 이력 보존.
- 계정·금액·귀속 기간·원천 연결과 전표 차변/대변 합계 검증.
- 과목 연결 변경이 과거 보고서를 소급 변경하지 않도록 당시 연결 보존.

선입금은 확정 정책 D8을 적용하고, 환불·음수 청구·과거 월 충당은 단순 수납 예시로 처리하지 않습니다. 실제 거래 성격과 상세 정책을 보완하며 미처리를 숨기지 않습니다. 재처리는 ADMIN 권한입니다. 회계 실패와 원천 업무의 처리 순서·복구 방식은 후속 상세 설계로 정합니다.

관리대상 전체·동별 조회를 제공합니다. 동 구분이 없는 관리대상은 전체로 조회합니다. 공통 귀속 금액과 동별 합계의 관계, 과거 소속 변경·외부 부담의 세부 귀속은 상세 설계에서 정리하고 임의로 동에 배분하지 않습니다. 통장 필터는 실제 자금 조회와 수익·비용 조회에서 의미가 다르므로 손익에 일괄 적용하지 않습니다.

합계 확인 흐름은 `손익계산서의 수선비 → 수선비 원장 → 기존 지출 상세`로 연결합니다. 과목 미연결·전표 미처리 자료의 목록·건수·금액을 표시하고 이를 제외한 숫자를 완전한 확정 손익으로 표시하지 않습니다.

## 6. 기존 자료 적용과 첨부 검토 기록

### 기존 업무 데이터 적용

관리대상별 회계 시작 월을 정하고 확인한 기초 잔액과 검토 완료한 기존 업무를 반영합니다. 기존 업무 데이터와 앞으로 발생하는 거래는 같은 원천 연결 방식으로 처리합니다. 실제 도입 월과 과거 자료 범위는 대상별 확인·설정 값이며 전역 날짜로 고정하지 않습니다.

- 기존 부과는 당시 항목과 금액을 보존한 채 과목 연결을 검토합니다. 이름만으로 과목을 일괄 확정하지 않습니다.
- 기존 지출·기타 입금은 검토용 추천과 분류 필요 목록을 제공하고 확인한 범위에서 회계에 반영하는 안입니다.
- 이미 확정된 지출은 직접 수정 금지 제약이 있습니다. 과목 연결·정정 저장 방식은 별도로 설계하며 기존 금액·배분을 덮어쓰지 않습니다.
- 과거 전표 생성도 신규 처리와 중복되지 않게 원천 연결을 검증합니다. 은행 원본과 수동 등록의 기존 중복 가능성을 회계 도입으로 해결한 것으로 가정하지 않습니다.
- 도입 이전 미수·선입금·통장·기타 잔액은 필요한 기초 계정과 대조합니다. 자료가 없는 과거 기간의 손익을 추정하거나 기초 잔액을 신규 수익·비용으로 자동 처리하지 않습니다.

참고 자료의 회계연도는 10월부터 다음 해 9월이고 손익계산서는 당기 1개월과 전기 12개월을 비교합니다. 제품은 관리대상별 회계연도 설정과 비교 기간 명시를 적용하며, 원본의 기간을 모든 대상의 고정값으로 사용하지 않습니다. 기존 은행 거래 업로드에 회계 보고서 업로드 기능이 추가된 것으로 해석하지 않습니다.

### 이 문서로 확인할 수 있는 범위

현재 문서는 첨부를 보지 않아도 계정과목 관리 원칙과 확정한 개발 범위·수익 및 비용 기준을 읽을 수 있습니다. 최종 기본 계정 목록·개별 자료의 성격·예외별 정정·저장 방식까지 모두 정해진 구현 명세는 아닙니다. 남은 상세 설계는 7절에 구분하며, 누락된 결정을 저장소 밖의 첨부 파일에 맡기지 않습니다.

원본의 정확한 서식이나 개별 금액을 다시 대조해야 하는 작업은 원본에 접근할 수 있는 환경에서 별도로 확인해야 합니다. 위 요약을 원본 파일의 사본이나 회계 적정성 검증 결과로 취급하지 않습니다.

## 7. 확정 범위와 개발 순서

| 단계 | 범위 | 다음 단계 전 확인 |
| --- | --- | --- |
| 0. 기본 기준 확정·상세 설계 | 기본 범위는 사용자 확정 완료. 실제 자료 분류·예외 처리·원천 대조와 저장 설계 보완 | 아래 D1~D9의 결정 결과와 남은 상세를 구분. 전체 기준의 재승인을 요구하지 않음 |
| 1. 계정과목 연결 | 기본 과목·설정, 부과·기타 입금·지출 연결, 기존 자료 검토 | 계정 식별·권한·과거 연결·귀속 기준 |
| 2. 최소 자동전표 | 업무 원천 연결, 생성·검증·중복 방지·처리 상태·정정·재처리 | 수납 예외·내부 이체·외부 부담·기초 잔액·업무 실패 처리 |
| 3. 손익·원장·정산 조회 | 월별·연간·선택 기간, 과목별 상세와 원천 연결, 다운로드 | 원천과 집계 대조, 미처리 표시, 비교 기간·보고서 범위 |

재무상태표·일월계표의 제품 화면, 범용 수동전표, 고정자산·감가상각 관리, 세무 신고와 실제 마감·잠금·재오픈은 후속 범위로 확정했습니다. 미지급·선급·회계 정정에 필요한 입력과 내부 전표 검증은 이번 범위에 포함합니다.

### 사용자 확정 결과

사용자는 제시한 권장안을 승인했습니다. 확정 기준의 원문은 [회계·정산 도메인 정책](../domain/domainRules.md#회계정산-개발-범위와-처리-기준-2026-11-04-사용자-확정)을 따르며 아래는 결정 결과의 요약입니다. 승인이 실제 자료의 성격이나 미제시된 예외 처리까지 결정했다는 뜻은 아닙니다.

| ID | 항목 | 결정 결과와 남은 상세 |
| --- | --- | --- |
| D1 | 손익 주체·방식 | 관리대상 운영 회계에 발생 기준 손익 추가. 기존 자금 정산 유지 |
| D2 | 수익 | 일반 관리비는 부과월 수익, 납부는 미수 회수. 예치·적립 등 실제 항목 성격은 확인 후 분류 |
| D3 | 비용 | 귀속 월 기준, 미지급 등록·지급 연결·선급 기간 배분 포함. 입력·기간 배분·원천 연결 상세 설계 필요 |
| D4 | 외부 부담 | 회수 권리가 확인된 외부 몫은 미수금, 우리 몫은 비용. 정산 제외·회수 포기·차액의 예외 처리는 보완 |
| D5 | 조회 | 월별·기간별·연간 12개월, 관리대상별 회계연도 설정, 전체·동별 조회. 공통 귀속·과거 소속의 상세 표현은 설계 |
| D6 | 과거 자료 | 대상별 회계 시작 월과 확인한 기초 잔액·기존 업무 적용. 실제 시작 월·반영 기간은 대상별 확인 |
| D7 | 메뉴·범위 | 회계·정산의 네 메뉴, 지출 과목 분할·부담 배분, Excel·PDF와 원천 상세 연결. 일월계표·재무상태표 화면·마감은 후속 |
| D8 | 선입금·예외 | 선수금 기본 처리 확정. 음수 청구·환불·수납된 청구의 정정은 실제 성격과 예외별 정책 보완. 미처리 누락 금지 |
| D9 | 권한·정정 | 회계 설정·조정·재처리 ADMIN, 조회 MANAGER 포함. 정정 이력 보존, 조회형 보고서 제공. 실패 처리·복구는 상세 설계 |

### 남은 상세 설계와 자료 확인

최종 기본·필수 계정 목록과 보고서 분류, 부과 수익의 통합/세분화, 명칭·코드 변경 이력과 미사용 과목 삭제 범위를 구체화합니다. 대상별 예치·적립 성격, 기초 잔액과 시작 월은 실제 자료를 확인합니다. 음수 청구·환불·회수 포기·수납 후 정정은 아직 결정되지 않은 업무 처리를 승인된 것으로 기록하지 않고 별도 정리합니다.

공통 기본 과목 제공의 물리 방식, ID·코드의 제약, 전표 생성의 동기/비동기 처리와 재시도 저장 방식은 확정한 업무 정책에 맞춰 상세 설계합니다. 후자의 기술 선택을 모두 사용자에게 개별 승인받아야 한다는 뜻은 아닙니다. 예외 정책과 원천 대조를 해결하기 전 전체 회계 구현을 완료한 것으로 표시하지 않습니다.

## 8. 후속 설계 문서의 책임

확정 정책은 [도메인 규칙](../domain/domainRules.md#9-회계), 저장 구조는 [ERD](../domain/erd.md#11-회계)에 반영합니다. 공유 API 계약은 구현 범위 확정 후 기능 단위로 모읍니다. 화면·상태·브라우저 동작은 `client/docs/`, 저장·트랜잭션·동시성·재처리는 `server/docs/`에서 관리합니다.

현재는 기획과 확정 정책을 문서에 반영한 단계입니다. 회계 전용 API·물리 스키마·빈 기능 슬라이스·Migration·업무 테스트를 미리 만들지 않습니다. 구현 시 관련 화면·API·저장 문서와 검증 결과를 함께 갱신하고, 범위 확정과 구현 완료를 구분합니다.
