# 세대 관리 API

작성일: 2026-10-10. **상태: 목록 조회·추가·기본 정보 수정, 동 추가·이름 수정, 세대 일괄 추가, 세대·동 삭제, 세대별 대표 주민·가입 요약과 Client 연결 구현.**

[도메인 규칙](domainRules.md#3-관리대상--동--세대)과 [ERD](erd.md#53-units)의 기존 세대 스키마를 사용하며 청구 취소 상태·감사 정보는 [관리비 Migration](../server/docs/billing.md#세대-추가삭제-연동)으로 추가합니다. 사용자가 세부 정책은 후속 결정하도록 요청한 범위의 초기 구현입니다. 세대·동 삭제는 2026-10-10 사용자 요청에 따라 기존 소프트 삭제 필드로 구현합니다. 별도 변경 이력 저장·비활성화·주민 이동 정책은 후속 결정 대상이며 과거 청구 스냅샷은 유지합니다. 동·세대 삭제의 주민·당월 청구 정리와 신규 세대 즉시 부과는 2026-10-12 확정 기준을 적용합니다.

## 인증과 범위

모든 요청은 Bearer 인증과 정상 계정 확인 후 `ManagementAccessService`로 현재 `ADMIN` / `MANAGER` 참여를 검사합니다. 이번 구현은 기존 관리 영역 접근 검증을 재사용하며 다른 업무의 권한 범위를 확정하지 않습니다. 현재 권한 조건과 인증 오류는 [관리 영역 접근 API](managementAccessApi.md#2-공통-인증과-조회-기준)를 따릅니다. 응답은 `Cache-Control: no-store`입니다. 주민 명부는 기존 관리소장 전용 권한을 유지하므로 세대별 주민 요약은 `ADMIN`에게만 반환하고 `MANAGER`에게는 `residentSummaries: null`을 반환합니다.

| 요청 | 성공 | 용도 |
| --- | --- | --- |
| `GET /api/properties/{propertyId}/units` | 200 | 저장된 동 구분·동·세대 목록 조회 |
| `POST /api/properties/{propertyId}/units` | 201 | 한 세대 추가 |
| `PUT /api/properties/{propertyId}/units/{unitId}` | 200 | 동일 ID 세대의 기본 정보 수정 |
| `POST /api/properties/{propertyId}/units/batch` | 201 | 자동 입력으로 만든 세대 일괄 추가 |
| `POST /api/properties/{propertyId}/buildings` | 201 | 동 있음 관리대상에 동 추가 |
| `PUT /api/properties/{propertyId}/buildings/{buildingId}` | 200 | 기존 동 ID를 유지해 이름 수정 |
| `DELETE /api/properties/{propertyId}/units/{unitId}` | 204 | 한 세대 소프트 삭제 |
| `DELETE /api/properties/{propertyId}/units` | 204 | 선택 세대 일괄 소프트 삭제 |
| `DELETE /api/properties/{propertyId}/buildings/{buildingId}` | 204 | 동과 연결 세대 소프트 삭제 |

## 목록 조회

```json
{
  "propertyId": "f5405dd1-42ea-4279-9302-812ffcc2d21b",
  "hasBuildings": true,
  "buildings": [
    { "id": "11111111-1111-4111-8111-111111111111", "name": "101동" }
  ],
  "units": [
    {
      "id": "22222222-2222-4222-8222-222222222222",
      "buildingId": "11111111-1111-4111-8111-111111111111",
      "unitNumber": "001",
      "displayName": null,
      "floor": -1,
      "status": "ACTIVE"
    }
  ],
  "residentSummaries": {
    "22222222-2222-4222-8222-222222222222": {
      "representativeName": "예시 주민",
      "total": 3,
      "approved": 1,
      "pending": 1,
      "notJoined": 1
    }
  }
}
```

삭제되지 않은 세대를 반환합니다. 상태는 기존 스키마의 `ACTIVE / VACANT / INACTIVE`를 읽고 비활성 세대의 수정은 허용하지 않습니다. 동 선택지에는 같은 관리대상의 삭제되지 않은 활성 동을 반환합니다. 청구 정보와 주민 연락처·계정 ID는 포함하지 않습니다. 정상적인 빈 목록에는 `units: []`를 반환하고 조회 실패는 오류로 구분합니다.

`residentSummaries`는 조회된 세대 UUID를 키로 하는 현재 주민 요약입니다. 관리소장 응답에는 모든 조회 세대의 항목을 포함하고, 등록 주민이 없는 세대는 이름 `null`·모든 건수 `0`을 반환합니다. `representativeName`은 현재 대표 주민의 이름이며 대표가 없으면 `null`입니다. `total`은 해당 세대에 현재 소속된 삭제되지 않은 주민 수입니다. `approved + pending + notJoined = total`을 만족합니다. 각 가입 상태와 확인된 주민만 집계하는 기준은 [주민 관리 API](residentManagementApi.md#목록-조회)의 판정을 재사용합니다. 소속 없는 주민·과거 세대 관계·삭제된 명부는 세대 집계에 포함하지 않습니다. 명부 조회 실패를 `0명`으로 대체하지 않고 요청 전체를 실패 처리합니다. 요약은 조회 결과로 계산하며 DB 집계 컬럼이나 별도 API를 추가하지 않습니다.

현재 목록 API는 전체 세대를 조회합니다. Client에서 동 이름·호수의 숫자를 인식하는 정렬, 동·호수·세대 별칭 검색, 동·상태 필터와 10 / 20 / 50개 페이지 표시를 처리합니다. 서버 페이지네이션 쿼리를 제공하는 API는 아닙니다.

## 추가·수정 요청

두 요청은 같은 본문을 사용합니다. 신규 ID는 서버가 생성하며 수정 ID는 URL로 지정합니다.

```json
{
  "buildingId": "11111111-1111-4111-8111-111111111111",
  "unitNumber": "001",
  "displayName": null,
  "floor": -1,
  "status": "ACTIVE"
}
```

- `buildingId`: 동 있음이면 같은 관리대상의 활성 동 UUID 필수. 동 없음이면 생략 / null.
- `unitNumber`: 앞뒤 공백 정리 후 1~30 Unicode 코드 포인트. 문자·앞자리 0·내부 공백·`호` 접미사 유지.
- `displayName`: 선택 입력, 공백만 입력하면 null. 최대 50 Unicode 코드 포인트.
- `floor`: 선택 입력, -32,768~32,767 정수. 지하는 음수.
- `status`: `ACTIVE / VACANT`만 허용. 주민 관계·접근권한은 유지하며 공실 전환·사용 중 복귀는 당월 부과 대상에 같은 트랜잭션으로 반영. 미납·수납은 별도 정책.

성공 응답은 목록의 세대 한 항목과 같은 구조입니다. 수정은 `id`, 관리대상 소속과 생성 시각을 유지합니다. 동·호수 변경은 현재 기본 정보만 변경하며 과거 시점의 이름을 보존하는 기능을 제공하지 않습니다. 주민 이사·퇴거 API로 사용하지 않습니다.

단일·일괄 추가한 사용 중 세대는 주민 명부 등록 여부와 관계없이 한국시간 당월 전액 청구를 같은 트랜잭션에서 생성·확정합니다. 공실 세대는 부과에서 제외합니다. 당월 적용 기본 설정을 복사하고 기존 청구·다음 달 예약 설정은 유지합니다. 청구 생성 실패 시 세대도 저장되지 않습니다.

호수 중복은 같은 동 안에서, 동 없음이면 같은 관리대상 안에서 검사합니다. 삭제된 세대의 호수는 재사용할 수 있으며 미삭제 세대만 중복 검사합니다. 재추가는 새 ID로 저장하고 삭제된 세대·주민 관계·청구 이력을 복구하거나 덮어쓰지 않습니다. 현재 쓰기 API는 관리대상 행의 비관적 잠금 안에서 중복 검사와 저장을 수행해 동시 요청을 직렬화합니다. DB 부분 유일 인덱스도 같은 미삭제 조건으로 중복을 차단합니다.

## 동 관리·일괄 추가

동 추가·수정은 `{ "name": "101동" }`를 받고 `{ "id": "동 UUID", "name": "101동" }`를 반환합니다. 초기 등록과 같은 동 접미사 정리 후 1~50 Unicode 코드 포인트를 허용합니다. 같은 대상의 삭제되지 않은 동 이름은 중복할 수 없습니다. 동 없음 관리대상의 동 구분을 바꾸지는 않습니다. 이름 수정에도 같은 관리대상의 활성 동인지 검사하며 연결 세대 ID를 유지합니다.

일괄 추가는 `{ "units": [단일 추가와 같은 입력, ...] }`를 받고 새 세대 응답 배열을 반환합니다. 1~1,000개 항목을 모두 검증하고 같은 관리대상 잠금·트랜잭션 안에서 저장합니다. 요청 내부 또는 기존 DB의 호수와 충돌하면 전체 요청을 거절하며 부분 저장하지 않습니다. 중복 검사에는 미삭제 세대와 요청 내부의 호수만 포함하며 삭제된 호수의 단일·일괄 재추가를 모두 허용합니다. Client 미리보기는 조회된 기존 호수를 제외하며, 그 후 발생한 동시 추가 충돌에는 오류를 표시하고 입력을 유지합니다.

## 세대·동 삭제

동 삭제는 같은 관리대상의 미삭제 동이 2개 이상일 때만 허용합니다. 마지막 동 삭제 요청은 `409 LAST_BUILDING_NOT_DELETABLE`이며 연결 세대도 변경하지 않습니다. 관리대상 행 잠금 안에서 개수를 확인해 동시에 서로 다른 동을 삭제해도 마지막 동을 보존합니다. 이미 삭제된 동의 재요청은 남은 동 수와 관계없이 204입니다.

일괄 삭제 본문은 `{ "unitIds": ["세대 UUID", ...] }`이며 1~1,000개의 UUID를 받습니다. 같은 ID가 반복되면 한 번만 처리합니다. 단일·일괄·동 삭제 모두 관리 권한과 URL의 관리대상 소속을 검증하며, 성공 응답은 본문 없는 204입니다. 존재하지 않거나 다른 관리대상에 속한 대상은 404이며 일괄 요청 일부만 삭제하지 않습니다.

삭제는 기존 `deleted_at` / `deleted_by`를 기록하고 목록·카드 집계에서 제외합니다. 동 삭제는 해당 동과 연결 세대를 같은 트랜잭션에서 처리합니다. 이미 삭제된 대상에 대한 재요청은 성공하며 최초 삭제 시각·처리자를 유지합니다. 추가·수정과 같은 관리대상 행 잠금을 공유해 삭제 중 세대가 새로 연결되는 것을 방지합니다. ID·호수·상태·별칭과 다른 동·계좌·등록 결과는 유지합니다. 삭제한 호수는 새 세대 ID로 다시 추가할 수 있으며 예전 삭제 요청의 재시도는 새 세대를 삭제하지 않습니다.

단일·일괄·동 삭제 모두 대상 세대의 현재 주민 명부·소속을 소프트 삭제하고 해당 관리대상의 주민 권한을 종료하며 삭제 세대의 대기 가입 신청을 취소합니다. 현재 주민이 연결되어 있으면 기존 주민 삭제 기준대로 ADMIN 권한이 필요합니다. 당월 청구는 취소 상태로 보존하고 목록·합계에서 제외하며 이전 달 청구는 유지합니다. 주민 정리·청구 취소·동·세대 삭제는 같은 트랜잭션으로 처리합니다. 이미 삭제된 동·세대의 재요청도 남은 현재 주민 관계·당월 청구를 정리하며 최초 삭제·취소 시각은 유지합니다. 수납·회계 연결에 따른 취소·정산은 후속 범위입니다.

## 오류

| HTTP | 코드 | 의미 |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | UUID·입력 형식·동 소속·동 구분 오류 |
| 401 / 403 | 기존 인증·계정·접근 오류 | 인증 또는 현재 관리 권한 없음 |
| 404 | `UNIT_NOT_FOUND` | 요청 관리대상 안에서 수정·삭제할 세대 또는 동을 찾을 수 없음 |
| 409 | `DUPLICATE_UNIT` | 동일 범위의 호수 중복 |
| 409 | `DUPLICATE_BUILDING` | 동일 관리대상의 동 이름 중복 |
| 409 | `LAST_BUILDING_NOT_DELETABLE` | 마지막 미삭제 동은 삭제 불가 |
| 409 | `UNIT_NOT_EDITABLE` | 비활성 세대 수정 시도 |
| 404 | `BILLING_SETTINGS_NOT_FOUND` | 즉시 부과에 필요한 관리비 설정 없음, 세대 추가 롤백 |
| 503 | `UNIT_SERVICE_UNAVAILABLE` | 세대 저장소 장애 |
| 500 | `INTERNAL_SERVER_ERROR` | 그 외 내부 처리 실패 |

오류 본문은 `code`와 고정된 `message`로 구성하고 SQL·내부 예외·입력 원문을 반환하지 않습니다. Client는 저장 실패에 모달 입력을 유지하며 자동 쓰기 재시도를 하지 않습니다. 저장 중에는 중복 제출과 취소·Escape를 차단하고 성공 후 서버 목록을 다시 조회합니다.

## Client 설계 참조

메뉴 계층과 화면 폴더, 표·카드·필터, 상세·수정·삭제의 진입점과 구조 검증은 [Client 세대 목록 설계](../client/docs/unitList.md)에서 관리합니다. 초기 등록의 초안 처리와 기존 모달 재사용 기준은 [Client 등록 설계](../client/docs/propertyRegistration.md)를 참조합니다. API가 제공하는 삭제 기능은 화면의 행 삭제 버튼을 요구하지 않습니다.
