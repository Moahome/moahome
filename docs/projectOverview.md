# 모아홈 프로젝트 개요

기준일: 2026-10-24. 프로젝트의 목적, 현재 구현 상태와 검토 후보를 관리합니다. 기능 상태가 바뀌면 아래 현황표를 갱신하고 상세 정책·계약은 해당 기준 문서에 반영합니다.

## 1. 프로젝트 소개

모아홈은 소규모 빌라·공동주택의 주민 관리, 관리비 부과·수납과 자금 관리를 연결하는 플랫폼입니다. 관리자가 처리한 청구·수납·은행 거래·지출을 원천으로 주민 조회와 정산을 구성하고, 회계 연결은 후속 범위로 둡니다. 범용 ERP 전체를 구현하는 것이 목적은 아닙니다.

## 2. 서비스 구성

| 사용자·영역 | 목적 | 상세 기준 |
| --- | --- | --- |
| 관리소장·부담당자 | 세대·주민·가입 요청, 부과·수납·통장·지출·정산 관리 | [도메인 규칙](domainRules.md)과 기능별 API |
| 주민 | 가입 승인 후 본인 세대의 관리비·납부 정보를 조회하는 서비스 목표 | 주민 참여는 구현, 주민 홈·조회는 아래 현황표 참조 |
| 회계 | 업무 결과를 자동전표·원장과 연결하는 후속 설계 | [회계 정책](domainRules.md#9-회계), [ERD](erd.md#11-회계) |

플랫폼 운영 권한과 관리대상별 ADMIN·MANAGER·RESIDENT 역할은 구분합니다. 역할별 허용 범위는 도메인 규칙에서 관리합니다.

## 3. 핵심 데이터 원칙

- 관리의 기본 단위는 Property이며 Building은 선택입니다. Unit은 항상 Property에 속합니다.
- 청구·수납·은행 원본·지출은 서로 다른 의미를 가진 연결 데이터입니다. 화면별로 금액과 납부 상태를 중복 저장하지 않습니다.
- 실제 입금과 청구 충당, 통장 출금과 동별 부담액, 은행 확인 잔액과 계산 잔액을 구분합니다.
- 원본과 확정 이력을 보존하며 허용된 취소·소프트 삭제·정정 절차를 사용합니다.
- 주민 화면 열람을 관리자 업무 처리의 실행 조건으로 사용하지 않습니다.

금액·상태·권한·예외의 상세 정책과 미정 사항은 [도메인 규칙](domainRules.md), 저장 구조는 [ERD](erd.md)에서 관리합니다.

### 검증 상태의 해석

Client에는 API·모델·브라우저 테스트, Server에는 단위·Security·격리 Redis/PostgreSQL 통합 테스트가 있습니다. 테스트의 존재와 이번 변경에서의 실행 결과는 구분합니다. 실제 카카오 로그인·제공자 설정·배포 환경 확인을 모의 응답 테스트의 통과로 대신하지 않습니다. 실행 명령은 각 영역의 AGENTS.md와 [개발 가이드](developmentGuide.md#6-테스트--빌드)를 따릅니다.

## 5. 개발 계획과 검토 후보

### 기존 개발 방향

2026-10-24에 정한 정산·회계의 상대적 순서는 월별 정산 조회·다운로드 → 업무 마감·정정 → 회계입니다. 첫 범위는 구현됐으며 나머지의 세부 정책·완료 기준은 관련 기능을 구현하기 전에 정합니다. 이 순서만으로 다음 작업이나 일정을 확정하지 않습니다.

기존 MVP 목표에서 남은 주민 홈·조회와, 수동 지출 취소·은행 연결 등 현재 기능의 미완성 범위는 위 현황표에서 관리합니다. 기존 1차·2차 기능 목록을 별도 완료 목록으로 중복 관리하지 않습니다.

### 추가 검토 후보

2026-10-24 사용자는 아래 항목을 고려사항으로 제시했습니다. 도입·정책 변경·구현은 아직 확정하지 않았습니다.

| 후보 | 상태 | 정해야 할 내용 |
| --- | --- | --- |
| 공지사항 | 검토 중 | 플랫폼 운영 공지와 건물·단지 공지의 구분, 작성·열람 대상과 공개 범위. 현재 준비 중 메뉴만 있음 |
| 채널톡 | 검토 중 | 모아홈 서비스 문의와 주민↔관리자 문의 중 목적·운영 주체·노출 대상. 현재 연동 없음 |
| 초대코드 추가·개편 | 검토 중 | 서비스 이용·주민 참여·외부 부담당자 중 초대 대상과 기존 가입 흐름과의 관계. 기존 외부 부담당자 코드 구현은 유지 |

기존 주민 가입은 참여 링크와 관리자 승인을 사용합니다. 추가 검토만으로 주민 초대코드 도입이나 기존 외부 부담당자 초대 정책 변경을 확정하지 않습니다.

은행 API·가상계좌·알림톡·PDF 고지서·증빙 첨부·외부 회계 연계도 후속 검토 대상이며 구현 일정은 없습니다. 후보의 대상·최소 범위·기존 기능 의존성을 확인한 뒤 다음 개발 묶음을 정합니다.

## 6. 관리비 및 은행 거래 기본 흐름

```text
관리 시작·기존 잔액 인계 → 월별 청구 생성·확정
실제 은행 이체 → 파일 업로드·수동 등록 → 세대 수납 확정·충당 → 납부 상태
은행 출금·수동 지출 → 부담 동·외부 배분 → 동별 잔고·외부 정산
기존 업무 원천 → 월별 정산 조회·보고서
```

파일 미리보기는 저장하지 않습니다. 가져오기에서 유일하게 일치한 입금은 자동 확정하고 나머지는 관리자 검토로 남깁니다. 지출은 배분을 검토한 뒤 확정합니다. 카드·PG 결제나 실시간 은행 API는 현재 사용하지 않습니다.

## 7. 회계 연결 원칙

회계는 부과·수납·지출의 업무 결과를 재입력 없이 연결하는 후속 설계입니다. 양수 부과의 미수금·관리비수익, 청구 충당 입금의 보통예금·미수금 등 예시와 미정 사항은 [회계 정책](domainRules.md#9-회계)에서 관리합니다. 현재 월별 정산은 전표·회계 마감 구현을 선행 조건으로 두지 않습니다.
