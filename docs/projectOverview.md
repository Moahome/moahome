# Project Overview

## 1. 프로젝트 소개

**모아홈(MoaHome)**은 소규모 빌라·공동주택의 관리 업무를 위한 관리비 통합 플랫폼입니다.

서비스는 다음 세 영역을 하나의 시스템으로 연결합니다.

- 주민 관리
- 관리자 관리비
- 관리비 회계

주민, 관리자, 회계 시스템이 각각 별도의 데이터를 관리하는 것이 아니라 동일한 관리비·수납·은행거래·지출 데이터를 기준으로 동작합니다.

관리자가 실제 관리 업무를 처리하면 주민 화면의 납부 상태가 갱신되고, 동일한 원천 데이터를 기반으로 회계 기록과 원장이 생성되는 구조를 목표로 합니다.

---

## 2. 서비스 구성

### 주민

주민은 복잡한 회계 정보가 아니라 자신의 세대와 관리비 정보를 쉽게 확인하는 데 집중합니다.

주요 기능:

- 카카오 로그인
- 초대코드를 통한 관리대상 참여
- 세대 정보 확인
- 이번 달 관리비 확인
- 관리비 상세 항목 확인
- 납부계좌 확인
- 납부 상태 확인
- 월별 관리비 / 납부 내역 확인
- 공용 지출 확인
- 공지사항 확인

주민 화면에는 차변, 대변, 전표, 계정과목 등 내부 회계 용어를 직접 노출하지 않습니다.

### 관리자

관리자는 실제 공동주택 관리 업무를 처리합니다.

관리대상별 관리소장(`ADMIN`)과 부담당자(`MANAGER`)를 구분합니다. 둘 다 주민 가입을 승인할 수 있고, 관리대상 역할 변경은 관리소장만 수행합니다. 서비스 전체 운영을 위한 플랫폼 관리자 권한은 이 역할과 별도로 관리합니다. 상세 정책은 [도메인 규칙](domainRules.md)을 따릅니다.

주요 기능:

- 관리대상 관리
- 동 / 세대 관리
- 주민 관리
- 초대 및 가입 승인
- 관리비 부과
- 납부 / 미납 관리
- 관리계좌 관리
- 은행 거래내역 관리
- 입금 매칭
- 지출 관리
- 회계 조회
- 정산 / 월 마감
- 공지 관리

### 관리비 회계

관리자의 업무 결과를 회계 데이터와 연결합니다.

주요 기능:

- 계정과목
- 자동 전표
- 계정별 원장
- 세대별 미수원장
- 거래처별 조회
- 월별 / 연간 손익
- 통장 대사
- 월 마감

범용 ERP 전체를 구현하는 것이 목적이 아닙니다. 관리비 운영에 필요한 회계 기능을 우선 구현합니다.

## 3. 핵심 데이터 원칙

### 하나의 원천 데이터

주민 화면, 관리자 화면, 회계 시스템을 위해 동일한 업무 데이터를 화면별로 따로 중복 관리하지 않습니다.

```text
관리비 부과
    ↓
세대별 청구
    ↓
수납 확인 및 배분
    ↓
납부 상태 반영
    ↓
회계 반영
```

청구, 수납, 은행 원본 거래와 회계 기록은 각자의 업무 의미를 갖는 연결된 데이터입니다.

같은 정보를 화면별로 따로 관리하면서 금액이나 납부 상태가 달라지는 구조를 만들지 않습니다.

주민 화면은 위 업무 데이터의 조회 결과를 보여줍니다. 주민이 화면을 열어야 입금 확인이나 회계 처리가 진행되는 구조로 만들지 않습니다.

### 관리대상 구조

관리의 최상위 단위는 `Property`입니다.

```text
Property
├── Building (optional)
│   └── Unit
└── Unit
```

모든 관리대상에 동이 존재하는 것은 아니므로 `Building`은 선택 사항입니다.

`Unit`은 항상 하나의 `Property`에 속하며, 동이 있는 경우에만 `Building`에도 연결합니다.

### 납부 상태와 수납 배분

- 납부 상태는 단순 Y/N 값으로 저장하지 않고 청구 금액과 실제 배분된 수납 금액을 기준으로 계산합니다.
- 은행 거래 수집, 입금 추천과 수납 확정은 서로 구분합니다.
- 부분납부를 지원할 수 있는 구조를 유지합니다.
- 하나의 수납을 하나 이상의 청구에 배분할 수 있는 구조를 유지합니다.

### 변경 이력

- 은행 원본 거래는 임의로 수정하거나 삭제하지 않습니다.
- 확정된 수납과 회계 기록은 취소, 역분개, 조정 등 이력을 보존하는 방식으로 정정합니다.
- 마감된 기간의 일반 수정은 제한합니다.

업무별 상세 기준과 아직 정하지 않은 정책은 [도메인 규칙](domainRules.md)에서 관리합니다.

## 4. 현재 개발 상태

프로젝트는 랜딩 페이지와 로그인 화면을 구현한 초기 개발 단계입니다.

- Client에는 `/` 경로의 반응형 랜딩 페이지와 공통 색상 토큰이 있습니다. 서비스 소개, 주요 기능, 이용 대상과 FAQ를 제공하며, 서비스 화면은 예시 목업입니다.
- Client의 `/login`에는 `(auth)` 라우트 그룹의 반응형 카카오 로그인 화면이 있습니다. 카카오 버튼은 Server 로그인 시작 주소로 연결되며, 전역 Provider가 앱 시작 / 새로고침 시 CSRF 조회 / 토큰 재발급 후 Access Token을 메모리에 보관하고 본인 정보를 조회합니다. `useSession()`으로 React Query 조회를 공유하고 `/login/callback`은 본인 정보 조회까지 성공하면 `/start`로 이동합니다. 약관은 준비 중 안내를 제공합니다.
- `/start`는 `(main)` 라우트 그룹의 시작 화면입니다. 세션 복원과 본인 정보 조회가 성공한 로그인 사용자만 접근하며 닉네임 / 선택 프로필을 표시합니다. 조회 중에는 확인 상태를 표시하고, 인증 거부나 이용 불가 계정은 `/login`으로 이동합니다. 일시 장애는 시작 화면 대신 재시도 안내를 표시합니다. 관리할 곳 만들기, 초대코드 참여와 승인 대기 안내는 데스크톱 / 모바일 배치를 지원합니다. 관리대상 등록 / 참여 / 요청 조회와 알림 API가 아직 없어 해당 버튼은 준비 중 안내를 표시합니다. 화면 요소와 전용 스타일은 `screens/start/ui/_components/`의 헤더, 시작 안내, 공통 시작 카드, 승인 대기 카드, 상태 안내와 다이얼로그로 분리하며 각각의 컴포넌트 폴더에 함께 둡니다. 시작 카드 전용 일러스트는 `start-card/`, 공유 아이콘은 `start-icon/`에서 관리합니다. 시작 화면의 기준은 첫 방문 여부가 아닌 접근 가능한 관리대상 0개 / 승인 대기 요청 없음이며, 재방문도 같은 조건을 따릅니다. 현재 본인 정보 응답에는 소속과 대기 요청이 없어 모든 정상 로그인 사용자의 공통 목적지로 사용하고 실제 분기는 후속 조회 API 구현 시 연결합니다.
- Server에는 JWT 검증, Redis 로그인 세션, 웹·앱 재발급 / 로그아웃 API, Bearer 기반 `GET /api/users/me`와 CSRF / CORS 설정이 있습니다. 본인 정보는 ID, 닉네임, 선택 프로필 이미지, 플랫폼 역할과 정상 계정 상태를 제공합니다. 인증 동작은 단위 테스트와 격리된 Redis 통합 테스트로 검증합니다.
- 웹 카카오 OAuth 시작 / 콜백과 사용자 / 소셜 계정의 세션 연결은 Server에 구현되어 있습니다. Client 공통 API / 세션 복원과 로그인 화면은 모의 인증 응답 기반 Playwright 테스트로 검증하며 실제 카카오 계정 로그인은 별도로 확인합니다.
- 관리대상별 로그인 진입 분기와 업무 화면, 해당 도메인 로직과 업무용 Migration은 후속 구현 범위입니다.
- 위 서비스 구성의 기능 목록은 서비스 목표이며 구현 완료 목록이 아닙니다.

현재 개발 상태가 변경되면 이 문서의 상태 설명도 함께 갱신합니다.

## 5. MVP 범위

서비스 전체 목표 기능을 한 번에 구현하지 않고 단계적으로 개발합니다.

### 1차 MVP

- 관리자가 관리대상과 세대를 등록할 수 있습니다.
- 주민이 카카오 로그인 후 세대 가입 승인을 받을 수 있습니다.
- 관리자가 월 관리비를 전체 세대에 생성할 수 있습니다.
- 주민이 자신의 관리비와 상세 항목을 조회할 수 있습니다.
- 주민에게 관리계좌, 납부금액과 입금 안내를 제공합니다.
- 관리자가 수동으로 수납을 등록할 수 있습니다.
- 수납 결과에 따라 미납 상태가 갱신됩니다.
- 관리비 부과와 수납에 대한 최소 자동전표를 생성합니다.
- 세대별 미수금 원장을 확인할 수 있습니다.

### 2차 기능

- 은행 Excel / CSV 업로드 및 포맷 매핑
- 입금 자동추천
- 부분납부 / 여러 달 수납 배분
- 통장 출금 기반 지출 분류
- 비용 회계
- 관리자 대시보드
- 월 마감
- 통장 대사

### 후속 확장

- 카카오 알림톡
- PDF 고지서
- 증빙 첨부
- 은행 API
- 가상계좌
- 외부 회계 / 세무 시스템 연계

각 단계의 상세 구현 순서와 기능별 완료 기준은 실제 개발 시 별도로 관리합니다.

## 6. 관리비 및 은행 거래 기본 흐름

초기에는 앱 내 카드 / PG 결제를 사용하지 않습니다.

주민에게 관리계좌와 납부금액을 안내하고, 주민이 자신의 은행 앱에서 직접 계좌이체하는 방식을 사용합니다.

```text
관리비 부과
    ↓
주민 고지
    ↓
주민 계좌이체
    ↓
은행 거래 반영
    ↓
입금 매칭
    ↓
수납 확정 및 배분
    ↓
납부 상태 반영
    ↓
회계 반영
```

초기 은행 거래 수집은 Excel / CSV 업로드 방식을 사용합니다.

업로드된 거래는 바로 수납으로 확정하지 않고 중복 여부와 거래 내용을 확인한 뒤 입금은 세대 후보, 출금은 지출 후보로 분류합니다.

입금 자동추천 결과와 실제 수납 확정은 구분하며 최종 확정은 관리자가 수행합니다.

은행 API와 가상계좌는 운영 규모와 필요성이 커질 경우 후속 확장으로 검토합니다.

## 7. 회계 연결 원칙

관리자가 동일한 업무 내용을 회계 시스템에 다시 입력하는 구조를 지양합니다.

관리비 업무의 결과가 회계 데이터로 연결되도록 구성합니다.

예:

```text
관리비 부과
→ 미수금 / 관리비수익

입금 매칭 확정
→ 보통예금 / 미수금

지출 확정
→ 비용 / 보통예금
```

확정된 회계 기록은 일반 데이터처럼 직접 삭제하지 않습니다.

잘못된 거래나 회계 기록을 정정해야 하는 경우 취소, 조정, 역분개 또는 정해진 재처리 절차를 사용하여 이력을 보존합니다.

범용 세무·급여·부가세·법인세 ERP 전체를 구현하는 것이 목적이 아닙니다. 관리비 운영에 필요한 회계 기록, 미수, 통장, 지출, 원장과 손익을 우선 범위로 합니다.

## 8. 기술 구성

| 영역 | 현재 구성 |
| --- | --- |
| Client | Next.js, React, TypeScript, Tailwind CSS |
| Client 구조 | FSD (Feature-Sliced Design) |
| Server | Java 21, Spring Boot, Spring Data JPA |
| Server 구조 | 도메인 중심 Layered Architecture |
| 영속 업무 데이터 | PostgreSQL |
| 세션 / 캐시 등 임시 데이터 | Redis |
| DB Migration | Flyway |

세부 구현 규칙, 명명 규칙, 색상과 검증 명령은 각 영역의 `AGENTS.md`를 따릅니다.

배포 환경은 아직 미정입니다.

초기 은행 거래 수집은 Excel / CSV 업로드를 기준으로 하며, 은행 API와 가상계좌는 후속 확장으로 검토합니다.

API 계약은 기능별 구현 범위를 정한 뒤 별도 문서로 작성합니다.

기본 정보 검증, 전체 정보 저장과 결과 조회의 요청 / 응답 / 오류는 [관리대상 등록 API](propertyRegistrationApi.md)에 함께 정의합니다. 화면 / 초안 관리는 [Client 등록 설계](../client/docs/propertyRegistration.md), 저장 / 중복 방지는 [Server 등록 설계](../server/docs/propertyRegistration.md)에서 관리합니다. 해당 API와 관리대상 업무 데이터 저장은 아직 구현되지 않았습니다.
