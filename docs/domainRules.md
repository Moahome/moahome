# 모아홈 도메인 규칙

## 1. 문서 목적과 상태

이 문서는 모아홈의 용어, 도메인 관계와 업무 규칙을 정의하는 프론트엔드 / 백엔드 공통 기준입니다.

`projectOverview.md`가 프로젝트의 목적과 전체 범위를 설명한다면,
이 문서는 각 업무가 어떤 기준으로 동작하는지를 정의합니다.

### 문서에서 사용하는 구분

- **기존 기준**: 프로젝트 문서에서 이미 제시한 업무 원칙입니다. 구현 완료를 의미하지 않습니다.
- **확정**: 사용자가 결정한 정책과 구현 기준입니다. 변경하려면 관련 정책을 다시 확인하고 문서와 구현을 함께 갱신합니다. 구현 완료를 의미하지 않습니다.
- **기존 설계안**: [ERD](erd.md) 등에 제시된 데이터 구조와 제약입니다. 최종 DDL 또는 상세 운영 정책의 확정을 의미하지 않습니다.
- **미정 / 확인 필요**: 아직 정하지 않았거나 문서 간 확인이 필요한 정책입니다. 구현 시 임의로 확정하지 않습니다.
- **후속 검토**: 현재 구현 범위 밖의 정책입니다. 관련 기능을 구현할 때 결정하며, 현재 구현의 선행 조건으로 추가하지 않습니다.

### 적용 원칙

- 업무 정책과 확정 여부는 이 문서에서, 테이블 / 컬럼 / 관계 / 제약은 [ERD](erd.md)에서 관리합니다. 정책 확정만으로 아직 검토하지 않은 상세 DDL, Enum 또는 API 계약까지 확정하지 않습니다.
- 기존 설계안에 있는 내용을 단순히 미정으로 되돌리지 않습니다.
- 기존 설계안이 존재하더라도 문서에 없는 세부 운영 정책까지 확정된 것으로 취급하지 않습니다.
- 업무 정책을 변경하면 관련 화면, 서버 로직과 테스트에 미치는 영향을 함께 확인합니다.
- 현재 구현에 필요한 미정 정책은 구현 전에 결정합니다.
- 문서 간 기준이 다르면 임의로 하나를 선택하지 않고 차이를 확인합니다.
- 새로 확정한 정책은 확정일과 결정 이유를 남기고 관련 ERD를 함께 갱신합니다. ERD와 실제 코드 / Migration의 차이를 확인하되, 구현되지 않은 전체 ERD를 미리 구현하지 않습니다.

프로젝트 전체 범위와 개발 단계는 [Project Overview](projectOverview.md)를 확인합니다.

코딩 규칙은 다음 문서를 따릅니다.

- [루트 AGENTS.md](../AGENTS.md)
- [Client AGENTS.md](../client/AGENTS.md)
- [Server AGENTS.md](../server/AGENTS.md)

## 2. 공통 용어

| 용어 | 의미 |
| --- | --- |
| 사용자 / User | 서비스에 로그인하는 사용자 계정입니다. 여러 관리대상에 참여할 수 있으며, 아직 참여한 관리대상이 없을 수도 있습니다. |
| 관리대상 / Property | 주민, 세대, 접근권한과 관리 업무를 구분하는 기본 관리 단위입니다. |
| 동 / Building | 동이 있는 관리대상에서 세대를 구분하는 선택적인 단위입니다. |
| 세대 / Unit | 관리비 부과와 주민 소속의 기준입니다. 반드시 하나의 관리대상에 속합니다. |
| 주민 / Resident | 관리자가 관리하는 실제 주민 정보입니다. 로그인 사용자와 구분하며 가입 전에도 명단에 존재할 수 있습니다. |
| 세대 관계 | 주민이 특정 세대의 소유자, 임차인, 가족 등으로 연결되는 관계입니다. 시스템 권한과 구분합니다. |
| 참여 / Membership | 사용자가 특정 관리대상에 참여하는 관계입니다. |
| 플랫폼 역할 | 서비스 전체 운영을 위한 계정 권한입니다. 일반 사용자와 플랫폼 관리자를 구분하며 관리대상별 역할과 별도로 판단합니다. |
| 관리대상 역할 / Role | 관리대상에서 사용자가 갖는 역할입니다. ADMIN은 관리소장, MANAGER는 부담당자, RESIDENT는 주민입니다. |
| 권한 / Permission | 특정 업무를 조회, 등록, 수정, 승인 또는 취소할 수 있는 범위입니다. |
| 초대 / Invitation | 관리대상이나 세대 등에 참여하도록 제공하는 초대 정보입니다. |
| 가입 요청 / Membership Request | 사용자가 관리대상과 세대에 참여하기 위해 승인을 요청한 기록입니다. |
| 부과기간 / Billing Period | 월별 관리비 부과를 관리하는 기간입니다. 회계기간과 구분합니다. |
| 청구 / Charge | 관리비 부과로 생성되는 세대별 청구 정보입니다. |
| 청구 항목 / ChargeItem | 청구 금액을 구성하는 개별 관리비 항목입니다. |
| 수납 / Payment | 관리비 납부로 인정하는 입금을 관리하는 업무 기록입니다. 은행 원본 거래와 구분합니다. |
| 수납 배분 / PaymentAllocation | 수납 금액을 특정 청구에 반영하는 연결 정보입니다. |
| 관리계좌 / Bank Account | 관리비 입금과 공용 지출에 사용하는 은행 계좌입니다. 주민 납부안내와 은행 거래 관리에 사용합니다. |
| 은행 거래 / BankTransaction | 은행에서 가져온 입금 / 출금 원본 거래입니다. 수납이나 지출 확정과 구분합니다. |
| 입금 매칭 | 은행 입금 거래를 세대 또는 수납 대상과 연결하는 업무입니다. 추천과 최종 확정을 구분합니다. |
| 지출 / Expense | 관리 업무에서 발생한 공용 지출 기록입니다. 은행 출금 거래와 연결될 수 있습니다. |
| 지출 상세 / ExpenseLine | 하나의 지출을 비용 항목별로 나누는 상세 정보입니다. |
| 계정과목 / Account | 회계 기록에서 금액을 분류하는 계정입니다. |
| 전표 / Journal Entry | 차변과 대변으로 구성되는 회계 기록입니다. |
| 회계 이벤트 / Accounting Event | 부과, 수납, 지출 등의 업무 결과를 회계 처리에 연결하는 기록입니다. |
| 회계기간 / Fiscal Period | 월별 회계 장부와 마감 상태를 관리하는 기간입니다. |
| 통장 대사 / Bank Reconciliation | 장부상 계좌 잔액과 실제 은행 잔액을 비교하는 업무입니다. |
| 마감 / Closing | 특정 기간의 업무 및 회계 데이터에 대한 일반 수정을 제한하는 처리입니다. |
| 감사 이력 / Audit | 주요 업무 처리와 변경을 추적하기 위한 기록입니다. |

## 3. 관리대상 / 동 / 세대

2026-10-10 세대 목록 구현 요청에 따라 저장된 세대의 단일·선택 삭제와 동·연결 세대 삭제를 제공합니다. 기존 소프트 삭제 필드로 원본 ID와 정보를 유지하며, 현재 구현 범위·재요청·호수 중복 기준은 [세대 관리 API](unitManagementApi.md#세대동-삭제)를 따릅니다. 동·세대 삭제와 주민·청구 연결은 아래 2026-10-12 확정 기준을 따르며 다른 상태 변경 정책은 후속 결정 대상입니다.

### 기존 기준

- 관리의 기본 단위는 `Property`입니다.
- `Building`은 선택 사항입니다.
- 동이 없는 빌라도 지원해야 합니다.
- `Unit`은 반드시 하나의 `Property`에 속합니다.
- 동이 있는 경우에만 `Building`에도 연결합니다.
- 특정 빌라나 특정 세대 수를 고정 전제로 사용하지 않습니다.
- 한 동, 여러 동, 동이 없는 관리대상을 고려합니다.

기본 관계는 다음과 같습니다.

```text
동이 있는 경우
Property → Building → Unit
                     └─ Unit은 Property에도 소속

동이 없는 경우
Property → Unit
```

동이 있다는 이유로 세대의 관리대상 소속을 대체하지 않습니다.

### 저장된 동의 최소 유지 기준

확정일: 2026-10-12. 저장된 동은 미삭제 동이 2개 이상일 때만 삭제할 수 있으며 마지막 동은 유지합니다. 초기 등록 초안의 삭제 흐름과는 구분합니다.

### 세대 변경과 주민·당월 청구 연결

확정일: 2026-10-12. 사용자가 다음 기준을 확정했습니다.

- 동·세대를 삭제하면 해당 세대에 현재 소속된 주민 명부와 현재 관계를 소프트 삭제합니다. 해당 관리대상의 주민 이용 권한을 종료하고 삭제 세대의 대기 가입 신청을 취소합니다. 다른 세대·관리대상의 주민과 권한, 과거 승인 이력은 유지합니다.
- 삭제한 세대의 한국시간 당월 청구는 취소하고 향후 부과 대상에서 제외합니다. 과거 월의 확정 청구·항목·금액·표시 스냅샷은 보존합니다. 취소도 원본을 제거하지 않고 최초 취소 시각·처리자·세대 삭제 사유를 남깁니다.
- 사용 중 세대 추가는 주민 명부 등록 여부와 관계없이 당월 전액을 즉시 부과합니다. 2026-10-12 변경에 따라 공실은 제외하며 당월 적용 기본 설정을 사용합니다. 다음 달 예약 설정은 당월 보충 청구에 적용하지 않습니다.
- 단일·자동 일괄 추가에는 같은 기준을 적용하며 기존 청구를 재계산하거나 중복 생성하지 않습니다. 주민 정리·당월 청구 취소·동·세대 삭제와 세대 추가·당월 부과는 각각 하나의 트랜잭션으로 처리합니다.
- 주민 명부 삭제의 기존 관리소장 전용 권한을 유지합니다. 현재 주민이 연결된 동·세대 삭제로 부담당자가 이 권한을 우회할 수 없습니다.

### 기존 설계안

물리 ERD v0.1에는 다음 기준이 제시되어 있습니다.

- 동 이름은 같은 관리대상 안에서 중복을 제한합니다.
- 동이 있는 세대는 같은 동 안에서 세대번호 중복을 제한합니다.
- 동이 없는 세대는 같은 관리대상 안에서 세대번호 중복을 제한합니다.
- 관리대상, 동, 세대에는 상태와 소프트 삭제를 위한 정보가 제안되어 있습니다.

2026-10-12 사용자 요청에 따라 삭제된 세대의 호수는 다시 사용할 수 있습니다. 같은 동(동 없음이면 같은 관리대상)의 미삭제 세대끼리만 호수 중복을 제한합니다. 구현에서는 재추가 시 새 세대 ID를 생성하고 삭제된 세대·관계·청구 이력은 보존합니다.

### 확정된 관리대상 등록과 초기 설정

확정일: 2026-10-05. 등록 도중에는 이전 단계의 입력을 유지하되, 초기 설정을 마치고 `관리 시작하기`를 선택할 때 전체 정보를 DB에 저장합니다. 중단한 등록으로 사용하지 않는 관리대상이 남지 않도록 합니다.

| 항목 | 확정 기준 | 결정 이유 |
| --- | --- | --- |
| 관리대상 이름 | 필수, 앞뒤 공백을 제거한 뒤 1~50자 | 등록 화면의 이름 제한과 저장 기준을 일치시킵니다. |
| 동 구분 | 동 있음 / 없음 선택을 필수로 받고 `has_buildings`에 저장 | 선택 결과와 초기 설정의 동 / 세대 구조를 일치시킵니다. |
| 단계 이동 | 다음 / 이전 이동에서 입력값 유지 | 앞 단계로 돌아가 수정할 수 있어야 합니다. |
| 새로고침 | 같은 등록 흐름의 입력값과 현재 단계 복원 | 새로고침 때문에 진행 중인 입력이 사라지지 않게 합니다. |
| 취소와 이탈 | 등록 취소, 등록 흐름 밖으로 이동, 탭 닫기 시 초안 폐기 | 등록을 그만둔 뒤에는 초안을 다시 사용하지 않습니다. |
| DB 저장 | 마지막 `등록하고 관리 시작`에서 전체 정보를 한 번에 저장 | 중간 단계에서 업무 데이터나 관리소장 권한을 생성하지 않습니다. |
| 완료 조건 | 세대, 관리계좌, 관리비 항목 각각 최소 1개 | 관리 운영에 필요한 초기 정보를 갖춘 뒤 시작합니다. |
| 초기 계좌 범위 | 공용 관리계좌만 등록하고 기본 계좌는 정확히 1개 지정 | 초기 납부안내 계좌를 명확히 하고 동별 계좌는 후속 계좌 관리에서 다룹니다. |
| 계좌 사용 시작일 | 등록 완료일로 자동 설정 | 초기 설정 화면에 사용 시작일 입력을 추가하지 않습니다. |
| 기본 관리비 금액 | 정수 원 단위, 0원·음수 허용(2026-10-08 변경) | 초기 기본 항목과 합계에 음수를 허용하며 실제 청구의 감액 / 조정 정책과 구분합니다. |

- 초기 등록은 2026-10-18 확정에 따라 기본 정보 → 동·세대 및 담당자 → 관리계좌 및 잔고 → 관리비 설정 → 최종 확인의 다섯 페이지로 관리합니다. 세부 입력·인계 기준은 [초기 설정 통합](#초기-설정의-인계관리-시작-통합-2026-10-18)을 따릅니다.
- 진행 중인 초안은 Client에서 현재 사용자와 탭 단위로 관리합니다. 로그아웃하거나 사용자가 바뀌면 폐기하며, 다른 계정이나 새 등록 흐름에 이전 입력을 사용하지 않습니다.
- 등록 초안을 DB나 Redis에 단계별로 저장하지 않습니다. 마지막 저장 전에는 `properties`, 동 / 세대, 관리계좌, 관리비 템플릿과 생성자 참여 레코드를 만들지 않습니다.
- 동 있음으로 등록하면 마지막 저장 시 최소 1개의 동을 등록하고 각 세대를 해당 관리대상의 동에 연결합니다. 동 없음이면 동을 생성하지 않고 모든 세대의 `building_id`를 비웁니다.
- 마지막 저장에서 Server가 전체 입력과 완료 조건을 다시 검증합니다. 기본 정보 검증 성공은 전체 등록 완료를 의미하지 않습니다.
- 마지막 저장은 관리대상, 필요한 동, 세대, 관리계좌, 관리비 템플릿 / 항목과 생성자의 관리소장 참여를 하나의 DB 트랜잭션으로 처리합니다. 검증 또는 저장 실패 시 일부 업무 데이터만 남기지 않습니다.
- 저장 전 요약 화면은 등록 정보 확인 단계입니다. Server의 저장 성공 응답을 받은 뒤 등록 완료를 표시하고 초안을 폐기합니다. 명확한 검증 / 저장 실패에는 입력을 유지해 수정하거나 재시도할 수 있게 합니다.
- 취소 시 미저장은 마지막 저장 요청을 시작하기 전의 초안에 적용합니다. 저장 요청 이후의 이탈로 이미 커밋된 등록을 삭제하거나, 응답 유실을 저장 실패로 단정하지 않습니다. 응답 유실 시 결과 확인과 중복 등록 방지는 최종 등록 API 계약을 따릅니다. 최종 제출과 같은 요청 ID로 결과 조회·재시도하며 성공을 확인한 뒤 완료를 표시합니다. 완료 후 목적지는 [Client 서비스 진입](../client/docs/serviceEntry.md#6-기존-등록-흐름과-연결)을 따릅니다.

공용계좌 / 기본 계좌 지정, 사용 시작일과 기본 관리비 금액 정책은 2026-10-05에 사용자가 추가로 확정했습니다. 초기 등록의 주민 연결은 필수가 아니며 명부 등록 이후 연결할 수 있습니다.

기본 정보 검증, 전체 저장 요청 / 응답 / 오류와 응답 유실 처리는 [관리대상 등록 API](propertyRegistrationApi.md)를 따릅니다. API의 형식 / 길이와 성공 결과 레코드는 구현을 위한 설계이며, 확정 정책을 넘어 전체 도메인의 상태 변경 / 삭제 기준을 확정하지 않습니다. 브라우저 임시 저장과 탭 복구는 [Client 등록 설계](../client/docs/propertyRegistration.md), 저장 내부 흐름은 [Server 등록 설계](../server/docs/propertyRegistration.md)에서 관리합니다.

### 초기 등록의 동·호수와 상태 입력

확정일: 2026-10-05. 초기 등록의 호수는 문자와 숫자를 허용하는 문자열로 입력하고 앞자리 0, 내부 공백과 `호` 접미사를 보존합니다. 층은 정수로 입력합니다. 동 이름에는 문자를 허용하고 `101` / `101동`, `A` / `A동`처럼 동 접미사 유무가 같은 저장 이름과 중복 검사 기준이 되도록 정리합니다.

초기 세대 상태는 사용중(`ACTIVE`) / 공실(`VACANT`)만 선택하고 비활성은 등록 입력에서 제외합니다. 등록 이후 비활성화 정책을 확정한 것은 아닙니다. 등록 초안의 세대 삭제에는 대상 동·호수를 표시한 확인 창을 제공하며 확인 전에는 입력을 유지합니다.

세대 자동 입력은 지하층의 음수 기호를 `B`로 바꿔 호수를 생성합니다. 예를 들어 -1층의 첫 호수는 `B101`이며 층 값은 -1로 보존하고 화면에는 `B1층`으로 표시합니다. 생성 범위에 0이 포함되어도 0층과 해당 호수는 생성하지 않습니다.

2026-10-08에 확정한 등록 초안의 동 관리 삭제는 동과 연결된 모든 세대를 함께 제거하는 방식입니다. 쓰레기통의 확인 창에 동 이름과 삭제할 세대 수를 표시하고 확인 후에만 해당 동과 세대를 제거합니다. 세대가 없는 동도 확인 후 제거합니다. 세대 목록에서는 개별 / 전체 선택 후 대상 동·호수와 개수를 확인해 선택한 세대만 삭제합니다. 동이나 검색 조건을 바꾸면 선택을 초기화합니다. 다른 동의 세대와 자동 입력 규칙은 유지합니다. DB에 저장된 동 / 세대의 삭제 정책을 의미하지 않습니다.

### 미정 / 확인 필요

- 관리대상 / 동 / 세대의 비활성화 조건
- 수납·회계가 연결된 청구의 취소·정산 처리 (세대 삭제의 당월 청구 취소·과거 보존은 위 기준으로 확정)
- 동 구조 변경 시 기존 세대 처리 방식
- 세대 이동 또는 세대번호 변경 시 과거 주민 / 청구 이력 처리 방식

### 초기 설정의 인계·관리 시작 통합 (2026-10-18)

사용자는 `/start`와 `/properties/add`의 초기 설정을 기본 정보 → 동·세대 및 담당자 → 관리계좌 및 잔고 → 관리비 설정 → 최종 확인의 다섯 페이지로 구성하도록 요청했습니다. 동·세대 페이지는 관리 담당자와 세대별 기존 미납·선납을 포함하고, 계좌 페이지는 실제 통장 잔액·동별 보유금을, 관리비 설정은 첫 부과월·기준일 확인을 포함합니다. 장부 기준일은 미납·선납 입력 때 선택하며 동별 잔고 기준일과 별도입니다.

기존 미납·선납 없음은 명시적으로 선택한 경우에만 전체 세대를 0원으로 인계합니다. 입력 모드의 빈 금액과 모르는 통장·동별 잔고를 자동으로 0원 확정하지 않습니다. 세대별 입력은 동별 합계로 확인할 수 있지만 동 단위 미납을 임의의 세대에 배분하지 않습니다. 통장·동별 잔고 차이도 자동 배분하거나 대사 완료로 확정하지 않습니다.

구현 선택: 새 최종 요청에만 인계 정보를 추가하고, 기존 등록·인계·동별 보유금·관리 시작·첫 부과와 성공 결과를 한 트랜잭션으로 저장합니다. 실패하면 모두 롤백하며 요청 UUID·정규화 본문의 재시도 계약을 유지합니다. 이전 요청에서 새 필드를 생략하면 원래 등록만의 동작·지문을 보존합니다. 기존 관리 화면의 인계·잔고 조회와 허용된 정정 기능은 유지합니다. 화면·입력 배치는 [Client 등록 설계](../client/docs/propertyRegistration.md#다섯-페이지-초기-설정과-잔액-인계-2026-10-18), 계약은 [등록 API](propertyRegistrationApi.md#초기-설정의-잔액-인계와-관리-시작)를 따릅니다.

### 초기 통장·동별 시작 잔고 입력 개편 (2026-10-24)

사용자가 두 번째 시안과 후속 의견 적용을 요청해 기존 관리계좌 및 잔고 단계 안에 `통장별 시작 잔액`·`동별 시작 보유금` 탭과 입력 완료 수·합계·차이 요약을 구현했습니다. 초기 등록 단계를 늘리지 않습니다. 이전의 별도 탭 제한은 이 초기 등록 화면에서 새 요청으로 대체하며 운영 중 `기준 잔고 확인` 화면의 기존 구성은 유지합니다.

통장 정보 모달은 계좌 정보만 입력하고 실제 잔액은 본문의 통장별 시작 잔액 탭에서 입력합니다. 통장 기준일은 기존 장부 기준일을 공유하고 동별 잔고 기준일은 별도입니다. 동별 시작 보유금은 통장을 선택한 뒤 통장×동별 금액으로 입력하며 통장 전환·탭 이동으로 초안을 지우지 않습니다. 같은 통장의 모든 동에 같은 동별 기준일을 사용하고 초기 등록은 통장 간에도 같은 동별 기준일을 사용합니다.

모든 금액이 입력되고 같은 기준일일 때만 은행 실제 잔액 합계와 동별 보유금 합계의 차이를 비교합니다. 빈칸을 0원으로 확정하거나 합계 일치를 강제하지 않으며 기준일이 다르면 비교 안내를 표시합니다. 날짜는 오늘 또는 이전 날짜를 허용합니다. 동 구분이 없으면 통장 실제 잔액만 입력합니다. 이전 단일 통장 초안은 보유금을 이어받고 다중 통장의 미귀속 보유금은 관리자가 선택 통장의 금액인지 확인한 뒤 가져옵니다. 이전 최종 요청의 본문·재시도 지문은 유지합니다. [등록 API](propertyRegistrationApi.md#초기-통장별-동-보유금-확장-2026-10-24)와 [Client](../client/docs/propertyRegistration.md#초기-통장동별-시작-잔고-입력-개편-2026-10-24)를 참조합니다.

## 4. 사용자 / 주민 / 참여 / 권한

### 기존 기준

- 로그인 사용자와 실제 주민 정보는 구분합니다.
- 사용자 탈퇴 후 재가입을 허용합니다. 재가입 시 새 `User`를 생성하고 기존 계정과 과거 관리대상 참여 이력은 복구하지 않습니다. 탈퇴 개인정보의 보존 / 파기 기간과 범위는 별도로 확정합니다.
- 사용자 상태는 `ACTIVE`(정상), `SUSPENDED`(이용 정지), `WITHDRAWN`(탈퇴)입니다. 정상 계정만 로그인과 서비스 인증 / 토큰 재발급을 허용합니다. 정지는 정상 상태로 해제할 수 있지만 탈퇴 계정을 복구하지 않습니다.
- 카카오 로그인으로 계정을 생성하고 로그인합니다. 별도의 휴대폰 소유 인증을 가입 또는 주민 참여의 필수 단계로 두지 않습니다.
- 전화번호는 관리자의 주민 확인과 연락을 위한 정보입니다. 전화번호 일치만으로 주민을 자동 연결하거나 관리대상 접근권한을 부여하지 않습니다.
- `users`는 로그인 계정 정보를 저장하고 전화번호는 저장하지 않습니다. 연락처는 주민 명부(`residents`)와 가입 요청 정보에서 관리합니다. 관리소장이 상세에서 연락처를 변경하면 해당 주민으로 확인 연결된 가입 요청의 번호도 함께 변경합니다. 주민 본인의 변경 절차는 후속 범위입니다.
- 로그인 식별자는 소셜 제공자와 제공자의 사용자 ID 조합입니다. 이메일이나 전화번호 일치만으로 계정을 자동 연결하지 않습니다.
- 탈퇴 시 사용자와 연결된 소셜 계정을 같은 트랜잭션에서 소프트 삭제합니다. 삭제되지 않은 소셜 계정의 로그인 식별자만 유일하게 유지하여 같은 소셜 계정의 재가입을 허용합니다.
- 한 사용자는 여러 관리대상에 참여할 수 있습니다.
- 권한은 관리대상별로 판단합니다.
- 주민의 세대 관계와 시스템 권한은 별개입니다.
- 관리대상별 역할은 `ADMIN`(관리소장), `MANAGER`(부담당자), `RESIDENT`(주민)입니다. 플랫폼 운영자의 관리자 권한과 구분합니다.
- `ADMIN` / `MANAGER`는 관리자 영역을 사용합니다.
- `RESIDENT`는 주민 영역을 사용합니다.
- 관리자 영역에 진입할 수 있다는 사실이 모든 관리 업무의 권한을 의미하지는 않습니다.
- Server에서 관리대상 소속과 업무 권한을 검증합니다.
- Client의 버튼 표시나 화면 접근 제한으로 Server 권한 검증을 대신하지 않습니다.
- 주민은 본인 세대 중심의 정보와 공개 대상으로 설정된 공용 정보를 조회합니다.

| 가입 승인 | 관리자가 입력된 동 / 호수와 주민 정보를 확인하고 승인하여 계정과 주민을 연결하고 권한을 부여합니다. | 세대 입력만으로 주민 권한을 자동 부여하지 않습니다. |
| 가입 요청 입력 | 신청자는 전화번호와 동 / 호수를 입력합니다. 실명 입력과 소유자 / 임차인 / 가족 등 세대 관계 선택은 요구하지 않습니다. 관리자 명부의 주민 이름과 세대 관계 정보는 유지합니다. | 주민 가입 입력을 줄이고, 관리자 명부와 연락처로 확인합니다. |
| 대기 요청 중복 | 같은 계정이 같은 관리대상 / 세대에 이미 대기 요청을 가지고 있으면 새 요청을 만들지 않고 기존 승인 대기 상태를 표시합니다. 다른 계정의 주민은 같은 세대에 각각 신청할 수 있습니다. | 세대에 여러 주민이 거주하는 경우를 지원하면서 같은 신청자의 중복 요청을 방지합니다. |
| 거절 후 재신청 | 거절된 요청은 이력으로 유지하고 새 가입 요청으로 재신청할 수 있습니다. | 이전 검토 결과를 보존하면서 다시 신청할 수 있게 합니다. |
| 승인 / 권한 변경 | 관리소장과 부담당자는 주민 가입을 승인할 수 있습니다. 관리대상 역할을 변경하는 권한은 관리소장에게만 있습니다. | 부담당자는 가입 업무를 처리하되 관리자 권한을 변경하지 않습니다. |
| 재입주 | 주민 명부를 재사용하더라도 새 가입 요청과 관리자 승인을 거쳐 접근권한을 다시 부여합니다. | 과거 소속으로 현재 접근권한을 자동 복구하지 않습니다. |
| 현재 세대 소속 | 같은 관리대상 안에서 한 주민은 동시에 하나의 세대에만 소속될 수 있습니다. 같은 세대에는 여러 주민이 소속될 수 있습니다. | 주민 한 명의 현재 소속과 세대의 여러 구성원을 구분합니다. |

주민 재등록은 `residents.deleted_at`과 `deleted_by`를 함께 해제하는 처리입니다. 사용자 탈퇴 후 재가입은 새 `User`를 생성하는 기존 정책을 유지하며, 주민 명부 복구로 탈퇴 계정을 복구하지 않습니다. 재입주 시에는 다시 승인받으며, 과거 퇴거 / 세대 관계 이력을 덮어쓰지 않습니다. 이력의 상세 저장 절차는 해당 기능 구현 시 결정합니다.

현재 세대 한 개 제한은 같은 관리대상 안의 현재 주민 소속에 적용합니다. 한 사용자가 여러 관리대상에 참여할 수 있다는 기존 기준과 과거 세대 이동 이력은 유지합니다.

### 확정된 세대 대표 지정과 변경

확정일: 2026-10-10. 아래는 사용자 결정이며 주민 기능의 구현 완료를 의미하지 않습니다.

- 일반 주민 명부 등록에서는 해당 호수에 최초로 등록되는 주민을 세대 대표로 자동 지정합니다. 관리소장 담당자 등록·본인 계정 연결은 아래 별도 예외를 적용합니다. 등록을 수행한 관리자 계정이 아니라 해당 세대에 등록되는 주민을 뜻합니다.
- 이후 같은 호수에 주민을 추가해도 기존 대표를 자동 변경하지 않습니다.
- 세대 대표 변경은 해당 관리대상의 관리소장(`ADMIN`)만 할 수 있습니다. 부담당자(`MANAGER`)와 주민(`RESIDENT`)은 변경할 수 없습니다.
- 최초 등록은 세대의 주민 명부 등록을 기준으로 하며 서비스 계정의 가입 요청·승인 순서와 구분합니다. 대표 지정만으로 로그인 계정을 연결하거나 관리대상 접근권한을 부여하지 않습니다.
- 대표 주민을 삭제하거나 다른 세대로 이동할 때 같은 세대에 남은 주민이 있으면 관리소장이 새 대표를 직접 선택해야 합니다. 자동 승계하지 않습니다. 별도 퇴거·재입주 흐름은 후속 범위입니다. 엑셀 등록의 최초 순서는 아래 확정 정책을 따릅니다. 개별 등록의 동시 요청은 [Server 주민 등록](../server/docs/residentRegistration.md)의 잠금으로 직렬화하며 대표 부재를 자동 승계로 처리하지 않습니다.

### 확정된 주민 목록 조회

확정일: 2026-10-10. 관리소장용 주민 목록은 해당 관리대상의 현재 관리소장(`ADMIN`)에게 제공합니다. 목록 화면과 조회 API를 구현했으며 계약은 [주민 관리 API](residentManagementApi.md)를 따릅니다.

- 삭제되지 않은 주민 명부 전체를 표시하고 주민의 활성·비활성 상태 필터를 두지 않습니다. 기존 ERD의 상태 컬럼을 목록 제외 조건이나 별도 비활성 UI 요구로 취급하지 않습니다.
- 요약 카드·표·필터는 가입 완료·미가입·승인 대기로 구분합니다. 승인 대기는 명부의 누구인지 확인된 주민만 표시·집계하고 미확인 신청을 같은 호수의 주민에게 임의로 붙이지 않습니다. 가입 상태의 조회 판정 기준은 API 계약을 따릅니다.
- 목록과 기본 상세는 연락처 끝 4자리만 응답·표시합니다. 상세에서 관리소장이 공개 버튼을 누르면 전체 번호를 조회할 수 있습니다.
- 주민당 한 행에 현재 소속 세대 하나와 대표 여부를 표시합니다. 같은 세대의 여러 주민은 각각 표시합니다.
- 목록·등록·상세·수정·삭제·엑셀 업로드를 구현했습니다. 삭제·이동 시 대표 승계를 지원하며 별도의 임의 대표 변경 기능은 후속 범위입니다. 등록 화면의 웹 모달·모바일 페이지 요구는 [Client 설계](../client/docs/residentList.md)에 기록합니다.

세대 목록의 대표 주민·가입 현황도 위 주민 조회 기준을 재사용합니다. 현재 세대별 주민 인원을 집계하고 기존 관리소장 전용 권한을 유지합니다. API 응답·권한별 표시 기준은 [세대 관리 API](unitManagementApi.md#목록-조회)를 따릅니다.

### 확정된 주민 목록 엑셀 다운로드

확정일: 2026-10-10. 다운로드 전에 미리보기를 제공하며 웹은 모달, 모바일은 뒤로가기가 있는 페이지를 사용합니다. 현재 검색·필터·동호수 정렬이 적용된 전체 결과를 내보냅니다.

- 파일에는 **주민명·연락처·동·호수** 세 항목만 저장합니다. 웹 모달·모바일 페이지의 미리보기에는 **주민명·연락처·동·호수**를 표시하며 연락처는 `**** 5678`처럼 끝 네 자리만 표시합니다. 주민 구분·대표 주민·가입 상태는 파일과 미리보기 모두 포함하지 않습니다.
- 전체 연락처는 다운로드 파일에만 포함하며 미등록 번호는 빈칸으로 저장합니다. 일반 목록·기본 상세의 끝 네 자리 정책은 유지합니다. 내보내기는 해당 관리대상의 관리소장(`ADMIN`)에게만 허용합니다.
- 파일 스타일은 [Client 엑셀 공통 서식](../client/docs/excelReports.md)을 따릅니다. 허용 열과 연락처 공개 범위는 이 정책을 유지합니다.
- 상세 요청·응답·오류는 [주민 관리 API](residentManagementApi.md#주민-목록-엑셀-다운로드)를 따릅니다.

### 확정된 개별 주민 등록

확정일: 2026-10-10. 관리소장이 주민 명부를 개별 등록하며 웹 모달·모바일 페이지와 저장 API를 구현했습니다.

- 이름·기존 소속 세대는 필수이며 연락처와 주민 구분은 선택입니다. 개별 등록과 엑셀 업로드에서 주민 구분을 생략하거나 비워두면 `OTHER`(기타)로 저장합니다. 확인된 소유주·임차인·가족 값은 유지하고 잘못된 구분 입력은 오류로 안내합니다. 입주일·대표 선택·계정 연결·가입 상태 입력을 추가하지 않습니다.
- 같은 관리대상에서 이름과 연락처가 모두 같은 미삭제 주민은 중복 등록을 막고 기존 주민 확인을 안내합니다. 연락처 없는 동명이인을 이름만으로 같은 사람으로 판단하지 않습니다.
- 명부 등록만으로 가입 승인·계정 연결·주민 권한 부여를 수행하지 않습니다. 최초 대표 지정은 위 확정 정책을 따릅니다.
- 요청·응답과 입력 정규화는 [주민 관리 API](residentManagementApi.md#주민-등록), 저장의 잠금·재시도 처리는 [Server 주민 등록](../server/docs/residentRegistration.md)을 따릅니다.

2026-10-12 명부 전체 삭제 후 재입력 요청을 반영해 개별·엑셀 등록에서 삭제된 명부의 재등록을 허용합니다. 같은 관리대상에서 이름과 정규화된 연락처가 정확히 일치하는 삭제 기록이 하나이면 기존 주민 ID를 유지하고 삭제 표시를 해제합니다. 엑셀 검증은 재등록 가능한 행으로 표시하고 선택 후 저장하며 검증만으로 복구하지 않습니다. 연락처 없는 동명이인은 이름만으로 병합하지 않으며 여러 삭제 기록이 일치하면 임의 선택하지 않습니다.

명부 삭제는 실제 퇴거로 취급하지 않고 관계의 삭제 표시로 현재 목록에서 제외합니다. 실제 세대 이동의 퇴거일과 과거 관계는 유지합니다. 재등록은 새 현재 관계를 저장하고 계정·승인·종료된 권한을 자동 복구하지 않습니다. 같은 세대의 삭제 전 대표를 재등록할 때 현재 대표가 없으면 원래 대표를 복원하며 현재 대표가 있으면 유지합니다. 이는 기존 대표 복원이며 다른 주민에게 임의로 자동 승계하지 않습니다.

### 확정된 주민 엑셀 일괄 등록

확정일: 2026-10-10. 사용자 결정에 따라 오류·중복 행은 제외하고 선택한 정상 행을 등록합니다. 기존 대표는 유지하며, 최초 등록 세대는 선택된 정상 행 중 엑셀에서 가장 위에 있는 주민만 대표로 지정합니다. 다음 주민은 대표로 지정하지 않습니다. 개별 등록의 필수 입력·중복 기준·가입 승인과 명부 등록의 구분을 동일하게 적용합니다.

업로드·검증·완료 화면과 API를 구현했습니다. `.xlsx` 양식·파일 제한·행별 저장·재시도·임시 데이터 수명은 구현 설계이며 [주민 관리 API](residentManagementApi.md#엑셀-검증과-일괄-등록), [Client 설계](../client/docs/residentList.md#5-엑셀-업로드), [Server 저장 설계](../server/docs/residentRegistration.md#엑셀-검증과-행별-저장)를 참조합니다. 결과 다운로드는 별도 서버 API 없이 화면에서 생성합니다.

### 확정된 주민 상세·수정·삭제

확정일: 2026-10-10. 관리소장용 상세·수정·삭제와 연락처 공개 API를 구현했습니다. 웹 상세는 모달, 모바일은 뒤로가기가 있는 페이지로 제공합니다. 화면 명칭은 동·호수·주민 구분·엑셀 업로드를 사용하며 `OWNER`는 소유주로 표시합니다. 기존 코드·저장 값은 유지합니다. 엑셀 결과 표에서 원본 행 번호는 표시하지 않습니다.

- 연락처는 기본 마스킹하고 공개 버튼으로 전체 번호를 확인합니다. 목록에는 전체 번호를 전달하지 않습니다.
- 연락처 변경은 명부와 해당 주민으로 확인 연결된 가입 신청에 함께 반영합니다. 번호 일치만으로 미확인 신청을 연결하지 않습니다.
- 주민 삭제 시 해당 관리대상의 연결된 주민 접근권한도 함께 종료합니다. 다른 관리대상 참여와 관리자 권한에는 적용하지 않습니다.
- 대표 삭제·이동 시 같은 세대에 남은 주민 중 새 대표를 직접 선택합니다. 명부·관계·대표·연락처·권한 변경은 각 수정 또는 삭제의 단일 트랜잭션으로 처리합니다.

### 플랫폼 권한과 관리대상 권한

플랫폼 운영자 권한과 공동주택 관리 업무의 역할은 분리합니다. 일반 사용자와 플랫폼 관리자를 구분하는 계정 권한은 `users.system_role`, 관리소장 / 부담당자 / 주민 역할은 `property_members.role`로 표현합니다. `User.systemRole`과 후속 Migration으로 플랫폼 역할 저장을 구현했으며, 신규 가입과 기존 계정의 기본값은 `USER`입니다. 플랫폼 관리자 지정 / 회수 API는 아직 제공하지 않습니다.

| 권한 범위 | 설계 위치 | 값과 의미 |
| --- | --- | --- |
| 플랫폼 운영 | `users.system_role` | `USER`: 일반 사용자, `ADMIN`: 플랫폼 관리자 |
| 관리대상 업무 | `property_members.role` | `ADMIN`: 관리소장, `MANAGER`: 부담당자, `RESIDENT`: 주민 |

플랫폼 관리자라는 사실만으로 특정 관리대상의 관리소장이나 주민이 된 것으로 처리하지 않습니다. 플랫폼 관리자 기능의 상세 범위와 부여 / 회수 절차는 해당 기능 구현 전에 결정합니다.

| 관리대상 업무 | 관리소장 (`ADMIN`) | 부담당자 (`MANAGER`) | 주민 (`RESIDENT`) |
| --- | --- | --- | --- |
| 주민 목록 조회 | 가능 | 불가 | 불가 |
| 주민 명부 개별 등록 | 가능 | 불가 | 불가 |
| 주민 목록 엑셀 다운로드 | 가능 | 불가 | 불가 |
| 주민 상세·연락처 공개·수정·삭제 | 가능 | 불가 | 불가 |
| 주민 가입 승인 | 가능 | 가능 | 불가 |
| 관리대상 역할 변경 | 가능 | 불가 | 불가 |
| 세대 대표 변경 | 가능 | 불가 | 불가 |

가입 승인에 따른 기본 주민 참여 권한 부여는 별도 역할 변경과 구분합니다. 부담당자가 주민 가입을 승인할 때 `RESIDENT` 참여 권한을 반영할 수 있지만, 승인으로 관리소장 / 부담당자 역할을 부여하거나 변경할 수 없습니다.

전화번호 보안 처리는 기존 공통 `PhoneSecurity`를 재사용합니다. 구현과 키 설정 기준은 [보안 설계](securityDesign.md)의 전화번호 저장 절을 따릅니다.

### 확정된 관리대상 생성자 권한

확정일: 2026-10-05. 관리대상을 등록한 사용자는 해당 관리대상의 관리소장(`ADMIN`)으로 자동 지정합니다. 별도의 승인이나 역할 선택 없이 등록자가 관리 업무를 시작할 수 있도록 합니다.

- 생성자 계정은 요청 본문의 사용자 ID가 아닌 Server가 인증한 정상 사용자로 결정합니다.
- 관리대상 생성과 생성자의 `property_members` 등록은 하나의 DB 트랜잭션으로 처리합니다. 어느 한쪽이 실패하면 둘 다 저장하지 않습니다.
- 생성자의 참여 상태는 `ACTIVE`, 관리대상 역할은 `ADMIN`으로 저장합니다.
- `users.system_role`은 변경하지 않습니다. 관리대상 관리소장 지정과 플랫폼 관리자 지정은 별개입니다.
- 관리소장 권한은 주민 명부나 세대 소속과 구분합니다. 최초 등록자는 거주 여부를 명시적으로 선택합니다. 거주자이면 이름·연락처·등록한 동/호수로 본인 주민 명부와 현재 세대 관계를 함께 생성하고 로그인 계정을 즉시 연결합니다. 외부자이면 ADMIN 참여만 생성하고 주민 명부에는 넣지 않습니다.

최초 등록자의 거주 선택은 2026-10-17 사용자 확정입니다. 별도 가입 신청·자기 승인 절차나 추가 RESIDENT 역할을 만들지 않고 ADMIN을 유지합니다. 관리소장 담당자 등록은 일반 주민 등록의 최초 대표 자동 지정에서 제외합니다. 거주 관리소장은 주민 목록에 관리소장 역할로 표시하되 세대 대표로 자동 지정하지 않습니다. 기존 주민과 계정을 연결할 때에도 저장된 대표 여부를 유지합니다. 주민 구분은 기존 기본값 OTHER로 저장하며 관리소장 역할과 별도로 표현합니다. 소유주·임차인 여부를 관리소장 역할에서 추측하지 않습니다. 주민·현재 세대 관계·계정 연결·초기 설정·성공 결과는 같은 트랜잭션이며 하나라도 실패하면 전체를 롤백합니다. 이전 등록자의 거주 여부를 추측해 기존 데이터에 주민을 소급 생성하지 않습니다.

2026-10-17 추가 확정: 담당자 이름은 로그인 닉네임과 구분해 입력합니다. 거주자와 외부 관리자 모두 담당자 이름·연락처를 관리하고 거주자만 등록된 세대를 선택합니다. 외부 관리자의 담당자 연락처는 주민 명부를 생성하는 방식으로 저장하지 않습니다. 담당자 연락처는 선택 입력입니다. 미입력은 허용하고 입력한 번호는 기존 연락처 형식과 보호 저장 기준을 적용합니다. 거주 호수는 거주자에게 필수이며 화면에도 별표로 표시합니다.

현재 구현은 위 다섯 페이지 흐름을 사용하며 거주 관리소장의 연락처 생략·대표 자동 지정 예외와 추가 등록의 동일 저장 흐름을 적용합니다. 외부 담당자 이름·연락처 저장은 후속 범위입니다. 기존 관리소장의 본인 계정 연결은 실제 저장을 지원합니다. 기존 관리소장에게 주민을 소급 생성하거나 이름·연락처만으로 자동 연결하지 않습니다.

기존 관리소장은 주민 명부에서 본인을 명시적으로 선택해 현재 로그인 계정과 연결합니다. 현재 관리소장 권한·정상 계정·같은 대상의 미삭제 주민·현재 세대와 화면에서 확인한 세대의 일치를 저장 시 다시 검증합니다. 다른 계정에 연결된 주민이나 같은 계정의 다른 주민 연결은 덮어쓰지 않습니다. 기존 관리소장 참여·세대 대표·이름·연락처·주민 구분은 유지하고, 별도 가입 신청이나 역할 변경을 만들지 않습니다. 같은 계정·주민·현재 관계로 재요청하면 중복 저장하지 않습니다. 연결 당시 관계 ID의 이력과 현재 활성 참여가 일치할 때 가입 완료로 조회하며 새 세대 관계에 과거 연결을 자동 적용하지 않습니다.

관리소장 인계는 아래 2026-10-17 확정 정책을 따릅니다.

### 확정 정책: 주민 역할·관리소장 인계와 초대 (2026-10-17)

사용자는 주민 역할 관리와 외부 관리자 관리를 구현하도록 요청했고, 추가 확인으로 관리소장 1명 유지·인계 후 기존 관리소장의 부담당자 전환, 초대 신청 후 관리소장 승인과 코드의 발급 후 1일 유효기간을 선택했습니다.

- 화면의 열 제목과 입력 라벨은 `역할`로 통일합니다. 주민 구분(소유주·임차인 등), 세대 대표, 역할과 가입 상태를 구분합니다. 주민 목록·상세에 연결 계정의 현재 역할을 표시합니다. 계정 권한이 없으면 미가입 주민을 `RESIDENT` 권한 보유자로 표시하지 않습니다.
- 승인된 계정이 연결된 주민은 기존 주민 수정 모달/페이지의 `역할` 항목에서 부담당자 또는 주민으로 변경합니다. 현재 관리소장만 변경하며 명부·세대 관계·대표·플랫폼 역할은 변경하지 않습니다.
- 관리소장은 관리대상마다 현재 1명을 유지합니다. 대상 참여자에게 전용 인계 API로 인계하면 기존 관리소장은 부담당자로 변경합니다. 두 역할 변경은 하나의 트랜잭션이며 역할 변경 전후·처리자·시각을 보존합니다.
- 관리소장 인계 없이 자신의 역할을 낮추거나 관리소장을 일반 역할 변경으로 해제하지 않습니다. 기존 역할 충돌·중복 참여를 임의로 합치지 않고 확인이 필요한 오류로 거부합니다.
- 외부 관리자는 주민 명부 없이 부담당자로 초대할 수 있습니다. 미거주 부담당자의 접근 종료와 주민 역할로 변경하는 절차를 구분합니다.
- 2026-10-17 후속 사용자 지시에 따라 주민 상세의 초대·코드 발급·가입 승인 영역을 제거합니다. 주민은 공유된 관리대상 참여 주소에서 동·호수와 연락처로 신청하고, 기존 `가입 요청` 메뉴에서 관리소장·부담당자가 명부의 주민을 직접 선택해 승인합니다. 주민 가입에는 초대코드를 사용하지 않습니다. 이름·전화번호만으로 계정을 자동 연결하지 않습니다.
- 외부 부담당자의 초대코드는 무작위 값으로 발급하고 해시만 저장합니다. 최초 발급 화면에서만 원문을 제공하며 URL·로그·브라우저 저장소에 남기지 않습니다. 발급 후 1일 동안 한 계정만 신청할 수 있고 신청만으로 권한을 부여하지 않습니다. 만료 전에 관리소장이 승인해야 하며 미사용 초대는 철회할 수 있습니다.
- 외부 부담당자 초대 승인은 관리소장만 처리합니다. 주민 가입 신청·승인·거절은 별도 가입 요청 화면/API로 구현하며 관리소장과 부담당자가 승인할 수 있습니다. 주민용 홈과 주민 명부가 없는 신청자의 신규 명부 작성은 후속 범위입니다.

API는 [참여자·초대 관리 계약](memberManagementApi.md), 화면은 [Client 역할 관리](../client/docs/memberManagement.md), 저장·인계는 [Server 역할 관리](../server/docs/memberManagement.md)를 따릅니다.

### 관리자 시작 흐름

```text
카카오 로그인
    ↓
관리할 곳 만들기
    ↓
기본 정보 등록
이름 / 주소 / 동 여부
Client 초안 유지, DB 저장 없음
    ↓
초기 설정
세대 / 계좌 / 관리비 항목
    ↓
등록 정보 확인
    ↓
등록하고 관리 시작
전체 검증 / 등록·인계·운영 시작의 트랜잭션 저장 / 생성자 ADMIN 지정
    ↓
완료 확인 후 관리비 부과 화면
```

저장 / 중단 / 완료 조건은 위의 확정된 관리대상 등록과 초기 설정 정책을 따릅니다. 마지막 저장에 실패하면 완료로 표시하거나 관리 화면으로 이동하지 않습니다.

### 주민 참여 흐름

```text
카카오 로그인
    ↓
공유된 관리대상 참여 링크 열기
    ↓
가입 정보 입력 / 확인
전화번호
동이 있는 경우 동 / 호수, 동이 없으면 호수
    ↓
가입 요청
    ↓
승인 대기
    ↓
관리자 검토
    ↓
승인
    ↓
주민 홈
```

- 카카오 로그인 성공과 관리대상 가입 승인은 서로 다른 처리입니다.
- 주민은 동이 있는 경우 동과 호수, 동이 없는 경우 호수로 참여할 세대를 지정합니다.
- 신청자는 전화번호를 필수로 입력하며 실명과 세대 관계는 입력 / 선택하지 않습니다. 관리자 명부의 주민 이름과 세대 관계 정보는 유지하고 승인 과정에서 확인합니다.
- 같은 계정의 같은 관리대상 / 세대에 승인 대기 요청이 있으면 대기 상태를 표시합니다. 다른 주민의 신청은 같은 세대라는 이유로 제한하지 않습니다.
- 거절 후 재신청은 새 요청으로 기록하고 거절 이력을 유지합니다. 재입주자도 새 요청과 승인을 거쳐야 합니다.
- 관리자는 기존 주민 명부와 가입 요청 정보를 확인한 뒤 승인합니다. 명부가 있으면 기존 주민을 연결하고, 명부가 없으면 먼저 주민 목록에서 등록한 뒤 연결합니다. 승인 과정의 신규 명부 작성은 후속 범위입니다. 동 / 호수 입력이나 전화번호 일치만으로 자동 승인하거나 주민 계정을 자동 연결하지 않습니다.
- 주민 연락처는 카카오톡 등 연락에 사용할 정보입니다. 실제 발송 방식은 연락 기능을 구현할 때 결정합니다.
- 관리소장의 연락처 수정은 위 확정된 상세 정책을 따릅니다. 주민 본인이 연락처를 변경하는 절차는 해당 기능 구현 시 결정합니다.
- 가입 요청이 승인되기 전에 해당 관리대상의 주민 권한이 부여된 것으로 처리하지 않습니다.
- 주민 신청·명부 연결·승인·거절은 관리자 사이드바의 기존 `가입 요청` 메뉴에서 처리합니다. 주민 상세에는 초대코드 발급이나 별도 가입 승인 영역을 추가하지 않습니다.
- 주민 참여는 `/join/[propertyId]`의 참여 링크를 사용합니다. 외부 부담당자용 코드는 주민 가입과 분리합니다.
- 관리할 곳 만들기와 주민 참여는 최초 가입 이후에도 사용할 수 있습니다.

### 가입 승인 시 함께 저장하는 범위

계정 연결은 확인한 주민의 `residents.user_id`에 신청자의 `users.id`를 저장하는 처리입니다. 세대 확인은 신청자가 입력한 동 / 호수가 해당 관리대상의 실제 `Unit`과 일치하는지 확인하고, 주민과 그 세대의 `unit_residents` 관계를 확인하는 처리입니다.

관리소장 또는 부담당자가 주민 가입을 승인하면 다음 변경을 하나의 DB 트랜잭션에서 처리합니다. 이는 별도 승인 단계를 추가하는 정책이 아니라 승인 결과가 일부만 저장되지 않도록 하는 구현 기준입니다.

1. 현재 구현은 명부에 등록된 주민을 직접 선택해 신청자 계정과 연결합니다. 승인 화면에서 새 명부를 작성하는 흐름은 후속 범위입니다.
2. 관리자 명부의 현재 주민 세대 관계와 신청 세대가 같은지 확인합니다. 현재 관계를 재사용하며 다른 세대에 소속된 주민을 중복 연결하지 않습니다. 재입주는 먼저 명부를 재등록해 새 현재 관계를 만든 뒤 승인하고 과거 퇴거 관계를 덮어쓰지 않습니다.
3. 해당 관리대상의 기본 주민 참여 권한(`RESIDENT`)을 `property_members`에 반영합니다. 현재 구현은 기존 관리자 역할과 충돌하면 승인하지 않고 오류로 반환합니다.
4. 가입 요청을 `PENDING`에서 `APPROVED`로 변경하고 검토자와 검토 시각을 기록합니다.

처리가 실패하면 주민 연결, 세대 관계, 권한과 요청 상태를 함께 롤백합니다. 다른 관리대상의 주민 / 세대 / 권한을 섞어서 연결하지 않습니다. 같은 동 / 호수에 여러 주민이 있을 수 있으므로 세대 확인을 사람의 자동 식별로 취급하지 않습니다.

### 로그인 이후 진입 기준

Desktop은 랜딩 페이지에서, Mobile은 로그인 화면에서 시작합니다.
로그인 이후의 관리대상 / 권한 분기 기준은 동일합니다.

#### 확정된 관리자 영역의 우선 연결

확정일: 2026-10-09. 이번 단계는 관리자 사이드바와 공통 레이아웃, 임시 대시보드와 기본 진입을 먼저 연결합니다. 대시보드 업무 내용을 구성하거나 주민 홈 / 승인 대기 / 별도 관리대상 선택 화면의 구현을 선행 조건으로 추가하지 않습니다. 현재 공통 UI와 서버 목록 / 현재 관리자 권한 API를 구현해 아래 표의 기본 진입에 연결했습니다.

여기서 **관리 가능한 관리대상**은 현재 유효한 관리소장(`ADMIN`) 또는 부담당자(`MANAGER`) 참여가 있는 대상입니다. 정상 계정과 현재 관리대상 / 참여 상태를 서버에서 확인합니다. 플랫폼 관리자 역할이나 등록 당시 역할 스냅샷은 현재 관리 권한을 대신하지 않습니다.

| 상황 | 이번 관리자 영역의 기본 진입 |
| --- | --- |
| 관리 가능한 대상 0개 | 관리할 곳 만들기 / 주민으로 참여하기 시작 화면 |
| 관리 가능한 대상 1개 | 해당 관리대상의 대시보드 |
| 관리 가능한 대상 2개 이상, 최근 선택이 현재 목록에서 유효함 | 최근 선택한 관리대상의 대시보드 |
| 관리 가능한 대상 2개 이상, 최근 선택이 없거나 현재 권한이 없음 | 서버 목록의 첫 번째 관리대상 대시보드 |
| 목록 / 권한 확인 중 또는 조회 실패 | 목적지 결정을 보류하고 확인 / 재시도 표시 |

이 기본 분기는 일반 시작 화면의 직접 접근에도 적용합니다. 명시적인 추가 등록 단계, 미확인 등록의 복구와 등록 완료 확인을 일괄 자동 이동으로 건너뛰지 않습니다. 관리대상이 있다는 사실은 회원당 한 개만 등록할 수 있다는 제한을 의미하지 않습니다.

설정 본문의 `등록 및 참여` 버튼에서 `/properties/add`로 진입하면 기존 관리대상이 있어도 만들기·초대 참여 화면을 표시합니다. 기존 시작·등록 컴포넌트를 재사용하고 해당 경로의 안내 문구를 추가·참여 용도로 바꿉니다. 일반 `/start`의 자동 진입 기준과 개별 업무 권한 검증은 유지합니다.

등록 성공 뒤에는 완료 페이지를 유지하고 사용자가 대시보드 이동을 선택하면 해당 대상의 현재 관리 권한을 확인합니다. 완료 정보와 최근 선택 기록만으로 관리자 영역을 열지 않습니다.

실제 경로, 공통 레이아웃·사이드바와 브라우저 최근 선택 보관은 [Client 서비스 진입 설계](../client/docs/serviceEntry.md), 조회 조건·정렬·요청·응답은 [관리 영역 접근 API](managementAccessApi.md)를 따릅니다. 최근 선택 UI의 배치는 후속 작업이며 여러 관리대상 참여를 지원하는 기존 기준을 유지합니다.

#### 주민과 승인 대기 연결의 기존 기준

아래는 주민 / 승인 대기 기능을 연결할 때 적용할 기존 기준입니다. 위 관리자 우선 구현에서 최근 선택이 없는 경우에는 별도 선택 화면 대신 관리자 표의 첫 번째 대상 기준을 적용합니다. 관리자 대상 목록이 비었다는 사실만으로 주민 참여나 승인 대기 요청까지 없다고 판단하지 않습니다.

| 상황 | 기본 진입 기준 |
| --- | --- |
| 관리대상 0개, 승인 대기 요청 있음 | 승인 대기 화면 |
| 관리대상 0개, 승인 대기 요청 없음 | 관리할 곳 만들기 / 주민으로 참여하기 |
| 관리대상 1개 | 선택 화면 없이 해당 관리대상으로 진입 |
| 관리대상 2개 이상, 최근 사용 정보 있음 | 최근 사용한 관리대상으로 진입 |
| 관리대상 2개 이상, 최근 사용 정보 없음 | 관리대상 선택 화면 |

관리대상을 결정한 뒤 해당 관리대상의 역할에 따라 이동합니다.

- `ADMIN` / `MANAGER`: 관리자 대시보드
- `RESIDENT`: 주민 홈

최근 사용 정보는 접근권한 검증을 대신하지 않습니다. 주민 기능 연결 전에는 이 역할 분기를 현재 구현된 기능으로 취급하지 않습니다.
진입 이후에도 관리대상을 변경할 수 있어야 합니다.

### 기존 설계안

물리 ERD v0.1에는 다음 내용이 제시되어 있습니다.

- 주민 정보는 가입 전 명단으로 존재할 수 있습니다.
- 가입 승인 시 주민 정보와 사용자 계정을 연결합니다.
- 관리대상 접근권한은 주민의 세대 관계와 분리합니다.
- 세대 관계 유형으로 소유자 / 임차인 / 가족 / 기타가 제안되어 있습니다.
- 퇴거는 주민 이력을 없애는 대신 상태와 퇴거일로 기록합니다.
- 초대는 만료시간과 사용횟수를 확인하도록 설계되어 있습니다.

### 미정 / 확인 필요

- 확정된 주민 목록 조회 / 명부 개별 등록 / 가입 승인 / 역할 변경 / 세대 대표 변경 외 업무의 역할별 조회 / 등록 / 수정 / 취소 범위
- 플랫폼 관리자 기능의 상세 범위와 권한 부여 / 회수 절차
- 관리소장 인계 이후 탈퇴·장기 부재 등 별도 복구 절차. 정상 인계는 위 확정 정책을 따릅니다.
- 대량 초대의 상세 정책. 주민은 참여 링크와 가입 요청을 사용하며 외부 부담당자 초대만 코드를 사용합니다.
- 가입 요청 거절 사유의 필수 여부와 표시 범위. 거절 후 새 요청으로 재신청 가능 정책은 확정입니다.
- 다른 세대 / 관리대상의 여러 승인 대기 요청이 있을 때의 표시와 처리 방식
- 탈퇴 개인정보의 보존 / 파기 기간과 범위
- 전화번호 중복 제한이 필요한지 여부와 중복된 연락처의 관리자 확인 방식
- 주민 본인의 연락처 변경 절차. 관리소장 수정의 명부·확인된 신청 반영은 확정된 상세 정책 적용
- 카카오톡 연락의 발송 방식과 대상 정보 관리
- 이용 정지 / 해제 권한과 사용자 탈퇴 및 관리자에 의한 참여 해제 절차
- 기존 주민이 다른 계정에 연결되어 있거나 신청 계정에 기존 관리자 역할이 있을 때의 처리 방식
- 사전 명부에 없는 신청자의 주민 이름과 세대 관계 정보를 관리자가 확인 / 등록하는 상세 절차. 신청자에게 실명이나 세대 관계를 입력받는 단계는 추가하지 않습니다.
- 퇴거한 주민의 과거 청구 / 납부 내역 열람 범위
- 주민 영역에서 최근 사용한 관리대상에 더 이상 접근할 수 없을 때의 진입 처리. 관리자 영역의 대체 선택은 위 확정 기준을 따릅니다.

## 5. 관리비 부과 / 청구

### 기존 기준

- 관리비는 월 단위 부과를 기본으로 합니다.
- 관리자는 기본 관리비 항목을 기준으로 전체 세대의 청구를 생성할 수 있어야 합니다.
- 실제 청구는 세대별로 관리합니다.
- 청구는 상세 관리비 항목으로 구성합니다.
- 특정 세대의 금액 또는 항목에 대한 예외 조정을 지원하는 방향입니다.
- 청구 작성과 부과 확정은 구분합니다.
- 부과가 확정되면 주민에게 청구를 공개하고 회계 처리와 연결합니다.
- 마감된 기간의 청구는 일반 수정으로 변경하지 않습니다.

기존 계획서의 관리비 예시는 다음과 같습니다.

| 항목 | 예시 금액 |
| --- | ---: |
| 일반관리비 | 15,000원 |
| 청소비 | 8,000원 |
| 엘베비 | 25,300원 |
| 기타 | 1,700원 |
| 합계 | 50,000원 |

위 항목과 금액은 설명용 예시입니다.
모든 관리대상의 기본값이나 고정 부과금액을 의미하지 않습니다.

### 기존 설계안

- 관리비 템플릿과 실제 청구 항목을 분리합니다.
- 청구 생성 시 항목명, 금액과 연결 계정 정보를 청구 항목에 보존하는 구조입니다.
- 템플릿 금액을 변경해도 기존 청구 항목의 금액이 자동 변경되지 않습니다.
- 청구 항목의 합계는 청구 총액과 일치해야 합니다.
- 같은 부과기간의 같은 세대에 대한 청구 중복을 제한하는 기준이 제시되어 있습니다.

2026-10-08에 초기 관리비 설정은 빈 목록으로 시작하며 항목 금액에 0원과 음수를 허용하는 정수 원 단위 입력으로 변경했습니다. 이전의 0원 이상 제한을 대체하고 합계도 부호를 유지합니다. 최소 1개의 항목을 등록해야 합니다. 금액 / 합계 범위는 [등록 API](propertyRegistrationApi.md)의 입력 계약, 템플릿 초기값은 [Server 등록 설계](../server/docs/propertyRegistration.md)에서 관리합니다. 실제 청구의 0원·음수 허용은 [월별 부과 정책](#확정-정책-월별-부과-범위날짜변경-적용과-금액-2026-10-10)을 따르며, 감액 이후 수납 / 정산 처리는 별도 정책으로 구분합니다.

### 확정 정책: 기본 관리비 항목 종류 (2026-10-09)

- 추천 항목 종류를 선택하거나 항목명을 직접 입력할 수 있습니다. 초기 목록은 빈 상태로 유지하고 항목과 금액을 자동으로 추가하지 않습니다.
- 추천 종류는 항목 코드로 구분하고 표시 항목명을 별도로 보존합니다. Client에서 추천 종류를 추가·수정할 때는 선택지의 정해진 이름을 사용하며, 직접 입력을 선택할 때만 항목명을 작성합니다. API의 항목명은 종류 선택 여부와 관계없이 필수입니다.
- 직접 입력은 항목 코드 없이 저장합니다. 기존 항목도 이름으로 종류를 추측해 자동 분류하지 않습니다.
- 추천 종류는 일반관리비·청소비·승강기 유지비·공용 전기료·공용 수도료·정화조 청소비·생활폐기물 처리비의 7개입니다.
- 추천 코드 목록과 생략 / null의 요청 의미는 [등록 API](propertyRegistrationApi.md#기본-관리비-항목)를 따릅니다. 종류 선택은 부과 방식이나 회계 계정의 자동 연결을 확정하지 않습니다.
- Server의 코드 검증·저장과 Client의 추천 종류 / 직접 입력 선택 및 코드 초안 복원을 구현했습니다.

### 확정 정책: 월별 부과 범위·날짜·변경 적용과 금액 (2026-10-10)

사용자는 우선 전체 세대를 대상으로 월별 부과를 운영하고, 기본 설정 변경을 다음 달부터 적용하며 실제 청구에도 0원과 음수를 허용하기로 결정했습니다. 기본 설정과 청구를 수정할 때 수정 사유는 필수입니다.

- 현재 부과 범위는 관리대상 전체 세대입니다. 동별로 부과 대상을 선택하는 기능은 이번 범위에 포함하지 않습니다. 2026-10-12 변경에 따라 사용 중(`ACTIVE`) 세대만 포함하고 공실(`VACANT`)·비활성·삭제 세대는 제외합니다. 자동 부과 실행 시 저장된 세대를 대상으로 합니다.
- 부과일과 납부기한을 부과 정보에 포함하며 둘 다 필요합니다. 날짜 계산은 아래 월별 스케줄 부과 정책을 따릅니다.
- 월별 기본 관리비 항목·금액을 변경하면 다음 부과월부터 적용합니다. 예를 들어 10월에 변경한 기본 설정은 11월 부과부터 사용하며, 10월 청구나 과거 청구에 소급 적용하지 않습니다. 변경 전 설정과 다음 달 적용 예정 설정을 구분할 수 있어야 합니다.
- 위 다음 달 적용 기준은 반복 부과에 사용하는 기본 설정의 변경을 뜻합니다. 세대별 초안 수정과 확정 후 취소 / 조정의 허용 범위까지 확정한 것은 아닙니다.
- 실제 청구 항목과 청구 합계는 0원과 음수를 허용합니다. 0원이라는 이유로 청구 생성 / 확정을 차단하거나, 음수 합계를 0원으로 치환하지 않습니다. 음수 청구의 납부 상태, 환급 / 이월 및 회계 반영 방식은 별도로 정합니다.
- 초기 등록의 기본 금액에 대한 기존 0원·음수 허용도 유지합니다.
- 기본 항목·금액 또는 세대별 청구 항목·금액을 수정할 때 수정 사유를 필수로 입력하고 변경 내역과 함께 보존합니다. 사유가 없거나 공백뿐이면 수정을 저장하지 않습니다. 수정 사유가 있다는 이유로 확정 청구의 직접 덮어쓰기를 허용하지 않으며 확정 후 변경 절차는 별도 기준을 따릅니다.

### 확정 정책: 월별 스케줄 부과 (2026-10-10)

- 사용자는 매월 1일 자동 부과하고 해당 월 말일을 납부기한으로 두기로 확인했습니다. 매달 반복되는 부과를 스케줄로 처리하며, 매월 수동으로 부과일 / 납부기한을 지정하는 것을 기본 흐름으로 삼지 않습니다.
- 부과일은 해당 부과월의 1일, 납부기한은 해당 월의 실제 마지막 날로 계산합니다. 예를 들어 2026년 10월 부과일은 10월 1일, 납부기한은 10월 31일입니다. 30일까지 있는 달과 2월도 실제 월말을 사용합니다.
- 기본 항목·금액 변경의 다음 달 적용 기준을 함께 따릅니다. 10월 중 변경한 기본 설정은 11월 1일 자동 부과에 사용하고, 이미 생성한 10월 청구를 다시 계산하지 않습니다.
- 스케줄은 청구 생성부터 부과 확정까지 자동으로 수행합니다. 관리자가 매월 별도의 확정 버튼을 눌러야 하는 절차를 두지 않습니다. 생성과 확정은 업무 처리 단계로 구분하되 스케줄에서 연속 처리하며, 확정된 청구는 주민 공개와 회계 처리로 연결합니다.
- 실행 기준은 한국시간 매월 1일 00시입니다. 2026-10-17 변경에 따라 신규 등록만으로 청구를 생성하지 않습니다. 기존 잔액 인계에서 관리 시작을 확정한 뒤 지정한 첫 부과월부터 부과하며, 이후 매월 1일 반복합니다. 기존 운영 데이터의 부과월과 청구는 보존합니다.
- 다음 달 적용 예정 설정을 반복 변경하면 마지막 저장본을 사용하고, 모든 변경 버전·수정 사유·수정자를 보존합니다. 예정 설정의 취소와 수동 청구 초안 편집은 이번 범위에 포함하지 않습니다.
- 실패한 부과는 재시도하며 같은 관리대상·월·세대의 청구를 중복 생성하지 않습니다. 생성·항목 저장·자동 확정 중 하나라도 실패하면 해당 월의 처리를 함께 롤백합니다.
- 현재 구현은 설정 조회·다음 달 설정 저장·월별 조회·자동 생성 및 확정까지입니다. 주민 공개 화면·수납 상태·환급·회계 전표 연결은 별도 구현입니다. API는 [관리비 API](billingApi.md), 화면은 [Client 관리 레이아웃](../client/docs/managementLayout.md#관리비-부과-2026-10-10), 재시도와 트랜잭션은 [Server 관리비 설계](../server/docs/billing.md)를 참조합니다.

### 확정 정책: 공실 제외와 상세 청구 삭제 (2026-10-12)

- 부과 기준은 저장된 세대 상태입니다. 운영 시작이 확정되고 첫 부과월이 도래한 대상에서 사용 중 세대를 추가하면 당월 전액을 부과하고 공실·삭제 세대는 제외합니다. 주민 명부 등록 여부를 부과 조건으로 사용하지 않습니다. 이전의 공실 포함 기준을 대체합니다.
- 당월 청구와 합계에서 삭제된 동·세대의 잔여 청구를 제외합니다. 같은 이름의 동을 다시 추가해도 새 세대와 이전 삭제 세대를 함께 집계하지 않습니다. 과거 확정 이력은 보존합니다.
- 2026-10-12 후속 요청에 따라 개별 청구 상세의 수동 삭제 버튼은 제거합니다. 동·세대 삭제와 공실 전환에 따른 자동 부과 제외는 유지합니다. 기존 취소 청구의 원본·취소 시각·처리자·사유는 보존합니다.
- 구현에서는 공실 전환을 당월 부과 제외 상태로 반영하고 사용 중 복귀 시 당월 전액을 다시 표시합니다. 기존 스냅샷이 있으면 재사용하며 수동 취소 청구를 자동 복구하지 않습니다. 과거 월의 공실 제외 상태는 변경하지 않습니다.

### 확정 정책: 기존 잔액 인계와 관리 시작 (2026-10-17)

사용자는 기존 관리 이력이 있는 관리대상도 도입할 수 있도록 등록·잔액 인계·첫 부과를 분리하는 첨부안을 문서와 코드에 반영하도록 요청했습니다. 과거 월별 장부 전체를 재입력하지 않고 기준일 잔액으로 시작할 수 있습니다.

- 관리비 부과는 기존 화면 내부 탭을 유지합니다. 기존 잔액 입력도 이 화면의 `기존 잔액 인계` 탭에서 처리하며 사이드바 드롭다운으로 분리하지 않습니다.
- 기존 계약의 관리대상 등록은 기본 정보·세대·계좌·기본 항목·생성자 관리소장 권한만 저장합니다. 2026-10-18 새 초기 설정은 마지막 `등록하고 관리 시작`에서 명시한 잔액 인계와 운영 시작을 함께 확정합니다. 중간 단계와 기본 정보만의 등록으로 청구를 자동 확정하지 않습니다. 운영 시작 전에는 세대 추가·상태 변경·스케줄도 청구를 생성하지 않습니다.
- 관리소장은 기존 장부 기준일, 첫 신규 부과월, 세대별 기존 미납·선납과 계좌별 실제 시작 잔액을 입력합니다. 세대 잔액은 공실도 인계할 수 있습니다. 입력 당시 전체 미삭제 세대·계좌를 확정 직전에 다시 검증합니다.
- 10월분을 새로 부과한다면 9월 30일 기준 잔액·첫 부과월 10월을 선택합니다. 10월분을 이미 고지했다면 정리한 최근 기준일의 남은 잔액·첫 신규 부과월 11월을 선택합니다. 이미 고지한 10월 전체 청구를 새로 생성하지 않습니다.
- 기존 미납은 신규 월 관리비와 구분되는 `OPENING_RECEIVABLE`로 저장합니다. 기존 선납은 수납을 만들지 않고 별도 충당 이력을 남깁니다. 현재 세대 대표에게 과거 채무를 자동 귀속하지 않으며 발생월·부담 주체 메모는 선택적으로 보존합니다.
- 기존 선납은 유효한 양수 청구에 자동 충당합니다. 실제 수납 배분과 기존 선납 충당을 합쳐 청구 한도를 검증하고 남은 선납은 이후 실제 청구에 사용합니다. 가짜 은행 입금·당월 신규 수익으로 합산하지 않습니다.
- 통장 잔액은 계좌 단위로 별도 저장합니다. 세대별 미납·선납을 합산해 통장 잔액이나 동별 보유금으로 만들지 않습니다. 이 인계 기능만으로 잔액 대사 완료를 표시하지 않습니다. 동별 보유금·외부 회수는 동별 잔고·정산 후속 범위를 따릅니다.
- 관리 시작 확정은 인계·운영 시작·지정한 첫 월 부과·기존 선납 충당을 하나의 트랜잭션으로 저장합니다. 첫 부과월이 미래이면 미래 청구를 만들지 않습니다. 재확정·동시 요청도 중복 부과하지 않습니다.
- 기준일 이하의 은행 입금은 파일 가져오기에서 제외하고 수동 등록·수납 확정·기타 입금 확정에서도 차단합니다. 기준일 이후 실제 입금만 새 수납입니다.
- 구현은 확정 수납이 없을 때에만 인계 취소·재인계를 지원합니다. 기존 월별 청구와 최초 기준일·첫 부과월은 유지하고 원 인계와 충당 취소 이력을 남깁니다. 수납 이후 조정·회계전표·월 마감 이후 정정은 후속 정책입니다.
- 이미 운영 중인 기존 데이터는 등록 당시 첫 부과월과 모든 청구·수납을 보존합니다. 기존 원장에 초기 잔액을 임의로 소급 추가하지 않습니다.

설명용으로 월 관리비가 50,000원일 때:

| 기존 미납 | 기존 선납 | 신규 관리비 | 새 입금 전 납부 필요액 | 남은 선납 |
| ---: | ---: | ---: | ---: | ---: |
| 100,000 | 0 | 50,000 | 150,000 | 0 |
| 0 | 30,000 | 50,000 | 20,000 | 0 |
| 0 | 80,000 | 50,000 | 0 | 30,000 |
| 0 | 0 | 50,000 | 50,000 | 0 |

초안 직접 입력·엑셀 검증과 가져오기·합계·확정·사용 전 취소를 구현했습니다. 이 입력·검증·정정 구성은 첨부안을 구체화한 구현 설계이며, 과거 장부 전체 가져오기나 수납 이후 조정 정책을 확정한 의미는 아닙니다. 요청·오류는 [관리비 API](billingApi.md#기존-잔액-인계), 저장은 [ERD](erd.md#76-기존-잔액-인계)를 따릅니다.

### 미정 / 확인 필요

- 추천 목록 이후의 항목 확장과 관리대상별 변경 범위
- 세대별 예외 금액의 적용 방식
- 다음 달 적용 예정 설정의 취소와 수동 초안 편집 정책 (반복 변경의 마지막 저장본 사용·이력 보존은 확정)
- 세대 삭제·상세 당월 취소 외의 확정 청구 변경 / 취소 / 재발행 절차
- 취소된 청구가 있는 경우 같은 기간에 다시 부과하는 방식
- 연체료·감액·마감 후 정정이 누적 이월에 미치는 영향. 실제 양수 부과·확정 수납·기존 잔액의 이월은 구현 범위입니다.
- 연체 판단 및 연체료 도입 여부
- 음수 청구의 납부 상태 / 환급 / 이월 / 회계 처리와 감액 / 조정 절차

## 6. 수납 / 수납 배분 / 납부 상태

2026-10-18 후속 사용자 요청으로 월별 수납 엑셀은 현재 선택한 납부 상태 탭의 결과를 내려받습니다. 구현은 검색·동 조건도 목록과 공유하고 페이지 구분에 관계없이 해당 조건의 전체 세대와 합계를 내보냅니다. 월별 수납은 전체 통장의 세대 수납을 합산하는 기존 기준을 유지합니다.

### 기존 기준

- 수납과 은행 원본 거래는 서로 다른 업무 개념입니다.
- 수납이 존재한다는 사실만으로 특정 청구를 납부완료로 판단하지 않습니다.
- 납부 상태를 단순 Boolean 값으로 별도 관리하지 않습니다.
- 납부 상태는 청구 금액과 해당 청구에 유효하게 배분된 수납 금액을 기준으로 계산합니다.
- 부분납부와 여러 달에 대한 일괄입금을 고려합니다.
- 하나의 수납은 여러 청구에 배분될 수 있습니다.
- 하나의 청구에는 여러 수납이 배분될 수 있는 구조를 유지합니다.
- 수납의 처리 상태와 청구의 납부 상태는 구분합니다.
- 잘못된 수납 처리는 이력을 보존하는 방식으로 취소합니다.
- 미확정 입금 삭제와 확정 납부 취소를 구분합니다. 미확정 입금은 목록 편집에서 선택 삭제하고 같은 파일로 다시 가져올 수 있습니다. 확정 납부는 상세에서 취소하고 원본 검토 초안과 취소 이력을 유지합니다.

### 기존 설계안

물리 ERD v0.1에는 다음 기준이 제시되어 있습니다.

- 수납은 수동 등록 또는 은행 거래 연결로 생성할 수 있습니다.
- 수납 배분은 활성 / 취소 상태로 이력을 보존합니다.
- 한 수납에 대한 배분 합계는 해당 수납 금액을 초과할 수 없습니다.
- 한 청구에 대한 배분 합계는 해당 청구 금액을 초과할 수 없습니다.

취소된 배분을 유효한 납부 금액으로 계속 계산하지 않습니다.
전체 취소와 부분 취소의 지원 범위 및 연동 처리 절차는 별도 정책으로 정합니다.

2026-10-16 후속 요청으로 입금 관리의 월별 수납 목록은 선택월에 실제 부과된 세대만 표시하며 취소·공실 제외·해당 월 미부과 세대를 목록에 넣지 않습니다. 세대 수를 고정하지 않고 실제 발행 청구를 기준으로 판정하며 과거 원장은 보존합니다. 과거 입금의 직접 매칭은 입금월 청구 유무와 관계없이 현재 사용 중 세대를 선택합니다. 월별 수납 목록의 실제 부과 세대 제한은 유지합니다. 화면의 세대 선택 범위·이름·추천 근거 표시는 [Client 설계](../client/docs/paymentManagement.md)를 따릅니다.

### 세대별 누적 수납과 자동 확정 (2026-10-16 후속 확정)

사용자는 입금 전액을 세대별로 누적하고, 이름 또는 동·호수가 명단에 일치하는 입금은 개별 확인 없이 확정하도록 요청했습니다. 같은 달 여러 입금이나 이미 완납한 세대의 입금을 중복으로 취급하지 않습니다. 입금자의 미납월·선납 의도를 추정하거나 고지월별 입력을 요구하지 않습니다.

- 같은 계좌의 거래번호 또는 제공된 날짜·입금자·금액·시간·잔액으로 식별하며 정보 없는 양식과 기존 키는 호환합니다. 같은 날 같은 금액이라도 구별 가능한 별도 입금은 보존하고 날짜가 다른 실제 입금도 누적합니다. 상세 판정은 통장 계약을 따릅니다.
- 이름 또는 동·호수의 공백 차이를 정리해 현재 명단과 대조합니다. 동·호수는 마지막 `호`를 생략한 `103동501`도 `103동 501호`와 동일하게 찾습니다. 정확하게 한 세대에 일치하면 파일 가져오기에서 자동 확정합니다. 여러 세대에 걸친 동명이인·미일치·기존 수동 수납 중복 의심은 확인 필요로 남깁니다. 보류는 자동 확정하지 않습니다.
- 누적 양수 유효 부과액과 확정 입금 전액을 비교해 미납과 선입금을 구분합니다. 미납이 0이어도 수납 확정을 허용하며 초과분은 선입금입니다.
- 다음 달 실제 관리비가 부과되면 기존 선입금을 충당합니다. 전액 충당하면 납부완료, 부족하면 일부납부·미납을 표시합니다. 미래 청구를 미리 생성하지 않습니다.
- 구현은 장부 일관성을 위해 미납 청구월 순으로 미사용 수납을 충당합니다. 이 순서는 입금자의 의도를 판정한 결과가 아니며 화면에 추천·청구월 배분 입력을 요구하지 않습니다.
- 삭제는 PENDING·ON_HOLD 초안에 적용하며 활성 은행 중복 키를 해제합니다. 2026-10-18 사용자 요청으로 은행 미연결 MANUAL의 CANCELED도 취소 상태·사유·충당·감사 이력을 보존한 소프트 삭제를 허용합니다. 같은 날 후속 사용자 요청으로 통장 거래의 선택 삭제는 미연결 수동 입금의 확정 여부와 관계없이 허용합니다. 확정 건은 수납·충당 취소와 소프트 삭제를 같은 트랜잭션에서 처리합니다. 은행 연결 취소 이력은 은행 원본 선택 삭제로 처리합니다. 납부 취소는 CONFIRMED 수납과 충당을 유효 합계에서 제외하고 원본을 확인 필요로 돌립니다. 취소 초안을 명단 일치만으로 다시 자동 확정하지 않습니다.

### 월별 실제 입금 합계 (2026-10-16 후속 요청)

월별 수납 현황은 그달의 세대 입금액·기타 입금액·전체 입금액을 함께 표시합니다. 실제 입금일이 선택월인 CONFIRMED 기록의 전액을 합산하며 일부납부·선입금을 포함합니다. 취소·확인 필요·보류·LINKED는 제외합니다. 전체 입금액은 세대 입금액과 기타 입금액의 합계입니다. 기존 청구 충당·납부 상태 계산과 구분하며 동·세대 검색은 이 전체 월 합계를 바꾸지 않습니다.

### 세대 외 기타 입금 (2026-10-16 후속 확정)

사용자는 세대가 아닌 외부인의 비정기 입금과 예금이자를 별도로 관리하도록 요청했고, 기타 입금의 항목명·메모 입력과 별도 조회·확정 취소 방식을 선택했습니다.

- 확인 필요 은행 입금을 관리자가 `기타 입금`으로 분류하고 항목명을 입력합니다. 메모는 선택입니다. 이름만으로 항목이나 입금 목적을 자동 확정하지 않습니다.
- 세대·주민을 만들거나 연결하지 않으며, 정기 관리비 부과·세대 수납·미납·선입금·청구 충당에서 제외합니다. 실제 은행의 양수 입금액·입금일·입금자·원본 메모를 보존합니다.
- 확정하면 확인 필요에서 빠지고 기타 입금 목록에 표시합니다. 항목·메모로 검색하고 선택월의 기타 입금 합계·건수를 조회합니다. 동에 귀속시키지 않습니다.
- 확정 취소는 기존 분류·사유·처리자를 이력에 남기고 같은 은행 원본을 확인 필요 초안으로 돌립니다. 이후 세대 납부 또는 기타 입금으로 다시 분류할 수 있습니다. 확정 이력 삭제와 구분합니다.
- 외부인에 대한 별도 고지·미수금 추적, 이자의 세전 금액·원천세 분개, 동별 배분과 회계전표는 이번 확정에 포함하지 않습니다. 은행의 실제 순입금액만 기록합니다.

### 수동 입금 용도와 동별 직접 입금 (2026-10-18 후속 요청)

사용자는 수동 등록에서도 입금 목적에 맞게 세대 입력을 분리하고 기타 입금·동별 입금을 지원하도록 요청했습니다. 후속 지시로 명단 일치 자동 수납은 수동에서 제외하고 업로드에만 유지합니다. 동이 직접 납부한 돈도 한 동 전액 또는 여러 동에 다른 금액으로 귀속하며 수동·업로드 모두 지원합니다. 예: 입금 150만 원을 2동 100만 원·3동 50만 원으로 지정합니다.

- 세대 관리비 직접 지정은 기존 대표 주민·초안·상세 수납 확정 흐름을 유지합니다. 이 용도에서만 세대를 필수로 선택합니다.
- 기타 입금은 실제 입금 통장·일자·입금자·금액·항목과 선택 메모를 등록하며 세대·주민을 연결하지 않습니다. 등록 시 기타 입금으로 확정하고 세대 관리비·미납·선입금·청구 충당에 합산하지 않습니다.
- 동별 입금은 같은 입력에 실제 관리 동과 균등·비율·직접 금액 배분을 더합니다. 한 동에 전액 지정할 수 있고 여러 동에 서로 다른 금액을 지정할 수 있습니다. 입금 전액과 배분 합계가 일치해야 하며 원 미만 나머지를 자동 배정하지 않습니다. 동별 입금은 세대별 납부로 추정하지 않습니다.
- 수동 기타·동별 입금은 관리자가 은행에서 확인한 입금으로 기록합니다. 동별로 지정한 금액은 해당 입금일의 동별 보유금에 반영하며 미배분 기타 입금은 특정 동에 자동 반영하지 않습니다. 파일 원본·거래 후 잔액을 생성하지 않고 통장별 확인 잔액은 기존 은행 원본·인계값 기준을 유지합니다.
- 구현 선택: 용도는 최초 요청에 보존하고 요청 UUID·통장·날짜·금액·입금자·항목·메모·배분의 재시도를 검증합니다. 같은 은행 거래를 나중에 업로드하면 기존 중복 검토·수동 입금 연결을 사용해 두 번 집계하지 않습니다. 취소·삭제는 기존 이력 보존 규칙을 따르고 유효 잔고에서 제외합니다. 동별 배분과 외부 회수의 중복 사용 금지도 유지합니다.

## 7. 관리계좌 / 은행 거래 / 입금 매칭

### 기존 기준

- 초기 납부는 앱 내 카드 / PG 결제가 아니라 기존 관리계좌로의 직접 계좌이체를 사용합니다.
- 주민에게 은행, 계좌번호, 예금주와 납부금액을 안내합니다.
- 계좌번호 복사, 금액 복사와 권장 입금자명 안내를 제공합니다.
- 은행 거래 수집은 실시간 은행 API보다 파일 업로드 방식을 먼저 도입합니다.
- 계획된 업로드 파일 형식은 `.xlsx`, `.xls`, `.csv`입니다.
- 파일 미리보기는 저장하지 않습니다. 2026-10-16 후속 요청에 따라 10건씩 확인하고 가져올 입금을 선택·제외합니다. 선택한 거래만 저장하며 명단의 유일한 일치 세대가 있는 입금은 자동 확정합니다. 제외 건은 다음 업로드에서 다시 선택할 수 있습니다.
- 거래 검증, 중복 확인과 미리보기 단계를 둡니다.
- 입금 거래는 세대 매칭 후보로, 출금 거래는 지출 후보로 분류합니다.
- 판단하기 어려운 거래는 보류하거나 미분류 상태로 검토할 수 있어야 합니다.
- 은행 원본 거래의 금액, 일시와 적요를 임의로 덮어쓰지 않습니다. 아래 2026-10-17 선택 삭제는 원본과 처리 이력을 보존하는 소프트 삭제입니다.
- 같은 은행 거래가 중복 반영되지 않도록 합니다.
- 미일치·동명이인·기존 수동 수납 중복 의심은 관리자가 처리합니다. 자동 확정 기준은 위 후속 확정 정책을 따릅니다.

```text
    ↓
입금: 일치 건 자동 확정 / 나머지 관리자 확인
출금: 관리자 분류·확정
```

위 흐름은 업무 단계의 설명입니다.
원본 파일 저장, 거래 저장과 업무 확정이 모두 한 번에 처리된다는 의미는 아닙니다.

### 입금 매칭 기준

현재 기준은 [세대별 누적 수납과 자동 확정](#세대별-누적-수납과-자동-확정-2026-10-16-후속-확정)입니다. 명단의 이름 또는 동·호수의 유일한 일치를 사용하며 금액이나 납부 패턴으로 세대를 추정하지 않습니다.

### 기존 설계안

- 관리계좌는 관리대상과 연결합니다.
- 특정 동과 연결하는 선택적인 관계가 제안되어 있습니다.
- 예금주, 계좌 사용기간과 사용 상태를 관리하는 구조입니다.
- 은행 거래에는 계좌별 중복방지 키를 두는 설계가 제시되어 있습니다.
- 원본 거래 정보와 업무 처리 상태를 구분합니다.

공용계좌와 동별 계좌의 연결 구조가 있다는 사실만으로
실제 동시 사용 정책과 납부계좌 선택 우선순위가 확정된 것은 아닙니다.

### 확정된 초기 관리계좌의 예금주 입력

확정일: 2026-10-05. 초기 설정에서 예금주 이름은 필수로 입력하고, 주민 명부 연결은 선택 사항으로 둡니다. 주민 명부를 등록하기 전에도 관리계좌를 설정할 수 있도록 합니다.

- 은행 계좌의 예금주 이름은 `bank_accounts.holder_name_snapshot`에 저장합니다.
- 초기 설정에서는 주민을 선택하는 입력을 요구하지 않고 `holder_resident_id`를 비워 저장할 수 있습니다.
- 예금주가 실제 주민이어도 주민 명부 레코드가 아직 없을 수 있습니다. 예금주 이름 입력과 주민 ID 연결은 별도의 처리입니다.
- 예금주 이름만으로 주민을 자동 생성하거나, 동명이인 중 한 명을 자동 연결하거나, 로그인 사용자의 닉네임을 주민 실명으로 사용하지 않습니다.
- 주민 명부 등록 이후 계좌 설정에서 확인한 주민을 선택해 연결할 수 있습니다. 연결 대상은 같은 관리대상의 주민이어야 하며 상세 변경 권한 / 절차는 해당 기능 구현 시 결정합니다.
- 주민 연결만으로 등록 당시 예금주 이름을 자동 변경하지 않습니다. 예금주 이름 변경은 계좌 정보 변경으로 명시적으로 처리합니다.

초기 등록의 계좌는 공용계좌로 받고 기본 계좌를 정확히 1개 지정하며 사용 시작일은 등록 완료일로 설정합니다. 이 추가 확정 정책의 요청 형식은 [등록 API](propertyRegistrationApi.md)를 따릅니다. 기존 계좌의 정보 정정은 아래 후속 확정을 적용하고, 동별 전용 계좌 지원은 별도 정책이며 여러 공용 통장과 기본 지정 전환은 아래 다중 통장 운영을 따릅니다.

### 기존 관리계좌 정보 정정 (2026-10-18)

사용자는 설정의 `계좌 변경`을 다른 계좌로의 전환이 아닌 기존 계좌의 은행·계좌번호·예금주 오입력 정정으로 선택했습니다. 기존 계좌 ID와 연결된 은행 거래·수납·지출·잔고는 유지하고 새 계좌를 생성하거나 과거 거래를 다른 계좌로 옮기지 않습니다. 사용기간·공용 기본 지정도 유지합니다.

구현 선택: 현재 통장 관리와 같은 ADMIN 권한을 사용하고, 저장 시 관리대상 잠금과 조회 당시 계좌 ID·수정 시각을 확인합니다. 계좌번호는 기존 암호화·HMAC·끝 네 자리 저장을 재사용하며 원문은 인증된 정정 화면과 아래 통장 상세의 명시적 공개 요청에서만 조회합니다. 같은 정정의 응답 유실 재시도는 중복 변경하지 않습니다. 기본 계좌 전환은 후속 다중 통장 운영을 따르며 기존 청구의 납부안내 변경 정책은 미정 범위를 유지합니다. API는 [통장 관리](bankingManagement.md#기존-관리계좌-정보-정정-api)를 따릅니다.

### 공용 통장의 동별 거래 분류

확정일: 2026-10-16. 사용자는 **하나의 통장으로 여러 동을 관리**하고, 통장 거래의 입금·출금을 분류해 고지서 수납과 동별 비용 내역에 연결하도록 요청했습니다. 다음은 현재 공용 통장 운영의 확정 정책입니다. 기능별 구현 범위는 [프로젝트 현황](projectOverview.md#4-현재-개발-상태)을 참조합니다.

- 같은 관리대상의 여러 동이 공용 관리계좌를 사용합니다. 2개 동·8개 동은 예시이며 동 수를 고정하지 않습니다. 초기 등록의 계좌 수·기본 계좌 계약은 유지하고 기존 계좌를 임의로 삭제하지 않습니다.
- 관리비 입금은 동·호수의 실제 고지서와 연결해 수납을 확정합니다. 고지서 납부 상태는 기존 유효 수납 배분으로 계산하고, 해당 세대가 속한 동의 수납 내역에서 조회합니다.
- 출금은 비용 과목과 부담 동으로 분류합니다. 한 동의 비용은 해당 동에, 공동비용은 선택한 부담 동에 나누어 반영합니다. 두 동이 공동 부담하는 청소비를 절반씩 나누는 경우를 지원합니다.
- 은행 원본 출금은 1건으로 유지하고 동별 비용 부담액을 별도로 연결합니다. 동별 배분 합계는 해당 지출금액과 일치해야 하며 원본 출금·지출·배분을 더해 전체 지출을 중복 집계하지 않습니다.
- 관리자는 전체 동과 특정 동의 수납·배분 지출을 구분해 조회합니다. 동별 비용 배분만으로 실제 동별 은행 통장이나 출금, 동 간 미정산금을 생성하지 않습니다.
- 입금은 위 명단 일치 자동 확정 정책을 적용하고, 지출은 관리자 검토 후 확정합니다. 수납 확정·부분납부·여러 달 배분·선입금과 원본 연결은 [입금 API](paymentApi.md)의 기존 계약을 재사용합니다.

요청·응답은 [통장 계약](bankingManagement.md), 저장 구조는 [ERD](erd.md#94-공용-통장-거래-분류), 화면·내부 처리는 해당 영역 설계를 참조합니다.

균등·비율 배분과 직접 금액 조정, 출금의 외부·공통 귀속은 아래 2026-10-17 후속 범위를 적용합니다. 동별 보유금·외부 회수는 아래 동별 잔고·정산 후속 범위를 적용합니다. 기타 입금 동별 배분과 잘못 가져온 거래의 선택 삭제는 아래 2026-10-17 후속 요청을 적용합니다. 지출 일반 취소·재분류는 미정입니다. 현재 입금의 ADMIN 전용 권한과 중복 제외 정책을 이 요구만으로 변경하지 않습니다. 동별 권한을 새로 도입하거나 서로 다른 관리대상 사이에 공용 통장·비용을 연결하는 정책도 확정하지 않습니다.

### 통장 관리 페이지와 특수 배분 (2026-10-17)

사용자는 입금·지출의 사이드바 그룹을 통장 관리로 합치고 통장 거래, 월별 수납 현황, 지출 내역을 사용하도록 요청했습니다. 초기에는 업로드·거래 처리를 페이지로 전환했으나 후속 사용자 지시로 PC 상세·거래 설정은 공통 모달로, 업로드·미리보기는 목록과 분리한 `/banking/upload` 페이지로 맞춥니다. 모바일 저장 거래 상세는 상단 뒤로가기가 있는 페이지를 유지하며, 파일 행을 전체·입금·출금으로 필터링하고 선택한 거래를 함께 처리합니다. 필터·페이지 이동은 선택과 입력을 지우지 않습니다.

- 후속 사용자 요청: 목록은 입금의 `입금자`와 출금의 `지출명`을 구분하고 중복된 내용 열을 두지 않습니다. 원본 내용은 상세에서 확인하며, 출금의 연결 동은 외부로 지정한 동까지 포함한 부담 동의 개수로 표시합니다. 2026-10-18 후속 요청으로 연결 열은 `처리 내용`으로 통일하고, 세대 수납·기타 입금·배분 동 개수를 구분합니다. 기타 입금은 항목명을 붙이지 않고 표시합니다. 출금의 101·102·103동은 `지출 / 3동 부담`으로 표시하며 상세 표현은 [Client 설계](../client/docs/bankingManagement.md#공통-디자인과-시안-반영)를 따릅니다. 출금 지출명은 원본 내용으로 자동 입력하고 필요할 때 변경하며 별도 비용 항목을 일일이 입력하지 않습니다. 지출 내역은 입금·매칭·배분 열과 원본 출금 전액을 제거하고 각 동의 실제 부담액을 표시합니다. 전체 동 합계에도 외부 부담액을 포함하지 않습니다.
- 출금은 선택 부담처 균등 배분을 기본 입력안으로 제공하고, 비율 지정·금액 직접 입력으로 거래별 예외를 처리합니다. 전기료의 각 동 1/4 배분은 25%씩 입력하며 남은 50%의 귀속도 관리자가 지정합니다. 101동을 자동 생성하거나 외부 부담처로 미리 확정하지 않습니다.
- 외부·공통 부담처는 세대나 실제 계좌를 생성하지 않는 지출 배분 표시명입니다. 외부 고지·미수금 추적까지 구현한 의미는 아닙니다.
- 구현 선택: 원 단위에서 나누어떨어지지 않는 균등·비율 배분은 확정을 막고 금액 직접 입력으로 조정하게 합니다. 임의의 동이나 외부 부담처에 나머지를 숨겨 넣지 않습니다. 배분액은 양수, 합계는 원본 출금액과 같아야 합니다. 비율은 소수점 둘째 자리까지, 합계 100%입니다.
- 관리자가 선택한 배분 규칙은 다음 업로드의 제안에 사용합니다. 과거 확정 배분은 변경하지 않으며 규칙만으로 지출을 자동 확정하지 않습니다.
- 구현 선택: ADMIN 권한과 같은 관리대상의 선택한 사용 중 공용 통장을 사용합니다. 계좌 생략의 기존 호출만 기본 통장으로 처리합니다. 선택 전체는 한 트랜잭션으로 저장하며 하나라도 잘못되면 전체를 롤백합니다. 미리보기·선택 제외는 원장을 바꾸지 않습니다.
- 입금은 기존 자동 수납 정책을 유지하되 가져오기 전에 세대를 직접 지정하거나 기타 입금 용도를 명시할 수 있습니다. 명시한 기타 입금은 이름이 명단에 일치하더라도 세대 수납으로 자동 확정하지 않습니다.
- 환불 등 입출금은 방향별 원본을 각각 보존합니다. 이번 구현은 환불 관계 연결·비용 환입·외부 정산 잔액을 자동 생성하지 않습니다.

구현 범위·API·한계는 [통장 관리](bankingManagement.md)를 따릅니다.  지출 취소·재분류와 여러 비용 항목 분할은 여전히 후속 정책입니다.

사용자는 통장의 동별 기준 잔고와 입금을 등록했는데도 잔액이 `원본 없음`으로 보이는 문제를 지적했습니다. 은행 파일에 거래 후 잔액이 없어도 계산할 근거가 있으면 통장 계산 잔액을 표시합니다. 실제 은행 확인값과 계산값을 구분하며 실시간 은행 연동으로 설명하지 않습니다.

구현 선택: 해당 통장의 현재 관리 동별 기준값이 모두 있으면 저장된 동별 기준 잔고를 합산하고 등록된 원본 입출금 및 기존 현금 인식 기준의 미연결 확정 수동 OTHER·SHARED 입금을 누적·역산합니다. 원본은 미분류·외부 부담·통장 내부 이체도 실제 이동 전액을 포함합니다. 취소·삭제한 수동 입금은 제외하고 원본에 연결한 수동 입금은 한 번만 반영합니다. 은행 미연결 수동 세대 수납의 기존 현금 제외 기준은 유지합니다.

계산값은 실제 은행 확인 잔액을 덮어쓰지 않습니다. 실제 확인값이 없을 때 계산값과 출처를 표시하고, 기준값이 누락된 통장은 0원으로 보완하지 않습니다.

후속 사용자 요청: 계산 잔액이 포함됐다는 이유만으로 잔고 비교 차이를 `확인 필요`로 표시하지 않습니다. 화면의 통장 잔액 합계에서 동별 잔고 합계를 뺀 금액을 표시하며 계산 잔액이 포함된 차이임을 설명합니다. 차이가 0원이어도 은행 대사 완료를 뜻하지 않으며, 계산할 통장·동별 금액 자체가 없으면 금액을 만들지 않습니다.

후속 사용자 요청: 9월 30일부터 있던 통장은 8월 조회에 나타나면 안 됩니다. 사용 전 월에는 통장 선택 목록·통장 잔액·동별 합계에서 제외하며, 기준 잔고가 있다는 이유로 사용 전 월의 금액을 역산해 만들지 않습니다.

구현 선택: 기존 등록일 자동 지정 정책은 유지합니다. 앱 등록 전에 사용한 기존 통장의 과거 이력을 보존하기 위해 등록된 사용 시작일과 해당 통장의 실제 은행 원본·수납·지출 중 가장 이른 날짜를 조회 가능 범위의 시작으로 사용합니다. 2026-10-24 사용자 정정에 따라 동별 기준값·최초 잔고·직접 잔액 확인은 입출금 이력과 구분하고 시작 범위를 앞당기지 않습니다. 기준일 자체를 모든 통장의 개설일로 간주하지 않으며, 과거 사용 근거가 있는 통장의 기준일 이전 역산은 유지합니다. 사용 전 통장이 선택된 채 월을 바꾸거나 과거 URL로 접근하면 그 월의 전체 통장 조회로 복원합니다. 원본·시작일·기준 잔고를 자동 수정하지 않습니다.

### 잔고 화면의 통장 상세·계좌번호 공개 (2026-10-18)

사용자 확정: 동별 잔고·정산의 `통장별 확인 잔액`에서 통장 행을 누르면 은행·통장 정보와 계좌번호를 확인합니다. PC는 모달, 모바일은 독립 페이지를 사용하며 버튼을 눌러 전체 계좌번호를 표시합니다.

구현 선택: 기존 ADMIN 권한과 같은 관리대상 공용 통장 소속을 상세 조회·전체 번호 공개마다 확인합니다. 기본 상세는 은행·별칭·예금주·사용 상태·기본 지정 여부와 끝 네 자리만 반환하고 선택 통장 원문은 별도 POST에서만 복호화합니다. 종료 통장도 과거 조회에 유지하며 삭제·다른 관리대상·비공용 계좌는 허용하지 않습니다. 전체 번호는 브라우저 임시 상태에만 두고 숨김·닫기·이탈 시 폐기합니다. 기존 설정용 원문 API는 유지합니다. 상세 잔액은 조회 월의 기존 확인값 우선·계산값 대체 기준을 공유하며 미확인을 0원으로 보완하지 않습니다. 상세를 열어도 목록의 조회 통장은 바꾸지 않습니다. API는 [통장 관리 계약](bankingManagement.md#선택-통장-상세와-계좌번호-공개), 화면은 [Client 설계](../client/docs/bankingManagement.md#통장별-확인-잔액의-통장-상세)를 참조합니다.

### 은행별 업로드와 수동 출금 (2026-10-23)

확정일: 2026-10-23. 선택 통장의 저장된 은행 코드가 지원 대상일 때만 해당 은행 양식의 업로드를 허용합니다. 지원 은행은 `.xls`·`.xlsx`를 모두 허용하되 모든 채널·기관 코드의 양식 호환을 추측하지 않습니다. 지원 코드·열 매핑·CSV 호환·오류는 [통장 계약](bankingManagement.md#은행-코드별-업로드-구현-상태-2026-10-23)에서 관리합니다.

- 기존 원본 ID·중복 키·확정 수납을 자동 정정하지 않습니다. 시간·잔액을 포함하는 새 식별과 기존 원본 대조를 함께 적용하며 판정할 수 없는 거래는 자동 저장·수납하지 않습니다.
- 농협 음수 출금도 실제 잔액 증가와 원문 부호를 보존합니다. 양수 INCOME 원본으로 저장하되 자동 세대 수납에서 제외하며 원지출의 취소·환입을 자동 생성하지 않습니다.
- 수동 지출은 [등록 정책](#수동-지출-등록-2026-10-23-후속-확정)을 따르고 은행 확인 잔액을 생성하지 않습니다.
- 기관 코드별 추가 양식, 불완전한 식별의 관리자 대사, 수동 지출 취소·은행 연결·연결 해제·원본 삭제·외부 회수 취소의 관계는 미정입니다.

은행 API·현금 지갑·회계전표·환불 자동 연결은 이 확정에 포함하지 않습니다. 운영 중 실제 잔액 직접 확인은 [별도 정책](#운영-중-은행-잔액-직접-확인-2026-10-24)을 따릅니다.

### 통장 거래의 수동 입금 합계 (2026-10-23 후속)

사용자는 통장 거래에 표시된 수동 동별 입금도 상단 합계에 포함하도록 요청했습니다. 통장 거래의 입금 합계·입출금 차액은 조회 월·통장·검색·상태 범위의 은행 원본과 취소되지 않은 수동 입금을 포함합니다. 취소 이력으로 추가 표시한 입금은 중복 합산하지 않고, 은행 원본과 연결된 수동 입금은 원본 한 건으로 집계합니다. 방향 탭·페이지 이동은 기존처럼 합계 범위를 바꾸지 않습니다.

이 변경은 통장 거래 화면의 집계 기준입니다. 은행 확인 잔액·시각은 실제 은행 자료를 유지하며 세대 수납의 동별 보유금 인식·정식 회계 정책을 변경하지 않습니다.

### 사용 종료 통장 표시 (2026-10-23 후속 확정)

사용자는 사용 종료 통장이 현재 목록과 필터에 계속 남는 문제를 지적하고 아래 표시 기준 적용을 승인했습니다. 통장·거래·수납·지출·인계 기록은 삭제하지 않습니다.

- 실제 입출금 이력이 없는 종료 통장은 종료 월을 포함해 목록과 필터에서 숨깁니다. 2026-10-24 사용자 정정대로 10월 등록·무거래·10월 종료 계좌는 표시하지 않고, 10월 시작 계좌를 9월에 표시하지 않습니다. 은행 확인 자료가 없다는 사실만으로 미사용으로 판정하지 않습니다.
- 사용한 종료 통장은 사용 시작 범위부터 종료 월까지 거래·지출의 목록과 필터에 유지하고 다음 월부터 숨깁니다.
- 실제 사용한 계좌의 잔고·정산 화면은 종료 다음 월 이후에도 통장 잔액 또는 동별 자금이 남거나 외부 부담금 회수가 미완료이면 유지합니다. 확인 잔액과 계산 잔액이 모두 미확인인 경우도 0원으로 간주해 숨기지 않습니다. 각 동의 자금이 서로 상쇄되어 통장 합계가 0원이어도 남은 동별 자금은 유지합니다.
- 실제 사용 근거는 은행 거래, 수납, 지출입니다. 2026-10-24 사용자 정정에 따라 동별 기준값·최초 잔고·잔액 직접 확인만으로 입출금 이력이 있다고 판정하지 않습니다. 취소·삭제로 현재 금액에 반영하지 않는 과거 이력도 사용 흔적으로 보존합니다. 조회 시작 범위는 기존 사용 전 월 제외 규칙을 함께 적용합니다.
- 해당 월에 숨겨진 통장이 선택된 URL은 전체 통장으로 복원합니다. 다른 관리대상의 통장 접근 제한은 유지합니다.

### 운영 중 은행 잔액 직접 확인 (2026-10-24)

상태: **구현**. 사용자는 엑셀 업로드 외에 실제 은행 잔액을 직접 기록하는 기능과 초기 잔고 입력 개편을 적용하도록 요청했습니다. 이후 통장별 행의 메뉴 시안과 모달 중앙 배치·입력 행 정렬·필수 별표 표시를 지정했습니다.

- 운영 중 통장별 실제 은행 잔액을 직접 기록하고 확인 이력을 조회합니다. 은행 확인 잔액, 통장 계산 잔액과 동별 보유금을 구분하며 실시간 은행 연동으로 설명하지 않습니다.
- 확인 기록은 최초 통장 잔액·동별 기준 잔고·입출금·수납·지출·외부 정산을 변경하지 않습니다. 차이를 맞추는 가상 거래나 동별 자동 배분을 생성하지 않고 이후 통장 계산의 새 시작값으로 사용하지 않습니다.
- 최초 등록의 통장 실제 잔액은 유지하고 운영 중 확인값은 별도 이력으로 보존합니다. 금액과 함께 실제 확인시점·출처를 표시하고 시스템 기록시점은 별도로 관리합니다.
- 확인값은 조회 월말까지의 초기/독립 잔액 기록·엑셀 거래 후 잔액·유효 직접 확인 기록의 기준시점으로 선택합니다. 입력·업로드 순서로 최신값을 정하지 않습니다. 최신 거래의 잔액 누락을 이전 확인값으로 숨기지 않습니다.
- 날짜만 있는 거래에는 시각을 만들지 않습니다. 같은 날의 시각 자료와 선후를 입증할 수 없거나 동일 시각의 금액이 충돌하면 순서 확인 상태를 표시합니다. 기준일 마감이라는 의미가 있는 기존 인계·기초 잔액은 그 날짜의 거래 이후 값으로 비교하되 가상의 시각을 저장하지 않습니다. 같은 시점·정밀도·금액의 자료는 복수 출처로 표시합니다.
- 확인시점과 월말 동별 보유금 계산시점이 다르면 `비교 시점 다름`을 안내합니다. 서로 다른 통장의 확인시점도 표시하며 합계를 실시간 현재 잔액이나 같은 시점의 대사 결과로 설명하지 않습니다. 차이 또는 0원만으로 오류·정산 필요·대사 완료를 확정하지 않습니다.

구현 선택: 기존 ADMIN 권한을 사용합니다. 신규 기록은 같은 관리대상의 사용 중 공용 통장만 허용하고, 종료 통장은 이력 조회·취소를 허용합니다. 잔액은 0 이상 원 단위 15자리, 확인시점은 한국시간으로 초까지 입력하며 오프셋을 포함해 저장하고 미래시점을 거부합니다. 메모는 선택 500자입니다. 같은 요청 UUID·본문의 재시도는 중복 생성하지 않습니다.

잘못 입력한 확인값은 ADMIN이 필수 취소 사유(500자 이내)와 취소 요청 UUID로 취소하며 원문·처리자·시각·사유를 보존합니다. 같은 취소 재시도는 중복 변경하지 않고 취소 뒤 등록 재시도도 복원하지 않습니다. 필요한 정정은 새 확인 기록으로 남깁니다. 이력은 전체 확인 기록을 실제 확인시점·기록시점 내림차순으로 조회하고 화면은 기본 5개, 5/10/20/50개 표시 선택과 페이지 이동을 제공합니다. 상태 필터·확인 기준시점/시스템 기록시점 정렬을 지원합니다. 확인 이력은 잔액의 출처로 보존하되 입출금 사용 이력에는 포함하지 않습니다. 통장 노출에는 기존 시작 범위·사용 이력·종료 후 잔액 유지 규칙을 함께 적용합니다.

시각이 부족하거나 같은 시점의 자료가 충돌할 때 특정 엑셀·확인값을 강제로 우선하는 별도 대사 기능은 후속 범위입니다. 잘못 입력한 직접 확인값은 이력에서 취소할 수 있습니다. 화면은 [Client](../client/docs/bankingManagement.md#은행-잔액-직접-확인-화면-2026-10-24), API는 [통장 계약](bankingManagement.md#은행-잔액-직접-확인-api-2026-10-24), 저장은 [ERD](erd.md#은행-잔액-직접-확인-저장-2026-10-24)을 참조합니다.

## 8. 지출

### 기존 기준

- 은행 입금과 출금은 서로 다른 업무 흐름으로 처리합니다.
- 은행 출금 거래는 지출 후보로 분류할 수 있습니다.
- 관리자는 비용 항목, 거래처와 메모 등을 지정하여 지출을 확정합니다.
- 지출 확정 결과는 관리 지출 및 회계 비용 기록과 연결합니다.
- 주민에게 공개할 공용 지출과 내부 관리용 정보를 구분합니다.
- 실제 공개 범위는 관리자 정책에 따라 제어하는 방향입니다.

### 기본 흐름

```text
은행 출금 거래
    ↓
지출 후보
    ↓
비용 항목 / 거래처 / 메모 확인
    ↓
지출 확정
    ↓
회계 비용 반영
```

### 기존 설계안

물리 ERD v0.1에는 다음 기준이 제시되어 있습니다.

- 하나의 지출을 여러 지출 상세로 분리합니다.
- 지출 상세마다 비용 항목과 금액을 관리합니다.
- 지출 상세의 합계는 지출 총액과 일치해야 합니다.
- 지출 상세별로 주민 공개 여부를 관리하는 구조입니다.
- 확정된 지출의 정정은 삭제보다 취소 이력을 남기는 방향입니다.
- 은행 거래 연결 없이 등록할 수 있는 데이터 구조가 제안되어 있습니다.

### 미정 / 확인 필요

- 지출의 상세 필수 입력 정보
- 여러 비용 항목으로 나누는 입력 화면과 처리 절차
- 은행 거래 없는 수동 지출은 아래 [수동 지출 등록](#수동-지출-등록-2026-10-23-후속-확정)으로 구현했습니다. 취소·은행 연결 등의 수명주기는 후속 정책입니다.
- 증빙의 필수 여부와 파일 관리 정책
- 지출 확정 / 취소의 상세 권한
- 잘못 확정한 지출의 취소 / 재분류 방식
- 주민 공개 기본값과 공개 가능한 정보 범위
- 주민에게 증빙을 공개할지 여부
- 수동 지출과 이후 업로드한 출금 거래 연결은 후속 설계안에서 명시적 연결·일회 집계를 제안했으며 연결 해제·원본 삭제 등의 정책은 미정입니다.

공동비용의 선택 동 배분·합계 일치·원본 1건 보존은 [공용 통장의 동별 거래 분류](#공용-통장의-동별-거래-분류)의 2026-10-16 사용자 요구를 적용합니다. 여러 비용 과목으로 나눈 항목별 동 배분은 [ERD 확장 설계안](erd.md#105-expense_line_allocations-설계안)을 참조하며 후속 범위입니다. 현재 단일 비용 항목의 배분과 원 미만 처리는 위 2026-10-17 기준을 적용하고 취소 정책은 별도로 정합니다.

### 수동 지출 등록 (2026-10-23 후속 확정)

사용자는 수동 지출 등록을 PC 모달·모바일 페이지로 구현하고 후속 지시로 등록 버튼을 통장 거래 화면으로 이동하도록 요청했습니다. 후속 지시로 수동 입금처럼 과거 출금일을 직접 입력하며 기준 잔고 날짜 이전·당일이라는 이유로 등록을 막지 않습니다.

구현 범위는 통장·출금일·지출명·금액·선택 메모와 기존 동·외부 부담처 배분의 등록·조회입니다. 기존 ADMIN·사용 중인 같은 관리대상 공용 통장·관리 시작 검증과 오늘 이후 날짜 금지는 재사용합니다. 기준일 마감 잔고 자체는 바꾸지 않고 기존 누적·역산 계산에 입력한 출금일의 이동을 반영합니다. 조회 월의 지출은 그 월에 표시합니다.

수동 지출은 은행 원본·거래 후 잔액을 생성하지 않습니다. 통장 계산 잔액에는 전액을 한 번, 동별 원장에는 각 동의 부담액을 반영합니다. 외부 부담처는 기존 정산에서 같은 통장의 기타 입금과 회수 연결할 수 있습니다. 요청 UUID 재시도는 내용이 같으면 중복 생성하지 않고, 다른 내용이면 충돌로 거부합니다. 확정 지출·배분의 불변 이력은 유지합니다.

수동 지출의 취소·은행 연결·연결 해제는 이번 등록 구현에 포함하지 않았습니다. 나중에 업로드한 같은 출금을 자동 연결·중복 제외하는 기능은 없으며, 같은 실제 거래를 별도 은행 지출로 확정하면 중복 집계될 수 있습니다. 해당 연결·대사 정책은 위 미정 범위를 유지합니다. 계약은 [통장 관리](bankingManagement.md#수동-지출-등록-api-2026-10-23)를 따릅니다.

## 9. 회계

### 확정된 개발 우선순위

2026-10-24 사용자는 회계를 후순위로 두고 `정산 / 마감`의 초기 범위를 `월별 정산`으로 좁혔습니다. 회계 메뉴는 현재 노출에서 제외했고, 자동전표·계정별 원장·회계용 세대별 미수원장·정식 손익의 개발은 후속으로 둡니다. 기존 회계 설계와 업무 원천의 연결 원칙은 유지합니다.

월별 정산의 조회·점검·Excel·PDF 다운로드는 자동전표 구현을 선행 조건으로 두지 않습니다. 현재 수납 화면의 미납 조회도 유지합니다. 아래 회계 기준과 분개 예시는 후속 설계이며 회계 처리 자체는 미구현입니다.

### 기존 기준

- 관리비 업무 결과가 회계 데이터로 연결되는 구조를 유지합니다.
- 같은 내용을 관리 업무와 회계 업무에서 반복 입력하는 것을 기본 방식으로 삼지 않습니다.
- 부과 확정, 수납 확정과 지출 확정을 회계 처리의 업무 기준으로 사용합니다.
- 청구 작성이나 입금 추천만으로 회계 처리가 확정된 것으로 보지 않습니다.
- 전표의 차변 합계와 대변 합계는 일치해야 합니다.
- 확정된 전표를 일반 CRUD처럼 직접 삭제하거나 금액을 덮어쓰지 않습니다.
- 오류 정정은 취소, 역분개, 조정 또는 정해진 재처리 절차로 이력을 보존합니다.
- 관리비 회계 기능을 자체적으로 제공하되 범용 ERP 전체를 구현하는 것을 목표로 하지 않습니다.

### 기본 회계 연결 예시

기존 계획서에 제시된 기본 분개는 다음과 같습니다.

| 업무 | 차변 | 대변 |
| --- | --- | --- |
| 관리비 부과 확정 | 미수금 | 관리비수익 |
| 관리비 입금 매칭 및 수납 확정 | 보통예금 | 미수금 |
| 공용 지출 확정 | 해당 비용 계정 | 보통예금 |

이 표는 계획서의 기본 업무 예시입니다. 부과 분개는 양수 청구의 예시이며, 음수 청구의 회계 반영 방식은 [관리비 부과의 미정 항목](#5-관리비-부과--청구)을 따릅니다.

수납 예시는 수납액이 해당 청구에 배분되는 경우를 설명합니다.
초과입금, 선수금, 환불과 미배분 금액까지 같은 분개로 처리한다는 뜻은 아닙니다.

### 부분납부 예시

청구액 50,000원 중 30,000원이 수납되어 해당 청구에 배분된 경우입니다.

```text
청구액: 50,000원
수납 및 배분액: 30,000원

차변: 보통예금 30,000원
대변: 미수금   30,000원

잔여 미수금: 20,000원
```

이후 추가 수납이 배분되면 잔여 미수금과 납부 상태에 반영합니다.

### 제공할 회계 조회

- 계정별 원장
- 세대별 미수원장
- 거래처별 지출 조회
- 월별 / 연간 손익
- 통장 대사
- 전표와 원천 업무 기록의 연결 확인

### 기존 설계안

- 업무 원천과 회계 이벤트, 전표를 연결합니다.
- 동일한 회계 이벤트가 중복 전표를 만들지 않도록 중복방지 기준을 둡니다.
- 회계 이벤트는 처리 대기 / 완료 / 실패를 구분하는 구조입니다.
- 전표 확정 이후 직접 수정하지 않는 기준이 제시되어 있습니다.
- 전표 상세의 각 행은 차변 또는 대변 한쪽 금액으로 구성합니다.
- 공통 계정과 관리대상별 계정 및 기본계정 매핑 구조가 제안되어 있습니다.

회계 이벤트가 생성되었다는 사실과 전표 처리가 완료되었다는 사실은 구분합니다.

### 미정 / 확인 필요

- 실제 기본 계정과목과 관리대상별 변경 범위
- 자동전표의 확정 조건과 수동 조정 권한
- 초과입금 / 선수금 / 환불의 회계 처리
- 수납일, 배분일과 회계 기준일이 다른 경우의 처리
- 이벤트 처리 실패 시 재처리 절차
- 취소 / 역분개 / 조정 전표의 구체적인 연결 및 집계 방식
- 업무 데이터와 회계 데이터의 불일치 확인 및 복구 절차
- 동기 처리와 비동기 처리의 구체적인 구현 방식

## 10. 통장 대사 / 월 마감

### 확정된 월별 정산 범위

2026-10-24 사용자는 기존 통장 관리와 동별 잔고·정산을 유지하고 `정산 / 마감`에는 `월별 정산` 하나만 두도록 요청했습니다. 후속 구현 요청에서 메뉴는 관리비 부과처럼 드롭다운 없는 단일 링크로 지정했습니다. 한 달의 업무 결과와 확인할 항목을 모아 검토하는 것이 목적입니다.

| 구분 | 이번 범위 | 후속 범위 |
| --- | --- | --- |
| 월별 요약 | 입금·출금, 관리비 수납·미납, 동별 보유금, 외부 미회수액 조회 | 확정 보고서 보존 |
| 월말 점검 | 미분류 거래, 통장 잔액 차이·확인 자료 부족 확인 | 마감 차단 조건과 검증 결과 확정 |
| 보고서 | 월별 정산 종합보고서 Excel·PDF·이미지(PNG) 다운로드·미리보기 | 별도 보고서 메뉴의 필요성 검토 |
| 월 마감 | 이번 범위에 포함하지 않음 | 마감 확정·잠금·재오픈·마감 후 정정 |

통장 잔액 확인과 보고서 다운로드는 월별 정산 안에서 제공하며 별도 하위 메뉴를 만들지 않습니다. 거래 분류·수납 확정·지출 배분·외부 부담금 회수 등 원천 업무는 기존 화면에서 처리합니다. 월별 정산을 위해 같은 거래나 납부 상태를 따로 입력·관리하지 않습니다.

월별 정산 조회나 Excel·PDF 다운로드를 마감 확정·정산 완료로 취급하지 않습니다. 실제 마감 구현 전에는 원천 업무 변경으로 조회 결과와 새로 내려받은 보고서가 달라질 수 있습니다. 화면 구성은 [Client 월별 정산 설계](../client/docs/monthlySettlement.md)를 따릅니다.

2026-10-24 후속 사용자 요청으로 **동별 입출금·잔액 명세는 동별 잔고·정산 다운로드로 이동**하고, 월별 정산에는 첨부 PDF·Excel 템플릿의 종합보고서를 적용했습니다. 월별 보고서는 전체 관리대상의 8개 핵심 지표·6개 점검·통장 확인·동별 자금·수납/미납·실제 통장 입출금·외부 부담금을 제공합니다. 기존 동별 명세의 동/계좌 선택·기초/거래 후/월말 잔액·월초→월말 정렬은 잔고·정산에서 유지합니다. 두 Excel 모두 한 시트이며 예시 데이터와 별도 시트 구성은 복사하지 않습니다. Excel·PDF·이미지의 형식 선택과 실제 파일 미리보기, 실패 재시도를 유지하고 페이지 이동 버튼은 미리보기 아래에 둡니다. 지난 월의 `9월 마감`·현재 월 `집계 중`은 기간 표시이며 원장 잠금·재오픈을 구현한 것으로 보지 않습니다. 기존 `마감 미확정 자료` 문구 제거는 유지합니다. 상세 출력 구성은 [월별 정산](../client/docs/monthlySettlement.md#excelpdf-자료-범위)과 [잔고·정산](../client/docs/bankingManagement.md#동별-입출금-명세-다운로드)을 따릅니다.

후속 사용자 정정: **월별 정산의 외부 부담금은 선택 월에 지출한 내역만** 표시합니다. 10월에는 지출일이 10월인 부담금만 목록·미회수 합계·점검 건수·다운로드에 포함합니다. 회수액·미회수액은 기존 조회 월말 기준 계산을 유지하고 정산 제외분은 합계에서 뺍니다. 과거 미회수까지 확인·회수하는 동별 잔고·정산의 누적 범위는 유지합니다.

### 월별 정산 집계 기준

월별 정산에 적용하는 지표 구분입니다. 상세 조회 계약은 [월별 정산 API](monthlySettlementApi.md), 화면·파일 구성은 [Client 정산](../client/docs/monthlySettlement.md)을 따릅니다.

- 실제 입금월과 청구 충당월을 구분합니다. 수납·미납은 [기존 수납 정책](#6-수납--수납-배분--납부-상태)을 참조하고, 이전 선입금 충당액을 이번 달 실제 입금액으로 다시 합산하지 않습니다.
- 통장 전체 출금액과 관리 동의 부담 지출액을 구분합니다. 외부 부담액·회수액·미회수액은 별도 지표이며 회수 입금을 관리비 수납으로 바꾸지 않습니다.
- 내부 이체의 통장 입출금과 운영 지출 반영은 [다중 통장 계약](bankingManagement.md#다중-통장내부-이체-api-2026-10-18)을 따릅니다. 전체 운영 수입·지출과 통장별 실제 입출금을 같은 합계로 표시하지 않습니다.
- 은행 확인 잔액·통장 계산 잔액·동별 보유금을 구분합니다. 비교 시점·출처·자료 부족 처리는 [운영 중 은행 잔액 직접 확인](#운영-중-은행-잔액-직접-확인-2026-10-24)을 따릅니다. 미확인 값을 0원으로 채우거나 동별 보유금과의 차이만으로 오류·대사 완료를 확정하지 않습니다.
- 취소·삭제·수동 수납의 은행 원본 연결 등은 기존 유효 집계 기준을 재사용합니다. [수동 지출](#수동-지출-등록-2026-10-23-후속-확정)의 은행 원본 연결·중복 대사가 완료된 것으로 가정하지 않습니다.
- 미수금이나 외부 미회수액의 존재를 오류 또는 마감 불가 조건으로 임의 지정하지 않습니다. 원 미만 금액·음수 청구·환급 등 기존 미정 정책을 보고서 계산으로 새로 확정하지 않습니다.

### 월별 정산 조회 구현

2026-10-24 후속 요청으로 조회·점검·Excel·PDF와 단일 메뉴를 구현했습니다. 아래는 기존 업무 계산을 재사용한 구현 선택이며 새로운 마감·회계 정책을 확정하지 않습니다.

- 기존 통장·수납과 같은 ADMIN 조회 범위를 사용합니다. 월을 생략하면 한국시간 현재 월을 조회하고 조회 API에는 통장·동 추가 필터를 두지 않습니다. 화면에서 수납 명세를 필터링해도 전체 월 조회 응답은 유지합니다. 월별 종합보고서는 화면 필터와 별도로 관리대상 전체를 출력하고 동·계좌별 입출금 명세는 잔고·정산에서 선택합니다.
- 수납·미납은 기존 월별 수납 대상 세대와 월말 누적 계산을 그대로 사용합니다. 전월 이월을 포함한 `월별 수납 미수금`으로 표시하며 모든 과거 세대의 독립 회계 미수원장이라고 하지 않습니다. 0원·음수 청구의 정산 확인 상태도 유지합니다.
- 통장 입출금은 해당 월 은행 원본과 은행 미연결 확정 수동 입금·수동 지출을 포함합니다. 내부 이체도 실제 통장 이동으로 표시하며 이를 운영 수익·비용이나 손익으로 이름 붙이지 않습니다. 취소·연결된 수동 입금은 중복 합산하지 않습니다.
- 현재 유효 원천 자료를 조회 월 기준으로 계산하며 과거 마감 당시 상태를 복원하지 않습니다. 취소·뒤늦은 등록 이후 다음 조회와 새 파일의 금액이 바뀔 수 있습니다.
- 통장 차액은 월말의 일 마감 확인값과 월말 계산값을 모두 확인할 수 있을 때만 표시합니다. 날짜·시각 정밀도가 다르거나 확인 순서가 불명확하면 비교 불가로 남깁니다. 차액 0원도 대사 확정으로 처리하지 않습니다.
- 미분류·보류·취소·이체 연결 대기 거래, 잔액 비교 자료, 동별 기초 보유금, 미정 청구와 외부 미회수 내역을 확인 항목으로 제공합니다. 같은 통장·날짜·방향·금액의 수동 등록과 은행 원본은 중복 가능성만 안내하며 자동 제외하지 않습니다.
- 동별 자료가 없거나 잔고가 미설정이면 동별 보유금을 0원으로 채우지 않습니다. 외부 정산 제외분은 내역에서 보존하고 미회수 합계에서는 뺍니다.
- 동일한 조회 응답으로 화면과 Excel·PDF를 구성합니다. 파일에는 기존 조회 명세의 세대 대표·거래 입금자 표시를 사용하며 주민 연락처·계좌번호 원문 열은 추가하지 않습니다. 상세 요청·응답·오류는 [월별 정산 API](monthlySettlementApi.md)를 따릅니다.

동일 시점 대사를 위한 거래 순서 확인·시점 보정, 수동 지출과 은행 원본의 명시적 연결·중복 제거, 전체 과거 세대를 포함한 독립 미수원장과 확정 보고서 보존은 후속입니다. 아래 마감 권한·재오픈 등의 정책을 이번 조회 기능에 적용한 것으로 해석하지 않습니다.

### 기존 기준

- 월 마감 전 청구액, 수납액, 미수금, 지출과 통장 잔액을 확인합니다.
- 통장 대사는 장부상 계좌 잔액과 실제 은행 잔액을 비교하는 업무입니다.
- 마감된 기간은 일반 수정으로 변경하지 않습니다.
- 마감 후 정정에는 별도 권한과 절차가 필요합니다.
- 마감 또는 재오픈 같은 주요 처리의 이력을 유지합니다.

### 기존 설계안

- 관리비 부과기간과 회계기간은 별도 개념으로 관리합니다.
- 회계기간은 열림 / 마감 진행 / 마감 상태를 구분하는 구조입니다.
- 통장 대사에는 장부 잔액, 은행 잔액과 차액을 기록합니다.
- 재대사를 수행할 경우 이전 대사와 새로운 결과의 관계를 보존합니다.
- 마감 검증 결과를 항목별로 기록합니다.
- 마감을 차단하는 검증 실패가 있으면 마감할 수 없는 구조입니다.
- 마감 / 재오픈의 성공 및 실패 이력을 보존하는 설계입니다.

### 미정 / 확인 필요

- 마감 실행 권한
- 마감 전 필수 검증 항목과 경고 항목
- 미분류 거래, 미처리 회계 이벤트 또는 잔액 차이가 있을 때의 처리
- 마감 후 재오픈 허용 조건
- 재오픈과 다음 기간 조정 중 어떤 방식을 적용할지에 대한 기준
- 재오픈이 기존 보고서와 이후 기간에 미치는 영향
- 대사 차액의 원인을 조사하고 정정하는 업무 절차

미수금이 존재한다는 사실만으로 마감 가능 여부를 임의로 결정하지 않습니다.
실제 마감 차단 조건은 별도 정책으로 확정합니다.

## 11. 금액 / 업무 무결성 / 감사 이력

### 금액의 기존 기준

- 금액 계산에서 부동소수점 오차가 발생하지 않도록 합니다.
- 청구 총액과 청구 항목 합계의 일치를 확인합니다.
- 수납 및 청구 금액을 초과하는 배분을 방지합니다.
- 지출 총액과 지출 상세 합계의 일치를 확인합니다.
- 전표의 차변 합계와 대변 합계의 일치를 확인합니다.

물리 ERD v0.1은 금액을 소수 자릿수 0인 `numeric(15,0)`으로 제안하고 있습니다.

이는 기존 저장 설계안입니다.
비율 계산 과정의 정밀도나 반올림 시점까지 정한 것은 아닙니다.
Java 타입과 DB 구현 규칙은 Server 문서를 따릅니다.

### 업무 무결성의 기존 기준

- 하나의 업무 단위에서 함께 변경되어야 하는 데이터는 중간 실패로 일부만 반영되지 않도록 합니다.
- 동일한 요청이나 원천 거래가 중복된 업무 결과를 만들지 않도록 합니다.
- 추천, 검토, 확정과 회계 처리 완료를 서로 구분합니다.
- 재처리를 하더라도 기존 확정 결과를 중복 생성하지 않도록 합니다.
- 주민 조회 여부와 무관하게 관리자 업무 및 회계 처리가 동작해야 합니다.

외부 은행 이체, 파일 업로드, 수납 확정과 회계 처리가
모두 하나의 DB 트랜잭션이라는 의미는 아닙니다.

각 업무의 완료 기준과 실패 시 복구 범위는 실제 구현 전에 정합니다.

### 감사 이력의 기존 기준

- 부과, 수정, 매칭, 취소와 지출 분류의 작업자 및 처리 시각을 기록합니다.
- 확정된 업무 기록은 삭제 대신 정정 이력을 보존합니다.
- 개인정보 원문을 일반 로그나 감사 로그에 그대로 남기지 않습니다.
- 전화번호, 계좌번호와 입금자명 등을 오류 메시지에 노출하지 않습니다.

기존 ERD는 감사 이력을 추가 전용으로 관리하고,
기록된 감사 로그의 수정과 삭제를 금지하는 방향입니다.

### 미정 / 확인 필요

- 지원 통화와 금액 입력 단위
- 비율 계산의 소수 자릿수와 반올림 시점
- 업무 날짜와 시간대 기준
- 기간 경계와 월 귀속 판단 방식
- 업무별 중복 요청 판정 기준
- 재처리 가능 범위와 처리 이력
- 감사 이력의 상세 필드, 열람 권한과 보존 기간

### 흐름 해석 원칙

- 청구 작성과 부과 확정은 같은 단계로 취급하지 않습니다.
- 은행 거래 업로드와 수납 확정은 같은 단계로 취급하지 않습니다.
- 수납 확정과 청구에 대한 금액 배분은 서로 다른 업무 의미를 가집니다.
- 회계 이벤트 생성과 전표 처리 완료를 구분합니다.
- 마감은 납부완료 상태를 대신하지 않습니다.
- 실패와 취소가 발생한 경우 연결된 기록의 처리 결과를 함께 확인합니다.

## 13. 구현 전 확인과 문서 관리

### 구현 전 확인 순서

1. `projectOverview.md`에서 현재 구현 대상과 개발 단계를 확인합니다.
2. 이 문서의 해당 기능에 대한 확정 정책 / 기존 기준과 [ERD](erd.md)의 컬럼 / 관계 / 제약을 함께 확인합니다.
3. 미정 / 확인 필요 항목 중 현재 구현에 영향을 주는 정책을 구분합니다.
4. 필요한 정책을 임의로 결정하지 않고 먼저 확정합니다.
5. 허용되는 상태 변경, 금액 계산, 권한과 취소 / 실패 결과를 문서에 반영하고 관련 ERD를 갱신합니다. 기존 코드 / Migration과의 차이도 확인합니다.
6. 확정한 기준에 맞춰 화면, Server 로직과 테스트를 구현합니다.
7. 문서와 실제 구현이 다른 부분이 있는지 확인합니다.

### 다른 문서와의 관계

- `projectOverview.md`는 프로젝트 전체 범위와 개발 단계를 설명합니다.
- `domainRules.md`는 업무 규칙과 미정 정책을 관리합니다.
- [erd.md](erd.md)는 데이터 관계, 컬럼과 제약을 관리하고 확정 범위 / 설계안 / 미정 항목을 구분합니다.
- [propertyRegistrationApi.md](propertyRegistrationApi.md)는 기본 정보 검증, 최종 등록과 결과 조회의 공통 API 계약을 관리합니다.
- [Client 등록 설계](../client/docs/propertyRegistration.md)와 [Server 등록 설계](../server/docs/propertyRegistration.md)는 각 영역의 구현 책임과 검증 기준을 관리합니다.
- `AGENTS.md`는 공통 및 영역별 구현 규칙을 정의합니다.
- 업무 정책을 변경하면 관련 문서와 구현에 미치는 영향을 함께 확인합니다.
- 기능이 문서에 있다는 이유로 구현 완료된 것으로 판단하지 않습니다.
- 현재 개발 범위에 없는 기능을 미리 구현하지 않습니다.
- 공지사항·채널톡·초대코드 추가·개편은 [프로젝트 개요의 검토 후보](projectOverview.md#추가-검토-후보)로만 관리합니다. 기존 초대·참여 정책은 새 결정 전까지 유지합니다.
