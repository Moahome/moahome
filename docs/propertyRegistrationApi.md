# 관리대상 기본 정보 API

이 문서는 관리대상 등록 첫 단계의 입력, 검증 요청, 응답과 오류를 정의합니다. 초기 설정 마지막에 전체 정보를 저장하는 정책에 따라, 기본 정보 단계의 API는 입력을 검증하고 정리한 값을 반환합니다. 관리대상이나 생성자 권한을 저장하지 않습니다.

작성일: 2026-10-05. 업무 정책은 [도메인 규칙](domainRules.md)의 확정된 관리대상 등록과 초기 설정, 데이터 구조는 [ERD](erd.md)를 따릅니다. 아래 계약은 구현을 위한 API 설계이며 현재 Controller / Service / Entity / Migration은 구현되지 않았습니다.

## 1. 적용 범위

- 기본 정보 입력은 관리대상 이름, 주소, 상세주소, 건물 유형과 동 구분입니다.
- 정상 로그인 사용자가 기존 관리대상 유무와 관계없이 새 등록을 시작할 수 있습니다. 플랫폼 관리자 역할은 요구하지 않습니다.
- 첫 단계의 `등록하고 계속`은 검증 성공 후 Client 초안을 유지하고 동 / 세대 단계로 이동합니다. DB 저장 성공을 의미하지 않습니다.
- 마지막 `관리 시작하기`는 별도의 최종 등록 API로 전체 정보를 저장하고 생성자를 해당 관리대상의 관리소장으로 지정합니다. 해당 API의 전체 요청 / 응답과 중복 등록 방지는 후속 계약 범위입니다.
- 주소 검색 서비스, 동 / 세대, 관리계좌, 관리비 항목의 상세 API는 이번 계약에 포함하지 않습니다.

## 2. 기본 정보 검증 요청

| 항목 | 계약 |
| --- | --- |
| Method | `POST` |
| Path | `/api/property-registrations/basic-info/validate` |
| 인증 | `Authorization: Bearer <Access Token>` |
| 요청 형식 | `Content-Type: application/json` |
| 응답 형식 | `application/json`, `Cache-Control: no-store` |
| 업무 데이터 저장 | 없음 |

기존 업무 API와 동일하게 Bearer로 인증합니다. Refresh 쿠키를 인증 수단으로 사용하지 않으며 업무 API에는 `X-CSRF-TOKEN`을 요구하지 않습니다. 인증 동작과 CORS는 [보안 설계](securityDesign.md)의 기존 기준을 따릅니다.

### 입력 필드

| 필드 | 타입 | 필수 | 검증과 정리 | 최종 저장 컬럼 |
| --- | --- | --- | --- | --- |
| `name` | string | 필수 | 앞뒤 공백 제거 후 1~50자 | `properties.name` |
| `address` | string | 필수 | 앞뒤 공백 제거 후 1~255자 | `properties.address` |
| `addressDetail` | string 또는 null | 선택 | 앞뒤 공백 제거 후 최대 255자, 생략 / null / 빈 값은 null | `properties.address_detail` |
| `propertyType` | string 또는 null | 선택 | 앞뒤 공백 제거 후 최대 30자, 생략 / null / 빈 값은 null | `properties.property_type` |
| `hasBuildings` | boolean | 필수 | true / false만 허용, 생략 / null / 문자열은 거부 | `properties.has_buildings` |

문자열 길이는 앞뒤 공백을 제거한 뒤 Unicode 코드 포인트 수로 판단합니다. 한글 등 특정 문자만 허용하는 제한을 추가하지 않습니다. 문자열 필드에 숫자나 객체가 들어오면 문자열로 자동 변환하지 않고 잘못된 입력으로 처리합니다. `hasBuildings = false`는 정상 입력입니다.

건물 유형은 현재 ERD의 선택적인 문자열 설계를 유지하며 이번 계약에서 새로운 유형 Enum을 만들지 않습니다. 화면의 유형 목록과 코드 체계는 해당 입력 UI를 구현할 때 정리합니다. 주소는 입력 형식과 길이를 검증하며, 이 API 성공을 주소의 실재 여부나 건물 소유 확인으로 해석하지 않습니다.

요청에는 생성자 ID, 역할, 상태, 주민 ID를 받지 않습니다. 등록 계약 밖의 필드는 허용하지 않고 `400 / INVALID_REQUEST`로 거부합니다. 관리소장 지정은 최종 등록 시 인증된 계정을 기준으로 Server가 수행합니다.

### 요청 예시

## 3. 검증 성공 응답

HTTP `200 OK`로 정리한 기본 정보 객체를 직접 반환합니다. 선택 필드는 입력에서 생략해도 응답에 null로 포함합니다.

```json
{
  "name": "성내빌라",
  "address": "서울특별시 강동구 예시로 1",
  "addressDetail": null,
  "propertyType": "빌라",
  "hasBuildings": false
}
```

초안을 Server에 보관하지 않으므로 `propertyId`, `registrationId`, 참여 역할이나 다음 단계 URL을 발급하지 않습니다. Client는 응답을 현재 등록의 기본 정보에 반영하고 동 / 세대 단계로 이동합니다. 검증 호출을 반복해도 관리대상이나 참여 레코드가 생기지 않습니다.

## 4. 오류 응답

기존 인증 API와 같은 `code`, `message` JSON 구조를 사용합니다. 오류 메시지에는 입력한 이름 / 주소 원문, 토큰이나 내부 저장소 오류를 넣지 않습니다.

```json
{
  "code": "INVALID_REQUEST",
  "message": "요청 형식이 올바르지 않습니다."
}
```

| HTTP | code | 발생 조건 | Client 처리 |
| --- | --- | --- | --- |
| 400 | `INVALID_REQUEST` | JSON 형식 오류, 필수 필드 누락, 타입 / 길이 오류, 계약 밖 필드 | 현재 입력 유지, 입력 기준과 형식 확인 안내 |
| 401 | `AUTHENTICATION_REQUIRED` | Bearer 인증 없음 | 기존 로그인 흐름 적용 |
| 401 | `INVALID_TOKEN` | 토큰이 유효하지 않음 | 기존 세션 오류 흐름 적용 |
| 401 | `ACCESS_TOKEN_EXPIRED` | Access Token 만료 | 기존 `authenticatedAPI()`의 재발급 후 원래 요청 1회 재시도 |
| 401 | `SESSION_EXPIRED` | 로그인 세션 만료 / 없음 | 기존 로그인 흐름 적용 |
| 403 | `ACCOUNT_UNAVAILABLE` | 정지 / 탈퇴 등 이용 불가 계정 | 등록 초안 폐기, 기존 계정 이용 불가 흐름 적용 |
| 403 | `ACCESS_DENIED` | 인증 계층에서 접근 거부 | 접근 거부 안내 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | JSON 이외의 Content-Type | 입력 유지, JSON 형식으로 요청하는지 확인 |
| 500 | `INTERNAL_SERVER_ERROR` | 예상하지 못한 내부 검증 처리 오류 | 입력 유지, 오류 안내 |
| 503 | `AUTH_SERVICE_UNAVAILABLE` | 인증에 필요한 Redis / 계정 조회 저장소 장애 | 입력 유지, 일시 장애 안내와 명시적 재시도 |

415의 `message`는 `JSON 형식으로 요청해주세요.`, 500의 `message`는 `요청을 처리하지 못했습니다.`로 사용합니다. 새 오류의 예외 매핑은 이 API 구현 범위이며 기존 인증 오류 코드는 변경하지 않습니다.

이 API는 관리대상을 생성하지 않으므로 이름 / 주소 중복을 임의로 `409` 오류로 추가하지 않습니다. 최종 저장의 중복 요청 처리와 무결성 오류는 최종 등록 계약에서 정의합니다.

통신 실패나 응답을 해석하지 못하는 경우는 HTTP 오류 응답과 구분해 기존 `NETWORK_ERROR` / `INVALID_RESPONSE` 처리 기준을 적용합니다. 인증 장애나 서버 오류에서 다음 단계로 이동하지 않습니다.

## 5. Client 연결

1. 첫 단계에서 입력의 필수 여부와 길이를 확인합니다. 같은 입력 규칙을 Server에서도 검증합니다.
2. `등록하고 계속`을 선택하면 기존 `authenticatedAPI()`로 검증 요청을 보내고, 응답 대기 중에는 같은 버튼의 중복 요청을 막습니다.
3. 성공하면 정리한 입력을 Client 초안에 반영하고 동 / 세대 단계로 이동합니다. 입력 오류와 일시 장애에는 현재 단계와 입력을 유지하며 인증 / 계정 오류에는 위의 오류 응답별 처리를 적용합니다.
4. 이전으로 돌아가면 초안의 기본 정보를 표시합니다. 수정 후 다시 다음으로 이동할 때 기본 정보를 재검증합니다.
5. 새로고침하면 같은 사용자 / 탭의 진행 중인 입력과 현재 단계를 복원합니다. 취소, 등록 흐름 이탈, 탭 닫기와 로그아웃 시에는 초안을 폐기합니다.
6. 마지막 저장에서는 기본 정보를 포함한 전체 정보를 Server가 다시 검증합니다. 이전 검증 응답을 저장 권한이나 검증 생략의 근거로 사용하지 않습니다.

기본 정보 검증에는 업무 데이터 쓰기가 없으므로 응답 전에 취소하거나 통신이 끊겨도 부분 등록은 남지 않습니다. 최종 등록 요청 시작 이후의 결과 확인은 별도 최종 등록 계약을 따릅니다.

## 6. 구현 시 검증 기준

- 정상 로그인 사용자의 검증 성공과 선택 필드의 생략 / null / 공백 정리를 확인합니다.
- 이름 50자 / 51자, 주소 255자 / 256자, 상세주소 255자 / 256자, 건물 유형 30자 / 31자와 공백만 있는 필수 입력을 검증합니다.
- `hasBuildings`의 true / false 성공과 생략 / null / 문자열 입력 거부를 확인합니다.
- 계약 밖 생성자 / 역할 필드와 잘못된 JSON / Content-Type을 거부하고 오류에 입력 원문이 포함되지 않는지 확인합니다.
- 인증 실패, 이용 불가 계정과 인증 저장소 장애를 입력 오류와 구분합니다.
- 성공, 반복 요청과 오류에서 업무 테이블 쓰기가 발생하지 않는지 확인합니다.
- Client의 이전 단계 복원, 새로고침 복원, 취소 / 탭 닫기 후 새 등록의 초안 폐기, 계정 변경 시 초안 격리와 오류 시 입력 유지를 확인합니다.

현재 작업은 문서 작성 범위입니다. 위 항목은 API와 화면을 구현할 때 수행할 검증이며, 이미 실행된 테스트를 의미하지 않습니다.
