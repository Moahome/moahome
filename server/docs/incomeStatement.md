# 손익 원천 연결과 분류 이력

상태: 2026-11-04 구현. [공통 API](../../docs/api/incomeStatementApi.md)와 [회계 기준](../../docs/domain/domainRules.md#9-회계)을 따릅니다. 이 구현은 확정 청구와 유효 출금의 손익 조회·명시적 분류이며 정식 복식부기 전표 엔진 구현과 구분합니다.

## 조회 경계

`IncomeStatementService`는 관리대상 접근을 먼저 검사하고 읽기 전용 REPEATABLE_READ 트랜잭션에서 조회합니다. 프로필 유무와 무관하게 최초 부과월을 기준으로 조회하며 조회에서 DB를 쓰지 않습니다. 기존 프로필의 늦은 시작 월은 부과를 가리지 않으며 저장 이력은 보존합니다. `BillingIncomeSourceService`가 부과 영역 내부에서 유효한 확정 월별 청구·항목·부과월을 반환합니다. 인계 미수·초안·취소 청구는 수익으로 복사하지 않습니다. 부과 확정 실행이나 입금 수익 재생성을 하지 않습니다.

확정 관리비의 모든 구성 항목은 이름·표준 코드·저장된 기본 계정 연결의 유무와 관계없이 `401 관리비수입`에 자동 연결합니다. 별도 과목의 최신 명시적 확인은 유지합니다. 양수·0원 청구의 사용자 지정 차감 항목도 부호를 유지해 같은 401에 합산하며 별도 매칭 대상으로 남기지 않습니다. 세대당 50,000원에 포함된 수선비 -3,300원 × 20세대는 지출이 아니라 부과 총액 1,000,000원의 구성입니다. 부과 합계/항목 불일치, 전체 음수 청구, 유일하게 연결할 수 없는 과거 동은 이슈로 드러냅니다. 과거 청구 동명과 보존된 동이 유일하게 일치하는 경우에만 귀속하며 선택 동으로 임의 배분하지 않습니다.

지출은 기존 BankingService의 유효 확정 원천과 기존 동 배분을 재사용합니다. 지출명에 입력한 비용 코드·기본 과목명과 통상 표기는 같은 관리대상의 비용 계정 ID로 자동 매칭합니다. 예를 들어 전기료·전기요금은 804, 엘리베이터는 803, 정화조는 807, 문자수수료는 808입니다. 두 과목 이상에 매칭되면 임의 선택하지 않으며 최신 명시적 분류가 우선합니다. 별도 귀속 월이 없으면 원본 지출 날짜의 월로 자동 귀속하며 기존에 명시적으로 저장한 귀속 이력은 보존합니다. 2026-11-05 사용자 확정에 따라 외부 부담 배분은 `102 미수금`, 실제 회수 연결은 미수금 감소로 연결합니다. 우리 부담분만 비용 계정에 매칭하며 외부 몫은 비용·수익에 합산하지 않습니다. 미지급/선급 전표는 이 단계에서 생성하지 않습니다. 비용 과목이 미연결인 지출만 확인 대상에 남기며 조회 범위 밖의 지출은 합산하지 않습니다. 실제 회수 연결액을 제외한 확정 기타 입금은 사용자 지정 `901 영업외수익`에 자동 연결하고 기존 동별 배분을 사용합니다. 예금이자 메모에서 세전 금액·세금을 추정하지 않습니다.

2026-11-05 원천 표시 보완: 이슈의 원본 이름·거래일·기존 부담처와 청구 당시 부과월·동/호수/표시명을 확인 사유와 분리해 반환합니다. `BillingIncomeSourceService`는 기존 청구 스냅샷의 호수·표시명을 전달하며 현재 세대 조회로 과거 귀속을 추정하지 않습니다. 과거 원천 검증에 필요한 동 목록은 유지하고 삭제 여부를 함께 반환해 Client 선택 목록의 중복을 방지합니다. 표시 보완은 손익 인식·원천 금액·미확인 상태를 변경하지 않으며 새 컬럼·Migration을 추가하지 않습니다.

## 저장과 동시성

`AccountingWriteService`는 ADMIN 검사를 수행하고 관리대상 행을 잠근 후 현재 역할을 재검사합니다. 같은 관리대상의 시작 기준·과목 생성·원천 분류 변경이 서로 경합하지 않게 처리합니다. 다른 관리대상의 계정·지출·부과 항목 연결을 거부합니다.

첫 분류 저장 시 필요한 프로필과 `DefaultAccount`의 기본 계정 19개(812 보험료·813 잡비·901 영업외수익 포함)를 같은 트랜잭션에서 생성합니다. 누락 계정은 조회와 저장에 같은 결정적 UUID를 사용하고 기존 ID를 보존합니다. 과목은 코드 오름차순으로 반환하고 계정 ID로 선택·원천을 연결합니다. 확정 관리비의 구성 항목은 `401 관리비수입`에 기본 연결하며 명시적 분류 정정은 우선합니다. 동일 설정 재시도는 성공하고 기존 기준을 다른 값으로 직접 덮어쓰지 않습니다. 과목 생성도 분류·이름이 같은 요청을 같은 계정으로 처리합니다.

원천 분류는 기존 행 수정 대신 revision을 추가합니다. 요청의 expectedRevision과 최신 이력을 대조하고 동일 행위자·내용·사유의 재전송은 추가 저장하지 않습니다. 사용자에게 변경 사유를 요구하지 않으며 사유 생략 시 기존 감사 컬럼에는 `계정과목 매칭`을 암호화해 남깁니다. 원문을 로그에 남기지 않습니다. 매칭 저장의 월은 요청값 대신 원본 지출 날짜에서 결정합니다. 분류가 원천 금액·거래일·부담 배분을 수정하지 않습니다. API의 수정은 다음 조회의 과거 기간 합계도 바꿀 수 있으며 마감 자료 보존이 아닙니다.

외부 미수금 응답은 발생 지출 날짜가 조회 시작·종료 월에 속한 항목으로 제한합니다. 발생이 조회 기간 밖이어도 기존 회수 링크는 입금 대조에 유지해 당기 회수 입금을 901 수익으로 중복 인식하지 않습니다.

## 검증 범위와 남은 작업

서비스·Controller 검사는 역할, 시작 전 조회, 명시적 수익 분류, 지출 날짜 기준 자동 귀속·기존 명시적 귀속 보존, 사유 없는 매칭, 미확인 자료, 중복·충돌·저장 실패를 확인합니다. PostgreSQL 검사는 기존 스키마에서 손익 분류·후속 코드 Migration을 적용해 원천 보존·복합 FK·이력 불변성과 연속 revision을 확인합니다. 전체 `./gradlew build`도 실행합니다.

정식 자동전표/차대변 대조, 미지급·선급·선수금 원장, 과목별 지출 분할, 정식 외부 미수금 분개, 계정별 원장·계정과목 설정 화면과 마감은 남은 범위입니다. 이슈가 남은 합계는 잠정 손익이며 누락을 숨겨 완전한 회계 처리로 표시하지 않습니다.
