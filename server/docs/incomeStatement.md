# 손익 원천 연결과 분류 이력

상태: 2026-11-04 구현. [공통 API](../../docs/api/incomeStatementApi.md)와 [회계 기준](../../docs/domain/domainRules.md#9-회계)을 따릅니다. 이 구현은 확정 청구와 유효 출금의 손익 조회·명시적 분류이며 정식 복식부기 전표 엔진 구현과 구분합니다.

## 조회 경계

`IncomeStatementService`는 관리대상 접근을 먼저 검사하고 읽기 전용 REPEATABLE_READ 트랜잭션에서 조회합니다. 회계 설정이 없거나 시작 전 기간이면 원천을 임의 생성하지 않습니다. `BillingIncomeSourceService`가 부과 영역 내부에서 유효한 확정 월별 청구·항목·부과월을 반환합니다. 인계 미수·초안·취소 청구는 수익으로 복사하지 않습니다. 부과 확정 실행이나 입금 수익 재생성을 하지 않습니다.

부과 항목 ID의 최신 명시적 확인만 관리비수익에 연결합니다. 추천 종류·이름으로 예치·적립을 추측하지 않습니다. 부과 합계/항목 불일치, 0원·음수 항목, 유일하게 연결할 수 없는 과거 동은 이슈로 드러냅니다. 과거 청구 동명과 보존된 동이 유일하게 일치하는 경우에만 귀속하며 선택 동으로 임의 배분하지 않습니다.

지출은 기존 BankingService의 유효 확정 원천과 기존 동 배분을 재사용합니다. 지출명은 계정 ID가 아니므로 비용 과목·귀속 월의 최신 확인이 있어야 반영합니다. 외부 부담 권리·미지급/선급 계정은 이 단계에서 추정하지 않습니다. 미확인 지출은 출금월로 숨기지 않고 확인 대상에 남깁니다. 확인 뒤 조회 범위 밖 귀속이면 합산하지 않습니다. 기타 입금은 일반 수익으로 자동 처리하지 않습니다.

## 저장과 동시성

`AccountingWriteService`는 ADMIN 검사를 수행하고 관리대상 행을 잠근 후 현재 역할을 재검사합니다. 같은 관리대상의 시작 기준·과목 생성·원천 분류 변경이 서로 경합하지 않게 처리합니다. 다른 관리대상의 계정·지출·부과 항목 연결을 거부합니다.

시작 기준은 기본 관리비수익 과목과 같은 트랜잭션에서 생성합니다. 동일 설정 재시도는 성공하고 기존 기준을 다른 값으로 직접 덮어쓰지 않습니다. 과목 생성도 분류·이름이 같은 요청을 같은 계정으로 처리합니다.

원천 분류는 기존 행 수정 대신 revision을 추가합니다. 요청의 expectedRevision과 최신 이력을 대조하고 동일 행위자·내용·사유의 재전송은 추가 저장하지 않습니다. 사유는 기존 암호화 지원을 재사용하며 원문을 로그에 남기지 않습니다. 분류가 원천 금액·거래일·부담 배분을 수정하지 않습니다. API의 수정은 다음 조회의 과거 기간 합계도 바꿀 수 있으며 마감 자료 보존이 아닙니다.

## 물리 저장과 Migration

- `V20261104124735__add_income_statement_accounting_reviews.sql`: 시작 기준, 손익 과목, 지출 확인 이력. 관리대상 복합 FK, 같은 과목·revision 유일성, 불변 이력과 비용 계정 검증.
- `V20261104125540__record_revenue_item_accounting_reviews.sql`: 부과 항목별 성격 확인 이력, 원천 관리대상·연속 revision 검증.
- `V20261104130000__allow_reviewing_pre_start_expense_attribution.sql`: 도입 전 지출도 과거 귀속으로 확인할 수 있게 후속 제약 변경. 보고서의 시작 전 조회 차단은 유지.

기존 청구·입출금·인계 데이터의 금액은 수정하지 않습니다. DB 트리거도 시작 기준·계정·확인 이력의 UPDATE/DELETE를 막고 순차 revision을 검사합니다. 실제 컬럼과 향후 전표 설계는 [ERD](../../docs/domain/erd.md#11-회계)에서 구분합니다. 운영 적용은 [배포 규칙](../../docs/operations/deploymentRules.md)을 따르며 로컬 검사 통과를 운영 적용으로 보고하지 않습니다.

## 검증 범위와 남은 작업

서비스·Controller 검사는 역할, 시작 전 조회, 명시적 수익 분류, 출금과 다른 귀속 월, 미확인 자료, 중복·충돌·저장 실패를 확인합니다. PostgreSQL 검사는 기존 스키마에서 3개 Migration을 적용해 원천 보존·복합 FK·이력 불변성과 연속 revision을 확인합니다. 전체 `./gradlew build`도 실행합니다.

정식 자동전표/차대변 대조, 미지급·선급·선수금 원장, 과목별 지출 분할, 외부 부담금 권리 회계, 계정별 원장·계정과목 설정 화면과 마감은 남은 범위입니다. 이슈가 남은 합계는 잠정 손익이며 누락을 숨겨 완전한 회계 처리로 표시하지 않습니다.
