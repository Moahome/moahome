# 계정별 원천 조회

상태: 2026-11-07 1차 구현. 계약은 [계정별 원장 API](../../docs/api/accountLedgerApi.md), 업무 기준은 [회계 도메인](../../docs/domain/domainRules.md#9-회계)을 따릅니다. 101·102·103·201의 기존 원본 연결을 추가했습니다. 202 발생·지급 연결과 101 기초잔액·합산 잔액을 구현했습니다. 정식 전표 엔진·전 과목 이월 잔액은 후속입니다.

## 조회·원천 연결

AccountLedgerService는 읽기 전용 REPEATABLE_READ 트랜잭션에서 IncomeStatementService를 호출합니다. 기존 관리대상 접근 검사, 시작 월, 수익·비용 분류·외부 회수 제외·동별 배분을 재사용하며 같은 조건의 손익과 원장이 서로 다른 인식 기준을 갖지 않게 합니다. 과목은 조회된 동일 관리대상의 계정 목록에서 검사합니다.

IncomeStatementResponse.Entry에 원본의 종류·ID·거래일·원본 시각·이름·문맥·상대 경로를 추가합니다. 부과 원천의 항목별 반영액·청구 ID는 유지하되 원장에서는 월·계정 ID별로 합산합니다. 전체 조회는 동을 합쳐 한 행, 동 선택은 해당 동의 한 행이며 sourceIds로 원본 청구 항목 ID를 보존합니다. 원장 부과 원천은 BILLING으로 구분하고 미납 수납 상세로 보내지 않습니다. 부과일은 BillingIncomeSourceService가 기존 billing_periods.billing_date를 전달하며 생성·수납 날짜로 대체하지 않습니다. 지출은 기존 지출·거래 ID, 기타 입금은 수납 ID로 연결합니다. 손익 응답의 기존 필드·금액은 바꾸지 않습니다.

조회 조건의 전체 행을 과거순으로 정렬해 계정 ID별 누계를 계산한 뒤 최신순으로 반환합니다. 실제 거래일·원본 시각을 우선하고 부과는 저장된 월초 부과일로 정렬합니다. 날짜가 없는 이전 호환 자료만 내부 정렬에 귀속 월의 월초를 사용합니다. 동률은 귀속 월·증가→감소·적요의 동호수 숫자순·원본 행 ID로 결정합니다. 같은 순서로 누계를 계산하고 그 역순을 API에 반환합니다. Client의 기본 과목·최신 일자 표시 기준은 공통 API를 따릅니다. Client의 최신순은 같은 날짜도 포함한 계산 순서의 정확한 역순이며 누계 값은 다시 계산하지 않습니다. 실제 거래일·시각을 추정해 응답에 쓰지 않습니다. 누계는 선택 기간의 같은 과목 반영액이며 이월·기초 잔액이 아닙니다.

## 불변식·남은 범위

조회는 저장하지 않으며 신규 테이블·Migration·계정 코드 변경은 없습니다. 원천의 금액·동 배분·과목 ID·최신 분류 이력을 유지하고 다른 관리대상의 과목을 거부합니다. 회계 자료 누락은 손익의 issues를 그대로 반환하며 특정 과목에만 해당한다고 단정하지 않습니다.

AccountLedgerAssetService는 기존 BankingService·BankingBalanceService·BankTransferPostingService·PaymentService·BillingIncomeSourceService의 읽기 경계를 사용합니다. 101은 실제 입출금, 102는 청구/인계 미수와 유효 충당·외부 부담/회수, 103은 저장된 이체 계정 FK와 양쪽 행, 201은 초과 수납/인계 선납과 미래 청구 충당을 연결합니다. 즉시 청구에 충당한 수납은 선수금 증가·감소 두 행으로 부풀리지 않습니다. 충당 반영일은 원 입금/인계일과 부과일 중 늦은 날짜입니다. 현재 유효 충당을 재구성하므로 처리 당시 이력이나 마감 고정 잔액이 아닙니다. 구체적인 계약·제한은 공통 API에 모읍니다.

202도 supported=true이며 발생·실제 지급 원본을 연결합니다. 101은 BankingBalanceService의 기존 장부 기준을 재사용하며 별도 기초잔액을 생성하지 않습니다. 전 과목 기초/기말 잔액·차대변 전표·역분개·재처리는 후속입니다. 기존 인계 미수·선납은 원본으로 표시하며 신규 수익·입금을 생성하지 않습니다. 기간 누계에 범위 밖 인계 잔액을 임의로 포함하거나 가상 0원 기초 잔액을 만들지 않습니다.

서비스 테스트는 손익 금액 대조·계정별 누계·과목 필터·원본 시각 정렬·기존 귀속 월·타 과목 거부·미지원 상태를 확인합니다. Controller 테스트는 인증 선행·필터 전달·no-store를 검증합니다. 기존 손익 테스트와 전체 `./gradlew build`를 함께 실행합니다. 실행 중인 개발 서버와 분리한 임시 buildDirectory·project-cache-dir을 사용하며 서비스 테스트 통과를 운영 배포나 개발 서버 재기동으로 보고하지 않습니다.

### 101 합산과 다중 과목

AccountLedgerBankService는 기존 BankingService 원본·수기 보충 자료와 BankingBalanceService의 기간말 장부 잔액을 대조합니다. 기간 시작 잔액은 같은 전체 유효 이동의 순증감을 기간말에서 빼서 구하며 과거 조회도 기존 기준 잔액 역산과 일치합니다. 은행 분류 취소는 실제 은행 입금을 없애지 않고, 취소 이체는 현금 계산에서 제외합니다. 전체 계좌는 시작 잔액을 합산해 누적하고 같은 내부 이체 양쪽은 한 사건의 순액을 한 번 반영합니다. 실제 계좌를 선택하면 해당 계좌의 시작 잔액·이동만 사용합니다. 금액 근거가 없으면 null을 유지합니다.

AccountLedgerService는 선택 계정 ID 집합을 대상 안에서 검증하고 표시·누계 전에 필터링합니다. 계정별 누계와 101의 기초 포함 잔액은 별도 필드입니다. 응답·모바일·다운로드의 범위 계약은 공통 API를 따릅니다.

### 미지급 저장·동시성

PayableService는 관리대상 잠금 안에서 ADMIN 권한을 재확인합니다. 등록과 실제 출금 연결은 요청 UUID·원본 내용으로 재시도를 대조합니다. 지급 연결은 기존 확정 지출의 전액이며 하나의 지출은 하나의 활성 미지급 연결만 가집니다. 여러 실제 출금으로 부분 지급할 수 있고 초과 지급·발생 전 지급·다른 과목/동은 거부합니다. 등록 시 비용을 인식하고 연결된 실제 지급은 손익에서 제외해 비용 중복을 막습니다.

`V20261107082855__add_payable_expenses_and_payment_links.sql`은 발생/지급 이력, 복합 FK, 양수 금액, 활성 지출 유일성, 발생·지급 원본/분류 불변성과 초과 연결 방지를 저장합니다. 연결 해제는 감사 상태를 남기고 실제 출금을 지우지 않습니다. 활성 지급이 있으면 발생 등록을 취소할 수 없습니다. PayableSourceService는 지급 원본을 배치 조회해 손익·원장·상세가 같은 활성 연결을 사용합니다. 실제 운영 적용과 격리 PostgreSQL 테스트를 구분합니다.
