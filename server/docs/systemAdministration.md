# 시스템 관리 저장과 동시성

2026-11-03 구현. [공통 정책·API](../../docs/api/systemAdministration.md)를 따르며 운영 DB에 적용한 상태를 뜻하지 않습니다.

SystemAdminService는 각 요청에서 DB의 정상 계정·현재 시스템 역할을 확인합니다. JWT나 클라이언트가 전달하는 역할을 권한 근거로 사용하지 않습니다. 대상 계정 조회 전에 관리자 여부를 검사합니다. 회원 조회는 닉네임 LIKE 검색의 `%`, `_`, 역슬래시를 이스케이프하고 전체 UUID 검색을 지원합니다.

권한 변경은 처리자·대상 UUID 문자열순으로 사용자 행을 잠근 뒤 현재 역할·정상 상태를 다시 확인합니다. 같은 대상끼리의 변경과 최종 관리대상 생성은 `users`의 같은 행 잠금으로 직렬화됩니다. 생성이 먼저 잠금을 잡으면 생성 커밋 후 회수가 완료되고, 회수가 먼저 완료되면 뒤의 신규 생성은 미허용으로 거부합니다. 기존 관리대상의 참여·저장 자료는 변경하지 않습니다.

잠금 대기 전에 같은 계정을 읽었을 수 있으므로 잠금 획득 후 EntityManager.refresh로 DB 값을 다시 읽습니다. 행 잠금만으로는 이미 영속성 컨텍스트에 있는 계정의 역할·생성 허용 값이 갱신되지 않아 먼저 완료된 권한 회수를 놓칠 수 있습니다.

요청 UUID의 트랜잭션 advisory lock으로 서로 다른 대상에 같은 UUID가 동시에 제출된 경우도 직렬화합니다. system_admin_events의 최초 처리자·대상·동작·요청 값과 생성 권한의 이전 값으로 재시도를 확인합니다. 재시도는 현재 회원 정보를 반환하고 과거 변경을 다시 실행하지 않습니다. 권한 변경과 감사 INSERT는 같은 트랜잭션이므로 저장 장애 시 둘 다 롤백합니다. UUID·역할·허용 여부·시각만 보관하며 닉네임·연락처 원문을 감사 기록에 복사하지 않습니다.

PropertyRegistrationService는 새 등록에만 현재 생성 허용 여부와 사용자 행 잠금을 요구합니다. 이미 성공한 requestId는 기존 결과·현재 관리대상 접근권한과 본문 지문을 먼저 검사해 권한 회수 뒤에도 응답 유실을 복구합니다. 등록 전 기본 검증과 은행 파일 미리보기도 현재 생성 허용 여부를 확인합니다.

최초 시스템 관리자는 운영자가 대상 계정을 식별한 후 DB에서 기존 `users.system_role`만 지정합니다. 실제 운영 계정 ID를 저장소에 기록하지 않습니다. 시스템 관리자에게도 생성 허용이 기본 부여되지 않으며 필요한 계정에 화면에서 별도로 부여합니다. 이 작업에서 운영 역할 변경·Migration·배포는 수행하지 않았습니다.
