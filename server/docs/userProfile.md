# 본인 프로필 사진 저장

공통 요청·응답·파일 제한은 [본인 프로필 API](../../docs/api/userProfileApi.md), 저장 컬럼은 [ERD](../../docs/domain/erd.md#41-users)를 따릅니다. 사진 자체는 별도 테이블·Migration 없이 기존 컬럼을 사용합니다. 탈퇴 유예 상태·인증 버전은 아래 후속 Migration으로 추가합니다.

## 저장과 정리 순서

`ProfileImageService.save`는 정상 계정 확인 → 파일 검증·PNG 재인코딩 → 새 객체 업로드 → 최신 계정 행 잠금 아래 이름·사진 참조 변경 → DB 커밋 → 이전 객체 삭제 순서로 처리합니다. 소셜 이미지나 외부 주소는 삭제 대상에 포함하지 않습니다.

명시적인 DB 롤백에서는 새 업로드 객체를 보상 삭제하고 이전 참조는 유지합니다. 커밋 결과가 불명확하면 참조 중인 객체를 삭제하지 않도록 새 객체를 보존하고 경고를 기록합니다. 업로드 응답 유실·보상 삭제 실패·커밋 이후 이전 객체 삭제 실패에는 미참조 객체가 남을 수 있습니다. S3 SDK 재시도 이후의 실패는 안전한 경고로 기록하며 별도 영속 정리 큐·주기 재시도는 아직 구현하지 않았습니다. 운영에서 DB 참조와 객체를 대조해 정리해야 하며 S3 도입만으로 외부 저장소와 DB의 원자성을 보장한다고 설명하지 않습니다.

객체 키는 `profiles/<인증 계정 UUID>/<서버 생성 버전 UUID>.png`입니다. API 입력으로 경로·버킷을 받지 않습니다. DB에는 `/api/users/me/profile-image?v=<version>`을 저장하므로 버킷 이관 시 사진 파일도 같은 키로 함께 옮겨야 합니다. PNG는 최대 변 512px로 다시 인코딩하고 이미지 읽기 응답은 2MiB까지 제한합니다. 원본 파일명·EXIF·원본 파일은 저장하지 않습니다.

## 인증과 환경

버킷은 비공개·퍼블릭 액세스 차단·ACL 비활성화를 유지합니다. 브라우저는 서버에만 업로드·조회하고 S3 CORS·공개 객체 URL·프런트엔드 AWS 키를 사용하지 않습니다. 실제 환경변수와 로컬 프로필 사용은 [개발 환경](../../docs/development/developmentGuide.md#프로필-사진-s3)을 따릅니다.

S3 버킷을 설정하지 않으면 기존 로그인·이름 수정은 사용 가능하고 사진 저장소 요청만 503으로 실패합니다. 버킷·인증·파일 크기 설정이 바뀌면 서버를 재시작합니다. 운영 예제는 `server/deploy/.env.example`에 있으며 실제 운영값·키는 추적하지 않습니다. Mac의 `moahome-dev` 프로필을 배포 이미지에 포함하지 않습니다.

## 검증

Processor 테스트는 MIME 위장·SVG·손상 파일·크기·픽셀 제한과 재인코딩을 검사합니다. 저장소 테스트는 인증 계정 키 생성·외부 참조 거부·삭제 호출·읽기 크기 제한을 검사합니다. PostgreSQL 통합 검사는 교체·이름 수정·소셜 재로그인·삭제와 롤백 보상 삭제를 검증하며 실제 AWS 자격 증명을 사용하지 않습니다. Controller와 보안 통합 검사는 Bearer 필수·Refresh 쿠키 거부·JSON 오류·이미지 바이트 응답을 검사합니다.

## 탈퇴 유예·복구와 최종 정리

업무 기준은 [회원 탈퇴와 복구](../../docs/domain/domainRules.md#회원-탈퇴와-복구-2026-11-08)를 따릅니다. `AccountLifecycleService`가 신청·복구·최종 삭제를 조율합니다. `V20261108055709__support_account_withdrawal_grace_period.sql`은 유예 시각과 `auth_version`을 추가하며 기존 정상 계정·인증 버전 0의 세션은 유지합니다. 빈 DB 전체 적용과 직전 버전의 기존 계정 업그레이드를 격리 PostgreSQL에서 검증합니다. 운영 배포는 [배포 규칙](../../docs/operations/deploymentRules.md)에 따라 전체 이력·선행 Migration 확인 후 백엔드를 먼저 적용해야 합니다. 로컬 검증은 운영 이력 확인·배포를 의미하지 않습니다.

신청은 현재 참여 대상 UUID 정렬 순서의 행 잠금 → 사용자 행 잠금 → 최신 상태·관리소장 인계 재검증 → 유예와 인증 버전 증가 → DB 커밋 순서입니다. 참여 부여·관리소장 변경도 대상 → 정상 사용자 잠금을 사용합니다. 잠금 사이 새 참여 대상이 생기면 역순 잠금을 추가하지 않고 409로 재시도를 요구합니다. 개인정보와 참여는 유예 동안 보존합니다.

복구는 사용자 잠금 아래 기한을 확인하고 ACTIVE로 전환합니다. 인증 버전을 낮추지 않으므로 신청 전 토큰이 다시 유효해지지 않습니다. DB 복구와 Redis 세션 발급은 별도 자원이므로, DB 복구 후 Redis 실패에는 같은 10분 복구 전용 증명으로 일반 세션 발급을 재시도하도록 ACTIVE 상태의 재요청을 멱등 처리합니다. 복구 세션·Origin·CSRF는 Controller 진입 전에 검증합니다.

`AccountWithdrawalScheduler`는 기동 시와 60초 간격으로 만료 계정을 최대 20개 조회합니다. 기본 활성화이며 테스트에서는 `moahome.account-withdrawal.scheduler-enabled=false`입니다. 여러 인스턴스의 중복 실행도 동일 계정 잠금과 최신 상태 검사로 중복 확정을 막습니다.

최종 정리는 대상 잠금 → 소셜 식별자 잠금 → 사용자 잠금 → 최신 만료 검사 → S3 사진 삭제 → 현재 참여 종료·이벤트 기록 → 소셜 원문 제거 → 사용자 비식별화·소프트 삭제 → DB 커밋 순서입니다. 소셜 로그인과 식별자 → 사용자 순서를 맞춥니다. 주민 명부·세대·회계 원본은 변경하지 않습니다.

최종 정리의 S3 삭제는 일반 사진 교체 후 정리와 달리 실패를 삼키지 않습니다. 실패하면 DB를 롤백하고 만료 상태·참조를 남겨 다음 주기에 재시도합니다. S3 삭제 후 DB가 실패한 경우 삭제 요청을 반복할 수 있습니다. 두 자원의 원자적 트랜잭션은 없으며 이때도 기한이 지난 계정의 로그인·복구를 허용하지 않습니다. 현재 사진 외에 과거 업로드·보상 실패로 남은 미참조 객체는 위의 기존 별도 점검 대상입니다.

통합 테스트는 30일 경계, 유예 중 개인정보 보존, 복구 후 이전 토큰 차단, 복구 전용 세션의 업무 접근·일반 재발급 거부, Origin·CSRF, 인계 차단, S3 실패 후 재시도, 소셜 식별자 제거·새 ID 재가입과 공동 기록 보존을 검증합니다. 실제 계정에 탈퇴 요청을 보내 검증하지 않습니다.
