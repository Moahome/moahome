# 통장 관리 저장과 동시성

상태: 2026-10-17 **구현**. 정책·요청·응답·오류는 [공통 통장 계약](../../docs/bankingManagement.md), 수납은 [기존 수납 저장](payment.md), 저장 구조는 [ERD](../../docs/erd.md)를 참조합니다.

2026-10-23 후속 요청은 아래 [처리 설계안](#은행별-업로드와-수동-출금-처리-설계안-2026-10-23)이며 미구현입니다. 기존 Reader·중복 키 설명과 후속 수동 지출 등록 구현을 구분합니다.

## 책임과 처리 순서

BankTransactionReader.readAll은 입출금 원본을 읽고 기존 read는 입금만 반환합니다. 입출금이 동시에 양수인 행·잘못된 날짜·수식 등은 거부합니다. 같은 가맹점 출금과 환불 입금은 방향을 나누어 보존합니다.

BankingService는 매 요청 ADMIN 권한·관리대상·선택한 사용 중 공용 계좌를 확인합니다. 계좌를 생략한 호환 호출만 기본 계좌를 사용합니다. 미리보기는 중복·인계 이전을 제외하고 기존 PaymentService의 후보를 재사용하며 저장하지 않습니다. upload는 관리대상 잠금을 획득한 뒤 권한을 재확인하고 관리 시작 상태와 모든 선택을 원본 파일에서 재검증합니다. 선택 출금 원본·확정 배분과 입금 원본·수납을 한 트랜잭션으로 처리하므로 이후 검증·저장에 실패하면 모두 롤백됩니다.

선택 거래의 `transfer`는 해당 필드의 JsonSetter에서 생략·null만 false로 기본 처리합니다. Jackson의 전역 primitive null 검증은 유지합니다. 일반 거래에서 이체 표시가 빠진 실제 multipart 요청, 명시한 true·false·null 및 잘못된 boolean 문자열을 Controller 테스트에서 검증합니다.

PaymentService.importBankRows는 기존 원본·수납 초안·감사·자동 확정·누적 충당을 재사용합니다. 명시한 기타 입금이나 세대 지정은 자동 확정보다 먼저 적용합니다. 기존 입금 ID·수납 연결·중복 키는 유지합니다. 미일치는 기존 PENDING으로 남습니다.

ExpenseService는 호출자가 확보한 권한·잠금 아래 원본이 출금인지 확인하고 같은 관리대상의 활성 동을 조회합니다. 실제 동 표시명과 외부 부담처 표시명을 암호화해 스냅샷으로 저장합니다. Expense.allocate는 정수 금액·비율·합계·중복 부담처를 검증합니다. 지출명(기존 category 키)과 부담액을 함께 저장하며 원본 한 건당 지출은 하나입니다. 같은 출금 확정 재시도는 내용이 같으면 기존 결과, 다르면 충돌입니다.

## DB와 개인정보

후속 Migration `V20261017074932__add_banking_expense_allocations.sql`이 direction과 expenses·expense_allocations를 추가합니다. 적용된 이 파일은 체크섬 `-1029174370`을 보존합니다. 확정 이력의 변경·삭제와 원본 변경 보호는 별도 `V20261017083529__protect_confirmed_expense_history.sql`로 추가합니다. DB 이력 수정·repair 없이 기존 파일에서 업그레이드합니다. 복합 FK로 관리대상을 제한하고 지연 제약 트리거로 커밋 직전 원본·지출·배분 합계와 비율을 검증합니다. 수납은 입금 원본만 참조할 수 있습니다. 확정 지출·배분의 직접 변경/삭제와 확정 출금의 금액·방향 변경도 차단합니다.

지출명·메모·부담처 표시명은 기존 PaymentTextSecurity를 재사용해 암호화합니다. 적요 규칙 키는 HMAC이며 사용자 원문·계좌·분류 내용은 오류나 로그에 남기지 않습니다. 일반 동 ID는 외부 부담처와 구분합니다.

규칙은 저장 표시가 있는 확정 지출의 최신 스냅샷을 계좌·적요별로 조회합니다. 새 규칙을 저장해도 과거 확정 지출은 변경하지 않습니다. 별도 규칙 관리 도메인·외부 정산처 원장을 미리 만들지 않습니다.

## 검증

파서·배분 계산 단위 테스트, Controller의 인증·multipart·중첩 입력 검증, PostgreSQL의 선택 입출금·1/4 배분·외부 부담·재시도·합계 제약·타 관리대상 거부·전체 롤백·기존 데이터 업그레이드를 검증합니다. test Profile은 기존 업무와 같이 BankingService·ExpenseService를 Mock으로 격리합니다. 실제 서비스는 database-test Profile에서 검증합니다. 필수 최종 검증은 Java 21 `./gradlew build`입니다.

## 동별 보유금·외부 회수 저장

`BankingBalanceService`는 잔고 조회를 repeatable-read로, 변경을 read-committed와 관리대상 행 잠금으로 처리합니다. 같은 잠금을 쓰는 수납 확정·취소·파일 업로드와 시작값·회수액 갱신을 직렬화합니다. Controller는 ADMIN 확인과 계산을 Service에 위임하며 응답을 캐시하지 않습니다. [공통 계약](../../docs/bankingManagement.md#동별-잔고외부-회수-api)과 [ERD](../../docs/erd.md#95-building_cash_openings)를 참조합니다.

신규 HOUSEHOLD 수납은 PaymentService의 자동·직접·누적 확정 경로에서 확정 당시 동 ID를 보존합니다. 세대 이동으로 스냅샷을 바꾸지 않습니다. 기존 null인 확정 HOUSEHOLD 은행 입금은 후속 Migration에서 연결 세대의 동으로 자동 기록합니다. 이후 같은 조건의 이관·확정도 DB 트리거가 최초 연결 동을 기록하고 이미 저장된 동은 유지합니다. 세대 연결·동 정보가 없을 때만 관리자 확인을 유지합니다. 은행 원본을 연결하지 않은 수동 세대 수납과 세대 선납 인계는 동별 현금에 반영하지 않습니다. 수동 기타·동별 입금은 [수동 저장 설계](payment.md#수동-기타동별-입금-2026-10-18)를 적용합니다.

최초 등록은 현재 활성 동과 공통 기준일을 검증하며 재시도와 새 동 추가를 지원합니다. 기준일·기존 마감 잔고 정정은 별도 API에서 등록된 동 전체와 기대 revision을 검증합니다. 관리대상 잠금으로 변경을 직렬화하고 DB가 이전·새 값과 수정자를 이력에 저장합니다. 삭제·이력 변경·감사 정보 없는 덮어쓰기는 차단하며 공통 기준일은 지연 제약으로 보장합니다. 요청 UUID를 이력과 대조해 재시도가 이후 정정을 되돌리지 않게 합니다.

외부 회수는 요청 UUID로 멱등 처리합니다. 확정 OTHER 입금·같은 계좌·외부 배분 대상·양수·입금과 부담액의 잔여 한도를 검증합니다. 지연 DB 트리거도 한도를 검사합니다. 기존 연결은 수정·삭제하지 않으며 수납 취소는 조회의 유효 회수 합계에서 제외합니다. 새 외부 원문 복사 없이 기존 암호화된 수납·지출 표시명을 읽습니다.

기준일 이전 월은 조회 월 말과 기준일 중 늦은 날까지 확정 현금을 읽어 역산합니다. 월 기초·말 잔고는 같은 기준 잔고에서 각각 계산하고 월 입출금에는 조회 월 전체만 포함합니다. 은행 확인 잔고·외부 회수액은 조회 월 말에 제한하며 미래 월 금액을 과거 월에 섞지 않습니다. 연결 세대 정보는 현재 상태를 확인용으로만 응답하며 과거 귀속은 지정하지 않습니다.

`BuildingCashCalculationTest`는 기준일 경계·이월·음수·역산·윤년·연도 경계를, PostgreSQL의 `PaymentPersistenceTest`는 시작값 중복·불변·세대 이동 후 귀속 보존·1/4 지출·부분 회수·과다 연결·수납 취소 복원과 실제 Migration 업그레이드를 검증합니다. 신규 Controller 테스트는 인증·캐시·중첩 입력 검증을 확인합니다.

정산 제외·복원은 `ExternalSettlementDecision`의 추가 이력으로 저장합니다. Service의 관리대상 잠금·요청 UUID 멱등 처리·기대 revision 검증과 DB의 외부 부담처 FK·연속 버전·이력 불변 검증을 함께 사용합니다. 제외 상태의 새 회수 링크는 DB 트리거에서도 차단합니다. 복원과 제외를 반복해도 원본·지출 배분·회수 기록과 원 단위 금액은 바꾸지 않습니다. 기존 적용 Migration을 수정하지 않고 후속 Migration으로 추가했습니다.

## 선택 삭제·기타 입금 배분 저장

BankingService의 선택 삭제는 관리대상 행 잠금 뒤 선택 전체의 소속을 확인합니다. PaymentService가 연결 수납·충당의 취소·삭제 이벤트를 남기고 누적 충당을 재계산한 뒤 은행 원본을 소프트 삭제합니다. 확정 지출과 배분은 수정하지 않으며 조회에서 유효 원본에 연결된 결과만 사용합니다. DB는 삭제자 없는 삭제·활성 수납을 남긴 삭제·삭제 표시 원복을 차단합니다.

외부 부담금 상세의 삭제도 같은 선택 삭제를 재사용합니다. BankingBalanceService가 외부 배분의 원본 transactionId·transactionAmount를 반환해 출금 전체의 삭제 범위를 확인하게 하며, 외부 부담액만 변경하거나 별도 삭제 테이블·Migration을 만들지 않습니다. PostgreSQL 통합 테스트에서 두 동과 외부 부담처가 함께 있는 원본의 삭제·재시도 후 동별 지출 제거와 확정 배분 이력 보존을 확인합니다.

기타 입금 배분은 IncomeAllocationService를 통해 같은 잠금 안에서 실제 확정 OTHER 수납·활성 동·합계·비율·외부 회수 사용 여부를 검증합니다. 업로드는 활성 은행 원본을, 수동 등록은 명시한 SHARED 용도를 검사합니다. income_allocations는 동 이름 스냅샷을 암호화하여 저장하고 확정 배분 재시도의 내용 일치를 대조합니다. DB 불변·합계 제약도 적용합니다. 원본 삭제·수납 취소는 배분 이력을 보존하며 유효 집계에서 제외합니다. 외부 회수와 배분은 양방향 DB 제약으로 중복 사용을 막습니다. 공통 API·정책은 루트 문서를 참조합니다.

## 기존 계좌 정보 정정

BankAccountService는 현재 ADMIN 권한을 확인하고 조회 시에만 계좌번호를 복호화합니다. 정정은 업로드·수납과 같은 관리대상 행 잠금으로 직렬화하고 호환 정정에서는 현재 공용 기본 계좌 ID·updated_at과 중복 은행·번호를 확인합니다. 다중 계좌 설정은 아래 후속 저장을 따릅니다. 같은 정정 재시도는 변경하지 않고 현재 결과를 반환합니다. BankAccount.correctDetails는 은행·예금주와 보호된 번호 컬럼만 변경하며 ID·사용기간·기본 지정·거래 FK를 유지합니다. flush 후 PostgreSQL 마이크로초 정밀도의 수정 시각을 응답해 연속 수정에서도 충돌 판단이 일치하게 합니다. DTO 문자열 표현은 원문을 숨깁니다. API는 [공통 계약](../../docs/bankingManagement.md#기존-관리계좌-정보-정정-api)을 참조합니다.


수동 선택 삭제는 요청의 paymentIds를 은행 원본 ID와 분리해 검증합니다. 같은 관리대상의 MANUAL·은행 미연결만 PaymentService.removeManualReceipts로 전달하며 초안·보류·확정·취소 수납 모두 삭제 표시와 감사를 남깁니다. 확정 수납은 은행 거래 삭제와 공유하는 취소·충당 재계산 흐름에서 취소 후 삭제합니다. 이미 취소된 수납의 최초 사유·충당 이력은 바꾸지 않습니다. 은행 원본 선택과 같은 트랜잭션에서 처리해 혼합 요청도 일부만 반영하지 않습니다. 기존 DB 삭제 제약·상태 불변식을 재사용합니다.


## 다중 통장 저장과 내부 이체 (2026-10-18)

정책·API는 [공통 다중 통장 계약](../../docs/bankingManagement.md#다중-통장내부-이체-api-2026-10-18), 컬럼·제약은 [ERD 확장](../../docs/erd.md#다중-관리계좌내부-이체-확장-2026-10-18)을 참조합니다.

BankAccountService는 같은 관리대상 잠금으로 계좌 추가·정정·기본 전환·사용 종료를 직렬화합니다. 추가 UUID·기존 updated_at·조회한 기본 계좌 ID를 대조하고 번호 중복을 검사합니다. 기본 전환은 이전 지정 해제 flush 후 새 지정 적용으로 활성 기본 유일 인덱스를 지키며, 지연 제약이 커밋 시 정확히 1개를 확인합니다. 원문은 ADMIN 설정 조회에서만 복호화합니다.

BankingService와 PaymentService는 선택 통장을 미리보기·저장·수납 생성 전체에 전달합니다. 같은 계좌의 중복만 제외하고 기존 수납 자동 매칭·충당·취소 정책은 재사용합니다. 사용 종료한 통장은 신규 입력에서 거부하지만 조회는 포함합니다.

이체 선택은 원본만 저장하고 수납·지출 Service를 호출하지 않습니다. BankTransfer는 같은 잠금 안에서 양쪽 원본을 검증하고 UUID 멱등으로 연결합니다. 원본·연결 ID는 유지하고 해제는 취소 감사만 저장합니다. DB도 수납·지출과의 중복 분류·중복 연결·부분 원본 삭제를 막습니다. 기존 확정 지출 보호 Migration은 수정하지 않습니다.

BankingBalanceService는 선택 통장 또는 전체 공용 통장의 원본을 읽어 유효 세대 수납·기타 배분·지출을 통장×동 기준으로 계산합니다. 각 통장의 기준일에서 누적·역산한 뒤 전체 범위에서는 계산 결과를 합산합니다. 은행 확인 잔액은 각 계좌에서 마지막 원본의 순서·잔액과 같은 계좌 인계값을 판정한 뒤 합산합니다. 한 계좌라도 미확인이면 전체는 null입니다. 연결 이체 원본은 확인 필요에서 제외하며 대기 원본은 이체 연결 대기로 남깁니다.

PostgreSQL 통합 테스트는 통장 동적 추가·동일 은행/다른 번호·멱등·기본 전환·과거 FK 보존·권한/대상/버전 거부·종료 통장 입력 금지·통장별 파일 중복·전체 수납/동별 보유금 합산·잔액 미확인·이체 연결/해제/재연결/삭제·업로드 롤백과 기존 스키마 업그레이드를 검증합니다.


### 통장×동 기준 잔고와 기존 값 이관

선택 accountId의 소속을 검증하고 기준값·입출금·미처리·기타 입금·외부 정산을 같은 계좌 집합으로 제한합니다. 같은 통장의 동들은 같은 기준일을 유지하며 다른 통장은 독립 기준일을 사용합니다. 필요한 기준값이 누락되면 잔고를 null로 표시합니다. 수정은 관리대상 잠금 안에서 선택 통장의 등록 동 전체·기대 revision·요청 UUID를 검증하며 이력에도 bank_account_id를 보관합니다.

후속 Migration은 기존 값 등록 당시 존재한 공용 통장이 하나였던 경우 그 통장으로 귀속시킵니다. 뒤늦게 추가한 통장 때문에 원래 확정된 금액·기준일·버전·정정 이력을 잃지 않습니다. 소속을 입증하지 못하는 null 계좌 값은 삭제하지 않습니다. 통장별 확정 전에는 legacyOpening으로 기존 날짜·금액을 안내하고 명시적 확정을 받습니다. 기존 계좌 전체 잔액 인계(bank_opening_balances)는 동별 보유금과 합쳐 중복 집계하지 않습니다.


### 통장 계산 잔액

통장 조회는 Repository의 registration_order 순서를 공통으로 사용합니다. 초기 설정은 입력 배열 순서, 추가 등록은 관리대상 잠금 아래 기존 최대 순서 다음 값을 저장하며 기본 지정 전환·정정·사용 종료로 바꾸지 않습니다. 기존 자료는 후속 Migration에서 created_at·id 순으로 안정적으로 보정합니다. 같은 시각에 등록된 기존 통장의 원래 입력 순서는 저장되어 있지 않아 복원하지 않으며 이후 신규 등록부터 명시적인 입력 순서를 보존합니다. Migration은 잔고·원본·수납·기본 계좌를 변경하지 않습니다.

BankingBalanceService는 모든 공용 통장의 실제 확인값과 별도로 통장별 동 기준값을 검증해 calculatedBalance·calculationBasisDate를 반환합니다. BuildingCashCalculation의 누적·역산을 재사용하고 동별 원장 배분과 통장 전체 이동은 구분합니다. 원본 입출금은 전액, 기존 현금 인식 기준의 미연결 확정 수동 OTHER·SHARED는 한 번 포함합니다. 원본 연결 뒤에는 수동 금액을 별도로 더하지 않습니다. 누락 기준값·취소·삭제·다른 통장·다른 조회 월의 금액을 잘못 합산하지 않으며 기존 bankBalance·asOf의 실제 확인 의미와 대사 결과는 유지합니다. 파생 조회이므로 테이블·Migration·저장 이력을 추가하지 않습니다.

통장의 조회 가능 시작은 [공통 계산 기준](../../docs/domainRules.md#기준-잔고-기반-통장-계산-잔액-표시-2026-10-18-후속)의 실제 사용 근거로 판정합니다. 계좌 범위를 먼저 결정한 뒤 기준값·동별 원장·은행 잔액·정산을 계산하므로 사용 전 통장이 전체 합계에 섞이지 않습니다. 범위 밖의 같은 대상 계좌 선택은 전체로 복원하고, 실제 과거 원본을 나중에 가져온 통장의 과거 조회는 유지합니다. PostgreSQL 통합 테스트에서 9월 말 시작 통장의 8월 제외·9월 포함·오래된 선택 복원·과거 원본 추가·사용 통장이 없는 월을 검증합니다.


### 선택 통장 상세와 번호 공개

[공통 계약](../../docs/bankingManagement.md#선택-통장-상세와-계좌번호-공개)에 따라 BankAccountService의 공통 소속 검증으로 ADMIN·같은 대상·미삭제 공용 계좌를 확인합니다. 기본 상세는 저장된 끝 네 자리와 예금주 등만 사용하여 보안 키·복호화를 요구하지 않습니다. 별도 공개 요청에서만 기존 AccountNumberSecurity를 사용해 선택 계좌 한 건을 복호화합니다. 종료 통장은 허용하고 다른 대상·삭제·비공용·대상 없음은 동일 권한 오류로 거부합니다. 응답 DTO의 toString은 원문을 출력하지 않습니다. 기존 저장 구조를 재사용하며 Migration은 추가하지 않습니다. BankAccountServiceTest와 BankAccountControllerTest에서 권한·소속·기본 상세 복호화 없음·선택 공개·응답 마스킹과 no-store를 검증합니다.

## 은행별 업로드와 수동 출금 처리 설계안 (2026-10-23)

상태: **미구현 제안**. 지원 양식·매핑·요청·응답·오류는 [공통 설계안](../../docs/bankingManagement.md#은행별-업로드와-수동-출금-설계안-2026-10-23), 저장 책임은 [ERD 변경안](../../docs/erd.md#은행별-업로드와-수동-지출-저장-설계안-2026-10-23)을 기준으로 합니다. 아래 클래스 구성·순서는 내부 구현 제안입니다.

### 파일 해석과 식별

Reader의 크기·실제 파일 형식·압축 해제·수식·행 수 검증을 재사용하고 은행별 필수 헤더·열 매핑·집계 제외 규칙을 한곳에 정의합니다. 은행별 설정만으로 표현되지 않는 농협 부호·집계 해석만 별도 처리하며 모든 은행마다 형식적인 Service 계층을 만들지 않습니다. 지원 응답과 실제 파서 선택은 같은 정의를 사용합니다.

BankingService·PaymentService의 모든 파일 진입점에서 권한·통장 소속·사용 상태 확인 후 저장된 은행 코드를 Reader에 전달하는 안입니다. 미리보기와 저장이 다른 규칙을 사용하지 않도록 업로드 잠금 안에서 현재 계좌 정보·지원 여부·파일을 다시 검사합니다. 새 은행 규칙을 적용한 뒤 입금 후보 계산도 같은 해석 결과를 사용해야 하며 범용 `read` 경로가 남아 제한을 우회하지 않게 합니다.

신한 매핑 변경은 새 파일 해석에 적용하고 기존 잘못된 상대 이름·중복 키·수납을 자동 정정하지 않습니다. 여러 메모·거래 종류와 실제 상대 정보를 구분하며 상대 확인 근거가 부족한 행은 표시용 내용과 자동 매칭용 이름을 분리하는 안입니다. 파일 셀 문자열을 명령·설정·정책으로 실행하거나 해석하지 않습니다.

중복 식별은 기존 키 조회·새 버전 조회·저장된 일시/잔액 비교를 같은 관리대상 잠금 아래 처리하는 안입니다. 새 키가 달라도 기존 원본과 일치하면 한 번만 저장하고 오래된 키가 같아도 다른 원본이면 별도 행으로 유지합니다. 판단 불가능한 건은 확정 경로에 넘기지 않습니다. 과거 자료에서 부족한 정보를 임의 생성하지 않으며 식별용 원문은 로그에 남기지 않습니다.

### 수동 지출 처리

등록은 권한·통장·날짜 검증, 요청 UUID 재시도 확인, 기존 배분 계산·대상 검증, 지출 사실·배분 저장을 같은 트랜잭션에서 수행하는 안입니다. 현재 `ExpenseService.confirm`은 은행 원본 필수이므로 가짜 `BankTransaction`을 만들지 않고 배분 검증을 재사용할 범위만 분리합니다. 업무 제약은 업무 코드와 DB 양쪽에서 보장합니다.

취소·은행 연결은 업로드·수납·기준 잔고 변경과 같은 관리대상 잠금을 사용해 직렬화하는 안입니다. 은행 연결은 활성 미분류 원본과 지출의 대상·통장·금액·방향을 대조하고 중복 지출·이체 연결을 거부합니다. 요청 UUID 재시도는 현재 취소 상태나 이후 변경을 과거 상태로 되돌리지 않습니다. 확정 배분 본문은 덮어쓰지 않습니다.

조회는 은행 원본·유효 수동 지출·연결·취소를 같은 스냅샷에서 판단합니다. 통장 거래와 지출 조회, 월 합계·엑셀, 동별 원장·외부 부담금, 계산 잔액·조회 가능 시작일을 함께 점검합니다. 은행 원본 연결 후 수동 출금을 별도로 차감하지 않으며 은행 실제 확인값 계산에는 수동 입력을 포함하지 않습니다. 외부 정산의 생성·취소 범위는 업무 정책 확정 후 연결합니다.

### 구현 검증 계획

- 파서: 익명 자료로 각 은행 헤더·제목·병합·여러 메모·합계 행·시간·잔액·정렬을 재현하고 신한의 거래 종류/상대 분리를 검사합니다. 농협 음수 행은 정책에 따른 결과를 검사하며 조용한 제외·절댓값 출금을 금지합니다.
- 식별: 국민·농협·우리의 같은 날짜·상대·금액인 별도 입금, 같은 초의 거래, 누락 정보, 새 키/기존 키 교차 재업로드, 기존 신한 자료 검토, 동시 요청·삭제 후 재가져오기를 검사합니다.
- API·저장: 미지원 은행의 신규·호환 경로 거부, 다른 대상·종료 통장 거부, 수동 등록·배분 원자성·재시도·취소 이력·은행 연결 일회 집계와 전체 롤백을 검사합니다.
- Migration: 기존 ID·키·수납·배분·감사 이력 보존, 불변·합계·통장 FK·활성 원본 유일성 보장을 PostgreSQL 업그레이드 테스트로 확인합니다.

위 항목은 향후 구현의 검증 계획이며 이번 문서 작성에서 실행한 테스트가 아닙니다. 최종 검사·빌드는 기존 Server 규칙을 따릅니다.


## 수동 지출 등록 구현 (2026-10-23 후속)

[등록 계약](../../docs/bankingManagement.md#수동-지출-등록-api-2026-10-23)과 [실제 저장 구조](../../docs/erd.md#수동-지출-등록-저장-구현-2026-10-23)를 적용했습니다. 앞의 처리 설계안 중 등록·배분·조회만 구현했습니다. BankingService가 ADMIN·관리 시작·통장 소속·활성·미래 날짜를 확인하고 READ_COMMITTED 트랜잭션의 관리대상 잠금 안에서 ExpenseService에 저장을 위임합니다. 기준일 이전·당일을 차단하지 않습니다.

ExpenseService는 기존 배분 검증·암호화·동 명칭 스냅샷을 재사용하고 은행 원본 없이 지출·배분을 함께 저장합니다. 요청 UUID 재시도는 당시 내용을 비교하며 동이 이후 비활성·이름 변경되어도 이미 성공한 요청을 중복 생성하지 않습니다. DB 실패 시 지출 머리글까지 롤백합니다.

BankingBalanceService는 실제 출금일·통장으로 수동 지출을 조회하고 과거 사용 시작 근거에도 포함합니다. 동별 원장은 배분액, 통장 계산은 전액을 한 번 반영하고 은행 실제 확인값 계산은 유지합니다. 외부 회수의 통장 검증은 확정 지출의 통장을 사용합니다. 취소·은행 연결 저장과 출금 중복 대사는 후속 범위입니다.

PostgreSQL 통합 테스트에서 은행 원본 없음·재시도·권한·미래 날짜·통장/동 범위·원 미만·배분 저장 오류의 롤백·기준일 이전/당일 역산·외부 회수·기존 지출 Migration 보존을 검증합니다.


## 사용 종료 통장 조회 구현 (2026-10-23 후속)

업무 기준과 API는 [공통 계약](../../docs/bankingManagement.md#사용-종료-통장-조회-계약-2026-10-23-후속)을 따릅니다. BankAccountRepository는 관리대상 공용 통장별 거래·수납·지출·동별 기준값·확정 은행 인계 중 가장 이른 사용 날짜를 한 조회로 집계합니다. 취소·삭제 이력도 사용 흔적에는 포함하되 잔액 계산에는 기존 유효성 검증을 적용합니다. 미귀속 동별 기준값은 공용 통장이 하나일 때만 사용 근거로 귀속합니다.

BankAccount의 조회 기간 판정은 Workspace 메타데이터와 잔고 조회에서 공유합니다. 잔고 조회는 전체 공용 통장의 확인값·계산값과 동별 입출금·기준값을 읽고, 종료 후 통장 잔액·동별 자금·미회수 외부 부담금 예외를 판정한 뒤 같은 범위로 잔고·정산 응답을 만듭니다. 확인값과 계산값이 모두 null이면 미확인으로 유지하며 동별 기준값이 없는 귀속 거래도 미확인 자금으로 보존합니다. 회수 제외 결정은 미회수 예외에서 제외하고 유효 회수 연결만 회수액으로 차감합니다. 새 저장 컬럼이나 Migration은 없습니다.
