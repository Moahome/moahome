# 공용 통장 거래 분류 저장 설계

작성일: 2026-10-16. 상태: **Server 설계안, 미구현**. 사용자 요구와 업무 예시는 [공통 설계](../../docs/bankingManagement.md), 정책은 [도메인 규칙](../../docs/domainRules.md#공용-통장의-동별-거래-분류), 컬럼·관계는 [ERD](../../docs/erd.md#94-공용-통장-거래-분류-확장-설계안)를 따릅니다.

## 1. 기존 구현과 확장 책임

| 영역 | 현재 구현 | 확장 방향 |
| --- | --- | --- |
| banking | BankAccount·BankTransaction·Repository·입금 파일 Reader | 같은 계좌의 출금 원본·입출금 구분·거래 조회 |
| payment | 수납·청구 배분·원본 연결·확정·전체 취소 | 통장 거래 진입에서도 기존 Service 유스케이스 사용 |
| expense | 코드·Migration 없음, ERD 설계안 | 원본 출금 연결·상세·동별 배분·확정 |
| property | 현재 관리 권한·공유 관리대상 잠금 | 범위 검증과 동시성 제어 재사용 |
| accounting·closing | 후속 설계 | 업무 확정과 전표·마감 연결은 별도 구현 |

기존 PaymentService와 BankTransactionReader의 현재 동작은 [Server 입금 설계](payment.md)를 따릅니다. 입금 파일 가져오기는 원본과 수납을 함께 저장하고 명단에 유일하게 일치하면 자동 확정합니다. 미일치·중복 확인 항목은 PENDING으로 남깁니다. 통장 거래 화면을 추가해도 같은 은행 원본에 두 개의 활성 수납을 만들지 않습니다.

Controller는 인증 주체·요청 DTO를 Service에 전달합니다. 거래 조회·수집은 banking, 수납 확정은 payment, 지출과 동별 배분은 expense 책임으로 둡니다. 새로운 전역 분류 Service가 각 도메인의 상태와 금액을 직접 수정하는 구조를 만들지 않습니다. 실제 패키지는 [Server 규칙](../AGENTS.md)의 `controller/service/repo/domain/dto`를 따릅니다.

## 2. 원본 수집과 조회

현재의 날짜·선택 시간·입금자·적요·금액·선택 잔액·중복 키를 보존하고 출금 구분과 출금 상대방을 표현할 수 있도록 확장합니다. 기존 입금은 입금 방향으로 보정하되 거래 ID·금액·수납 연결·중복 키를 유지합니다. 날짜만 있는 과거 거래에 임의의 거래시간을 부여하지 않습니다.

현재 입금 중복 정책은 유지하고 출금의 중복 판정은 별도로 확정합니다. 입출금 방향을 도입할 때 같은 날짜·상대방·금액의 입금과 출금이 충돌하지 않는지 검토합니다. 기존 입금의 재업로드 호환성을 깨는 일괄 중복 키 재생성은 수행하지 않습니다.

입출금 파일 수집은 검증·중복 재검사·원본 저장을 담당하고, 입금은 기존 명단 일치 자동 확정 규칙을 재사용합니다. 지출은 별도 분류 후 확정합니다. 기존 PENDING 수납 생성 유지 여부, 기타 입금 분류로 전환할 때 초안 처리, 출금 보류 상태의 저장 책임은 신규 계약에서 함께 정합니다. 파일 배치·원본 파일·행별 오류의 보관은 미정이며 참고안의 테이블을 먼저 전부 생성하지 않습니다.

계좌번호 보호에는 AccountNumberSecurity, 기존 입금 보호에는 PaymentTextSecurity를 재사용할 수 있는지 확인합니다. 신규 출금 상대방·분류 사유도 로그·오류에 평문을 남기지 않으며 원본 파일이나 행 JSON을 보관한다면 보호 방식·보존기간·권한을 먼저 정합니다.

## 3. 수납 분류 확정

현재 수납 권한·청구 선택·배분 한도·상태 전이·재시도·원본 연결은 [입금 API](../../docs/paymentApi.md)와 기존 PaymentService를 사용합니다. 프론트엔드가 전송한 동 이름으로 새로운 Payment·청구를 생성하거나 고지서의 납부 Boolean을 갱신하지 않습니다.

기존 수동 확정 수납과 은행 원본이 같은 입금이면 기존 link 유스케이스를 사용합니다. 수납 전액과 고지서 배분액·선입금 잔액을 각각 조회합니다. 확정·취소 후 거래 화면과 기존 입금 화면이 같은 저장 상태를 읽도록 합니다.

동별 과거 집계에는 수납 당시의 귀속이 필요합니다. 현재 Unit.buildingId만 조인하면 이후 세대 이동으로 과거 동의 수납액이 달라질 수 있으므로 [ERD의 귀속 보존 설계](../../docs/erd.md#94-공용-통장-거래-분류-확장-설계안)를 검토합니다. 기존 수납에 확실한 과거 근거가 없으면 현재 동을 과거 스냅샷이라고 단정해 보정하지 않습니다.

## 4. 지출 분류 확정

아래는 구현할 유스케이스의 저장 순서입니다. 상세 입력·권한·취소 계약은 아직 미정입니다.

1. 정상 계정·현재 관리 권한·지출 업무 권한을 확인합니다.
2. 기존 세대·부과·수납 변경과 같은 관리대상 잠금을 획득합니다.
3. 해당 계좌·은행 거래·부담 동이 같은 관리대상에 속하는지 확인하고 출금 원본인지 검사합니다.
4. 다른 유효 지출이나 수납에 이미 연결되지 않았는지 확인합니다.
5. 비용 과목별 지출 상세 합계와 원본 출금액, 각 상세의 동별 배분 합계를 검증합니다.
6. 지출·상세·동별 배분·확정자·시각·처리 이력을 한 DB 트랜잭션으로 저장합니다.
7. 커밋 성공 뒤 확정 결과를 반환합니다. 저장 후반에 실패하면 전체를 롤백합니다.

DB에도 같은 관리대상 복합 FK와 유효 원본 연결의 유일성, 금액·합계 제약을 적용하는 안입니다. 여러 행 합계는 Service 검증만으로 끝내지 않고 지연 제약 등 DB 보완 방법을 검토합니다. 구체적인 SQL과 인덱스는 지출 상태·취소·재분류 정책을 정한 뒤 확정합니다.

같은 확정 요청 재시도는 기존 결과를 반환하고, 내용이 다른 재확정이나 이미 처리된 거래의 동시 확정은 충돌로 처리하는 설계입니다. 요청 ID·본문 비교·버전 토큰의 실제 계약은 통장·지출 API 작성 시 정합니다. 확정 기록을 일반 UPDATE로 덮어쓰지 않습니다.

지출 취소·재분류는 최초 원본과 배분 이력을 보존하는 별도 유스케이스로 설계합니다. 은행의 실제 환불 입금은 지출 취소와 구분합니다. 회계 연결 전 단계에서도 원본 은행 금액·잔액을 취소에 맞춰 바꾸지 않습니다.

## 5. 집계와 동시성

집계는 은행 원본, 확정 수납, 확정 지출 배분별로 먼저 수행하고 조회 결과를 조합합니다. 은행 거래·지출 상세·배분 행을 한 번에 조인해 원본 금액을 배분 수만큼 중복 합산하지 않습니다. 모든 조회에 관리대상 범위를 적용합니다.

조회 기준·수납일과 고지월·기간 수지·은행 잔액의 차이는 [공통 지표 설계](../../docs/bankingManagement.md#5-조회-금액과-잔액의-구분)를 따릅니다. 원본 미연결 수동 수납·미분류·동 귀속 미확인 항목을 확인 가능하게 하고 합계를 맞추기 위해 가상 거래를 저장하지 않습니다.

여러 합계를 한 응답으로 조회할 때는 기존 원장처럼 일관된 스냅샷에서 읽는 방식을 검토합니다. 성공·오류 응답은 기존 업무 API의 no-store·고정 오류 구조를 따르고 DB 장애를 빈 내역으로 반환하지 않습니다. 신규 조회 API의 페이지네이션과 합계 범위는 공통 API 계약에서 정의합니다.

## 6. Migration과 검증 기준

현재 적용된 은행·수납 Migration은 수정하지 않습니다. 새 Migration에서는 빈 DB 전체 적용과 기존 계좌·입금·수납·청구·원본 연결이 있는 스키마의 업그레이드를 모두 검증합니다. 신규 출금·지출·동별 배분 테이블은 해당 기능을 구현할 때만 추가합니다.

- 기존 입금 ID·원본·잔액·수납 배분·중복 재업로드 결과 보존.
- 같은 원본의 동시 분류·확정 재시도·후반 저장 실패에서 중복 및 부분 저장 방지.
- 입금과 출금의 구분, 다른 관리대상 동·계좌·세대의 연결 차단.
- 한 항목의 여러 동 배분, 여러 비용 항목의 서로 다른 배분, 합계 초과·부족 차단.
- 원본 출금 1건의 전체 지출이 배분 행 수만큼 증가하지 않음.
- 은행 원본 미연결 수동 수납과 미분류 거래의 집계 차이를 보존.
- 수납·지출 정정의 이력, 원본 불변과 과거 동 귀속 보존.

Server의 필수 검증은 Java 21 `./gradlew build`이며 [Server AGENTS.md](../AGENTS.md#16-test--build)를 따릅니다. 위는 향후 구현의 검증 기준이며 현재 실행한 테스트 결과가 아닙니다.
