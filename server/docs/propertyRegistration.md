# Server 관리대상 등록 설계

이 문서는 관리대상 등록 API의 Server 검증, 저장 초기값, 트랜잭션과 중복 방지 구현을 설명합니다. 요청 / 응답 / 오류는 [공통 등록 API](../../docs/propertyRegistrationApi.md), 컬럼 / 관계 / 제약은 [ERD](../../docs/erd.md), 확정 정책은 [도메인 규칙](../../docs/domainRules.md)을 참조합니다.

작성일: 2026-10-05. 수정일: 2026-10-10. 관리대상 등록 Controller / Service / Entity와 Migration을 구현했습니다. 이 문서는 저장 흐름과 현재 구현 범위를 설명하며 후속 주민 / 계좌 변경 / 월별 부과 정책은 확정하지 않습니다.

## 1. 검증과 계층 책임

- Controller는 인증된 사용자, 요청 DTO와 입력 검증 결과를 Service에 전달하고 API 계약의 HTTP 상태 / 응답을 반환합니다. Repository를 직접 호출하지 않습니다.
- 동 이름은 DTO와 Entity에서 같은 접미사 정리를 적용해 `101` / `101동`의 중복을 차단합니다. 호수는 문자와 앞자리 0을 보존하는 문자열로 받고 층의 정수 범위를 검증하며 초기 상태는 사용중 / 공실만 받습니다. 세부 입력 기준은 공통 등록 API를 따릅니다.
- DTO 검증은 필수 / 타입 / 형식 / 길이를 담당하고, Service는 동 참조, 중복, 기본 계좌 수와 전체 완료 조건을 검증합니다. 문자 길이는 공통 계약의 Unicode 코드 포인트 기준으로 검사합니다.
- 기본 정보 검증은 정리한 객체만 반환하고 어떤 업무 테이블도 저장하지 않습니다. 최종 저장은 기본 정보까지 전체 입력을 다시 검증합니다.
- Server가 DB ID, 관리대상 상태, 생성자 참여와 등록 시각을 결정합니다. Client 역할 / 사용자 ID를 저장 권한의 근거로 사용하지 않습니다.
- 입력 오류와 저장소 오류를 구분해 등록 API에 예외 매핑을 추가합니다. 현재 인증 Controller 전용 예외 처리가 새 업무 API까지 처리한다고 가정하지 않습니다.

## 2. 트랜잭션 저장 흐름

1. Bearer 인증과 정상 계정을 확인하고, 요청 DTO의 형식 / 길이 / 배열 조건을 검증합니다.
2. 해당 사용자 / requestId의 동시 저장을 직렬화하고 기존 성공 결과가 있으면 본문 지문과 현재 접근권한을 확인합니다.
3. 새로운 저장이면 전체 관계와 기본 계좌, 관리비 금액을 다시 검증하고 관리대상을 `ACTIVE`로 생성합니다.
4. 동을 생성해 clientId → DB ID를 연결하고 세대의 `property_id`와 필요한 `building_id`를 지정합니다.
5. 계좌번호를 보호해서 공용 관리계좌를 저장하고 공통 등록 시각에 따른 사용 시작일을 설정합니다.
6. 기본 관리비 템플릿과 항목을 저장하고 Server가 항목 합계를 계산합니다.
7. 인증된 사용자의 `ADMIN / ACTIVE` 참여를 생성하고 joined_at을 등록 시각으로 설정합니다. users.system_role은 변경하지 않습니다. 거주 선택 시 아래 최초 등록자 주민 연결을 같은 트랜잭션에서 처리합니다.
8. 인계 정보가 있는 현재 요청은 아래 RegistrationOpeningService 조합으로 인계·운영 시작·도래한 첫 월 청구·선납 충당을 같은 트랜잭션에서 저장합니다. 생략한 이전 요청은 등록만 저장합니다. 미래 첫 부과월은 스케줄에서 처리합니다.
9. 성공 응답 스냅샷과 본문 지문을 같은 트랜잭션으로 저장하고 커밋 성공 뒤 응답합니다.

외부 은행 확인이나 알림 발송을 이 DB 트랜잭션의 성공 조건으로 추가하지 않습니다. 등록 요청 원문을 Redis 초안이나 DB 초안으로 보관하지 않으며, 성공 결과 레코드에는 민감한 요청 본문을 저장하지 않습니다. 현재 API에서 성공 결과에 자동 만료를 두지 않고, 삭제 / 탈퇴에 따른 보존·정리는 해당 정책을 정할 때 중복 방지 보장과 함께 검토합니다.

트랜잭션 경계는 `property/service/PropertyRegistrationService`의 유스케이스에 두고 관련 도메인의 Repository를 조합합니다. 기본 정보 검증은 입력 정리만 수행하고 업무 데이터 생성은 최종 등록 Service에서 처리합니다. `V20261005034120__create_property_registration.sql`은 등록에 필요한 8개 테이블만 추가합니다. `property_members`의 일반 참여 중복 정책은 미정이므로 조회 인덱스만 두고, 이번 등록의 생성자 중복은 관리대상 생성과 성공 결과의 직렬 처리로 방지합니다.

`units`와 `bank_accounts`의 동 관계는 `property_id + building_id` 복합 FK로 같은 관리대상 소속을 보장합니다. 미구현 주민 / 회계 테이블의 연결 컬럼은 이번 등록에서 NULL로 두며 해당 테이블을 구현할 때 FK를 추가합니다.

## 3. 내부 초기값과 금액 처리

| 대상 | 저장 기준 |
| --- | --- |
| 관리대상 / 동 | ACTIVE, 동 없음에는 동 레코드 미생성 |
| 동 / 세대 연결 | clientId → 생성한 동 UUID 매핑, 각 세대의 property_id와 필요한 building_id 검증, clientId 자체는 DB에 저장하지 않음 |
| 관리계좌 | building_id / holder_resident_id / gl_account_id / valid_to는 NULL, 상태 ACTIVE, 예금주 이름은 holder_name_snapshot |
| 계좌 사용 시작일 | 공통 등록 시각 createdAt을 Asia/Seoul로 변환한 날짜, 재시도 시 최초 날짜 유지 |
| 관리비 템플릿 | 이름 기본 관리비, is_default=true, ACTIVE, effective_from은 등록 한국시간 월의 1일, effective_to는 NULL. 월별 적용·버전은 [관리비 설계](billing.md) 참조 |
| 관리비 항목 | item_code는 요청의 enum 이름 또는 NULL, item_name은 요청의 표시 이름, revenue_account_id는 NULL, is_active=true |
| 표시 순서 | 동과 항목 각각 요청 배열 순서대로 sort_order를 0부터 부여 |
| 생성자 참여 | 인증된 사용자의 ADMIN / ACTIVE, joined_at은 공통 등록 시각, 플랫폼 역할 변경 없음. 거주 선택 시 본인 명부·현재 세대 관계 생성 |

금액은 정수 원 단위로 받고 0원과 음수를 허용합니다. BigInteger로 전체를 정확히 합산한 뒤 최종 양·음수 범위를 검사합니다. 중간 합계 초과를 뒤의 음수 항목이 상쇄할 수 있으므로 요청 순서에 따른 거부는 하지 않습니다. 개별 값과 합계는 공통 API의 범위를 검증해 numeric(15,0)과 charges.total_amount의 저장 범위에 맞춥니다. 합계는 부호를 유지한 세대당 월 기본값이며 기본 설정을 저장한 뒤 인계 정보를 포함한 요청은 같은 트랜잭션의 관리 시작 확정에서 첫 청구를 생성합니다. `V20261008132205__allow_signed_fee_template_amount.sql`은 기존 행을 보존하며 `default_amount`의 양수 CHECK만 제거합니다.

`billing/domain/FeeItemCode`는 공통 등록 API의 추천 종류를 표현합니다. 요청 DTO와 `FeeTemplateItem.itemCode`에 같은 enum을 사용하고 `@Enumerated(EnumType.STRING)`으로 기존 `varchar(30)`에 저장합니다. 등록 JSON 변환기는 enum의 숫자 / 빈 문자열 변환을 거부하고 잘못된 코드의 필드 경로만 반환합니다. 생략 / null은 코드 없는 직접 입력이며 표시 이름은 기존 검증으로 별도 보존합니다. 후속 `V20261016135709__validate_fee_item_codes.sql`의 CHECK는 같은 코드·NULL만 허용합니다. 추천 종류 확장 시 Enum과 DB 제약을 함께 변경하며 이름으로 기존 항목을 자동 분류하지 않습니다.

## 4. 계좌번호 보호

정규화한 계좌번호로 account_number_encrypted, account_number_hmac과 account_last4를 생성합니다. 앞자리 0을 유지하고 공백 / 하이픈 제거와 입력 검증은 공통 계약을 따릅니다. 암호화 / HMAC 키는 외부 설정으로 관리하며 요청 / 응답 로그와 오류에 원문을 기록하지 않습니다.

전화번호용 `PhoneSecurity`의 암호화 방식을 확인했으며 전화번호 정규화와 기존 암호문 호환성을 유지하기 위해 그대로 둡니다. 계좌 전용 `common/security/AccountNumberSecurity`가 AES-256-GCM과 무작위 nonce, 버전 / 키 ID가 포함된 암호문, 별도의 HMAC-SHA256과 마지막 네 자리를 생성합니다. 계좌용 AAD / HMAC 문맥은 전화번호와 구분하며 외부 은행의 실계좌 확인은 수행하지 않습니다.

외부 키 설정은 [개발 환경 가이드](../../docs/developmentGuide.md#server-환경변수)를 따릅니다. `config/PropertyRegistrationConfig`가 추적되는 `propertyRegistration.properties`의 환경변수 연결을 읽습니다. 키를 코드나 Migration에 넣지 않으며 설정이 없거나 잘못된 키이면 시작을 거부합니다. 암호화 키 교체 시 기존 키 ID를 유지하고, 등록 지문 키 교체 시 기존 버전을 유지해야 기존 계좌 복호화와 성공 요청 재비교가 가능합니다.

## 5. 중복 방지와 등록 결과

성공 결과 저장 구조는 [ERD의 property_registration_results](../../docs/erd.md#58-property_registration_results)를 따릅니다. 필드 정의는 ERD에 유지하고 이 문서에서는 처리 순서를 설명합니다.

- 인증된 userId / requestId 단위의 저장을 DB 트랜잭션에서 직렬화합니다. 사전 조회나 Redis TTL, Client 버튼 잠금만으로 생성 횟수를 보장하지 않습니다.
- 기존 성공 결과가 있으면 저장된 키 버전으로 정규화 본문 지문을 비교하고 현재 접근권한을 확인한 뒤 최초 응답 스냅샷을 반환합니다. 다른 본문에는 계약의 충돌 오류를 반환합니다.
- 새로운 결과는 업무 데이터와 같은 트랜잭션에서 저장하고 복합 PK / property_id 유일성으로 무결성을 보장합니다. 성공 결과 레코드에 요청 원문이나 계좌번호를 보관하지 않습니다.
- 동시 요청을 제한 시간 안에 직렬 처리할 수 없으면 계약의 처리 중 오류를 반환합니다. 아직 진행 중인 상태를 DB 초안이나 성공 결과로 저장하지 않습니다.
- 결과 조회의 404는 커밋된 성공 결과가 없다는 의미이며 진행 중 요청이 없거나 저장 실패가 확정되었다는 의미가 아닙니다.
- 결과 조회 / 재반환마다 제출자와 현재 접근권한을 검증합니다. 이전 스냅샷의 ADMIN을 현재 역할로 복구하지 않습니다.
- 커밋 전 실패는 모든 변경을 롤백합니다. 커밋 후 응답 전달 실패에는 성공 결과를 유지해 조회 / 동일 요청 재시도로 복구합니다.

`property/repo/PropertyRegistrationLock`은 사용자 / requestId에서 만든 64비트 키로 PostgreSQL `pg_advisory_xact_lock`을 사용합니다. 잠금 대기는 3초로 제한하며 SQLSTATE `55P03`이면 처리 중 오류로 응답하고 트랜잭션을 롤백합니다. 성공 시 기존 lock_timeout을 복원하고 잠금은 커밋 / 롤백 때 자동 해제됩니다. 등록 트랜잭션에 `READ_COMMITTED`를 명시해 잠금 대기 뒤 최초 요청이 커밋한 결과를 새로 조회합니다. 키 해시 충돌은 관계없는 요청을 직렬 처리할 수 있지만 서로의 성공 결과나 접근권한을 공유하지 않습니다.

`RegistrationFingerprint`는 requestId를 제외한 정규화 DTO의 고정된 JSON 표현으로 HMAC을 계산합니다. 저장된 키 버전으로 재비교하고 배열 순서와 전체 입력을 비교합니다. 관리비 코드가 있으면 지문에 포함하고 `FeeItemInput.itemCode`가 null이면 해당 JSON 필드를 생략합니다. 코드 필드가 없던 이전 직렬화 표현을 유지해 기존 성공 요청의 재시도를 허용하며, 코드의 생략 / 명시적 null은 같은 지문입니다. 이름·금액이 같아도 코드만 바뀌면 충돌로 처리합니다. 결과 반환은 현재 활성 참여와 관리대상 상태를 확인하며 스냅샷을 권한 복구에 사용하지 않습니다.

관리자 화면 연결을 위한 목록 / 현재 관리 권한 조회는 [관리 영역 접근 API](../../docs/managementAccessApi.md)와 [Server 관리 영역 접근 설계](managementAccess.md)에 따라 별도로 구현했습니다. 등록 결과 조회의 현재 접근 확인은 유지하고, 관리 영역 전용 조회에는 현재 `ADMIN` / `MANAGER` 조건을 적용합니다. 등록 Service에 로그인 후 목적지 선택이나 최근 선택 저장을 추가하지 않습니다.

## 6. 구현 시 검증

### 기본 정보 검증

- 정상 로그인 사용자의 검증 성공과 선택 필드의 생략 / null / 공백 정리를 확인합니다.
- 이름 50자 / 51자, 주소 255자 / 256자, 상세주소 255자 / 256자, 건물 유형 30자 / 31자와 공백만 있는 필수 입력을 검증합니다.
- `hasBuildings`의 true / false 성공과 생략 / null / 문자열 입력 거부를 확인합니다.
- 계약 밖 생성자 / 역할 필드와 잘못된 JSON / Content-Type을 거부하고 오류에 입력 원문이 포함되지 않는지 확인합니다.
- 인증 실패, 이용 불가 계정과 인증 저장소 장애를 입력 오류와 구분합니다.
- 기본 정보 검증의 성공, 반복 요청과 오류에서 업무 테이블 쓰기가 발생하지 않는지 확인합니다.

### 최종 등록과 결과 조회

- 동 없음 / 단일 동 / 여러 동의 정상 등록과 예시 합계 50,000원, 생성자 ADMIN / ACTIVE, 플랫폼 역할 유지.
- 세대 / 계좌 / 항목의 빈 배열, 동 없음에서 동 입력, 누락된 동 참조, 중복 동 이름 / clientId / 동 내부 세대번호의 거부와 같은 번호의 다른 동 세대 허용.
- 각 문자열 경계와 공백 입력, 잘못된 타입 / 상태, smallint 층수 경계, 계좌번호의 앞자리 0 / 공백 / 하이픈 정규화.
- 예금주 이름 필수와 주민 연결 없이 저장, 기본 계좌 0개 / 2개 이상 거부, 공용계좌 저장과 Asia/Seoul 날짜 경계, 재조회 시 사용 시작일 유지.
- 추천 항목 코드 전체와 직접 입력의 저장 / enum 재조회, DB varchar 유지, 잘못된 코드 / 숫자 / 빈 문자열 거부, 코드 선택 시에도 표시 이름 필수.
- 코드 생략 / null의 기존 지문 호환과 코드만 변경한 같은 requestId의 충돌.
- 관리비 0원·음수 허용, 소수 / 숫자 문자열 거부, 개별 / 최종 합계의 양·음수 범위, 상쇄 항목과 항목별 순서 유지.
- 생성자 ID / 역할 등 계약 밖 입력 거부, 정상 계정 인증, 인증 장애와 업무 저장 장애의 구분, 오류 / 로그 / 응답의 계좌번호 원문 미포함.
- 동 / 세대 / 계좌 / 템플릿 / 참여 / 성공 결과 중 하나의 저장 실패에서 업무 데이터와 성공 결과 모두 롤백.
- 같은 ID / 본문의 순차·동시 재시도, 다른 본문의 ID 재사용 거부, 다른 사용자의 결과 조회 차단, 현재 권한 해제 시 결과 접근 거부.
- 커밋 후 응답 유실에서 결과 조회와 같은 ID 재시도가 같은 property.id를 반환하고 업무 데이터가 1회만 생성됨.
- 기본 정보 검증 이후 최종 입력을 변경해도 전체 재검증이 수행됨.

검증 명령은 [Server AGENTS.md](../AGENTS.md)를 따릅니다. 자동 테스트는 `property/controller/PropertyRegistrationControllerTest`, `property/service/PropertyRegistrationServiceTest`, `property/domain/RegistrationDomainTest`, `property/repo/PropertyRegistrationPersistenceTest`와 `common/security/AccountNumberSecurityTest`에 있습니다. 기존 `SecurityIntegrationTest`에서도 등록 API의 Bearer 인증과 CSRF 없는 업무 POST를 검증합니다.

PostgreSQL 테스트는 별도 임시 클러스터에서 빈 DB / 기존 사용자·관리비 항목이 있는 스키마의 Migration, 정상 저장, 저장 8단계별 강제 실패의 전체 롤백, 순차 / 동시 재시도, 3초 잠금 제한과 현재 권한 해제를 확인합니다. 위 상세 목록은 검증 기준이며 테스트 실행 결과는 실제 명령을 기준으로 보고합니다.


## 최초 등록자 주민 연결 (2026-10-17)

등록자의 명시적 거주 선택은 동일 트랜잭션에서 ADMIN·Resident·UnitResident를 저장합니다. 주민 구분 OTHER·대표 false이며 공실 표시는 주민 등록만으로 자동 변경하지 않습니다. 연락처는 선택이며 입력한 번호만 기존 주민 정규화와 PhoneSecurity로 보호합니다. 미입력은 보호 컬럼을 모두 NULL로 저장하며 보호 서비스가 없어도 저장할 수 있습니다. 외부자는 PropertyMember만 저장합니다.

기존 성공 결과의 administrator에는 주민·세대·관계 ID만 저장하고 원문 개인정보는 넣지 않습니다. ResidentRepository는 등록 결과의 사용자와 최초 관계 ID·현재 활성 참여를 함께 확인해 가입 완료를 판정합니다. 가입 요청을 가짜로 생성하지 않으며 관계가 끝나거나 재입주로 ID가 바뀌면 과거 연결을 승인 근거로 사용하지 않습니다. 새 거주 선택은 HMAC에 포함하고 생략된 이전 요청의 지문은 유지합니다. 기존 스키마·Migration은 수정하지 않습니다.

## 관리 담당자 후속 정책과 현재 구현의 차이 (2026-10-17)

[생성자 권한](../../docs/domainRules.md#확정된-관리대상-생성자-권한)에 관리소장 담당자 등록의 대표 자동 지정 예외가 추가되었다. 대표 자동 지정 예외와 연락처 선택 정책은 Server에 적용했다. 외부 담당자 정보의 입력 제한은 아직 유지한다. 외부 담당자 이름·연락처의 저장 구조는 후속 구현이다. 기존 관리소장 계정의 본인 명부 연결은 [참여자 저장](memberManagement.md#기존-관리소장-본인-명부-연결)에서 구현했다. 기존 데이터를 이름·전화번호로 자동 연결하거나 소급 변경하지 않는다.


## 초기 설정의 인계·운영 시작 조합 (2026-10-18)

RegistrationOpeningService는 최종 요청의 전체 세대·동·계좌 참조와 날짜를 검증하고 PropertyRegistrationService의 기존 READ_COMMITTED 트랜잭션에 반드시 참여합니다. 임시 동 식별자·호수·배열 위치를 실제 생성 ID로 매핑한 뒤 OpeningBalanceService의 save, BankingBalanceService의 saveOpenings, OpeningBalanceService의 confirm을 순서대로 재사용합니다. 권한·잠금·첫 부과·선납 충당은 기존 서비스를 따르고 실패 시 등록 결과까지 함께 롤백합니다. 새 입력이 없는 이전 등록은 조합 서비스를 호출하지 않아 저장·지문을 유지합니다. API 계약은 [공통 등록 문서](../../docs/propertyRegistrationApi.md#초기-설정의-잔액-인계와-관리-시작)를 참조합니다.


## 다중 통장 등록 (2026-10-18)

기존 계좌 배열·기본 지정 수 검증과 계좌별 인계값 저장을 그대로 사용합니다. 선택 alias만 계좌의 account_alias에 저장하고, null은 요청 지문 직렬화에서 생략해 이전 등록 요청 재시도를 보존합니다. 운영 중 추가·기본 전환·종료는 [통장 저장 설계](bankingManagement.md#다중-통장-저장과-내부-이체-2026-10-18)를 따릅니다.
