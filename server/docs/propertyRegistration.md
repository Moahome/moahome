# Server 관리대상 등록 설계

이 문서는 관리대상 등록 API의 Server 검증, 저장 초기값, 트랜잭션과 중복 방지 구현을 설명합니다. 요청 / 응답 / 오류는 [공통 등록 API](../../docs/propertyRegistrationApi.md), 컬럼 / 관계 / 제약은 [ERD](../../docs/erd.md), 확정 정책은 [도메인 규칙](../../docs/domainRules.md)을 참조합니다.

작성일: 2026-10-05. 현재 관리대상 등록 Controller / Service / Entity / Migration은 없습니다. 이 문서는 기존 API 설계에서 Server 책임을 분리한 구현 설계이며 새로운 업무 정책을 확정하지 않습니다.

## 1. 검증과 계층 책임

- Controller는 인증된 사용자, 요청 DTO와 입력 검증 결과를 Service에 전달하고 API 계약의 HTTP 상태 / 응답을 반환합니다. Repository를 직접 호출하지 않습니다.
- DTO 검증은 필수 / 타입 / 형식 / 길이를 담당하고, Service는 동 참조, 중복, 기본 계좌 수와 전체 완료 조건을 검증합니다. 문자 길이는 공통 계약의 Unicode 코드 포인트 기준으로 검사합니다.
- 기본 정보 검증은 정리한 객체만 반환하고 어떤 업무 테이블도 저장하지 않습니다. 최종 저장은 기본 정보까지 전체 입력을 다시 검증합니다.
- Server가 DB ID, 관리대상 상태, 생성자 참여와 등록 시각을 결정합니다. Client 역할 / 사용자 ID를 저장 권한의 근거로 사용하지 않습니다.
- 입력 오류와 저장소 오류를 구분해 등록 API에 예외 매핑을 추가합니다. 현재 인증 Controller 전용 예외 처리가 새 업무 API까지 처리한다고 가정하지 않습니다.

## 2. 트랜잭션 저장 흐름

1. Bearer 인증과 정상 계정을 확인하고, 요청 DTO의 형식 / 길이 / 배열 조건을 검증합니다.
2. 해당 사용자 / requestId의 동시 저장을 직렬화하고 기존 성공 결과가 있으면 본문 지문과 현재 접근권한을 확인합니다.
3. 새로운 저장이면 전체 관계와 기본 계좌, 관리비 금액을 다시 검증하고 관리대상을 `ACTIVE`로 생성합니다.
4. 동을 생성해 clientId → DB ID를 연결하고 세대의 `property_id`와 필요한 `building_id`를 지정합니다.
5. 계좌번호를 보호해서 공용 관리계좌를 저장하고 공통 등록 시각에 따른 사용 시작일을 설정합니다.
6. 기본 관리비 템플릿과 항목을 저장하고 Server가 항목 합계를 계산합니다.
7. 인증된 사용자의 `ADMIN / ACTIVE` 참여를 생성하고 joined_at을 등록 시각으로 설정합니다. users.system_role과 주민 명부는 변경하지 않습니다.
8. 성공 응답 스냅샷과 본문 지문을 같은 트랜잭션으로 저장하고 커밋 성공 뒤 응답합니다.

외부 은행 확인이나 알림 발송을 이 DB 트랜잭션의 성공 조건으로 추가하지 않습니다. 등록 요청 원문을 Redis 초안이나 DB 초안으로 보관하지 않으며, 성공 결과 레코드에는 민감한 요청 본문을 저장하지 않습니다. 현재 API에서 성공 결과에 자동 만료를 두지 않고, 삭제 / 탈퇴에 따른 보존·정리는 해당 정책을 정할 때 중복 방지 보장과 함께 검토합니다.

트랜잭션 경계는 등록 Service의 유스케이스에 두고 관련 도메인의 저장 책임을 조율합니다. 기본 정보 검증은 입력 정리만 수행하고 업무 데이터 생성은 최종 등록 Service에서 처리합니다. 현재 초기 구성 단계이므로 이 기능에 필요한 Entity / Repository / Migration만 후속 구현에서 만듭니다.

## 3. 내부 초기값과 금액 처리

| 대상 | 저장 기준 |
| --- | --- |
| 관리대상 / 동 | ACTIVE, 동 없음에는 동 레코드 미생성 |
| 동 / 세대 연결 | clientId → 생성한 동 UUID 매핑, 각 세대의 property_id와 필요한 building_id 검증, clientId 자체는 DB에 저장하지 않음 |
| 관리계좌 | building_id / holder_resident_id / gl_account_id / valid_to는 NULL, 상태 ACTIVE, 예금주 이름은 holder_name_snapshot |
| 계좌 사용 시작일 | 공통 등록 시각 createdAt을 Asia/Seoul로 변환한 날짜, 재시도 시 최초 날짜 유지 |
| 관리비 템플릿 | 이름 기본 관리비, is_default=true, ACTIVE, effective_from / effective_to는 NULL |
| 관리비 항목 | item_code / revenue_account_id는 NULL, is_active=true |
| 표시 순서 | 동과 항목 각각 요청 배열 순서대로 sort_order를 0부터 부여 |
| 생성자 참여 | 인증된 사용자의 ADMIN / ACTIVE, joined_at은 공통 등록 시각, 플랫폼 역할 / 주민 명부 변경 없음 |

금액은 최소 화폐 단위 정수 또는 BigDecimal로 정확히 합산합니다. 개별 값과 합계는 공통 API의 범위를 검증해 numeric(15,0)과 향후 charges.total_amount의 저장 범위에 맞춥니다. 합계는 세대당 월 기본값이고 실제 청구는 생성하지 않습니다.

## 4. 계좌번호 보호

정규화한 계좌번호로 account_number_encrypted, account_number_hmac과 account_last4를 생성합니다. 앞자리 0을 유지하고 공백 / 하이픈 제거와 입력 검증은 공통 계약을 따릅니다. 암호화 / HMAC 키는 외부 설정으로 관리하며 요청 / 응답 로그와 오류에 원문을 기록하지 않습니다.

현재 전화번호용 PhoneSecurity는 계좌번호를 처리하는 API가 아닙니다. 공통 코드의 재사용 가능 범위를 확인하고 실제 계좌 보호와 키 설정은 이 저장 기능을 구현할 때 연결합니다. 계좌번호 보호나 은행 확인이 이미 구현된 것으로 문서화하지 않습니다.

## 5. 중복 방지와 등록 결과

성공 결과 저장 구조는 [ERD의 property_registration_results](../../docs/erd.md#58-property_registration_results)를 따릅니다. 필드 정의는 ERD에 유지하고 이 문서에서는 처리 순서를 설명합니다.

- 인증된 userId / requestId 단위의 저장을 DB 트랜잭션에서 직렬화합니다. 사전 조회나 Redis TTL, Client 버튼 잠금만으로 생성 횟수를 보장하지 않습니다.
- 기존 성공 결과가 있으면 저장된 키 버전으로 정규화 본문 지문을 비교하고 현재 접근권한을 확인한 뒤 최초 응답 스냅샷을 반환합니다. 다른 본문에는 계약의 충돌 오류를 반환합니다.
- 새로운 결과는 업무 데이터와 같은 트랜잭션에서 저장하고 복합 PK / property_id 유일성으로 무결성을 보장합니다. 성공 결과 레코드에 요청 원문이나 계좌번호를 보관하지 않습니다.
- 동시 요청을 제한 시간 안에 직렬 처리할 수 없으면 계약의 처리 중 오류를 반환합니다. 아직 진행 중인 상태를 DB 초안이나 성공 결과로 저장하지 않습니다.
- 결과 조회의 404는 커밋된 성공 결과가 없다는 의미이며 진행 중 요청이 없거나 저장 실패가 확정되었다는 의미가 아닙니다.
- 결과 조회 / 재반환마다 제출자와 현재 접근권한을 검증합니다. 이전 스냅샷의 ADMIN을 현재 역할로 복구하지 않습니다.
- 커밋 전 실패는 모든 변경을 롤백합니다. 커밋 후 응답 전달 실패에는 성공 결과를 유지해 조회 / 동일 요청 재시도로 복구합니다.

## 6. 구현 시 검증

### 기본 정보 검증

- 정상 로그인 사용자의 검증 성공과 선택 필드의 생략 / null / 공백 정리를 확인합니다.
- 이름 50자 / 51자, 주소 255자 / 256자, 상세주소 255자 / 256자, 건물 유형 30자 / 31자와 공백만 있는 필수 입력을 검증합니다.
- `hasBuildings`의 true / false 성공과 생략 / null / 문자열 입력 거부를 확인합니다.
- 계약 밖 생성자 / 역할 필드와 잘못된 JSON / Content-Type을 거부하고 오류에 입력 원문이 포함되지 않는지 확인합니다.
- 인증 실패, 이용 불가 계정과 인증 저장소 장애를 입력 오류와 구분합니다.
- 기본 정보 검증의 성공, 반복 요청과 오류에서 업무 테이블 쓰기가 발생하지 않는지 확인합니다.

### 최종 등록과 결과 조회

- 동 없음 / 단일 동 / 여러 동의 정상 등록과 예시 합계 50,000원, 생성자 ADMIN / ACTIVE, 플랫폼 역할 유지.
- 세대 / 계좌 / 항목의 빈 배열, 동 없음에서 동 입력, 누락된 동 참조, 중복 동 이름 / clientId / 동 내부 세대번호의 거부와 같은 번호의 다른 동 세대 허용.
- 각 문자열 경계와 공백 입력, 잘못된 타입 / 상태, smallint 층수 경계, 계좌번호의 앞자리 0 / 공백 / 하이픈 정규화.
- 예금주 이름 필수와 주민 연결 없이 저장, 기본 계좌 0개 / 2개 이상 거부, 공용계좌 저장과 Asia/Seoul 날짜 경계, 재조회 시 사용 시작일 유지.
- 관리비 0원 허용, 음수 / 소수 / 숫자 문자열 거부, 개별 / 합계 금액 범위와 항목별 순서 유지.
- 생성자 ID / 역할 등 계약 밖 입력 거부, 정상 계정 인증, 인증 장애와 업무 저장 장애의 구분, 오류 / 로그 / 응답의 계좌번호 원문 미포함.
- 동 / 세대 / 계좌 / 템플릿 / 참여 / 성공 결과 중 하나의 저장 실패에서 업무 데이터와 성공 결과 모두 롤백.
- 같은 ID / 본문의 순차·동시 재시도, 다른 본문의 ID 재사용 거부, 다른 사용자의 결과 조회 차단, 현재 권한 해제 시 결과 접근 거부.
- 커밋 후 응답 유실에서 결과 조회와 같은 ID 재시도가 같은 property.id를 반환하고 업무 데이터가 1회만 생성됨.
- 기본 정보 검증 이후 최종 입력을 변경해도 전체 재검증이 수행됨.

검증 명령은 [Server AGENTS.md](../AGENTS.md)를 따릅니다. PostgreSQL 무결성 / 동시 저장 / 전체 롤백과 Migration은 실제 PostgreSQL로 검증합니다. 위 항목은 후속 구현에서 실행할 기준이며 이미 통과한 테스트를 의미하지 않습니다.
