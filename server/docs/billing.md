# 관리비 저장과 자동 부과

상태: 실제 API·설정 버전·월별 청구 생성과 자동 확정 구현. 정책은 [도메인 규칙](../../docs/domainRules.md#5-관리비-부과--청구), 요청 / 응답 / 오류는 [관리비 API](../../docs/billingApi.md), 컬럼·제약은 [ERD](../../docs/erd.md#7-관리비-부과)를 기준으로 합니다.

## 설정 변경

BillingService는 매 요청 ManagementAccessService로 현재 권한을 확인합니다. 저장 시 세대 관리와 같은 Property 행의 비관적 잠금을 획득한 뒤 최신 revisionId와 서버 기준 다음 달을 검증합니다. 성공하면 기존 템플릿·항목을 변경하지 않고 증가한 revision의 템플릿과 항목을 함께 추가합니다. 사유·변경자·적용월을 보존합니다. 합계는 BigDecimal로 계산하고 numeric(15,0) 범위를 검증합니다.

BillingTemplates는 적용월 이하의 ACTIVE 기본 템플릿 중 최신 revision을 선택합니다. 최초 템플릿의 effective_from과 첫 부과월은 등록한 한국시간 월을 기준으로 합니다. 기존 NULL 날짜는 Migration에서 같은 기준으로 보정합니다. 적용 시작 날짜 추가는 기존 데이터 전체를 UPDATE하므로 배포 전 레코드 수·잠금 시간을 확인합니다. 이전 Migration과 등록 결과 스냅샷은 변경하지 않습니다.

## 전체·동별 설정과 독립적인 임시 부과 (2026-10-25)

기본 billingMode와 임시 temporaryMode를 서로 독립적으로 저장합니다. BillingSettingsRequest는 전체 기본 items와 동별 buildingItems 중 선택한 범위만 허용하고, Service는 잠금 아래 현재 모든 동·중복·소속과 각 동의 기본 및 기본+임시 최종 합계를 검증합니다. 다음 달 전체 설정을 새 버전으로 저장하므로 재수정은 마지막 저장본을 사용하며 원본·수정자·사유를 유지합니다.

FeeTemplateItem은 관리대상·대상 동·임시 여부·선택 비고를 저장합니다. 기본 ALL·임시 BUILDING 및 기본 BUILDING·임시 ALL을 모두 허용합니다. BillingTemplates.applicableItems는 월·동별 기본 항목과 버전 적용 시작월에만 유효한 임시 항목을 합칩니다. 예정 조회·자동 생성·당월 보충에서 같은 함수를 사용하고, 임시 종료 후 기존 금액을 덮어쓰는 별도 복원 버전을 생성하지 않습니다.

해당 동의 기본 항목이 없으면 BILLING_SETTINGS_NOT_FOUND로 중단하고 빈 0원 청구나 다른 동의 금액을 임의로 만들지 않습니다. 동별 반복 부과 운영 중 새 동의 초기 설정을 받는 흐름은 후속 보완이 필요합니다.

설정 응답에서도 조회월에 끝난 임시 항목을 제외합니다. 임시 원본 항목은 삭제하지 않으며 ChargeItem의 source_template_item_id로 출처를 보존합니다. 기본·임시 항목 모두 템플릿 전체의 저장 순서를 사용해 한 청구 내 항목 순서가 겹치지 않습니다. 과거 확정 스냅샷은 재계산하지 않습니다.

후속 Migration은 기존 템플릿을 ALL, 기존 항목을 반복 항목으로 보정합니다. 새 property_id는 연결된 템플릿에서 채우고 필수화하며 템플릿·동의 관리대상 복합 FK를 추가합니다. 기존 템플릿/항목 ID와 청구 FK를 유지합니다. 컬럼 추가·UPDATE·필수화·FK 검증에는 잠금과 기존 항목 수에 비례한 작업이 필요하므로 실제 환경 적용 시간은 별도로 확인합니다. 실패 시 Flyway 트랜잭션으로 함께 롤백합니다.

## 이번 달 추가 부과와 항목별 적용월 (2026-10-25)

PUT 설정 저장은 임시 행의 month를 이번 달·다음 달로 나눕니다. 기본 설정은 다음 달에 저장하고, 이번 달 행은 별도의 비기본 템플릿·billing_additions·추가 Charge로 저장합니다. 모든 변경은 기존 Property 잠금 아래 한 트랜잭션이며 사유·처리자·출처를 보존합니다. 기존 확정 Charge·ChargeItem·납부 배분은 변경하지 않습니다. 다음 달 임시 행은 해당 다음 달 버전에만 저장합니다.

이번 달 요청의 requestId와 정규화 DTO의 SHA-256 지문을 보존합니다. 재시도는 현재 권한을 검증하고 같은 내용·처리자이면 원 성공을 유지하며 다른 내용이면 충돌입니다. 추가 부과 생성 후 실패하면 기본 변경까지 함께 롤백합니다. 기본 설정 revision과 추가 원본 revision은 같은 잠금 아래 순서대로 할당합니다.

BillingGenerationService는 추가 부과별 미생성 사용 중 세대만 보충합니다. 공실 제외·사용 중 복귀·세대 삭제도 기존 상태 동기화를 적용하고, 같은 추가 부과·세대 UNIQUE로 중복을 차단합니다. 적용 기간이 다른 다음 달에는 과거 추가 부과를 복사하지 않습니다. 수납 충당은 CumulativePaymentService를 재사용하며 기존 배분은 유지합니다.

월별 조회·상세는 실제 청구를 세대별로 합쳐 반환하며 이력의 세대 수는 distinct unit_id입니다. 추가 처리 시각·처리자·사유의 원본은 추가 부과·템플릿에 보존하고 기본 기간의 최초 확정 시각을 덮어쓰지 않습니다.

## 실행과 원자성

인계 정보를 생략한 이전 등록은 청구를 생성하지 않습니다. 현재 PropertyRegistrationService는 인계 정보가 있으면 RegistrationOpeningService로 같은 트랜잭션의 인계·관리 시작을 조합합니다. OpeningBalanceService.confirm에서 관리 시작·기존 미납·선납을 확정하고 도래한 첫 월에 BillingGenerationService를 호출합니다. 인계·첫 부과·선납 충당은 같은 트랜잭션이며 실패하면 전체를 롤백합니다. 미래 첫 부과는 기존 스케줄에서 처리합니다.

BillingScheduler는 Asia/Seoul의 매시 정각(매월 1일 00시 포함)과 ApplicationReadyEvent에서 실행합니다. 활성 관리대상의 첫 부과월부터 현재 월까지 누락을 확인하므로 일시 장애·서버 중단 후 복구합니다. 운영 시작 전 대상은 제외합니다. 이미 운영 중인 기존 대상은 등록월 기준을 유지하고 확정된 청구를 보존합니다. 당월 기간이 이미 있어도 현재 사용 중 세대의 누락 청구를 보충하므로 이전 구현에서 월중 추가 후 빠진 세대도 복구합니다. 과거 월에 이미 있는 기간의 누락 세대 청구는 소급 추가하지 않습니다. `moahome.billing.scheduler-enabled=false`로 자동 실행을 끌 수 있습니다. 이 값은 테스트용 속성으로도 사용합니다.

반복 부과의 각 월·관리대상은 별도 BillingGenerationService 트랜잭션입니다. Property 행 잠금으로 여러 서버·재시도와 세대 / 설정 변경을 직렬화합니다. 이미 ISSUED인 기간은 재생성하지 않습니다. 세대 추가 시 별도 보충 흐름으로 해당 월에 없는 신규 세대 청구만 생성합니다. 기간 → 청구·항목 스냅샷 → 자동 확정을 하나의 트랜잭션으로 저장하므로 중간 실패 시 모두 롤백합니다. DB의 관리대상·월 UNIQUE와 기간·세대 UNIQUE도 중복을 차단합니다.

실패한 관리대상은 그 달에서 멈추고 다른 관리대상 처리는 계속합니다. 다음 정각이나 재시작에 다시 시도합니다. 로그에는 대상 UUID·월·예외 종류만 기록하며 SQL·개인정보 원문은 기록하지 않습니다. 복구 시점의 현재 세대 목록과 해당 월 적용 템플릿을 사용합니다. 세대별 과거 소속 시점 복원과 수동 초안은 이번 기능에 없습니다.

## 세대 추가·삭제 연동

UnitManagementService는 세대 저장 후 BillingGenerationService.addCurrentMonthUnits를 같은 트랜잭션에서 호출합니다. 관리대상 잠금 아래 당월 기간이 없으면 전체 부과를 한 번 생성하고, 있으면 이번 신규 세대의 미생성 청구만 당월 적용 템플릿으로 보충합니다. 기존·취소 청구의 세대 ID도 중복 검사에 포함합니다. 스케줄과 경합해도 관리대상 잠금과 기간·세대 UNIQUE로 한 번만 생성하며 청구 저장 실패는 세대 저장까지 롤백합니다.

삭제에서는 ResidentManagementService.deleteForUnits로 현재 주민·관계·해당 대상 주민 권한과 삭제 세대의 대기 신청을 정리하고 BillingGenerationService.cancelCurrentMonthUnits로 한국시간 당월 청구만 취소합니다. 이후 동·세대를 소프트 삭제합니다. 모두 같은 트랜잭션이며 어느 단계라도 실패하면 전체를 롤백합니다. 현재 주민이 있으면 기존 ADMIN 검증을 적용합니다. 이미 삭제된 대상의 재요청은 이전 구현의 남은 관계도 정리하되 주민·동·세대·청구의 최초 삭제·취소 정보를 덮어쓰지 않습니다.

Migration `V20261012052031__support_unit_deletion_charge_cancellation.sql`은 기존 청구 원본을 변경하지 않고 CANCELED 상태와 취소 감사 컬럼·제약을 추가합니다. Migration 자체에서는 기존 업무 데이터를 변경하지 않습니다. 과거 월·취소 항목을 물리 삭제하지 않으며, 기존 당월 누락 청구는 위 스케줄 흐름에서 보충합니다. 적용 시 charges의 CHECK 제약 변경에 테이블 잠금이 필요하므로 운영 적용 시간은 별도로 관리합니다.

## 공실 제외·상세 취소·기존 삭제 누락

세대 상태 변경도 addCurrentMonthUnits를 같은 트랜잭션에서 호출합니다. 사용 중 세대만 생성하고 기존 당월 청구는 공실에 `EXCLUDED_VACANT`, 사용 중 복귀에 ISSUED로 동기화합니다. 금액·항목·발행 시각은 유지하며 과거 상태와 CANCELED 청구를 복구하지 않습니다. 당월 기존 청구가 없는 사용 중 세대에는 당월 설정으로 전액 부과합니다.

당월 보충은 과거 삭제된 동·세대의 잔여 청구도 확인합니다. 실제 deleted_by 근거가 있으면 UNIT_DELETED로 취소합니다. 삭제자가 없는 과거 자료에는 임의의 처리자를 만들지 않으며 당월 조회에서 제외합니다. GET은 업무 데이터를 변경하지 않습니다.

BillingService.cancelCharge는 관리 권한·현재월·관리대상/기간/청구 소속을 검증하고 같은 Property 잠금 아래 MANUAL_CANCELED로 취소합니다. 실패는 롤백하며 당월 재시도는 최초 감사를 유지합니다. 스케줄은 취소된 세대를 중복 생성하지 않지만 다음 달은 정상 대상입니다. 새 Migration은 기존 행을 변경하지 않고 상태·사유 CHECK만 확장합니다.

## 스냅샷과 조회

Charge는 동명·호수·별칭·총액·기한을, ChargeItem은 원본 항목 ID·코드·명칭·금액·순서·계정 연결 값을 보존합니다. 이후 세대 정정이나 기본 설정 변경으로 확정 청구를 다시 계산하지 않습니다. 세대 삭제 시 당월 청구만 취소 상태로 전환하고 과거 월 스냅샷은 유지합니다. 시스템 확정은 기간의 confirmation_source=SCHEDULE로 식별하고 시각을 보존합니다.

실제 기간이 없는 현재·미래 조회는 예정값만 계산하며 GET에서 저장하지 않습니다. 과거 조회에 가상 청구를 생성하지 않습니다. 조회·이력 금액은 BigDecimal 계산 후 문자열로 반환합니다. 수납·환급·전표 생성은 이 트랜잭션에 포함하지 않습니다.

대표 주민 이름은 ResidentListService의 현재 명부 조회를 한 번 재사용해 세대별로 연결합니다. 기존 세대 목록처럼 ADMIN에게만 제공하고 MANAGER에게는 이름을 반환하지 않습니다. 청구 스냅샷에 이름을 추가하거나 금액을 다시 계산하지 않으므로 대표 변경·삭제와 청구 금액 보존은 독립적입니다. 응답 계약은 [관리비 API](../../docs/billingApi.md#월별-응답)를 따릅니다.

## 검증

`./gradlew build`에 아래 검증을 포함합니다.

- BillingDomainTest: 윤년·한국시간 경계, 0원·음수·금액 범위, 상태 전이와 잘못된 입력의 상태 보존.
- BillingControllerTest: 인증·범위 전달·필수 사유·중첩 항목 검증·고정 오류 응답.
- BillingPersistenceTest: 일회성 PostgreSQL에서 최초 부과월, 사용 중 대상·공실 제외, 버전·사유 보존, 충돌, 청구 스냅샷, 동시 실행·전체 롤백·재시도·다른 관리대상 FK 차단.
- 기존 등록·주민·사용자 PostgreSQL 테스트: 빈 DB 전체 Migration과 이전 스키마 업그레이드 / 기존 ID 보존.

테스트 인프라 실행 경로와 분리는 [Server AGENTS.md](../AGENTS.md#16-test--build)를 따릅니다. 개발 / 운영 DB에 테스트를 실행하지 않습니다.

## 삭제한 호수 재등록

호수 중복 제한은 [세대 관리 API](../../docs/unitManagementApi.md#추가수정-요청)를 따릅니다. 재추가는 새 세대 ID이므로 기존 당월 취소 청구와 과거 월 스냅샷을 유지한 채 새 사용 중 세대에 당월 전액을 부과합니다. 주민 관계는 예전 세대에서 자동 복구하지 않습니다. 삭제한 예전 세대 ID의 재요청은 새 세대 청구에 영향을 주지 않습니다.

`V20261012063902__allow_deleted_unit_number_reuse.sql`은 units의 호수 제약만 부분 유일 인덱스로 바꾸고 기존 행과 FK를 변경하지 않습니다. Flyway 트랜잭션에서 제약 변경·인덱스 생성이 실패하면 함께 롤백합니다. 기존 스키마 업그레이드에서 동 있음·없음의 기존 행·청구 항목 보존과 미삭제 중복 차단을 검증합니다.

## 항목 코드와 조회 무결성

`V20261016135709__validate_fee_item_codes.sql`은 `fee_template_items`와 `charge_items`에 실제 `FeeItemCode` 허용값·NULL CHECK를 추가합니다. 추천 항목의 기존 코드와 직접 입력 항목의 NULL을 그대로 사용하며 항목명으로 종류를 추정하지 않습니다. Enum을 확장할 때 DB 제약도 함께 변경해야 하며 PostgreSQL 테스트는 전체 Enum 값과 NULL 조회, 미지원 코드 거부를 확인합니다. 기존에 잘못된 코드가 있으면 적용 전에 근거를 확인해 정정해야 하며 Migration이 이름·금액을 보고 임의 분류하지 않습니다.

## 기존 잔액 인계 저장 (2026-10-17)

OpeningBalanceService는 현재 ADMIN 권한과 관리대상 잠금 아래 초안 버전·전체 세대/계좌·기준일을 검증합니다. 관리 시작·초기 미수·확정 상태·첫 청구·기존 선납 충당을 같은 트랜잭션에서 저장하며 후반 실패 시 모두 롤백합니다. 같은 날짜를 저장해도 edit_token으로 revision을 갱신합니다. 신규 첫 부과월은 등록월 이후의 적용 가능한 설정을 사용합니다. SQL Migration은 기존 properties를 등록 시점과 첫 부과월로 보정해 기존 청구·수납을 보존합니다. 후속 인계 테이블·복합 FK·배분 지연 제약을 추가하며 운영 적용 전 테이블 잠금 시간을 확인합니다. 기존 선납과 실제 수납은 같은 청구 한도를 공유합니다. 사용 전 취소는 충당을 취소한 뒤 초기 미수만 취소하며 기존 월별 청구와 최초 운영 날짜를 보존합니다. [공통 API](../../docs/billingApi.md#기존-잔액-인계)를 참조합니다.
