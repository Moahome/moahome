# 입금 저장과 실제 청구 연결

구현: 2026-10-16. 외부 요청·응답·오류는 [입금 API](../../docs/paymentApi.md), 업무 기준과 테이블은 [도메인 규칙](../../docs/domainRules.md#6-수납--수납-배분--납부-상태)·[ERD](../../docs/erd.md#81-payments)를 참조합니다.

## 데이터와 권한

PaymentService는 기존 ManagementAccessService와 ResidentListService를 사용해 매 요청의 관리소장 권한과 현재 주민 명단을 확인합니다. 실제 units/residents/unit_residents, 발행된 billing_periods/charges의 기존 ID를 참조하며 예시 주민·청구·수납을 생성하지 않습니다. 관리비 기본 설정의 예정액을 실제 청구로 바꾸지 않습니다.

`V20261015231910__create_payment_workspace.sql`은 기존 테이블·ID·금액을 변경하지 않고 은행 원본, 수납, 배분, 처리 이벤트와 무결성 제약을 추가합니다. `V20261016002928__preserve_bank_transaction_details.sql`은 은행 원본의 선택 시간·잔액을 추가하고 무결성 함수의 스키마를 고정합니다. 적용된 초기 파일의 체크섬은 유지하며 후속 변경은 새 Migration으로만 적용합니다. Flyway는 기존 서버 실행 방식으로 적용하며 운영 DB를 직접 수정하지 않습니다.

입금자명·적요·보류·취소·별도 입금 사유는 PaymentTextSecurity로 암호화합니다. 기존 계좌 보안 키 설정을 재사용하지만 AES-GCM AAD와 HMAC 입력의 용도 접두사를 입금 전용으로 분리합니다. 번호는 뒤 네 자리만 반환합니다. 개인정보 원문·암호문·키를 로그에 남기지 않습니다.

## 저장 순서와 동시성

모든 변경은 현재 권한 확인 후 PropertyRepository.findForUnitUpdate로 관리대상을 잠급니다. 기존 세대 변경·부과 생성과 같은 잠금이므로 청구 변경과 확정 사이에 잔액 검사가 분리되지 않습니다. 조회는 REPEATABLE_READ로 원장의 여러 조회가 같은 스냅샷을 보게 합니다.

확정은 최신 유효 청구·기존 ACTIVE 배분을 검사하고 Payment 상태, PaymentAllocation, PaymentEvent를 한 트랜잭션에서 기록합니다. 실패하면 전부 롤백합니다. DB의 복합 FK, 활성 은행 원본 부분 유일 인덱스와 지연 배분 제약으로 같은 대상·세대 연결과 양쪽 금액 한도를 보완합니다. 이미 수납된 청구의 제외·변경은 Service와 DB에서 막아 자동 재분류를 수행하지 않습니다.

은행 원본 연결은 BANK_IMPORT 초안을 먼저 LINKED로 flush해 활성 원본 유일성을 해제한 뒤 기존 MANUAL 수납에 원본을 연결합니다. 취소도 이전 활성 수납을 먼저 flush한 뒤 원본 검토 항목을 복구합니다. 취소된 배분과 원래 금액·처리 이벤트는 남깁니다.

파일 미리보기와 가져오기는 같은 BankTransactionReader를 사용합니다. 가져오기에서는 같은 대상 잠금 아래 중복을 재확인하므로 동시에 같은 파일을 올려도 원본·초안이 두 번 생성되지 않습니다. 원본 파일의 영구 보관·범용 import_batches 화면·회계 이벤트/전표는 이번 구현에 포함하지 않습니다.

은행 XLS는 기존 Apache POI의 HSSFWorkbook, XLSX는 XSSFWorkbook으로 첫 시트를 읽습니다. 확장자와 파일 시그니처를 확인하고 XLSX의 압축 해제량 제한을 유지합니다. 제목·계좌 안내 뒤 거래 머리글을 탐색하고 전용 입금자 열이 없는 입출금 양식의 적요를 입금자로 사용합니다. 동일 적요·원본 시간·잔액은 그대로 보존하며 출금 행은 수납 후보에서 제외합니다. 상세 탐색 범위·필수 열·오류는 [입금 API](../../docs/paymentApi.md#은행-파일추천중복)를 따릅니다. DB 구조와 기존 중복 키는 변경하지 않습니다.

## 누적 충당·자동 확정·삭제

`CumulativePaymentService.settle`은 호출자가 보유한 관리대상 잠금과 같은 트랜잭션에서 확정 수납의 미사용 금액을 실제 양수 청구월 순으로 충당합니다. 기존 ACTIVE 충당을 보존하고 같은 수납·청구에 추가할 때 금액을 증가시킵니다. 증가 전 금액과 추가액은 `CUMULATIVE_APPLIED` 이벤트에 암호화해 보존합니다. 새 청구 생성·공실 복귀·수납 확정·취소·삭제에서 호출하며 미래 청구를 생성하지 않습니다. 스케줄 충당은 원 수납 확정자를 책임자로 기록하고 별도 자동 충당 이벤트로 구분합니다.

은행 파일 가져오기는 현재 주민 명단의 이름 또는 동·호수로 한 세대에 일치하면 `AUTO_CONFIRMED`를 기록하고 누적 충당을 수행합니다. 전액 선입금도 확정합니다. 기존 수동 수납 중복 의심·보류·여러 세대 이름 충돌은 처리하지 않습니다. 동·호수 매칭은 마지막 `호`의 생략도 허용하며 주민 이름 비교와 파일 중복 키에는 이 생략 규칙을 적용하지 않습니다. 기존 PENDING의 일괄 확정도 같은 helper와 잠금을 사용합니다. 읽기와 파일 미리보기에서는 확정하지 않습니다.

`V20261016120311__support_payment_deletion.sql`은 수납 삭제 감사 컬럼을 추가합니다. 후속 `V20261016122154__allow_reimport_of_deleted_bank_receipts.sql`은 은행 원본에도 감사 컬럼을 추가하고 미삭제 원본에만 계좌·중복 키 유일성을 적용합니다. 기존에 수납만 삭제된 고아 원본은, 활성 초안·확정 수납이 없는 경우에만 삭제 표시를 보정해 재가져오기를 허용합니다. 원본 내용과 과거 FK는 유지합니다.

선택 삭제는 관리대상 잠금 아래 전체 대상의 소속과 PENDING·ON_HOLD 상태를 먼저 검증한 후 수납·은행 원본을 함께 표시합니다. 실패하면 모두 롤백하고 이미 삭제한 ID 재요청은 이벤트를 중복 생성하지 않습니다. 확정 수납은 삭제 대신 납부 취소를 사용합니다. 취소 원본의 재검토 초안은 자동 매칭에서 제외해 취소가 자동으로 번복되지 않도록 합니다.

## 검증

PaymentPersistenceTest는 별도 PostgreSQL 클러스터에서 기존 자료 업그레이드와 실제 적용된 입금 초기 버전의 체크섬·은행 원본·수납·배분 보존, 대표 주민·실제 청구 연결, 재시도·파일 중복, 연결·보류·취소, 동시 과배분과 후반 저장 실패 롤백을 확인합니다. BankTransactionReaderTest는 CSV·XLSX·수식·날짜·금액 검증을, PaymentControllerTest는 인증·입력·응답 캐시를 확인합니다. 전체 검증은 `server/AGENTS.md`의 Java 21 `./gradlew build`를 따릅니다.

은행 양식 회귀 테스트는 가상 정보로 생성한 XLS의 6행 머리글·적요 입금자·입금 5건과 출금 4건의 분리·시간·잔액·수식 거부·확장자 위장·행수 한도를 확인합니다. PostgreSQL 테스트는 같은 형식의 XLS 미리보기 무저장·수납 후보 저장·고지서 확정·재업로드 중복 방지를 검증합니다. 사용자 제공 원본의 개인정보를 테스트 파일로 저장하거나 커밋하지 않습니다.

### 과거 부과와 수납 재계산 (2026-10-16)

현재 로컬 개발자료는 사용자 지정 50,000원 기준으로 8·9월 청구를 등록하고 10월 청구를 정정했습니다. 관리대상 잠금 안에서 유효 배분을 보관·해제하고 부과를 정정한 뒤, 세대별 입금과 청구의 누적 금액 구간이 겹치는 만큼 오래된 순서로 재충당했습니다. 원본 수납·은행 거래·취소 청구는 보존하고 배분 변경 전후를 `BILLING_RECALCULATED` 암호화 이벤트로 기록했습니다. 모든 제약을 확인한 같은 트랜잭션에서 커밋했습니다. 이 보정은 로컬 개발자료의 일회성 처리이며 일반 설정 API의 적용월 정책을 바꾸지 않습니다.

`V20261016130500__record_historical_billing_source.sql`은 과거 부과의 `HISTORY / recorded_by` 제약을 추가합니다. 자동 스케줄 기간은 기존 `SCHEDULE`과 null 처리자를 유지합니다.

카카오뱅크 XLSX의 `거래금액` 공용 열은 `구분`의 입금·출금 값으로 방향을 판정합니다. `내용`을 원본 입금자 표시로, `메모`를 별도 메모로 읽습니다. 기존 입금액·출금액 분리 양식은 같은 검증을 유지하고, 공용 열에서 알 수 없는 방향·음수 입금은 거부합니다. 실제 첨부 파일은 DB에 저장하지 않고 Reader로만 검증했습니다.

후속 7월 등록도 같은 관리대상 잠금·원본 보존·감사 이벤트·전체 제약 검증을 적용했습니다. 7월 기간과 20세대 청구를 추가하고 기존 8~10월 청구·항목은 변경하지 않았습니다. 월말 수납 현황은 입금일 기준으로 계산하므로 실제 7월 입금이 없는 자료의 7월 말 미납은 그대로 표시됩니다. 이후 실제 입금의 현재 충당 내역은 7월부터 다시 계산했습니다.

## 세대 외 기타 입금

`V20261016141400__support_other_bank_income.sql`은 기존 입금 기록에 `receipt_type`과 암호화한 기타 입금 항목·메모를 추가합니다. 기존 행은 HOUSEHOLD이며 원본 ID·입금액·배분은 보존합니다. OTHER는 은행 원본이 있는 확정·취소 이력만 허용하고 세대·주민·활성 청구 배분을 금지합니다. 후속 `V20261016142721__bind_other_income_validation_schema.sql`에서 교체한 배분 함수와 새 가드를 적용 스키마의 search_path로 고정합니다. 적용된 초기 파일을 수정하거나 Flyway 이력을 repair하지 않습니다.

`confirmOtherIncome`은 같은 ADMIN 권한·관리대상 잠금 아래 PENDING 원본과 기존 수동 수납 중복 여부를 검증하고 분류·확정·감사 이벤트를 함께 저장합니다. 항목·메모가 같은 재요청은 멱등 처리하며 감사 저장 실패는 모두 롤백합니다. 누적 충당은 HOUSEHOLD만 처리합니다. 기타 확정 취소는 기존 공통 취소 흐름으로 원본 초안을 복구하고 OTHER_INCOME_CANCELED 이벤트로 구분합니다. 세대 청구를 재계산하지 않습니다.

PostgreSQL 검증은 기타 확정의 원본 보존·암호화·재시도·권한·롤백·다음 달 충당 제외, 취소 후 세대 재분류와 SQL 배분 우회 차단을 확인합니다. 공통 업무 정책과 API는 루트 문서를 참조합니다.

## 미리보기 선택 가져오기

미리보기 ID와 저장 ID를 구분합니다. `previewId`는 기존 거래 키의 UUID 표현이며 서버에서 원본 파일을 다시 파싱해 선택 ID를 검증합니다. 관리대상 잠금 아래 전체 선택의 소속 검증을 마친 뒤 선택한 행만 원본·수납·자동 확정으로 처리합니다. 제외 행의 중복 키는 만들지 않고 이미 저장된 선택은 기존 중복 검사로 제외합니다. 파일만 전달하는 기존 호출은 전체 가져오기와 호환하며 화면은 선택 JSON을 항상 제출합니다. PostgreSQL 테스트는 선택·재시도·제외 건 재업로드와 파일 변경·잘못된 ID의 무저장을 검증합니다.

기타 입금의 선택 메모는 요청 DTO 생성 시 빈 문자열·공백을 NULL로 정리해 필수 텍스트 검증에서 거부되지 않도록 했습니다. 생략·NULL·빈 문자열·공백의 HTTP 확정 요청을 모두 검증합니다. 공통 TextInput의 다른 도메인 검증 기준은 변경하지 않습니다.

## 기존 미수·선납 연결 (2026-10-17)

CumulativePaymentService는 초기 미수를 월별 청구보다 먼저 처리하고 기존 선납은 credit_applications로 충당한 뒤 실제 수납의 미사용액을 충당합니다. 실제 수납과 선납의 유효 충당을 합쳐 잔액을 검사하며 DB 지연 제약도 동일 한도를 검증합니다. 기준일 이하 입금은 파일에서 제외하고 수동 등록·확정에서도 차단합니다. 원장 응답은 초기 선납을 openingCredits로 분리하며 payments·실제 입금 합계에 가짜 수납을 넣지 않습니다. [입금 계약](../../docs/paymentApi.md#기존-잔액-연결-2026-10-17)을 참조합니다.
