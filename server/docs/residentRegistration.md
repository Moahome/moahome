# Server 주민 등록

개별 등록·상세·수정·삭제·엑셀 업로드 API를 구현했습니다. 업무 정책·입력·응답·오류는 [주민 관리 API](../../docs/residentManagementApi.md#주민-등록)와 [도메인 규칙](../../docs/domainRules.md#확정된-개별-주민-등록)을 참조합니다.

## 저장 순서

`ResidentRegistrationService.register`의 단일 트랜잭션에서 현재 관리자를 확인하고 `PropertyRepository.findForUnitUpdate`로 관리대상 행을 잠급니다. 세대 추가·수정·삭제와 같은 잠금을 공유해 삭제와 주민 연결이 교차하지 않도록 합니다. 첫 잠금 획득 후 저장이 성공한 요청이 최초 등록입니다. 실패하면 잠금과 변경을 롤백하므로 다음 요청이 최초 등록이 될 수 있습니다.

같은 대상의 실제 세대·동을 검증하고 연락처가 있으면 암호화·HMAC·끝 네 자리를 만듭니다. 요청 ID의 기존 결과 확인, 이름·연락처 중복 검사, 해당 세대의 전체 관계 이력 조회 후 주민과 현재 관계를 함께 저장합니다. 과거·삭제 관계가 있는 세대의 대표 부재를 자동 승계로 처리하지 않습니다.

신규 등록에서 요청 ID는 주민 PK로 사용하고 재등록에서는 기존 주민 PK를 유지합니다. `resident_registration_results`에 요청 ID와 실제 주민·관계 ID를 함께 저장해 새 요청과 기존 주민을 연결합니다. Migration 이전 요청은 주민 PK 조회로 재시도를 지원합니다. 같은 대상·정규화된 이름·연락처 HMAC·현재 세대·관계가 모두 같으면 기존 결과를 반환합니다. 기존 주민·관계가 삭제·변경되었거나 다른 대상이면 고정 충돌 오류를 반환하며 기존 정보를 덮어쓰지 않습니다. `Resident`의 신규 저장은 `Persistable.isNew`로 `persist`를 선택하므로 서로 다른 대상의 동일 ID가 경합해도 `merge`로 기존 주민을 수정하지 않습니다.

개별·엑셀 재등록에서는 이름·정규화 연락처가 정확히 같은 삭제 명부 하나를 재사용합니다. `Resident.restore`로 삭제 표시만 해제하고 새 현재 관계를 저장하므로 과거 관계·계정 연결은 보존하며 종료된 이용 권한·승인은 복구하지 않습니다. 같은 세대의 삭제 전 대표는 현재 대표가 없을 때만 복원합니다. 이전 구현에서 명부만 삭제한 현재 관계도 먼저 소프트 삭제하고 flush합니다. 여러 삭제 기록이 일치하면 임의로 고르지 않으며 연락처 없는 주민은 이름만으로 병합하지 않습니다. 주민 복구·관계·요청 결과는 같은 트랜잭션에서 저장하고 어느 단계든 실패하면 전체 롤백합니다.

## 연락처 보안

공통 `PhoneSecurity`를 사용하며 외부 설정은 [개발 환경 가이드](../../docs/developmentGuide.md#server-환경변수)를 따릅니다. Bean을 지연 생성해 기존 로그인·조회와 연락처 없는 등록을 키 준비와 분리합니다. 연락처 포함 저장에서 키 생성이 실패하면 업무 오류로 바꾸며 평문·임의 생성 키로 대체하지 않습니다. 등록 DTO와 암호화 중간값의 `toString`도 원문을 숨깁니다.

## 상세·수정·삭제

공유 계약은 [주민 상세 API](../../docs/residentManagementApi.md#주민-상세연락처-공개수정삭제)를 따릅니다. `ResidentManagementService`의 기본 상세는 목록의 가입 상태 판정과 현재 세대 표시를 재사용하며 마스킹만 반환합니다. 전체 번호는 별도 상세 공개 또는 아래 목록 내보내기 메서드에서만 복호화합니다.

수정·삭제는 등록·세대 관리와 같은 관리대상 행 잠금을 획득한 뒤 처리합니다. 상세의 `expectedUpdatedAt`과 현재 수정 시각을 비교해 이전 화면의 덮어쓰기를 막습니다. 대표 승계 시 선택된 주민의 수정 시각도 갱신합니다. 같은 대상의 중복 이름·연락처 검사를 잠금 안에서 수행하며 실패 시 명부·신청·관계·대표 변경을 모두 롤백합니다.

연락처 KEEP은 복호화·키 생성 없이 보호 값을 유지하고 REPLACE는 공통 저장 정규화·보안 처리를 재사용합니다. 같은 주민으로 확인된 가입 신청의 보호 연락처도 같은 트랜잭션에서 변경합니다. 연결된 신청이 있으면 REMOVE를 거부해 필수 신청 연락처와 명부의 동기화 조건을 유지합니다.

세대 이동은 기존 관계를 `MOVED_OUT`과 퇴거일로 종료하고 새 현재 관계를 생성합니다. 기존 관계를 먼저 flush해 주민당 하나의 현재 관계 인덱스를 지킵니다. 출발 세대는 관리소장이 선택한 남은 주민에게 대표를 승계하고 도착 세대는 전체 이력 기준의 최초 대표 정책을 적용합니다.

명부 삭제는 명부·현재 관계의 삭제자/시각만 기록하고 실제 퇴거 상태·퇴거일을 생성하지 않습니다. 이전 구현의 과거 퇴거·삭제 관계를 변경하거나 재활성화하지 않습니다. 연결 계정의 같은 관리대상 `RESIDENT` 참여만 종료하고 확인 연결된 대기 신청을 취소합니다. 다른 대상·관리자 참여·승인 이력은 유지합니다. 이미 삭제된 명부의 재시도는 성공으로 처리합니다.

## 엑셀 검증과 행별 저장

공유 입력·응답·오류는 [엑셀 API 계약](../../docs/residentManagementApi.md#엑셀-검증과-일괄-등록)을 참조합니다. 아래는 Server 내부 구현입니다.

`ResidentExcelReader`가 Apache POI로 첫 시트를 읽습니다. 수식은 평가하지 않으며 파일 크기와 ZIP 해제량을 제한합니다. `ResidentImportService.preview`는 현재 관리자를 확인하고 입력 정규화·기존 세대 연결·이름과 연락처의 중복·재등록 가능 여부 검증 후 `resident_import_batches`에 저장합니다. 파일 원본은 저장하지 않습니다. 연락처는 개별 등록의 `PhoneSecurity`로 암호화하며 DB의 임시 JSON·DTO 로그에도 원문을 남기지 않습니다.

배치는 작성자·관리대상에 묶이고 24시간 후 만료됩니다. 매시간 만료 배치를 삭제하므로 서버가 가동 중일 때 저장 수명은 최대 약 25시간입니다. 장기 중단 후 첫 정리 실행에서도 만료 데이터를 제거하며 만료 시각 이후에는 정리 여부와 관계없이 저장 요청을 거부합니다. 원본 행마다 UUID를 생성해 저장 재시도의 요청 ID로 유지합니다. 재등록의 실제 주민 ID는 기존 ID를 재사용하고 결과 테이블에서 연결합니다.

`commit`에는 전체 트랜잭션을 걸지 않고 원본 순서의 선택된 정상 행마다 별도 `ResidentRegistrationService.register`의 트랜잭션을 호출합니다. 이 트랜잭션에서 권한·세대·중복 재검증과 주민+현재 관계 저장·대표 지정을 함께 처리합니다. 기존 관리대상 잠금을 그대로 쓰므로 동일 세대의 동시 등록도 대표가 중복 지정되지 않습니다. 다른 등록 요청이 먼저 저장되면 그 기존 대표를 유지합니다.

입력·중복 등의 업무 오류는 해당 행을 제외하고 다음 행을 처리합니다. 저장소·연락처 보안 장애는 요청 오류로 반환하되 앞서 완료한 행은 유지합니다. 같은 배치·선택을 재시도하면 고정 ID로 성공 행의 결과를 재사용하므로 연락처 없는 주민도 중복 생성하지 않습니다. 대표가 없는 과거 등록 세대를 신규 세대로 취급하지 않습니다. 삭제 전 대표의 동일 세대 재등록만 기존 대표 복원 기준을 적용합니다. 결과 다운로드는 Client에서 수행합니다.

파일 제한은 `ResidentImportConfig`가 읽는 `residentImport.properties`의 multipart 크기 설정과 파서 제한으로 적용합니다. 추가 보안 키는 도입하지 않으며 기존 연락처 저장 키를 사용합니다.

## 검증

`ResidentRegistrationControllerTest`에서 인증·입력·개인정보 없는 응답·오류를 검증합니다. 기존 `ResidentDirectoryPersistenceTest`에 실제 PostgreSQL 등록·연락처 암호화·선택 입력·중복·요청 재시도·권한·소속·롤백·동시 대표 지정 검증을 추가했습니다. 엑셀 임시 테이블은 `V20261010055020__create_resident_import_batches.sql`로 추가합니다. `ResidentExcelReaderTest`는 실제 배포 양식·선행 0·수식·파일/행/압축 제한을, `ResidentImportControllerTest`는 multipart·인증·선택 검증·안전한 응답을 확인합니다. PostgreSQL 테스트에서 검증 단계의 무저장, 암호화·중복 제외·원본 순서·최초 대표·기존 대표 유지·행별 재검증·부분 성공·연락처 없는 재시도·작성자와 권한·만료 정리를 검증합니다.

`ResidentManagementControllerTest`와 PostgreSQL 통합 테스트에서 상세 마스킹·명시적 번호 공개·다른 대상과 권한 거부·신청 번호 동시 변경·미확인 신청 유지·오래된 수정 거부·대표 선택 이동·삭제와 대상별 권한 종료·재시도·중복 실패의 롤백을 검증합니다.

## 주민 목록 내보내기

공유 계약은 [주민 목록 엑셀 다운로드 API](../../docs/residentManagementApi.md#주민-목록-엑셀-다운로드)를 따릅니다. `ResidentExportService`는 기존 목록 Service의 관리자 권한 검증과 현재 소속 조회를 재사용합니다. 선택한 전체 ID가 현재 대상의 명부인지 확인한 뒤 대상·미삭제 조건의 한 번의 Repository 조회로 보호 연락처를 읽습니다. 다른 대상이나 삭제 주민을 일부 누락한 결과로 내보내지 않습니다.

목록·보호 연락처는 read-only `REPEATABLE_READ` 트랜잭션으로 같은 스냅샷에서 읽고 요청 순서를 유지합니다. 전체 번호는 메서드 안에서만 복호화하며 번호 없는 주민은 보안 키를 요구하지 않습니다. 키·암호문 오류는 원문 없는 고정 오류로 변환하고 응답 DTO의 `toString`도 원문을 숨깁니다. 일반 목록 Repository projection에 암호문을 추가하지 않습니다.

개별 등록 DTO는 생략·null·공백 주민 구분을 `OTHER`로 정규화하고 다른 Enum 입력을 검증합니다. 엑셀 행 검증도 빈 주민 구분은 `OTHER`, 잘못된 비어 있지 않은 값은 행 오류로 처리합니다. 기존 관계 값을 보정하는 Migration은 필요하지 않으며 수정 폼은 현재 값을 유지합니다.

재등록 결과 테이블은 `V20261012054221__support_resident_reregistration_results.sql`에서 추가하며 기존 주민·권한·과거 관계는 변경하지 않습니다. 관계의 관리대상·주민·ID 복합 UNIQUE와 결과의 복합 FK로 다른 대상이나 주민의 관계를 등록 결과에 연결하지 못하게 합니다. 기존 관계 테이블의 UNIQUE 추가는 인덱스 생성과 잠금이 필요하므로 적용 시간은 데이터 규모에 맞춰 관리합니다.

부담당자도 같은 명부·연락처 업무를 수행하며 현재 관리소장 명부의 수정·삭제·복구는 공통 대상 검사로 거부합니다. 권한 기준은 [도메인 규칙](../../docs/domainRules.md#관리자-업무-권한-2026-10-24-최종-정정)을 따릅니다.
